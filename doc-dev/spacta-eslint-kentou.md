# ESLint と Spacta — 実測と、パラダイムシフトになりうる一点

対象: livingdoc（vendored 形式）と spacta 本体
測定: 実際に ESLint を走らせた結果に基づく。推測には「推測」と明記する

---

## 0. 要旨

**ESLint 採用は「やるべき」。ただしパラダイムシフトではない。**

761件の指摘のうち、実コードに対するものは **2件**。この比率そのものが「verify と ESLint の重なりの薄さ」の測定値になっている。両者は競合しないし、ESLint を足しても Spacta の何も変わらない。**足し算であって、転換ではない。**

ただし転換になりうる筋が一つだけある。それは「ESLint を足すこと」ではなく、**verify の 13 チェックのうち 10 が per-file であり、その 10 は 2026 年時点でもはや Spacta の独自性ではない、という事実を認めること**である。§6 で詳述する。

そして本稿には、既存の分析と食い違う実測が一つある（§1.2）。結論が変わるので先に読んでほしい。

---

## 1. 761件の解剖

### 1.1 内訳（実測）

livingdoc の `eslint.config.js` は現在これだけである。

```js
import js from "@eslint/js";
import tseslint from "typescript-eslint";
export default tseslint.config(
    js.configs.recommended,
    ...tseslint.configs.recommended,
);
```

`ignores` が無い。`languageOptions` も無い。結果:

| 場所 | 件数 | 正体 |
|---|---:|---|
| `.next/` | 598 | `next build` の生成物。人が書いていない |
| `verify/` | 160 | Spacta 本体の vendored コピー |
| `next-env.d.ts` | 1 | Next.js の自動生成 |
| **`src/`** | **2** | **← 本当に見るべきもの** |
| 合計 | 761 | |

`ignores` を足して再測定すると **2件**になる。759件は「lint してはいけない場所を lint した」結果である。

### 1.2 【重要】verify/ の160件は「直してはいけないコード」ではない

ここが既存の分析と食い違う点である。「160件 = vendored コピー + わざと壊してある fixtures であり、直すと L6 が壊れるので有害」という説明を受けているかもしれないが、**実測すると内訳はこうなっている**。

| 場所 | 件数 | ルール |
|---|---:|---|
| `verify/verify.mjs` 等 | 155 | うち **148 が `no-undef`** |
| `verify/fixtures/` | 5 | 全て `no-unused-vars` |

つまり:

- **「直すと L6 が壊れる」ものは 5件しかない。** 160件ではない。
- **148件は `process` や `console` が未定義だと言われているだけ。** `languageOptions.globals` に Node 環境が宣言されていない、という純粋な設定漏れである。コードの問題ですらない。

この差は結論を変える。「verify/ を lint するのは危険だから除外する」ではなく、**「ESLint に、これは Node のコードだと言っていない」** が真の診断である。

そしてここが効いてくる。**npm パッケージ化はこの 160件を消すが、原因を直さない。** `verify/` が `node_modules/spacta/` に移れば ESLint は既定で無視するので、症状は消える。しかし Node グローバル未宣言という設定欠陥はそのまま残り、次にこう刺さる:

- spacta 本体リポジトリに ESLint を入れた瞬間（`verify.mjs` 146KB、`tools/*.mjs`、`hooks/*.mjs`、`metrics/*.mjs` — 全部 Node の .mjs）
- livingdoc に `scripts/*.mjs` を1つ足した瞬間
- `eslint.config.js` 自身

**症状が消えると原因が見えなくなる**、という典型例なので、パッケージ化の前に設定側を直しておくのが順序として正しい。

### 1.3 実コード2件

両方 `src/features/pageview/core.ts` の `normalizeQuote` 内。

```ts
export function normalizeQuote(quote: string): string {
  return quote
    .toLowerCase()
    .replace(/[`*_>#\[\]()]/g, " ")   // ← 28行目: no-useless-escape
    .replace(/[\s ]+/g, " ")          // ← 29行目: no-irregular-whitespace
    ...
```

1件目（28行目）は文字クラス内の `\[` — エスケープ不要。無害な癖。

2件目（29行目）が本物である。`[\s ]` の `\s` と `]` の間、**18列目に U+00A0（NO-BREAK SPACE）が目に見えない形で入っている**。

挙動は確認した。JavaScript の `\s` は元から U+00A0 に一致するため、**この文字は完全に冗長で、動作は同一。バグではない。**

だが問題はそこではない。

## 2. Spacta が構造的に見えない層 — U+00A0 が示すもの

`normalizeQuote` がどこに立っているかを思い出してほしい。

- `quoteKey` は「同じ passage を同じ spot にまとめる」グルーピングキー（§4.1）
- **同じ関数を `POST /api/traces` と Core の両方が呼ぶ。** サーバが保存した `quote_key` と、クライアントがグルーピングに使うキーが「絶対にズレない」ことを、関数の同一性で保証している

そこに目に見えない文字が入っていた。今回はたまたま無害だった。

重要なのは、**この種の欠陥に対して Spacta の全機構が構造的に無力である**ことだ。順に確認する。

| 機構 | この欠陥を捕まえるか | 理由 |
|---|---|---|
| L1〜L10 | **× 全滅** | 掟は「コードがどこに置かれるか」「何を import してよいか」を見る。文字は見ない |
| cross-check（replay） | **×** | 実行を自分のリプレイと比べる。U+00A0 入りでも決定的なので完全に再現する |
| 振る舞いアサーション | **×**（現実的に） | `normalizeQuote("a b")` を nbsp 付きで書き分けたテストがある確率はゼロ |
| mutate | **×** | round trip の2ケースを壊す変異。正規表現の中身は触らない |
| tsc | **×** | 型は正しい |
| **ESLint** | **○** | `js.configs.recommended` だけで検出した。プラグイン不要 |

Spacta の中心命題は「verify が緑なら、機能 F のバグは (1) F の中に留まり (2) `(initData, actions[])` から再現でき (3) 隠れ入力を持たない」である。**U+00A0 のバグは、この3条件を全て満たしたまま間違う。** 完璧に局所的で、完璧に再現可能で、隠れ入力もない。

これは私が以前指摘した「**間違っているが決定的**」という穴の一実例であり、しかも振る舞いアサーションでも埋まらない部類のものだ。ESLint はその穴の別の一部を埋める。

**4,600行の feature コードに対して指摘2件**という数字は、重なりが薄いことの証明であると同時に、**ESLint が仕事をした2件が両方とも要所だった**ことの証明でもある。

## 3. 信頼階層に ESLint の席は無い — を掘り下げる

Spacta の信頼階層は `Law（失敗で物理的に強制） > Form（既定テンプレート） > Advice（verify の info） > Judgment（AI と人間）` である。

ESLint の `error` はブロッキングなので Law に見える。だが SPACTA.md に書かれていないし、L6 のような自己検査もない。モデルから見ると「SPACTA.md に無い赤信号」であり、どちらに従うべきか判断できない。ここまでは既存の分析の通りである。

ここから先を掘る。

### 3.1 Spacta 自身の判定基準を、検査そのものに当てる

v0.11 が結晶させた基準はこれだった。

> **機能を追加したとき変わるか？**
> No → 機構（mechanism）。Yes → 語彙（vocabulary）。

これを「検査」に当ててみる。

- L1〜L10 は、機能を追加しても変わるか？ **変わらない。** → 機構
- ESLint の `no-unused-vars` は？ **変わらない。** → 機構

**同じ側に落ちる。** つまり Spacta 自身の基準では、両者は別の階層のものではない。階層で分けようとするから席が無いのであって、そもそも軸が間違っている可能性がある。

### 3.2 正しい軸は「参照範囲」である

Spacta の中心命題をもう一度読む。

> アプリが大きくなっても、**1機能を追加・変更するのに必要な参照範囲は増えない**

この「参照範囲」こそが Spacta が守っている量である。そして検査は、参照範囲の大きさで綺麗に二分できる。

| | 参照範囲 | 例 | 誰が見るか |
|---|---|---|---|
| **ファイル間の関係** | N ファイル | L1（他機能を import するな）、L3（Effect の答えの受け皿）、role coverage、Tiers | **verify** |
| **1ファイルの中身** | 1 ファイル | 未使用変数、不可視文字、危険な正規表現 | **ESLint** |

ESLint は**参照範囲1の検査器**である。verify は**参照範囲Nの検査器**である。

この置き方には利点がある。新しい階層を発明しなくていいし、二重統治も起きない（範囲が重ならない）し、何より **Spacta 自身の中心命題から導かれる**ので、外部から借りてきた区分にならない。

### 3.3 逆説 — ESLint は Law 層ではなく Advice 層に置くべきである

素朴には「ESLint の error = ブロッキング = Law」と考えたくなる。**これは逆だと思う。**

決定的なのは `// eslint-disable-next-line` である。**コメント1行で無効化できるものは Law ではない。** Law の定義は「失敗によって物理的に強制される」であり、抑制可能性はその定義と両立しない。`linterOptions.noInlineConfig` で禁止できるが、禁止したという事実が設定ファイルの中にあるだけで、それは最も腐りやすい層である。

一方、**Advice 層は抑制を必要としている。** 現在 verify の info（clone、single-owner-export、L8）は消せない。「この重複は意図的だ」と言う手段が無いので、info リストは増える一方で、いずれ読まれなくなる。これは burn-in フェーズの構造的欠陥である。

ESLint はここに正確に噛み合う:

- `// eslint-disable-next-line rule -- 理由` で、**理由付きの了承済み例外**が書ける
- `reportUnusedDisableDirectives` で、**不要になった抑制が検出できる**（例外に期限がつく）

つまり **ESLint の設計中心（設定可能・抑制可能）は Law とは両立しないが、Advice とは完全に一致する。** 素朴な発想の逆に置くのが正しい。

## 4. verify の 13 チェックのうち 10 は per-file である

`CHECKS` レジストリを実際に分類した結果。

| | チェック |
|---|---|
| **`run`（1ファイル完結）— 10件** | L1, L2, L4, L5, L7, L9, L10, L8, engine-portability, data-layer-import |
| **`batch`（複数ファイル必要）— 3件** | L3（core.ts と types.ts を突き合わせる）, clone, export-ownership |

per-file の 10件は、**原理的には ESLint ルールとして書ける**。ESLint は `context.filename` を渡すので、「このファイルはどの feature に属するか」も判定できる。

さらに、typescript-eslint の `parserServices.esTreeNodeToTSNodeMap` を使えば **ESTree ノードから TypeScript のノードに降りられる**。verify の既存チェック関数は TS の AST を歩いているので、書き直しではなく**再利用**の道がある。

これは「やろうと思えばできる」という話であって、「やるべき」ではない。§6 で扱う。

### 案1: `ignores` を足す ★★★★★

```js
{ ignores: [".next/**", "replay-sessions/**", "next-env.d.ts", "verify/**"] }
```

761 → 2。実測で確認済み。`verify/**` は npm パッケージ化後は不要になるが、vendored のうちは要る。

**注意**: `dist/` や生成物を後から足す時、`src/` を巻き込まないこと。案3 が守っている2件は `src/` にある。

### 案2: `languageOptions.globals` に Node を宣言 ★★★★★

```js
import globals from "globals";
{ files: ["**/*.mjs", "*.config.js"], languageOptions: { globals: globals.node } }
```

148件の `no-undef` の真因。**§1.2 の通り、これは「除外すれば済む」問題ではない。** spacta 本体（.mjs だらけ）に ESLint を入れる時に必ず刺さるので、今直しておく方が安い。

パッケージ化が症状だけ消すことを知った上で、原因を先に潰す — という順序自体が、Spacta が繰り返し言っている「症状ではなく構造を直す」の実践になる。

### 案3: 不可視文字系ルールを死守する ★★★★★

`no-irregular-whitespace` は `js.configs.recommended` に含まれ、**既定で正規表現の中を見る**（`skipRegExps: false`）。だから今回 U+00A0 が捕まった。プラグインを足す必要はない。

やるべきことは「足す」ではなく「**失わない**」こと:

- `ignores` の拡張で `src/` を巻き込まない
- このルールを `off` や `warn` に落とさない
- 余裕があれば `require-unicode-regexp` を追加（`u` フラグ強制。文字クラスの曖昧さが減る）

根拠は §2 の通り、Spacta の全機構が構造的に無力な唯一の層だからである。

### 案4: ESLint を Advice 層に置く ★★★★★

具体的には:

- **`error` にしない。** CI では走らせるが、Law の赤とは別の赤にする（案7）
- `// eslint-disable-next-line rule -- 理由` を**許可する。理由必須**にする
- `linterOptions: { reportUnusedDisableDirectives: "error" }` を入れる。**例外に期限がつく**

これで ESLint は「消せる指摘」になる。verify の info が消せないせいで増える一方なのに対し、ESLint 側は了承済み例外が減っていく構造になる。**Advice 層が初めてまともに機能する。**

唯一の例外は案3の不可視文字系で、これだけは `error` にしていい。理由は「無害な例外が存在しない」から — 目に見えない文字が意図的に必要な場面は無い。

### 案5: verify の「この緑が保証しないもの」に1行足す ★★★★★

verify は毎回こう印字している。

```
NOT guaranteed by this green:
  - Type integrity (props / contracts)   → run `tsc --noEmit` separately
  ...
  - Semantic correctness                 → never checked
```

ここに1行足す。

```
  - Statement-level defects (unused, unsafe regex, invisible characters)
                                         → run ESLint separately
```

**これが最も費用対効果が高い。** コストはほぼゼロで、得られるものが大きい:

- ESLint に信頼階層内の**公式な居場所**ができる（SPACTA.md を書き換えずに）
- モデルが「SPACTA.md に無い赤信号」に遭遇した時、**verify 自身が言及している**ので優先順位を判断できる
- Spacta が既にやっている「穴を宣言する」という動作そのもの。新しい概念を持ち込まない

`tsc` が既にこの形で扱われている。**ESLint を tsc と同じ扱いにする**、という一言で説明が済むのも良い。

### 案6: `eslint-plugin-react-hooks` ★★★★

L10 は「feature の component で `useState`/`useEffect` を使うな」。そして **`shared/ui` は L10 の適用外**である（ウィジェット固有の状態は持ってよい、と SPACTA.md が明記している）。

つまり `shared/ui` は hooks について無法地帯になっている。hooks ルールは「使うなら正しく使え」を見るので、**L10 が意図的に手を引いた場所をちょうど埋める。** 重なりゼロで隙間を埋める珍しい例である。

### 案7: CI で別ジョブ・別の赤にする ★★★★

既に `.github/workflows/ci.yml` に `gates` / `harness` / `package` / `reference-app` の4ジョブがある。ここに `lint` を**5つ目として**足す。`gates` の中に入れない。

理由は Spacta が verify / measure / garden を分けているのと同じ、§8「目と手の分離」である。混ぜると `gates` の緑が「掟が守られている」なのか「lint も通っている」なのか分からなくなる。**緑の意味を1つに保つ**方が、赤の数を減らすより価値がある。

### 案8: ESLint の warn を garden に流す ★★★

`garden` は既に「verify の info/warn を作業指示書に変換する」変換器である。ESLint の warn も同じ口に入れられれば、AI に渡す掃除タスクが1本化する。

思想的には正しい（検知は分散、変換は garden に一元化）。ただし `garden.mjs` は `verify --json` の出力形式に依存しているので、ESLint の JSON を正規化するアダプタが要る。**痛みが出てからでいい。**

### 案9: Stop フックに ESLint を足す ★★★

現在の Stop フックは `verify` + `npm run typecheck` を走らせる。ESLint を足すかどうか。

- **賛成**: タイミングが同じ。差分があるターンだけ走る仕組みも既にある
- **反対**: block の `reason` に Law の赤と lint の赤が混ざると、**モデルがどちらを先に直すべきか判断できない**。Law は絶対、lint は了承可能（案4）なのに、同じ文面に並ぶと同格に見える

足すなら **error のみ・見出しを分けて・「これは Law ではない」と明記**すること。実行時間も増える（現在 0.35秒 / キャッシュヒット 0.05秒）。

私の推奨は **当面足さない**。CI（案7）で足りる。Stop フックの価値は「Law の緑を保つ」ことに絞った方が、フックの意味が濁らない。

### 案10: CHECKS から `eslint-plugin-spacta` を生成する ★★

**これが唯一のパラダイムシフト候補**なので、賛否を両方書く。

構想: `CHECKS` レジストリを単一のソースとし、そこから (a) verify のレポート と (b) ESLint プラグイン の**二つのレンダリング**を生成する。同じ掟が、エディタの赤波線としても、verify の1行としても現れる。**二重統治にはならない — 実装が1つだから、食い違いが構造的に起きない。**

先例もある。verify は既に `--write-docs` で `verify/README.md` のチェック表を CHECKS から再生成しており、「表と実装が食い違っていないか」を毎回検査している。同じ形の拡張である。

得られるもの:

- **フィードバックが「ターン終了時」から「タイプ中」になる。** これは質的な変化
- 一部の掟は autofix できる（`EFFECT_FAILED` の case 追加など）
- L6 の等価物として ESLint の `RuleTester` がある。むしろ**ルール単位で valid/invalid を書けるので今より精密**になりうる

やらない理由（現時点では、こちらが勝つ）:

- **痛みが出ていない。** verify は緑で、npm 化・CI・Stop フックでフィードバック遅延は既に大幅に縮んだ。エディタ連携の欠如がまだコストとして現れていない
- **corpus 単位の性質は移せない。** role coverage の「unclassified = 0」、Tiers、`measure` のゾーン、そして毎回印字される「保証しないもの」リスト — これらは ESLint では表現できない
- **「単一の緑」を失う。** Spacta の UX は「1コマンド・1判定 + 保証しない範囲の明示」。ルールに分解するとこれが消える
- 生成器を書くコスト > 現在の便益

**判断のトリガー**（これが満たされたら再検討する、という測れる条件）:

1. per-file の掟違反を「書いてから verify を走らせるまで」に平均何回踏むかを数え、**1セッション3回を超える**ようになったら
2. 採用者が **2プロジェクト以上**になり、それぞれがエディタ連携を要求したら
3. `verify.mjs` の per-file チェック部分の保守が、**batch チェック部分より頻繁に**なったら

### 案11: `no-restricted-imports` で L1/L7 を書く ★

**やらない。** L1 と L7 を verify と ESLint の2箇所で検査すると、必ずどこかで食い違い、その時「どちらが正しいか」を決める根拠がどこにもない。Spacta 自身が v0.11 で言っている「二度書かれたループは自分と食い違うループである」と同じ理屈である。

**ただし理由を精密にしておくこと**: 駄目なのは「二箇所で検査すること」ではなく「**独立に実装された二箇所**」である。案10 のように単一ソースから生成するなら成立する。この区別が、案10 と案11 を分ける全てである。

### 案12: Biome / dependency-cruiser ★

2026年時点で、per-file の構造検査を提供するツールは複数ある（`eslint-plugin-boundaries`、`dependency-cruiser`、`eslint-plugin-project-structure` 等）。§6 の議論には関係するが、**今この構成を乗り換える理由は無い**。ESLint は既に入っていて、既に仕事をしている。

## 6. パラダイムシフトになりうるか — 直答

### 単体では No

ESLint は verify が見ない層を見る。それは**追加**であって**転換**ではない。761件中2件という比率が、そのまま重なりの薄さの測定値になっている。ESLint を入れても Spacta の掟は1つも変わらないし、verify のコードは1行も減らない。

### ただし、本当の分岐点はその近くにある

問うべきは「ESLint を採用するか」ではない。こうである。

> **Spacta が自前で 146KB の AST ウォーカーを書いた時の前提は、まだ成立しているか？**

verify の 13 チェックのうち 10 は per-file である（§4）。そして per-file の構造検査は、2026年時点でもはや Spacta の独自性ではない。typescript-eslint の型認識ルールは複数ファイルにまたがる情報を持っているし、モジュール境界を宣言的に書けるツールも複数ある。

**Spacta にしか無いのは、per-file ではない方の3件と、その周辺の性質である。**

| Spacta 固有 | 他で代替できるか |
|---|---|
| L6 — 仕込んだ違反を必ず落とす自己検査 | ほぼ無い。`RuleTester` は近いが「検査器全体」の自己検査ではない |
| role coverage — unclassified = 0 | 無い。「全ファイルが厳密に1つの役割を持つ」は corpus 単位の性質 |
| 毎回印字される「保証しないもの」 | 無い。これは思想であって機能ではない |
| Tiers — 機能ごとの round trip 成熟度 | 無い |
| `mutate` — ゲート自体を壊して何が生き残るか測る | 無い |
| L1, L2, L4, L5, L7, L9, L10 | **ある。商品化している** |

だから本物のパラダイムシフトは「ESLint を足す」ではなく、こうなる。

> **verify を per-file 検査器として維持し続けるのをやめ、corpus 検査器に純化する。**

per-file の 10チェックを（CHECKS から生成した）`eslint-plugin-spacta` に出し、verify は「1ファイルでは絶対に分からないこと」だけを見る道具になる。146KB は縮み、エディタに赤波線が出て、**Spacta の独自性はむしろ濃くなる** — 商品化した部分を手放し、誰も持っていない部分だけが残るから。

### それでも、今やるべきではない

理由は案10 に書いた通りで、要は**痛みが出ていない**からである。Spacta は「検査を先回りで足す」プロジェクトではなく、「腐ったのを見つけてから機械化する」プロジェクトだった。v0.10 は vendored が腐っているのを見つけてから `vendor-sync` を作り、v0.11 は shared union が earn しなくなったのを確認してから解体した。**同じ規律をここにも当てるべきである。**

案10 のトリガー3条件を測れる状態にしておくこと。それが今回できる最善で、それ自体が Spacta 的な答えである。
