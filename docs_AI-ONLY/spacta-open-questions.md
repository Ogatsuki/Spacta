## 1. 原理

### 1.1 複雑性の凝縮 — 凝縮してよいのは「機構」であって「語彙」ではない **[更新]**

**⚠️ `archive/tmp-for-ai/spacta-fukuzatsusei-no-gyoshuku.md` を読む前に、必ずここを読むこと。
あの文書の実例2 は v0.11 で覆っている。**

元の原理（v0.9 期）:

> 複雑性を1箇所（1ファイル、1つの型定義、1つの構築点）に凝縮し、
> それ以外の場所はその1箇所を経由してのみ触れる。もぐら叩きが止まる。

あの文書は成功例を2つ挙げていた。

| | 内容 | v0.11 後 |
|---|---|---|
| 実例1 | `nextjs.mjs` が「名前 → 役割」を1箇所に持つ | **今も正しい。むしろ強化された** |
| 実例2 | 共有 `Effect` union が「語彙の定義を1箇所に凝縮した実例」 | **❌ v0.11 で解体した** |

**v0.11 は共有 `Effect` union を消滅させた。** 各機能が自分の `types.ts` で宣言し、
自分の `perform.ts` で実行する。`effectUnion.shared = 0`。
2機能が同じ Effect を使うなら**両方に書き出す**（duplication over coupling）。

**原理が間違っていたのではなく、判定基準が無かった。** v0.11 が見つけた基準:

> ### 機能を1つ足したときに、それは変わるか。
> - **変わらない** → 機構（mechanism）→ **凝縮してよい**
> - **変わる** → 語彙（vocabulary）→ **凝縮してはいけない。機能に持たせる**

実際の切り分け:

| もの | 機能を足すと | 判定 | 現在地 |
|---|---|---|---|
| `post` / `get` / `del` | 変わらない | 機構 | `shared/runEffect.ts` に共有 |
| `createRuntime`（エンジン） | 変わらない | 機構 | `spacta` パッケージ（`engine/` が唯一の正本） |
| `nextjs.mjs` の名前→役割 | 変わらない | 機構 | `verify/platform/` に共有 |
| `Effect` の各メンバ | **変わる** | 語彙 | **各機能の `types.ts`** |
| 答えの形（`Answer`） | **変わる** | 語彙 | **各機能の `types.ts`** |
| `ModerationCommand` | 変わらない（サーバとの契約） | 機構寄り | `shared/types.ts` に残す（D-004） |

**なぜ語彙の凝縮が害になるか。** 共有宣言は結合を*守っていた*のではなく、
**管理しているように見せていた**。2つの画面を縛っているのはエンドポイントであって宣言ではない。
`/api/bookmarks` を変えれば共有宣言があろうと両方壊れる。

**まだ効いている部分:** 「同じ意味のものを再発明し、しばしば間違える」という事故への処方としては
原理は今も正しい。v0.10 の `drain` 3実装（うち2つが答えを捨てていた）がその実例で、
エンジン化で解決した [解決]。

### 1.2 複雑性の2軸 — 振る舞い / 分量 **[仮説・未実測]**

出典: `archive/tmp-for-ai/spacta-fukuzatsusei-jiku.md`。**この論点は今も生きている。**

- **振る舞いの複雑性**: 分岐・副作用・データ形状の推論。**Spacta の膜はこの軸を切り離すためにある**
- **分量の複雑性**: JSX の行数、CSS のバリエーション、アニメーションの状態数、レスポンシブの分岐。
  **state/API を追い出してもこの軸は一切減らない**

「UI 層が純粋（振る舞いが単純）」と「UI 層が小さい（分量が少ない）」は別の主張である。
Amazon 的な密度の高い UI は、状態管理がゼロでも見た目の情報量だけでコンテキストを圧迫しうる。

**未測定のまま。** livingdoc は装飾の薄いアプリなので、この軸に負荷がかかっていない。
**アプリ2つ目を作るなら、密度の高い UI を1画面持つものを選ぶと、この軸が同時に測れる。**

安上がりな予備テスト: 想定するアプリの1画面分（アニメーション込み）の JSX + CSS の
行数・トークン数を概算する。これは今すぐできる。

## 2. 構造

### 2.1 `adapters/` ディレクトリ **[決定・未実装]** — ただし v0.11 で前提が変わった

出典: `archive/tmp-for-ai/spacta-adapter-bunrui.md`。**[確立・決定] と書かれているが、実装されていない。**

決定内容:

> `adapters/` という新しい物理ディレクトリを作り、束縛アダプター（フレームワーク配線）と
> データアダプター（`queries.ts` など）をそこに出す。

**理由だった問題:** `queries.ts` が `shared/`（Spacta 所有の名前空間）の中に他のコードと
同じ顔をして埋まっており、pageview だけを直すつもりの AI が
「これは複数機能に影響する共有コードだ」と気づけない。

**v0.11 で前提が変わった部分:**

- 用語は採用された（`measure` のゾーン名が `dataAdapter`）
- しかし**物理ディレクトリは作られていない**。`shared/source/` のまま
- **今日追加した `data-layer-import` 検査が、問題の半分を別の手段で解いた** —
  機能がデータ層を import したら verify が exit 1 で止める。
  「気づけない」の一部は、ディレクトリではなく検査が塞いだ

**残っている問題:** それでも `queries.ts` を**サーバ境界（`app/**`）から触る**ときは、
共有コードに触っている自覚が構造から伝わらない。検査は features からの import を止めるだけで、
`app/api/traces/route.ts` が `queries.ts` を触ることは正当だから止まらない。

**判断が要る:** ディレクトリ移動をまだやるか。やるなら `verify` の platform 表・`measure` の
ゾーン定義・`data-layer-import` の root を全部直すことになる。

### 2.2 データ経由の結合 **[未解決]** — Spacta 最大の穴

出典: `archive/tmp-for-ai/spacta-data-ketsugo-taisaku.md`。**`SPACTA.md` §3 が穴として明記している。**

`queries.ts` の `TRACE_SELECT` を pageview / search / profile が共有している。
`traces` テーブルに列を足す判断は3機能の読み経路に同時に波及するが、**`verify` は緑のまま。**

**これは今日も未解決である。** `data-layer-import` は「機能がデータ層を import しない」を守るが、
**複数機能が同じテーブルを読んでいる**という結合はまったく別の話で、何も守っていない。

**現在ある唯一の計器:** `measure` の `spread` —— 共有シンボルごとに消費者数を数えて出す。
現在 **107シンボル**、最大は `readViewer`（11 consumers）。
**数えるだけで止めない。** これは意図的（`SPACTA.md` §3「declared hole」）。

### 2.3 「意図の型」パターン **[仮説・未実装]**

2.2 への処方として提案されたもの。各機能が欲しいフィールドを型で宣言し、
データアダプター側の汎用ビルダーが個別に SQL を組み立てる。

```
今:      3機能が同じ関数（TRACE_SELECT）を直接共有
処方後:  pageview の意図 = { fields: ["id", "page_id", "quote", "author"] }
         search   の意図 = { fields: ["id", "quote", "votes"] }
         → 型定義された意図から、ビルダーがそれぞれ独立に組み立てる
```

**解決する部分としない部分が文書に明記されている（重要）:**

型定義は「形の整合性」を保証するが「意味（業務ルール）が全消費者にとって正しいか」は保証しない。
`hidden` フラグの判定ロジックの意味が変わっても型チェックは検出できない。

ただし失敗モードの性質は変わる:

| | 処方前 | 処方後 |
|---|---|---|
| リスク | 3箇所のどれかが更新漏れ（**見えない**波及） | 1箇所の変更が3機能にとって正しいか（**見える**単一の確認点） |
| 機械的検知 | なし | フィールドの過不足はコンパイルエラー |

**「隠れた地雷」から「見える単一の確認ポイント」への変換** —— これが Spacta が目指す水準であり、
完全解決を主張しないことが「潔癖症になりすぎない」に沿う。

**未着手:** 意図の型から SQL を組み立てる汎用ビルダーの設計そのもの。

## 3. AI の運用

### 3.1 モード分離 **[仮説・未実装]**

出典: `archive/tmp-for-ai/spacta-mode-bunri.md`。

> 「契約変更モード」と「通常実装モード」を分け、その間は排他にする。

要点は「誰が契約を決めるか」を「**その瞬間に共有契約の全消費者を見渡している主体が、
共有部分だけを決める**」に統一できること。統括 AI という役職を常設しなくてよい。

**この文書が明示的に訂正している点（重要）:** 人間はモードを切り替えると注意・記憶が失われるが、
**単一の連続したコンテキストを持つ LLM は何も忘れない。** モードとは記憶の境界ではなく
自分に課すルールセットの切り替えでしかないので、切り替えコストはほぼゼロ。

**未整理のまま残っているもの:**
1. どのモードが存在するかの列挙（意図的に後回し）
2. モード軸は層に直交する。「層×モード」の命名は組み合わせ爆発を招くので避けたい [直感]
3. 契約変更モードと並列委任モードが同一か、包含関係か

### 3.2 「構造の開示」と「読み込みの深さ」の分離 **[確立・部分実装]**

同文書。**これは今日の議論と直結する最重要の概念である。**

| 部分 | 保証できるか | 階層 |
|---|---|---|
| 消費者の**存在**の開示（誰がこれを import しているか） | **機械的に100%可能** | Law / Advice |
| その消費者を**どこまで読むか・意味的に安全か** | **不可能。判断に委ねる** | Judgment |

「本当に読んで理解したか」を検証スクリプトで確認するのは原理的に不可能であり、
それを目指すのは「潔癖症になりすぎない」に反する —— **これは当初の提案の誤りとして訂正されている。**

**部分実装されている:** `measure` の `spread` が消費者一覧を出す（107シンボル）。

**未実装:** 「契約変更モードに入ったら最初にこのスクリプトを走らせる」という入口。
`SPACTA.md` §4 の「`npm run verify` を自分で走らせろ」と同種の追加エントリーポイントとして
実現できるはず。読み込みの深さは**強制チェックリストではなく利用可能なメニュー**として扱う。

### 3.3 ファイル分割とエージェント分割は別の軸 **[確立・既定は未実測]**

出典: `archive/tmp-for-ai/spacta-bunkatsu-ryudo.md`。

| 軸 | 基準 |
|---|---|
| **軸A: ファイル分割** | **再利用。** `SPACTA.md` §2 に明文化済み（同じ形が2機能で重複した後にのみ `shared/ui` へ昇格） |
| **軸B: エージェント委任** | **コスト対効果。** 契約の言語化・起動・検証・統合という固定費 |

**24並列エージェント実験の再解釈:** コンポーネント1体ずつに AI を割り当てた実験は、
軸A の基準を軸B に無反省に横滑りさせていた可能性が高い。数十行の実装に対して固定費が大きすぎる。
ただし**「Spacta の隔離が本当に並列構築を許すか」の仮説検証としては意味があった**
—— 常設ワークフローとして採用すべきという結論とは別に評価すること。

**推奨される既定 [仮説・未実測]:** エージェント委任の既定粒度は「縦のライン1本 = 1エージェント」。
分割は**軸A で既に切り出す判断がされた、真に共有されている境界に沿ってのみ**行う。
これで2つの判断基準が「共有されているか」に収束する。

**`SPACTA.md` §4-7 に部分的に反映済み:** 「並列委任するときは上流層を先に実体化せよ。
**API の散文的説明は契約ではない。コードだけが契約である**」。

**未測定:** 「縦のライン1本」が実際に1エージェントのコンテキストに収まるか。1.2 と同じ問題。

## 5. 実行時 **[未解決・最大のリスク]**

**アプリは一度も動いていない。** テストが実際に実行するのは `engine/runtime.ts` と
`core.ts` の5機能分だけ。

**一度も実行されたことがないもの:** 全 `shell.tsx` / 全 `components/` /
全 `perform.ts` の中身 / 全 `route.ts` / `queries.ts` の **SQL 全部** / `shared/ui` / `page.tsx`。

`crosscheck` も `runtime.serialization` も `perform` をスタブに差し替えて駆動している。

### 特に未知なもの: React のバッチングと `useSyncExternalStore`

engine は**外部ストア**として React に繋がっている（`react.ts` が `useSyncExternalStore` を呼ぶ）。
React 18/19 でこれは相性問題が起きうる場所である。**`crosscheck` 自身がこう申告している:**

> The live run is engine-driven, not React-rendered. React's batching, Suspense
> and re-render timing are outside what these runs exercise.

**これが「実務で使うか」の唯一のブロッカーである。** 設計ではなく、確かめていないこと。

## 6. 配布

### 6.1 パッケージ化 **[解決 —— 2026-08-13、D-005]**

`npm install spacta` の1パッケージで、エンジン（`spacta/runtime` / `spacta/react`）と
`spacta-verify` / `spacta-measure` / `spacta-garden` / `spacta-init` が同時に入る。
`vendor-sync.mjs` は削除した。**利用者の木にエンジンのコピーは存在しない。**

「アプリ2つ目が何を配るべきかを教えてくれるから待つ」という保留理由は取り下げた。
待っている間にコピーの腐りを2回踏み、そして境界は2つ目を待たずに決まった ——
**エンジンと検証器は1つの契約の両半分**であり、`verify/fixtures/` は `engine/` が生む形そのものである。
外れたのは `mutate.mjs` と `replay/scenarios.mjs` だけで、どちらも参照アプリを相対パスで掴む。

**残っている問い:** 2つ目のアプリはまだ無いので、`starter/` を同梱し続けるのが正しいかは未検証である
（現状は同梱している —— L6 の配線テストが参照コーパスを必要とし、それは利用者側でも必要だから）。

### 6.2 CHANGELOG **[解決]**

0.11 のエントリを書き、配布形式の転換（D-005）もその中に入れた。

### 6.3 npm / bun **[解決]**

ツールは `process.execPath` を使うので、起動した実行系のまま動く。
scripts は `node` のまま残してある（bun を持たないプロジェクトでも使えるように）。
README に両方の実行方法を明記済み。**bun 必須にしない**のは、Next.js を使う大半の現場を
除外しないため。

## 8. この文書の使い方

**新しいセッションを始める AI へ:** 読むのは

開くなら §1.1 の警告を先に読むこと —— あそこには **v0.11 で覆った原理**が
