## 1. 背景・目的

### 1.1 解決したい課題

プログラミング教材 (公式ドキュメント、チュートリアル等) は「書かれた時点」で固定される。
一方、学習者のつまずき・解釈・回避策・補足知識は教材の外 (フォーラム、Discord、個人ブログ) に散逸し、次の学習者に届かない。

- 学習者は同じ場所で同じつまずきを何度も繰り返す
- 「この教材のこのページで他の人が何に悩み、どう乗り越えたか」を知る手段がない
- 独学は孤独である — 教材を開いても、そこに他の学習者の気配がない

### 1.2 提供する価値 (コアコンセプト)

**教材の各ページに、学習者の集合知がぶら下がっている状態**を作る。

学習者がある教材ページに到達したとき、Living Document を見れば「このページには他の学習者のこんな痕跡が残っている」と分かる。つまずいた箇所、複数の解釈、補足リソース — これらが年々蓄積し、教材の周辺知識が生き物のように育っていく。だから **Living Document**。

> 注: Brown 大学の Rust Book 実験 (rust-book.cs.brown.edu) は、62,000人超の学習データから教材のつまずき箇所を特定し改善する研究で成果を出している (OOPSLA 2023/2024)。「学習者の集合データで教材体験を改善する」というコンセプト自体には学術的裏付けがある。本アプリはこれをコミュニティ主導・任意の教材向けに行う試み。

### 1.3 MVP で検証したい仮説 (最重要)

> **仮説**: 教材ページ単位に学習者の痕跡が集約されて見える状態は、後続の学習者にとって「多角的に学べる」「孤独でない」価値を生み、かつ学習者は自発的に痕跡を残す。

MVP の全機能はこの仮説の検証に奉仕する。検証に不要な機能は作らない。

## 2. 想定ユーザー

初期ターゲットは **Rust 学習者コミュニティ** に意図的に限定する (英語圏、r/rust・users.rust-lang.org 中心)。

限定する理由:
- プログラミング愛が強く、公式教材 (The Rust Book 等) にほぼ全員が通る「共通の道」があるため、痕跡が同じページに集まりやすい (集合知の密度が出る)
- ほぼ全員が GitHub アカウントを持つ (認証の摩擦が低い)
- 専門コミュニティは自浄作用が強く、モデレーションコストが低い (Fermat's Library の成功要因 / Genius Web Annotator の失敗の裏返し)
- テスター募集のチャネル (r/rust) が明確

### ペルソナ

| ペルソナ | 状況 | 利用シーン |
|---|---|---|
| A. Rust 入門者 | The Rust Book を独学中。所有権で挫折しかけ | 4章を読む前に Living Document で同ページの痕跡を眺め、「みんなここで詰まるのか」と知って心理的安全を得る。複数の解釈を読み比べる |
| B. 学習中級者 | Rustlings を進めつつ復習中 | 自分がつまずいた箇所と自分なりの解釈を痕跡として残す。他人の痕跡に自分の解釈をぶら下げる |
| C. 経験者・貢献者 | Rust 経験者。教えるのが好き | つまずき痕跡に説明を書き込む。良い説明が投票で上位表示され、名声になる |

## 3. スコープ

### 3.1 MVP でやること

- Rust 学習教材 (運営が登録したカタログ) に対する痕跡の投稿・閲覧
- 教材 → ページ → スポット → 痕跡の三層表示 (§4)
- 痕跡へのコメント (解釈の積み重ね)、投票
- GitHub OAuth ログイン (閲覧は未ログインで可)
- 教材内検索・教材カタログの一覧

### 3.2 やらないことリスト (MVP)

| やらないこと | 理由 |
|---|---|
| ブラウザ拡張 (教材ページ上へのオーバーレイ表示) | Web 注釈の普及最大の壁は拡張インストールの摩擦 (W3C の分析、Hypothes.is の経験)。将来ロードマップに残すが MVP はサイト内完結 |
| 任意 URL への痕跡投稿 | 教材が無限に広がると集合知の密度が下がる。Rust 限定・カタログ制で密度を守る。カタログ追加はユーザーの「リクエスト」→運営承認制 |
| 「解決済み」フラグ | 解決済みでも別の解釈を付け加えてこそ集合知になる。解決/未解決の二値で議論を閉じない (設計判断として確定済み) |
| AI 要約 | 価値はあるが仮説検証に必須でなく、API 費用が $10/月 予算を圧迫。痕跡が十分溜まった後のフェーズ2 |
| 教材ランキング | 初期はデータが少なく空虚に見える。代わりに「最近活動のあった教材」リストで代替 |
| 日本語 UI・i18n | ターゲットが英語圏のため MVP は英語のみ。i18n は将来課題 |
| YouTube 等の動画教材・タイムスタンプ | 過去の宅建アプリの失敗領域。まずテキスト教材で仮説検証 |
| モバイルネイティブアプリ | レスポンシブ Web で代替 |
| 通知・フォロー・DM 等の SNS 機能 | 仮説検証に不要 |

### 3.3 将来ロードマップ (スコープ外だが方向性として記録)

1. ブラウザ拡張による教材ページ上でのインライン表示 (分断問題の根本解決)
2. AI によるスポット/ページ単位の要約 (「このページのつまずきまとめ」自動生成)
3. Rust 以外の言語・教材ドメインへの拡大
4. 大学教材への展開 (原点のユースケース: 教授が教材ブラッシュアップに集合知を使う)

## 4. 中核概念・情報モデル

### 4.1 粒度問題と設計方針

**問題**: Q&A スレッドを教材ページに直接ぶら下げると粒度が細かすぎる。1ページ学ぶのに大量のスレッドを読む必要が生まれ、「ページの集合知を一望する」体験が壊れる。逆にページ単位の掲示板ではどの記述についての話か分からない。

**解決**: 閲覧の単位と投稿の単位を分離し、中間に自動集約層を置く**三層モデル**を採用する。

```
教材 (Material)            例: The Rust Book
 └ ページ (Page)           例: 4.1 What is Ownership?   ← 閲覧の基本単位
    └ スポット (Spot)       例: "stack and heap" の段落   ← 引用箇所ごとの自動グルーピング
       └ 痕跡 (Trace)      例: 「ここが分からなかった。私の解釈は…」 ← 投稿の単位
          └ コメント        例: 「別の解釈: …」「この説明が役立った: <URL>」
```

- **痕跡 (Trace)**: 投稿の最小単位。教材ページ + (任意で) 引用テキストに紐づく。旧称「付箋」は廃止 — 付箋は「貼る」物理メタファーで矮小だが、痕跡は「学習者がそこに居た証拠」であり、孤独の解消というコンセプトに合う。英語 UI では **trace** を第一候補とする (§12 未決事項)。
- **スポット (Spot)**: 同じ引用テキスト (または近接する引用) を持つ痕跡の自動グルーピング。ユーザーが作る概念ではなく、システムが痕跡から導出する。ページを開くと「このページには5つのスポットがあり、この段落に痕跡が12個」と一望できる。
- **ページビューが集合知の顔**: ページを開いたときの初期表示はスポットの一覧 + 各スポットの代表痕跡 (投票上位) のみ。詳細はスポットを展開して読む。これにより「一望できる粗い層」と「詳らかに読める細かい層」を両立する。

### 4.2 痕跡のタイプ

痕跡には投稿時にタイプを 1 つ付ける。集合知を「質問と回答」に限定しないための設計。

| タイプ (英語 UI 案) | 内容 | 例 |
|---|---|---|
| Stuck (つまずき) | ここが分からなかった・詰まった | 「move の説明でなぜ借用が出てこないのか混乱した」 |
| Insight (解釈・気づき) | 自分なりの理解・言い換え | 「所有権はの本の説明より『値の削除責任者』と考えると腑に落ちた」 |
| Resource (補足リソース) | 役立った外部リソースへのポインタ | 「この動画の図解が分かりやすい: <URL>」 |
| Footprint (足あと) | 読了・学習した記録のみ (本文任意) | 「2周目。今回は理解できた」 |

- Stuck に対する説明・回答は独立した痕跡ではなく、その痕跡への**コメント**として積む。解決済みフラグは付けず、複数の解釈が並存する。
- Footprint は最軽量の投稿。書くことがなくても痕跡を残せるようにし、「他の学習者の気配」の密度を上げるコールドスタート対策を兼ねる。

### 4.3 集約と表示順

- スポット内・コメントの並び順は投票 (👍 Helpful) 順、同点は新着順
- ページビューのスポット並び順は痕跡数 × 投票の複合 (ホットな箇所が上)
- 投票は品質シグナルの最小実装。karma・ランク等のゲーミフィケーションは MVP ではやらない

## 5. 機能要件

### 5.1 必須機能 (MVP)

ユーザーストーリー形式。〔 〕は補足。

**F1. 教材カタログ**
- 訪問者として、登録済み Rust 教材の一覧 (The Rust Book / Rustlings / Rust by Example / Comprehensive Rust から開始) を見たい。教材を選ぶとページ (章・節) の目次が見え、各ページの痕跡数が分かる
- ユーザーとして、カタログにない教材の追加をリクエストしたい〔フォーム送信 → 運営が承認。自動追加はしない〕

**F2. ページビュー (集合知の一望)**
- 学習者として、教材ページを開くと、スポットの一覧と各スポットの代表痕跡が一画面で見たい。元教材への外部リンクが常に目立つ位置にある〔本家がメイン、当アプリはサブという立場を UI で明示。宅建アプリの教訓〕
- 学習者として、スポットを展開して全痕跡・コメントを読みたい

**F3. 痕跡の投稿**
- ログインユーザーとして、教材ページを選び、(任意で) 教材からコピーした引用テキストを貼り、タイプを選んで痕跡を残したい〔引用は手動ペースト。教材ページの自動取得・埋め込みはしない〕
- 投稿した痕跡が同じ引用を持つ既存スポットに自動合流するか、新しいスポットになる

**F4. コメントと投票**
- ログインユーザーとして、痕跡にコメント (解釈・説明・リソース) をぶら下げたい
- ログインユーザーとして、痕跡・コメントに 👍 Helpful を付けたい (1人1回、取り消し可)

**F5. 認証**
- ユーザーとして、GitHub アカウントでログインしたい。閲覧はログイン不要、投稿・投票はログイン必須
- ユーザーとして、自分のプロフィール (GitHub ユーザー名・アバター) と自分の痕跡一覧を見たい

**F6. 検索・発見**
- 学習者として、教材内をキーワード検索して関連する痕跡を見つけたい〔MVP は SQL LIKE / FTS の単純検索で可〕
- 訪問者として、トップページで「最近活動のあった教材・ページ」を見たい

**F7. モデレーション (最小限)**
- ユーザーとして、不適切な痕跡・コメントを報告したい
- 運営として、痕跡・コメントの非表示とユーザーの投稿停止ができる管理画面 (簡素で可) が欲しい〔Genius Web Annotator の失敗要因は濫用対策の欠如。最小限でも初日から持つ〕

### 5.2 あったら嬉しい機能 (MVP 後)

- AI 要約 (スポット/ページ単位)、教材ランキング、ブラウザ拡張、痕跡の RSS/埋め込み、Markdown 対応の充実、教材バージョン差分への追従、i18n

## 6. 画面一覧・画面遷移

```
[トップ] ── 教材カタログ + 最近の活動
   │
   ├→ [教材ページ目次] ── 章・節ごとの痕跡数
   │      └→ [ページビュー] ── スポット一覧 (代表痕跡)     ← 中心画面
   │             ├→ (スポット展開) 全痕跡 + コメント + 投票
   │             ├→ [痕跡投稿モーダル/画面] (要ログイン)
   │             └→ 元教材へ外部リンク ↗
   ├→ [検索結果]
   ├→ [プロフィール] ── 自分/他人の痕跡一覧
   ├→ [ログイン] (GitHub OAuth)
   └→ [教材リクエストフォーム]
[管理画面] ── 報告一覧・非表示操作・教材カタログ管理 (運営のみ)
```

## 7. データ要件

主なエンティティ (詳細設計は別途):

| エンティティ | 主な属性 | 備考 |
|---|---|---|
| User | GitHub ID、ユーザー名、アバター、ロール (user/admin)、投稿停止フラグ | 個人情報は GitHub 公開情報のみ保持 |
| Material | 名称、正規 URL、説明、ステータス (承認済み/リクエスト中) | 運営が管理 |
| Page | Material への参照、章節番号、タイトル、正規 URL | URL は正規化して保持 (§9 参照) |
| Trace | Page への参照、投稿者、タイプ、引用テキスト (任意)、本文、作成日時 | Spot はテーブルではなく引用の一致度から導出でも可 (詳細設計判断) |
| Comment | Trace への参照、投稿者、本文 | |
| Vote | 対象 (Trace/Comment)、ユーザー | 複合ユニーク制約 |
| Report | 対象、報告者、理由 | |

**URL 正規化の要件**: 同一教材に複数のミラー・バージョンが存在する (例: doc.rust-lang.org/book と rust-book.cs.brown.edu、stable/nightly)。痕跡が分散しないよう、カタログ登録時に正規 URL を定め、既知のミラー URL は正規ページに解決する。

## 8. 非機能要件

| 項目 | 要件 |
|---|---|
| パフォーマンス | ページビュー初回表示 2 秒以内 (通常回線)。閲覧系は CDN/キャッシュ活用 |
| 対応環境 | モダンブラウザ (Chrome/Firefox/Safari/Edge 最新)。スマホはレスポンシブ Web で閲覧・投稿とも可能なこと〔宅建アプリの教訓: スマホ体験を後回しにしない〕 |
| セキュリティ | GitHub OAuth のみ (パスワードを保持しない)。保持する個人情報は GitHub の公開プロフィールに限定。投稿レートリミット (スパム対策)。HTTPS 必須 |
| 可用性 | 個人運営の MVP として稼働率の SLA は定めないが、データは日次バックアップ |
| コンテンツの権利 | 引用テキストは出典 (教材ページ) への明示リンク付きの引用に留める。教材本文の複製・全文表示はしない |
| 運用コスト | **$10/月以下 (ハード制約)**。超過が予見される場合は機能を落とす |

## 9. 制約条件・技術方針

- 開発体制: 個人 + AI (Claude Code 等) による開発
- 技術スタック: Next.js + Tailwind CSS
- **ホスティング: Cloudflare を第一候補とする** (要件定義段階の推奨、基本設計で最終決定)
  - 根拠 (2026-07 調査): Cloudflare 無料枠は Workers 10万 req/日・D1 5GB・帯域無制限で、MVP 規模なら $0〜5/月に収まる見込み。Vercel Hobby は非商用限定の規約と帯域 100GB/月 制限があり、超過時の課金リスクが $10 制約と相性が悪い
  - D1 (SQLite) はテキスト中心の本データなら当面十分
- 期限: 特に定めないが、仮説検証を優先し MVP を小さく早く出す

## 10. 成功基準 (KPI)

r/rust での告知後 **4 週間** を検証期間とする。

| 種別 | 基準 | 意図 |
|---|---|---|
| 供給 (痕跡が残るか) | 運営以外のユーザーによる痕跡 100 件以上 | 「自発的に痕跡を残す」仮説の検証 |
| 相互作用 (集合知になるか) | 他人の痕跡へのコメント/投票が痕跡の 30% 以上に付く | 一方通行のメモ帳で終わっていないか |
| 密度 (一望価値が出るか) | 痕跡 10 件以上のページが 5 ページ以上 | 「ページに集合知がぶら下がる」画が実際に成立するか |
| 継続 | 2 回以上投稿したユーザーが 10 人以上 | 一見さんで終わっていないか |
| 定性 | フィードバックで「他の学習者の存在を感じた」「多角的に学べた」への言及 | コアバリューの直接検証 |

未達の場合は撤退ではなく、どの層 (供給/相互作用/密度) で詰まったかを特定して次の一手を決める。

### ローンチ手順の注意

r/rust は自己宣伝に慣習的なルールがある。告知前にサイドバーの規約を確認し、必要ならモデレーターに事前相談する。「プロジェクト宣伝」ではなく「学習者ツールを作った、フィードバックが欲しい」の体裁が受け入れられやすい (要事前調査)。

## 11. 市場環境と教訓 (調査サマリー)

| サービス | 状態 | 本アプリへの教訓 |
|---|---|---|
| Hypothes.is | 存続 (登録 100 万人超、機関向け B2B で収益化) | 汎用 Web 注釈は個人向けでは収益化困難。ドメイン特化 (Rust 学習) は差別化になる |
| Genius Web Annotator | 失敗・終了 | 濫用・ハラスメント対策の欠如が致命傷。最小限のモデレーションを初日から (F7) |
| Glasp | 成長中 (個人ハイライト特化) | ニッチを絞る戦略の有効性。ただし個人メモ寄りで「教材単位の集合知」は空白地帯 |
| Fermat's Library | 存続 (arXiv 論文注釈) | 専門コミュニティ + キュレーションは濫用が少ない。Rust 限定戦略の傍証 |
| W3C の普及分析 | — | 拡張機能インストールが最大の摩擦 → MVP はサイト内完結 (決定済み) |

**ポジショニング**: 「プログラミング教材 × ページ単位の集合知 × 特定言語コミュニティ」の組み合わせは既存サービスの空白地帯。
