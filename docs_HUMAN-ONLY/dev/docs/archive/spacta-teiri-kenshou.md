# Spacta 定理検証 — 設計書

**著者用。** 実装エージェントには `genzaichi-3` の変更⑤ だけを渡せば足りる。この文書は**結果をどう解釈し、反例が出たときに何を書き換えるか**を決めておくためのもの。

対応文書: `docs/spacta-genzaichi-3.md`（変更⑤） / `docs/spacta-sokutei-sekkei.md`（層4の測定）

---

## 0. なぜ定理を書く必要があるのか

Rust の借用チェッカが価値を持つのは、チェッカ自体ではない。**「この構造的性質が成り立つなら、このバグのクラス全体が不可能になる」という定理が証明されているから**である。チェッカは安く、定理が高い。

Spacta にも同じ形の定理がある。**ただし主張されているだけで、誰も検算していない。**

そして「検算していない定理」を根拠に「緑なら局所・再現可能です」と書くことは、**`verify` が v0.9.3 で捨てたはずの過大主張と同じ構造**である（0ファイル走査で「Guaranteed」と印字していた件）。誠実さの機械化を掲げる道具として、ここは放置できない。

### 4つの層のどこにいるか

| 層 | 問い | 手段 | この文書 |
|---|---|---|---|
| 1 | 掟が守られているか | `verify` + `tsc` | 対象外（できている） |
| **2** | **掟が主張する定理が成り立つか** | **リプレイ照合** | **★ この文書** |
| 3 | アプリのロジックが正しいか | property-based testing | 対象外（§7 で入口だけ書く） |
| 4 | 思想に価値があるか | 測定 | `spacta-sokutei-sekkei.md` |

## 1. 定理 — 正確な言明

> **`verify` が緑、かつ `tsc --noEmit` が0エラーであるとき、各機能 F について次が成り立つ。**
>
> **(1) 局所性** — F の状態遷移は、F の `core.ts` の `update` だけで決まる
> **(2) 再現性** — F の任意の実行は、`(initData, actions[])` を再生すれば同一の状態列に至る
> **(3) 隠れた入力の不在** — `update` の出力は引数（`state`, `action`）だけで決まる
> **(4) 波及の不在** — F への変更は、他機能の実行を変えない

**この4項が、Spacta の「バグは局所的・明示的・決定的である」という主張の全内容である。**

---

## 2. 前提条件 — 定理は何に依存しているか

各項が、どの掟・どの機構に支えられているか。**掟で担保されていない前提が2つある。**

| 項 | 支えているもの | 担保 |
|---|---|---|
| (1) 局所性 | L1（機能間 import 禁止）、L7（逆依存禁止）、L10（状態は Core に） | ✅ 掟 |
| (2) 再現性 | L2（純粋性）、L3（非決定性の注入）、**+ 状態遷移の直列化** | ⚠️ **直列化はどの掟も要求していない** |
| (3) 隠れた入力の不在 | L2、L3、L9（末端の IO 禁止） | ✅ 掟 |
| (4) 波及の不在 | L1、L7、**+ データ層を共有していないこと** | ❌ **データ層はどの掟も見ていない** |

> **定理の (2) と (4) は、掟が保証していない前提の上に立っている。**

これが「主張されているだけ」の正体である。(2) の欠けた前提は機構（エンジンの直列化）で埋められる。**(4) の欠けた前提は、現状のアーキテクチャでは埋められない。**

## 3. 既知の反例 — 2件

### 反例1 — 非直列 `drain` が (2) を破る [確立]

`pageview/shell.tsx` の `dispatch` はクロージャの `state` を読み、`drain` はローカルの `current` を繰り上げながら `commit = setState` で state 全体を上書きする。in-flight フラグも直列化もない。

**投票と投稿が重なると commit の順序が入れ替わり、Action ログをリプレイした最終状態が実走行と一致しない。**

- 破っている項: **(2) 再現性**
- 欠けている前提: 状態遷移の直列化
- **処方: `genzaichi-3` 変更① の不変条件4。これで閉じるはずである**
- **リプレイ照合は、この処方が実際に効いたかの検算になる**

### 反例2 — データ経由の結合が (4) を破る [確立]

`shared/source/queries.ts`（508行）の `TRACE_SELECT` を pageview / search / profile の3経路が共有し、読みモデル型 `TraceRecord` を3機能の9ファイルが消費している。`traces` テーブルに列を1つ足す判断が3機能の読み経路に同時に波及する。**`verify` は緑、L1 も緑。**

- 破っている項: **(4) 波及の不在**
- 欠けている前提: データ層を共有していないこと
- **処方: 無い。** 現状のアーキテクチャでは埋められない
- **リプレイ照合では検出できない**（プロセス内の Action ログに現れないため）

> **したがって定理の (4) は、現時点で「機能のコードレベルの変更については成立するが、スキーマ・共有クエリの変更については成立しない」に弱められなければならない。**

## 4. 検証方法 — リプレイ照合

### 原理

```
実走行:   init(initData) → 本番の経路で update を適用 → S_live[0..n]
リプレイ: init(initData) → actions.reduce(update)      → S_replay[0..n]

∀i. S_live[i] = S_replay[i]  であれば (2) と (3) は成立
```

### 不正な実装（これをやると検証が無意味になる）

| やってはいけないこと | なぜ |
|---|---|
| `State` を記録して比較する | 照合が自明に成功する。**記録するのは `initData` と Action 列だけ** |
| 最終状態だけを比較する | 途中で発散して偶然戻った場合を見逃す。**中間状態でも比較する** |
| リプレイでエンジンの内部状態やキャッシュを覗く | `init` と `update` だけから再導出すること |
| 照合が通るシナリオだけを記録する | §5 のシナリオを網羅すること |

### この照合で分かること・分からないこと

| 項 | 照合で | 理由 |
|---|---|---|
| **(2) 再現性** | ✅ 直接検算 | これが主目的 |
| **(3) 隠れた入力の不在** | ✅ 検算できる | `update` が時刻や乱数を隠れて読んでいれば発散する |
| **(1) 局所性** | ⚠️ 傍証まで | 1機能のセッションを単独でリプレイして一致するなら傍証 |
| **(4) 波及の不在** | ❌ 不可能 | データ層はプロセス内のログに現れない |

**照合が通ったときの出力に、(4) が未検証であることを必ず印字させること。** これを省くと、`verify` が0ファイル走査で「Guaranteed」と名乗っていたのと同じ過ちになる。

## 5. 反例の探し方 — シナリオ一覧

**「通るシナリオを1つ流して緑でした」では検証にならない。** 定理を壊しにいくシナリオを意図的に作る。

| # | シナリオ | 狙う項 | 期待 |
|---|---|---|---|
| S1 | 単純な直列操作（投稿→表示） | (2)(3) | 通るべき |
| S2 | **投票の連打**（同一対象に高速で複数回） | (2) | **変更①前は失敗する。後は通るべき** |
| S3 | **投票と投稿の重ね**（in-flight 中に別の dispatch） | (2) | **反例1 の直撃。変更①の検算** |
| S4 | **書き込みの失敗注入**（サーバが 500 を返す） | (2)(3) | 補償（ロールバック）が Action 経由で行われていれば通る |
| S5 | **成功と失敗の混在**（3件中2件目だけ失敗） | (2) | 順序依存の補償が正しいか |
| S6 | 時刻をまたぐ操作（日付境界） | (3) | `update` が時計を隠れて読んでいれば発散 |
| S7 | 複数機能を同一セッションで操作 | (1) | 各機能を単独でリプレイして一致するか |
| S8 | **同じ Action 列を2回リプレイ** | (3) | 2回目が1回目と一致しない＝ `update` が非決定的 |

**S2 / S3 は変更①の前後で必ず両方走らせること。** 前で失敗し後で通ることが、直列化が効いた証拠になる。**前でも通ってしまうなら、シナリオが反例を再現できていないので作り直す。**

## 6. 反例が出たときの扱い

**発散を見つけたら、選択肢は3つ。順に検討する。**

| # | 対応 | いつ選ぶ | 例 |
|---|---|---|---|
| **A** | **機構を直す** | 欠けている前提が機構で埋められるとき | 反例1 → エンジンの直列化 |
| **B** | **掟を足す** | 機構では埋まらず、構文的に検査できるとき | （現時点で該当なし） |
| **C** | **定理を弱める** | どちらもできないとき | 反例2 → (4) に「スキーマ変更を除く」を付ける |

### 絶対に守ること

> **定理を黙って弱めないこと。**

C を選んだ場合は、**弱めた事実と理由を必ず文書に書く。** そして弱めた定理を、`HUMAN_GUIDE` §0-4 と §6.2 の記述に反映する。「verify が緑なら隠れた入力は無い」のような断言が、弱めた後の定理と矛盾していないかを毎回確認する。

**これは §6.4「穴を隠さない」の、定理レベルへの適用である。** 検証器が自分の管轄範囲を申告するのと同じ理由で、**定理も自分の適用範囲を申告しなければならない。**

### 記録先

反例が出たら `docs/counterexamples/NN-<名前>.md` に残す。

```markdown
# 反例 NN — <名前>
- 発見日 / 発見方法（シナリオ番号）
- 破っている項: (1)/(2)/(3)/(4)
- 欠けている前提:
- 再現手順:
- 発散した Action（何番目で S_live と S_replay がずれたか）:
- 対応: A(機構) / B(掟) / C(定理を弱める)
- 対応後に書き換えた文書:
```

## 7. 層3（ロジックの正しさ）への接続 — 今回は保留

**リプレイ照合が通るようになると、層3の入口が構造的に開く。**

`update` が `(state, action)` の純粋関数であることが**検算済み**になれば、それは property-based testing とモデル検査の入力に**そのまま使える**。「core が純粋だから PBT が書ける」は現在は仮定だが、照合が通れば事実になる。

**ただし今回は実装しない。** 理由:

- 層2 が終わっていない段階で層3 に進むのは、土台が固まる前に上物を積むこと
- 層4 の測定を控えており、テストコードを足すと測定ゾーンの構成が変わる
- `SPACTA.md` にテストの規定が1行も無く、役割表の `test` ロールは参照コーパスに1件も無い。**設計から必要**であり、片手間で入れるものではない

**測定完了後の第一候補として記録しておく。** 現状 Spacta は「ロジックを検証可能にする」ところまでやって「検証する」を提供しておらず、**純粋性という高コストの前提条件を作りながら、その配当を受け取っていない。** これは思想の欠陥ではなく、未着手の区画である。

## 8. この文書の弱点（正直に）

- **シナリオが8つでは網羅ではない。** 反例が出なくても「定理が正しい」とは言えず、「これらのシナリオでは破れなかった」までしか言えない
- **(4) は原理的に検算できない。** データ層を含む波及は、別の道具（スキーマ変更の影響範囲解析）が要る
- **意味的な正しさは対象外。** `count + 2` は照合を通る
- **リプレイ照合自体が正しいことは、誰も検証していない。** L6（検証器の自己検証）と同じ問題が、1階層上で再発している。**照合ハーネスに対しても、既知の発散を埋めた fixture を用意して「必ず検出する」ことを確かめること**
