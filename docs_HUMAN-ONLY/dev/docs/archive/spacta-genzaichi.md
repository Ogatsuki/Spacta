## 1. Spacta とは何か（30秒）

AI にコードを書かせるための設計規律。実体は2つだけ。

- **`SPACTA.md`（67行・英語）** — AI が毎タスク読む幹
- **`verify/verify.mjs`** — その規律を AST で機械検査する検証器

一文で言うと **「膜（Core 境界）をデータだけが越える。IO は入らず、計算は出ない」**。`State` / `Action` / `Effect` / `InitData` の4語彙だけが膜を通る。信頼階層は `Law（機械施行）> Form（テンプレ・可変）> Advice（info）> Judgment（未検査）`。

そして最重要の作法：**穴があること自体は許される。穴を隠すことは許されない。** `verify` は毎回「この緑が保証すること / しないこと」を印字する。

**運用者は人間ではなく AI である [確立]。** 網羅的なステートマシンを手書きするのは人間には苦痛でモデルには安価 —— この非対称性が設計全体の前提。人間が `verify` を走らせるシナリオは設計対象ではない。

## 3. 何が解決したか — バージョンではなく問題で並べる

### 書き経路の戻り [確立・v0.9.3で実装]

**症状:** Core が `Effect` を吐き `runEffect` が実行するが、**結果が Core に戻る経路が存在しなかった。** livingdoc で実害が出ていた —— 仮ID `temp_*` がそのままサーバへ飛び、失敗した投稿が画面に残る。**`verify` 緑・`tsc` 0エラー・E2E 通過のまま。3つのゲートが同一の一点で同時に盲目になった。**

**解:** `Effect` が `correlationId` を持ち、Shell が結果を `EFFECT_SUCCEEDED` / `EFFECT_FAILED` という **Action** に変換し、Core が処理する。施行は分担 —— **`verify` が受け皿の存在を、`tsc` の `never` 終端が処理の網羅を**担う。

**設計上の要点2つ。**

1. **第5の膜語彙を作らなかった。** `EffectResult` は膜を越えない —— 越えるのは `Action` である。「第5の**膜**語彙」という命名が最初から圏を間違えている。語彙は4つのまま
2. **検査は宣言ではなく構築地点を見る。** `Effect` は `shared/types.ts` の単一 union で全機能が共有する（L7 の帰結）ので「この機能の Effect」は型レベルに存在しない。だが **`core.ts` は必ずどれか1機能に属する。** 構築地点で引くことで、大域化した語彙と戦わずに回避した

**実測で裏が取れた [確立]:** 恐れていたカスケード（必須化が6機能に波及する）は**起きなかった**。pageview が書く4つの Effect はすべて pageview 専用。**型は大域的でも構築は機能ごとだった。**

→ この「語彙の定義は大域的に凝縮し、構築は局所に任せる」というパターン自体を一般原則として取り出したものが [[spacta-fukuzatsusei-no-gyoshuku]]。読み経路（データ経由の結合）への輸入は [[spacta-data-ketsugo-taisaku]] を参照。

### 検査が何かに向いていることの証明 [確立・v0.9.2]

L6 の自己テストは checker **関数** にテキストを直接渡すので、`CHECKS` の glob（`root`/`match`）を一度も通らなかった。**glob を書き間違えて0ファイル走査になっても、自己テストは緑・本スキャンも緑。** 参照コーパスに対して各 glob が1件以上選ぶことを assert して塞いだ。判定は `> 0` で、調整された閾値ではない。

### 0ファイルの検査が「保証した」と名乗る問題 [確立・v0.9.3]

Next.js は `src/app/` を公式サポートする。そのレイアウトで L5 は**0ファイル走査のまま緑**になり、しかも信頼境界ブロックが `Guaranteed: L5 Server boundaries generate no ids, time or randomness` と印字していた。**誠実さの装置そのものが、検査していないものを保証だと主張していた。**

**解:** 0ファイルの検査は「Guaranteed」に載せず、`NOT verified in this project (0 files matched — the law was not enforced here)` に走査した root 付きで出す。**赤にはしない** —— app router や `components/` がまだ無いプロジェクトは正当であり、fatal にすると正直な状態が表現不能になり、検査を黙らせる訓練をしてしまう。**口に出すのが解決であって、走るのを拒むことではない。**

### フレームワーク名の列挙をやめる [確立・v0.9.4 進行中]

上の `src/app` は1件のパッチで直せるが、**クラスとしては直らない。** `layout.tsx` / `error.tsx` / `middleware.ts` と将来のあらゆる規約が、依然すべての err 検査の外にいた。名前を足す限り、Next.js が進化するたびに静かに穴が開く。

**解:** `verify/platform/nextjs.mjs` が **名前 → 役割** を引き受け、`CHECKS` は**役割**を語る。そして **役割が引けなかったファイルは INCONCLUSIVE**。

**この設計の核心 [確立]:**

> **役割が引けたファイルは、掟が弱くてもその弱さを印字できる。役割が引けないファイルだけが本当の穴である。**

だから `laws: []` は穴ではなく**宣言された弱さ**として扱う。そして **INCONCLUSIVE は「これが何か分からない」にだけ使い、「専用の役割が無い」には使わない** —— 後者に使うと、コロケートしたテスト1つで走行が止まり、**運用者は無視リストに手を伸ばす訓練を受ける。それは穴より悪い。**

**副産物として即座に成果が出た:** 役割で語らせた瞬間、`layout.tsx` は表では L5 が統治すると称しているのに**実際の L5 は走査していない**ことが露見した。L5 を拡張して `new Date()` in `app/layout.tsx` が赤になった。さらに **role-claim テスト**（表の主張を実際の走査で検算する）を入れたので、**同じクラスの欠陥は今後 verify 自身が落ちる形で捕まる。**

→ 「名前 → 役割」への凝縮がもぐら叩きを止めた実例として、一般原則化したものが [[spacta-fukuzatsusei-no-gyoshuku]]。

## 5. 判断基準 — 著者が重視していること

方針に迷ったときはここに戻る。

1. **小手先の解決でないこと。** `src/app` にパッチを当てて `layout.tsx` を放置するのがまさに小手先。**名前を足すべき場所に概念を置く**
2. **潔癖症になりすぎないこと。** すべてを検査に落とす必要はない。**あらゆるファイルに意見を持とうとせず、知らないものは知らないと言う**
3. **美しいこと。** 検証器自身の無知を可視化する設計を、カバレッジを最大化する設計より優先する
4. **既存仕様に縛られない。** 検証過程のブランチでは柔軟に方針を変えてよい
5. **AI が運用者である。** 人間が `verify` を走らせる前提で設計しない。**赤と exit 2 は、それを受け取ったエージェントが自分のタスクの中で解消できなければならない** —— 解消できない非ゼロ終了は、ループか回避策の捏造を招く
6. **vibe coder にとって最重要はアプリの質、次にコスト。** 人々は既に品質のために Opus / Fable 級を選んでいる。その意思決定の前では出力トークンの1.5倍はノイズ
7. ~~幹の行数は最重要予算。~~ **撤廃 [対話で再考]** — 経緯と結論は [[spacta-miki-gyousuu-saikou]] を参照

### err と info の選別基準 [仮説]

**「重要か」ではなく「失敗が沈黙するか」。** L8（色の直書き）が info でよいのは重要でないからではなく**失敗が見えるから**（人間が画面を見れば30秒で気づく）。L2 が err なのは重要だからではなく**失敗が沈黙するから**（テストも tsc も画面も通る）。Spacta は既にこの基準で動いているが明文化されていない。

**循環への注意:** 「AI は隔離のおかげで小さい範囲しか見ないから推論を信じてよい」は、**その隔離を作っているのが L1/L7/L2 なので循環する。** 緩和の候補は隔離を**消費**している掟（L8/L9/L10）だけ。

## 6. 概念

### コンテキスト隔離の機構 [確立]

**import の隔離は必要条件であり、かつ最も簡単な部分である。**

| | 止めるもの | 難易度 |
|---|---|---|
| L1 / L7 | **見える結合**（import グラフの静的な辺） | 簡単。ESLint でも8割できる |
| L2 / L3 / L9 / L10 + 4語彙 | **見えない結合**（共有可変状態、環境からの暗黙読み取り、末端からの IO） | **難しい。ここが Spacta の実質** |

本丸は **L2** である。`(state, action) => [state, effects]` が純粋なら、機能の全挙動が自分の引数だけの関数になり、「このファイルだけ読めば分かる」が真になる。L10 は「状態がどこにあるか探す」作業を消し、L9 は葉から伸びる隠れた IO の辺を消す。

### 名前の所有権による切り分け [確立]

「フレームワーク非依存 vs 依存」は雑な切り方である。規則の文言はタダで、価値は施行にあり、施行は必ず実ファイルを見る。実務的に効く線は **「その名前を所有しているのは誰か」**。

| Spacta が所有 | フレームワークが所有 |
|---|---|
| `core.ts` / `shell.tsx` / `features/` / `shared/` | `app/` / `page.tsx` / `layout.tsx` / `middleware.ts` |
| **誰にも動かされない** | **リリースで動く。追随が要る** |

実測: livingdoc 81ファイル中 `app/` は17（約21%）。**残り8割は Spacta が名前を所有する内側。** アダプタが小さく済む根拠。

### 二本脚モデル — 構造と検証 [確立]

- **第1の脚（構造）** `SPACTA.md` + starter + 4語彙。**これが AI 開発を成立させている部分**
- **第2の脚（検証）** `verify`。構造が破れていないことの証明

**検証器は商品ではない。構造が商品で、検証器はその保証である。** 帰結として **「Spacta in X」は検証器ゼロで出荷できる** —— 隔離・小さいタスク・影響範囲の限定は初日から手に入り、検証器は500タスク回したときの漂流を止めるためのもの。**言語ごとに AST 検査器を書くコストは参入コストではなく持続コストである。**

### 制約はアダプタの向こうに隠せない [確立]

ライブラリは**能力**を提供するので隠せる。Spacta が提供するのは**制約**であり、制約の価値は「あなたが書くコードに適用されること」から来る。壁の向こうにあるのは自分のビジネスロジックなので、壁は何も隠していない。

> **アダプタは Next.js を Spacta から隠せる。Spacta を Next.js から隠すことはできない。**

### 規律 / 機構 / 束縛の三分割 [着想]

ただし **Spacta の中にライブラリ化できる部分は実在する。**

| | 中身 | ライブラリ化 |
|---|---|---|
| **規律** | L1/L2/L7/L9/L10、膜語彙 | ❌ 検証器でしか届かない |
| **機構** | `drain` / Effect キュー / correlationId / **Action ログ** | ✅ **可能。しかもすべき** |
| **束縛** | React への配線、`app/` の解釈 | ✅ これが本当のアダプタ |

**機構は今プロジェクトごとに手で書かれていて、実際に壊れている。** livingdoc の `drain` は starter に無かったので実装者が発明し、その発明版が結果を握りつぶしていた。ライブラリなら間違えられなかった。効果は3つ —— 並行制御が一度だけ正しく解ければ済む、**フライトレコーダーがタダで手に入る**、starter が薄くなる。

代償: Spacta が「書き方」から「依存先」に変わる。判断基準は **「AI が編集すべきものは starter に、編集すべきでないものはライブラリに」**。

**v0.9.3 で置き方だけ先に対処済み** —— `drain` はコンポーネント内にネストせずモジュールレベルの関数として書いた。将来「移動」で済み「書き直し」にならない。

→ 「アダプター」という語の分類（束縛アダプター/データアダプター）とディレクトリ方針は [[spacta-adapter-bunrui]] に統合した。機構のライブラリ化がもぐら叩きを防ぐ一般原則としての位置づけは [[spacta-fukuzatsusei-no-gyoshuku]] を参照（`drain`の発明バグは実害の実例として引用されている）。

### sink か source か — 逃がし口の判定基準 [仮説]

「隔離が難しい領域は Next.js 側に置く」は、基準があれば妥当で、なければ危険（逃がし口が楽なら全部そちらへ移る）。

> **外に置いてよいのは Spacta の状態から「受け取る」もの（sink）だけ。状態に「書ける」もの、Core に値を注入できるもの（source）は外に置けない。**

書き経路への適用: **輸送は外でよい、判断は出せない。** 具体的には **Server Actions を Effect の輸送路に使う**とフレームワークとの競合が減る。読みは `InitData` の再注入として扱えばよい。

### 段位の申告 [着想 → v0.9.4 で部分実装]

部分適用は正しいが、**「逃がし口」ではなく「機械が申告する段位」として設計する。** `SPACTA.md` §2 は既に「shell は任意」と書いており芽はある。T0（page → components のみ）→ T1（+ Core）→ T2（+ Shell）→ T3（+ 書き経路の往復）。**`verify` が各機能の段位を印字すれば、「穴を隠さない」の一貫適用になる。** v0.9.4 の役割カバレッジ表がこの半分を実現している。

## 7. 認識を変えた要因 — 次の AI が同じ誤りに戻らないために

**① 「L1/L7 がコンテキスト隔離を作っている」は誤り。** 著者の実装経験による指摘で撤回。import の隔離は**最初にやって極めて簡単だった**部分であり、難しかったのは状態管理と API の隔離。誤りの出どころも特定されている —— `HUMAN_GUIDE` §0-1 は問題を「UI と状態管理の密結合」と正しく立てながら、答えを「物理的な隔離＝ディレクトリ + import 禁止」としか書いておらず、**状態側の機構（L2 / L10）が答えの段落に無い。**

**② 「Go は移植先として価値が高い」は取り下げ。** バックエンドでは状態がプロセス内になく DB にある。結合の主要因は共有テーブル・共有スキーマであり、**それは Spacta が「解決していない」と明言している結合そのもの。** 「Spacta in Go」は Spacta の最大の穴を主要問題として相続する。**隣接市場は他言語のバックエンドではなく、他プラットフォームの UI**（SwiftUI / Flutter / Compose）。→ 他プラットフォーム展開時に「名前→役割」凝縮パターンを先回りでテンプレート化する話は [[spacta-fukuzatsusei-no-gyoshuku]] を参照。

**③ 「検証器が Spacta の商品」は重み付けの誤り。** `HUMAN_GUIDE` §0 は既に4本立て（隔離 / 複雑性低減 / 契約駆動 / 機械的検証）で、hope-prompt は4本のうち1本。二本脚モデルへ。

**④ 「人間が NOT guaranteed を読む」前提が誤り。** 運用者は AI。誠実さの機械化の価値は消えないが、**その受け手は verify の出力ではなく文書の側にいる。** NOT guaranteed は消してはいけないが太らせてもいけない。

**⑤ トークンコストの懸念は弱い。** エージェント型ループでは**入力量が出力量を圧倒する**（20ファイル読んで30行書く）。隔離が入力を4〜10倍削るのに対し明示的ステートマシンが出力を増やすのは1.5〜2倍で、単価差を勘案しても削減側が桁で勝つ。プロンプトキャッシュがさらに入力を安くする。ガイド §0-2 の「未計測」は誠実だが戦略的には小さな留保。

**⑥ 「受け皿となる Action が存在すること」だけでは検査が空虚。** Shell は `correlationId` を**要求する側の Action**（`INCREMENT`）に既に載せているので、それで条件が満たされてしまう。**受け皿は「書き込みを要求する Action ではないもの」でなければならない。**

**⑦ 役割表の受け皿が貪欲だと、塞いだ穴が再発する。** `/^src\/.+\.tsx?$/` の catch-all が `src/app/page.tsx` を飲み込み、v0.9.3 の穴をその一般解を書いている最中に再度開けた。L6 の分類器自己テストが捕まえた。**catch-all は APP_ROOTS を除外しなければならない。**

## 10. 概念間接続メモ

- **コンテキスト隔離の機構** → **移植性**（安い部分と価値ある部分が一致しないので、移植コストの見積もりが変わる）
- **コンテキスト隔離の機構** → **err/info の選別基準**（隔離を生産する掟は、隔離を理由に緩められない = 循環）
- **名前の所有権** → **役割で語る**（他人が所有する名前だけが追随対象）
- **二本脚モデル** → **移植性**（検証器ゼロで出荷できるので参入コストが下がる）
- **AI が運用者** → **赤と exit 2 の設計**（解消できない非ゼロ終了は穴より悪い）
- **AI が運用者** → **データ結合の重み**（人間なら補完できるが AI は緑を見て通過する）
- **未解決1（データ結合）** は **未解決4（品質の実測）** の主要な交絡因子でもある
- **段位の申告** は **役割カバレッジ** の一般形
