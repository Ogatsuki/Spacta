## 1. Spacta とは何か（30秒）

AI にコードを書かせるための設計規律。一文で言うと **「膜（Core 境界）をデータだけが越える。IO は入らず、計算は出ない」**。`State` / `Action` / `Effect` / `InitData` の4語彙だけが膜を通る。信頼階層は `Law（機械施行）> Form（テンプレ・可変）> Advice（info）> Judgment（未検査）`。

**実体は3つ [確立・前版から訂正]。** 前版は「2つだけ」と書いていたが `garden` が抜けていた。

| 実体 | 何をするか | 回す主体 |
|---|---|---|
| `SPACTA.md`（67行・英語） | AI が毎タスク読む幹。掟の正本 | AI が読む |
| `verify/verify.mjs` | 規律を AST で機械検査。err で落とす | **AI が回す** |
| `garden/garden.mjs` | verify の info/warn を **AI が消化できる JSON 指示書**に変換 | **AI が回す** |

最重要の作法は3つとも共有している —— **穴があること自体は許される。穴を隠すことは許されない。** `verify` は毎回「この緑が保証すること / しないこと」を印字し、`garden` は未知の rule を黙って落とさず `kind:"unknown"` で必ず通し、`garden:keep` で保留した項目も指示書の `suppressed` に残す。**隠蔽ではなく可視の保留。**

### 前提: 開発者は AI である [確立・この文書の土台]

前版は「運用者は人間ではなく AI」と書いていたが、**運用者にとどまらない。設計判断を含めて AI が行う。**

- 網羅的なステートマシンを手書きするのは**人間には苦行、モデルには安価** —— この非対称性が設計全体の前提
- `verify` も `garden` も AI が回す。人間がこれらを実行するシナリオは**設計対象ではない**
- アプリ構築に必要な設計判断も、大半は AI が下す
- 人間の関与は**最小限もしくは皆無**。人間が持つのは「何を作るか」と受け入れの判断であって、どう作るかではない

**この前提は飾りではなく、以下すべての節の読み方を変える。** 具体的には —— 人間なら勘で補える曖昧さが、AI では緑を見て通過される。ゆえに **「気づける」を人間の注意力に依存させる設計はすべて無効**であり、構造かコンパイラか印字のどれかで表現されていなければ存在しないのと同じである。

## 2. 貫く原理 — 複雑性の凝縮 [確立]

これが現在地2の背骨である。前版で個別に見えていた解決・未解決は、すべてこの1本の軸に乗る。

> ある種類の複雑性・変化・多様性を、コードベース中の**1箇所（1ファイル、1つの型定義、1つの構築点）に集約**し、それ以外の場所はその1箇所を経由してのみ複雑性に触れるようにする。**エラーが起きたとき、見るべき場所が1つで済む状態を作ること。**

止まるもぐら叩きは2種類ある。

1. **外側の変化への追随** — フレームワークが規約を足すたびに、検査側が1つずつ後追いする必要がなくなる
2. **内側の再発明** — 同じ意味のものを機能・プロジェクトごとに独自に（しばしば少しずつ間違えて）再実装する事故がなくなる

**これは §7「コンテキスト隔離の機構」の「このファイルだけ読めば分かる」を、Core 内部から Core の外側（膜を横切る先）へ一般化したものである。**

### 凝縮の3つの実装形 [確立]

| 形 | 何を1箇所に置くか | 実例 |
|---|---|---|
| **役割マッピング型** | 「名前 → 役割」の対応表 | `verify/platform/nextjs.mjs`（v0.9.4） |
| **語彙定義型** | 「意味のある型」。**構築は各所に散らしてよい** | `shared/types.ts` の `Effect` union（v0.9.3） |
| **目と手の分離型** | 「検知」を1箇所に置き、他は変換・実行だけ | `verify` → `garden`（既存） |

3つ目は前版にも凝縮の文書にも書かれていなかったが、`garden.mjs` の設計原則にそのまま書いてある ——「**決定論的・AIなし。検知は verify に一元化し、garden は変換だけを行う（目と手の分離）**」。つまり**凝縮は Spacta の中で既に3回、独立に発見されている。** 原理として取り出す妥当性の傍証はこれで足りる。

### AI が開発者であることと、凝縮の目的 [確立]

凝縮の目的は「人間が把握できる量に減らすこと」ではない。

> **1エージェントの1コンテキストに収まる量に減らすこと。**

単位が変わると設計判断も変わる。人間なら「あ、これ共有ファイルだ」と勘で気づけるが、**AI は緑を見て通過する。** したがって凝縮の成果は、AI が読む前に効く形——**物理ディレクトリの配置・型定義・印字**——で表現されなければならない。レビュー時の注意喚起やコメントは、この前提では成果として数えない。

## 3. アダプター — 凝縮が住む場所 [確立・決定]

「アダプター」は**傘概念**であり、その下に2種を置く。前版が `edge` と呼んでいた層は、実は既に「アダプタ」と呼ばれていた束縛層と**同じ性質**——Spacta の外側にあって Spacta の語彙に翻訳する層——を持つ。

| | 旧称 | 何を吸収するか | 具体例 |
|---|---|---|---|
| **束縛アダプター** | 「アダプタ」 | フレームワークへの配線 | `verify/platform/nextjs.mjs`、React 配線、Server Actions を Effect 輸送路に使う |
| **データアダプター** | **`edge`** | データ取得・永続化 | `shared/source/queries.ts`、`TRACE_SELECT` |

**役割分類表の `edge` という表記は「データアダプター」に置き換える。**

### `adapters/` ディレクトリを作る [決定]

名前の所有権の切り分けに**第3の区分**を追加する。

| Spacta 所有 | フレームワーク所有 | **アダプター** |
|---|---|---|
| `core.ts` / `shell.tsx` / `features/` / `shared/` | `app/` / `page.tsx` / `layout.tsx` / `middleware.ts` | **`adapters/`** |
| 誰にも動かされない | リリースで動く。追随が要る | 両者を翻訳する |

**理由は §2 の最後の段落そのものである。** 今 `queries.ts` は `shared/`（Spacta 所有の名前空間）の中に他のコードと**同じ顔をして**埋まっており、pageview だけを直すつもりの AI が、自分が3機能共有のコードを触っていることに気づけない。危険の本体は「共有されていること」ではなく **「共有されていることが構造から見えないこと」** にある。別ディレクトリに出せば、**その場所にいるという事実だけで「ここは特別扱いが要る」と構造的に伝わる。** 検査ロジックを一切足さずに済む。

既存の粒度（`app/` / `features/` / `shared/` / `core.ts` / `shell.tsx`）に1つ足すだけなので、過剰なラベリングではない。

### 型定義とのペアリング [仮説]

「アダプターには型定義をセットにすべきか」——**アダプターの種類で答えが割れる。**

- **データアダプター: 全面的に有効。** 仕事が「値を取ってくる」ことなので、「どんな値を要求できるか」を型で縛るのがそのまま機能する（§5 の処方）
- **束縛アダプター: 一枚岩ではない。**
  - **値が Spacta の語彙に流れ込む部分**（Server Actions 経由の Effect 結果輸送）→ **要る。すでにある。** `Action` union と `tsc` の `never` 終端が担っている
  - **ファイルを役割に分類する部分**（`nextjs.mjs`）→ **型は噛み合わない。** ファイルパスの分類ロジックであってデータの形の話ではない。ここは L6 の分類器自己テスト（glob が最低1件マッチすることを assert）と role-claim テスト（表の主張を実走査で検算）が既に担っており、これはこれで正しい設計

### 制約はアダプタの向こうに隠せない [確立]

ライブラリは**能力**を提供するので隠せる。Spacta が提供するのは**制約**であり、制約の価値は「あなたが書くコードに適用されること」から来る。壁の向こうにあるのは自分のビジネスロジックなので、壁は何も隠していない。

> **アダプタは Next.js を Spacta から隠せる。Spacta を Next.js から隠すことはできない。**

これは `adapters/` を作ることと矛盾しない。`adapters/` が隠すのは**フレームワークの多様性**であって、Spacta の制約ではない。

## 5. 解決済み — すべて凝縮の実例として読み直す

前版はこれらを無関係な4つの修正として並べていた。**同じ原理の4回の適用である。**

### ① フレームワーク名の列挙をやめる（v0.9.4）— 役割マッピング型の凝縮 [確立]

**症状:** `src/app/` 対応は1件のパッチで直せるが、**クラスとしては直らない。** `layout.tsx` / `error.tsx` / `middleware.ts` と将来のあらゆる規約が、依然すべての err 検査の外にいた。名前を足す限り、Next.js が進化するたびに静かに穴が開く。**典型的なもぐら叩き。**

**解:** `verify/platform/nextjs.mjs` が **名前 → 役割** を1箇所で引き受け、`CHECKS` は**役割**だけを語る。役割が引けなかったファイルは INCONCLUSIVE。

> **役割が引けたファイルは、掟が弱くてもその弱さを印字できる。役割が引けないファイルだけが本当の穴である。**

だから `laws: []` は穴ではなく**宣言された弱さ**。そして **INCONCLUSIVE は「これが何か分からない」にだけ使い、「専用の役割が無い」には使わない** —— 後者に使うと、コロケートしたテスト1つで走行が止まり、**運用者は無視リストに手を伸ばす訓練を受ける。それは穴より悪い。**

**副産物:** 役割で語らせた瞬間、`layout.tsx` は表では L5 が統治すると称しているのに**実際の L5 は走査していない**ことが露見。L5 を拡張し `new Date()` in `app/layout.tsx` が赤になった。さらに **role-claim テスト**を入れたので、同じクラスの欠陥は今後 verify 自身が落ちる形で捕まる。**これが文書内で唯一、凝縮がもぐら叩きを止めたと実測できた例である。**

### ② 書き経路の戻り（v0.9.3）— 語彙定義型の凝縮 [確立]

**症状:** Core が `Effect` を吐き `runEffect` が実行するが、**結果が Core に戻る経路が存在しなかった。** 仮ID `temp_*` がそのままサーバへ飛び、失敗した投稿が画面に残る。**`verify` 緑・`tsc` 0エラー・E2E 通過のまま。3つのゲートが同一の一点で同時に盲目になった。**

**解:** `Effect` が `correlationId` を持ち、Shell が結果を `EFFECT_SUCCEEDED` / `EFFECT_FAILED` という **Action** に変換し、Core が処理する。施行は分担 —— **`verify` が受け皿の存在を、`tsc` の `never` 終端が処理の網羅を**担う。

**設計上の要点2つ。**

1. **第5の膜語彙を作らなかった。** `EffectResult` は膜を越えない —— 越えるのは `Action` である。「第5の**膜**語彙」という命名が最初から圏を間違えている。語彙は4つのまま
2. **検査は宣言ではなく構築地点を見る。** `Effect` は単一 union で全機能が共有するので「この機能の Effect」は型レベルに存在しない。だが **`core.ts` は必ずどれか1機能に属する**

**実測 [確立]:** 恐れていたカスケードは**起きなかった**。pageview が書く4つの Effect はすべて pageview 専用。**型は大域的でも構築は機能ごとだった。**

> **この実測が、§7 のデータ結合処方の全根拠である。** 「語彙の定義を1箇所に凝縮し、構築は局所に任せる」は書き経路で既に検証されている。読み経路への輸入は**新発明ではなく移植**である。

### ③ 検査が何かに向いていることの証明（v0.9.2）[確立]

L6 の自己テストは checker **関数**にテキストを直接渡すので、`CHECKS` の glob（`root`/`match`）を一度も通らなかった。**glob を書き間違えて0ファイル走査になっても、自己テストは緑・本スキャンも緑。** 参照コーパスに対して各 glob が1件以上選ぶことを assert して塞いだ。判定は `> 0` で、調整された閾値ではない。

### ④ 0ファイルの検査が「保証した」と名乗る問題（v0.9.3）[確立]

L5 は `src/app/` レイアウトで**0ファイル走査のまま緑**になり、しかも `Guaranteed: L5 Server boundaries generate no ids, time or randomness` と印字していた。**誠実さの装置そのものが、検査していないものを保証だと主張していた。**

**解:** 0ファイルの検査は「Guaranteed」に載せず、`NOT verified in this project (0 files matched — the law was not enforced here)` に走査した root 付きで出す。**赤にはしない** —— app router や `components/` がまだ無いプロジェクトは正当であり、fatal にすると正直な状態が表現不能になり、検査を黙らせる訓練をしてしまう。**口に出すのが解決であって、走るのを拒むことではない。**

## 7. データ経由の結合への処方 [仮説]

**結論を先に書く: 完全解決ではない。ただし「気づかれない事故」を「見える単一の確認ポイント」に変換するところまでは持っていける。** これは書き経路の戻り問題（v0.9.3）で達成したのと**同じ水準・同じ形**の解決である。

### 1. 物理ディレクトリで「触っている」ことを可視化する

`queries.ts` を `adapters/` に移す。pageview の機能修正タスクなら `features/pageview/` だけで完結し、`adapters/` に触れる理由がそもそも無い。触る必要が生じたら、**その場所にいるという事実だけで**「これは複数機能に影響する変更だ」と構造的に気づける。検査ロジックを一切足さずに実現する。

### 2. 語彙を型に凝縮し、構築を機能ごとに局所化する

v0.9.3 で実測されたパターンを読み経路に輸入する。

```
今: 3機能が同じ関数(TRACE_SELECT)を直接共有
  pageview → listTracesForPage() ─┐
  search   → searchTraces()      ─┼─→ 全部 TRACE_SELECT を呼ぶ
  profile  → listTracesByUser()  ─┘

処方後: 各機能は「意図」を型で宣言し、データアダプターが個別に組み立てる
  pageview の意図 = { fields: ["id", "page_id", "quote", "author"] }
  search    の意図 = { fields: ["id", "quote", "votes"] }
  profile   の意図 = { fields: ["id", "author"] }
  → 型定義された意図に対して、データアダプター側の汎用ビルダーが独立に SQL を組み立てる
```

意図の型に無いフィールドを機能側が要求すればコンパイルエラーになる。これにより:

- pageview が新フィールドを必要としても pageview の意図だけを変えればよく、search/profile に触れない
- 3機能が同じ文字列を共有しなくなるので、1機能の変更が他2機能に波及しない
- 機能側が語彙を勝手に拡張・独自解釈する（「5つ目の重複実装」）リスクが構造的に塞がる。**語彙の定義は1箇所にしかなく、機能側はそこから選ぶだけになる**

### この処方で解決する部分・しない部分 [確立]

型定義は「形（shape）の整合性」を保証するが、「意味（業務ルール）が全消費者にとって正しいか」までは保証しない。`hidden` フラグの判定ロジックの**意味**が変わったとき、型チェックは検出できない。ただし処方後はその実装が**1箇所**に凝縮されているため、失敗モードの性質が変わる。

| | 処方前 | 処方後 |
|---|---|---|
| リスクの所在 | 3箇所の呼び出し元のどれかが更新漏れ（**見えない**波及） | 1箇所の変更が3機能にとって正しいか（**見える**単一の確認点） |
| 機械的な検知 | なし。`verify` も `tsc` も緑 | フィールドの過不足はコンパイルエラー。共有コードへの接触は `adapters/` の配置で可視 |
| 残るリスク | **気づかれずに壊れる** | **気づいた上で**、実際に正しいかは検証が要る |

**「隠れた地雷」から「見える単一の確認ポイント」への変換** —— これが到達点である。完全な解決だと主張しないことが、判断基準2「潔癖症になりすぎない」に沿う。

### 残るもの

- 型定義された「意図」から実際の SQL を組み立てる**汎用ビルダー自体の設計は未着手**
- データアダプター内の実装変更が3機能すべてにとって振る舞い的に正しいかの検証は、型システムの外側の話として別途必要。**AI が開発者である以上、この確認も AI が回すテストとして表現されなければならない**（人間のレビューを当てにしない）
- **`traces` の物理スキーマそのものが複数機能から参照される事実は、どんなアダプターでも消せない。** カラムのリネーム・型変更は結局「誰が読んでいるか全員把握している主体」が要る。凝縮はこの主体の**担当範囲を1ディレクトリに閉じる**ところまでしかできない

## 8. 判断基準 — 著者が重視していること

方針に迷ったときはここに戻る。**前版の7項目から「幹の行数は最重要予算」を撤廃し、6項目 + 予算の再定義。**

1. **小手先の解決でないこと。** `src/app` にパッチを当てて `layout.tsx` を放置するのがまさに小手先。**名前を足すべき場所に概念を置く** —— これは §2 の凝縮そのものの言い換えである
2. **潔癖症になりすぎないこと。** すべてを検査に落とす必要はない。**あらゆるファイルに意見を持とうとせず、知らないものは知らないと言う**
3. **美しいこと。** 検証器自身の無知を可視化する設計を、カバレッジを最大化する設計より優先する
4. **既存仕様に縛られない。** 検証過程のブランチでは柔軟に方針を変えてよい
5. **AI が開発者である。** 人間が `verify` / `garden` を走らせる前提で設計しない。**赤と exit 2 は、それを受け取ったエージェントが自分のタスクの中で解消できなければならない** —— 解消できない非ゼロ終了は、ループか回避策の捏造を招く
6. **vibe coder にとって最重要はアプリの質、次にコスト。** 人々は既に品質のために Opus / Fable 級を選んでいる。その意思決定の前では出力トークンの1.5倍はノイズ

### 撤廃: 幹の行数予算 [決定]

~~7. 幹の行数は最重要予算~~

- **コスト論で成立しなかった。** §9-⑤が既に「トークンコストの懸念は弱い」と結論づけている。67行はキャッシュも効く無視できる絶対量であり、「行数=コスト」で幹の行数を最重要予算とするのは自己矛盾していた
- **統括エージェント案は著者が撤回。** 「統括だけが全文を読み、並列サブエージェントは役割別の縮小版を読む」構成が現れるのは**最初のプロダクト構築時だけ**。その後の保守・修正フェーズ（実運用では圧倒的多数）は、単一エージェントが全体を見渡し、隣接 feature も必要なら読み、編集だけ対象 feature に絞る使い方が主になる。縮小版を常設する設計は保守フェーズの実態に合わない
- **派生ファイルのドリフト懸念（AI 側から提起）も却下。** `SPACTA.md` は他者に配布してスクリプトで強制する対象ではなく、**著者本人が手作業で保守する内部文書。** 同期の機械的保証は要らない
- **結論:** ルールプロンプトの行数に潔癖症的にこだわる必要はない。増えたらそのとき考える。それより優先度が桁違いに高いのは **Spacta という機構そのものを整えること**

### 予算の再定義 [仮説]

行数を降ろした後に何が予算か。凝縮の軸から自然に出る答え:

> **予算は行数ではなく「1タスクで参照しなければならない箇所の数」である。**

`SPACTA.md` が 67行でも 90行でも、AI が1タスクで開くファイル数が変わらないなら支出はゼロに近い。逆に、幹を1行も増やさずに `queries.ts` を共有させ続けることは、**毎タスク 508行の支出**である。前版が「掟ゼロ・行数増ゼロで prevent-strong を得た」を成果として誇っていたのは正しかったが、誇るべき理由は行数ではなく**参照箇所を増やさなかったこと**だった。

### err と info の選別基準 [仮説・AI 前提で要改訂]

**「重要か」ではなく「失敗が沈黙するか」。** L2 が err なのは重要だからではなく**失敗が沈黙するから**（テストも tsc も画面も通る）。

**ただし前版の L8 の説明は、AI が開発者である前提と衝突する。** 前版は「L8（色の直書き）が info でよいのは**人間が画面を見れば30秒で気づく**から」と書いていた。**AI は画面を見ない。** この根拠のままでは L8 の info は正当化できない。

**成立する形に置き換える [仮説]:** L8 が info でよいのは、**`garden` が回収するから**である。`garden` は verify の info/warn を AI が消化できる指示書に変換する装置であり、「失敗が沈黙するか」の判定は次のように読み替わる。

> **err = 誰も回収しない失敗。info = `garden` が回収する失敗。**

この読み替えは garden の存在意義そのものを説明し、かつ「人間の目」への依存を設計から完全に除去する。**§10-④「人間が NOT guaranteed を読む前提は誤り」の、まだ実行されていなかった残りの半分がこれである。**

**循環への注意:** 「AI は隔離のおかげで小さい範囲しか見ないから推論を信じてよい」は、**その隔離を作っているのが L1/L7/L2 なので循環する。** 緩和の候補は隔離を**消費**している掟（L8/L9/L10）だけ。

## 9. 概念

### コンテキスト隔離の機構 [確立]

**import の隔離は必要条件であり、かつ最も簡単な部分である。**

| | 止めるもの | 難易度 |
|---|---|---|
| L1 / L7 | **見える結合**（import グラフの静的な辺） | 簡単。ESLint でも8割できる |
| L2 / L3 / L9 / L10 + 4語彙 | **見えない結合**（共有可変状態、環境からの暗黙読み取り、末端からの IO） | **難しい。ここが Spacta の実質** |

本丸は **L2**。`(state, action) => [state, effects]` が純粋なら、機能の全挙動が自分の引数だけの関数になり、「このファイルだけ読めば分かる」が真になる。L10 は「状態がどこにあるか探す」作業を消し、L9 は葉から伸びる隠れた IO の辺を消す。

**そしてデータ経由の結合は、この表に載っていない第3の列である** —— import の辺でもなく、プロセス内の共有可変状態でもなく、**同じテーブルを読んでいるという事実**による結合。だから L1〜L10 のどれにも引っかからない。§7 の処方が狙っているのはこの列である。

### 名前の所有権による切り分け [確立]

「フレームワーク非依存 vs 依存」は雑な切り方。規則の文言はタダで、価値は施行にあり、施行は必ず実ファイルを見る。実務的に効く線は **「その名前を所有しているのは誰か」**。所有者が3区分になったことは §3 を参照。

実測: livingdoc 81ファイル中 `app/` は17（約21%）。**残り8割は Spacta が名前を所有する内側。** アダプタが小さく済む根拠。

### 二本脚モデル — 構造と検証 [確立]

- **第1の脚（構造）** `SPACTA.md` + starter + 4語彙 + **`adapters/` の配置**。**これが AI 開発を成立させている部分**
- **第2の脚（検証）** `verify` + `garden`。構造が破れていないことの証明と、破れの回収

**検証器は商品ではない。構造が商品で、検証器はその保証である。** 帰結として **「Spacta in X」は検証器ゼロで出荷できる** —— 隔離・小さいタスク・影響範囲の限定は初日から手に入り、検証器は500タスク回したときの漂流を止めるためのもの。**言語ごとに AST 検査器を書くコストは参入コストではなく持続コストである。**

**凝縮の軸から見た補強:** §7 の処方1（`adapters/` への物理分離）は**第1の脚だけで実現し、検証器を1行も必要としない。** 最大の穴に対する最初の一手が検証器ゼロで打てるという事実は、二本脚モデルの主張の実例になっている。

### 規律 / 機構 / アダプター [着想 → §3 で再編]

前版の「規律 / 機構 / 束縛」の三分割を、アダプター傘の下に整理し直したもの。

| | 中身 | ライブラリ化 |
|---|---|---|
| **規律** | L1/L2/L7/L9/L10、膜語彙 | ❌ 検証器でしか届かない |
| **機構** | `drain` / Effect キュー / correlationId / **Action ログ** | ✅ **可能。しかもすべき**（§6 に実害の実例） |
| **アダプター** | 束縛（React 配線・`app/` の解釈）+ データ（取得・永続化） | ✅ これが本当のアダプタ。物理的な住所は `adapters/` |

### sink か source か — 逃がし口の判定基準 [仮説]

「隔離が難しい領域は Next.js 側に置く」は、基準があれば妥当で、なければ危険（逃がし口が楽なら全部そちらへ移る）。

> **外に置いてよいのは Spacta の状態から「受け取る」もの（sink）だけ。状態に「書ける」もの、Core に値を注入できるもの（source）は外に置けない。**

書き経路への適用: **輸送は外でよい、判断は出せない。** 具体的には **Server Actions を Effect の輸送路に使う**とフレームワークとの競合が減る。読みは `InitData` の再注入として扱えばよい。

**アダプター概念との関係 [仮説]:** データアダプターは定義上 **source** である（Core に値を注入する）。だから `adapters/` は「外」ではなく、**Spacta の管轄内にある翻訳層**として置かれなければならない。`adapters/` を「逃がし口」として使い始めたら、この基準に違反している。

### 段位の申告 [着想 → v0.9.4 で部分実装]

部分適用は正しいが、**「逃がし口」ではなく「機械が申告する段位」として設計する。** T0（page → components のみ）→ T1（+ Core）→ T2（+ Shell）→ T3（+ 書き経路の往復）。**`verify` が各機能の段位を印字すれば、「穴を隠さない」の一貫適用になる。** v0.9.4 の役割カバレッジ表がこの半分を実現している。

## 10. 認識を変えた要因 — 次の AI が同じ誤りに戻らないために

**① 「L1/L7 がコンテキスト隔離を作っている」は誤り。** import の隔離は**最初にやって極めて簡単だった**部分で、難しかったのは状態管理と API の隔離。出どころも特定済み —— `HUMAN_GUIDE` §0-1 は問題を「UI と状態管理の密結合」と正しく立てながら、答えを「物理的な隔離＝ディレクトリ + import 禁止」としか書いておらず、**状態側の機構（L2 / L10）が答えの段落に無い。**

**② 「Go は移植先として価値が高い」は取り下げ。** バックエンドでは状態がプロセス内になく DB にある。結合の主要因は共有テーブル・共有スキーマであり、**それは Spacta が「解決していない」と明言している結合そのもの。**「Spacta in Go」は最大の穴を主要問題として相続する。**隣接市場は他言語のバックエンドではなく、他プラットフォームの UI**（SwiftUI / Flutter / Compose）。展開時は `nextjs.mjs` と同じ「名前 → 役割」パターンを**先回りでテンプレート化**しておけば、新プラットフォームごとに一から作り直す未来のもぐら叩きを回避できる。

**③ 「検証器が Spacta の商品」は重み付けの誤り。** `HUMAN_GUIDE` §0 は既に4本立て（隔離 / 複雑性低減 / 契約駆動 / 機械的検証）で、hope-prompt は4本のうち1本。二本脚モデルへ。

**④ 「人間が NOT guaranteed を読む」前提が誤り。** 運用者は AI。誠実さの機械化の価値は消えないが、**その受け手は verify の出力ではなく文書の側にいる。** NOT guaranteed は消してはいけないが太らせてもいけない。**この訂正はまだ半分しか実行されていない** —— §8「err と info の選別基準」に人間の目への依存が残っていた。

**⑤ トークンコストの懸念は弱い。** エージェント型ループでは**入力量が出力量を圧倒する**（20ファイル読んで30行書く）。隔離が入力を4〜10倍削るのに対し明示的ステートマシンが出力を増やすのは1.5〜2倍で、単価差を勘案しても削減側が桁で勝つ。プロンプトキャッシュがさらに入力を安くする。

**⑥ 「受け皿となる Action が存在すること」だけでは検査が空虚。** Shell は `correlationId` を**要求する側の Action**（`INCREMENT`）に既に載せているので、それで条件が満たされてしまう。**受け皿は「書き込みを要求する Action ではないもの」でなければならない。**

**⑦ 役割表の受け皿が貪欲だと、塞いだ穴が再発する。** `/^src\/.+\.tsx?$/` の catch-all が `src/app/page.tsx` を飲み込み、v0.9.3 の穴をその一般解を書いている最中に再度開けた。L6 の分類器自己テストが捕まえた。**catch-all は APP_ROOTS を除外しなければならない。**

**⑧ 実体は2つではなく3つ。** 前版は `SPACTA.md` + `verify` と書いていたが、`garden`（`npm run garden`）が抜けていた。しかも garden は**凝縮の第3の実装形（目と手の分離）**を体現しており、かつ **info を回収する主体**として err/info 基準の正当化に不可欠だった。文書から実体が1つ落ちていたことで、判断基準に人間の目が残り続けていた。

**⑨ 「edge は Spacta が意図的に検査しない層」という枠組みが穴を温存していた。** `edge` を独自の圏として置いた瞬間、束縛アダプター側で解けている前例が見えなくなった。**アダプターという傘に入れ直すだけで、処方が既存パターンの移植に変わった。** 名前は説明ではなく、探索範囲の指定である。

## 13. 概念間接続メモ

- **複雑性の凝縮** → **解決済み4件すべて**（役割マッピング / 語彙定義 / 目と手の分離 の3形に分類できる）
- **複雑性の凝縮** → **未解決すべて**（データ結合 = 3箇所、機構 = プロジェクトごと、correlationId = 付け忘れ可能。ただし**往復の追跡だけは凝縮では解けない**）
- **AI が開発者** → **凝縮の単位**（「人間が把握できる量」ではなく「1エージェントの1コンテキストに収まる量」）
- **AI が開発者** → **成果の表現形**（構造・コンパイラ・印字のどれかでなければ存在しないのと同じ。レビュー時の注意喚起は数えない）
- **AI が開発者** → **err/info 基準**（人間の目を根拠にできない → `garden` が回収するか否かで引き直す）
- **AI が開発者** → **赤と exit 2 の設計**（解消できない非ゼロ終了は穴より悪い）
- **アダプター（傘概念）** → **データ結合の穴の再分類**（未知の層 → 既に解けた問題の別インスタンス。名前は説明ではなく探索範囲の指定）
- **`adapters/` ディレクトリ** → **二本脚モデル**（第1の脚だけで最大の穴に一手打てる = 検証器ゼロ出荷の主張の実例）
- **sink/source** → **`adapters/` の位置**（データアダプターは source なので「外」に置けない。逃がし口として使い始めたら基準違反）
- **幹の行数予算の撤廃** → **予算の再定義**（行数ではなく「1タスクで参照する箇所の数」）
- **凝縮** → **他プラットフォーム展開**（「名前→役割」をテンプレート化して未来のもぐら叩きを先回り）
- **未解決1（データ結合）** は **未解決4（品質の実測）** の主要な交絡因子
- **段位の申告** は **役割カバレッジ** の一般形
- **契約決定の主体** → **モード分離**（`spacta-mode-bunri.md`。§3アダプターの「共有＝凝縮対象」基準をUI構成の契約決定にも拡張）
- **凝縮の単位** → **分割粒度の別軸性**（`spacta-bunkatsu-ryudo.md`。ファイル分割とエージェント分割を同一基準に収束できるか）
- **予算の再定義** → **複雑性の2軸**（`spacta-fukuzatsusei-jiku.md`。振る舞いの複雑性と分量の複雑性は別物で、凝縮では分量軸は縮まらない）
