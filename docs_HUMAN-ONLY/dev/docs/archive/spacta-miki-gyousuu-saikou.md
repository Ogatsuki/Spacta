# 幹(SPACTA.md)の行数予算 — 再考の記録

`spacta-genzaichi.md` §5 判断基準7「幹の行数は最重要予算」について、著者とAIの対話で再検討した。**結論: この基準は撤廃する。**

## 検討の経緯

1. **コスト論では成立しなかった。** `spacta-genzaichi.md` §7-⑤は既に「トークンコストの懸念は弱い」と結論づけている。67行はキャッシュも効く無視できる絶対量であり、「行数=コスト」という理屈で幹の行数を最重要予算とするのは自己矛盾していた。行数へのこだわりを正当化するなら「ルールの普遍性を強制する踏み絵」といった別の理屈が要るが、著者の判断はそこにも留まらず、基準自体の撤廃に至った。

2. **統括エージェント案(検討したが撤回)。** 「統括エージェントだけが全文を読み、並列サブエージェントは役割別に縮小した幹ファイルを読む」という案を検討したが、著者が撤回した。理由: 統括+並列サブエージェント構成が現れるのは最初のプロダクト構築時だけで、その後の保守・修正フェーズ(実運用では圧倒的多数)は単一エージェントが全体を見渡しつつ、隣接featureも必要なら読み、編集だけ対象featureに絞る、という使い方が主になる。役割別に縮小した幹ファイルを常設する設計は、この保守フェーズの実態に合わない。

3. **ドリフト懸念(AI側から提起)は不成立と判断された。** 複数の派生ファイルを維持すると同期漏れ(ドリフト)が起きるという懸念をAIが提起したが、著者は却下。SPACTA.mdは他の開発者に配布してスクリプトで強制する対象ではなく、著者本人が手作業で保守する内部文書。同期を機械的に保証する必要がないので、この懸念はここでは的外れだった。

## 結論

- 幹の行数を固定予算として扱う判断基準は撤廃する。
- ルールプロンプト(`SPACTA.md`)自体の行数に潔癖症的にこだわる必要はない。増えたらそのとき考えればよい。
- それより優先度が桁違いに高いのは、**Spactaという機構そのものを整える**こと(§9の候補: edge層、n=2実測など)。ドキュメントの行数管理はそこに比べれば些末事。
