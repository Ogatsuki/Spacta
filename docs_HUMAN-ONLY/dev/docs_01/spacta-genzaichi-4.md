## 1. v0.11 は何をした版か [確立]

> **掟を1本も増やさずに、機能の語彙を機能に返した。**

3段階で進んだ。

1. **Effect を機能へ** — 共有 `Effect` union が消滅。各機能が自分の `types.ts` で宣言し
   自分の `perform.ts` で実行する。`effectUnion.shared = 0`
2. **答えを機能へ** — `Perform` の `id?: string` を `data?: R` に吸収。答えの経路は1本になり、
   その形は**質問した機能が宣言する**（`pageview` は `Answer = { id: string }`、`saved` は行）
3. **読みモデルを契約から分離** — `shared/types.ts` 195行 → **37行**。読みモデル155行は
   `shared/readmodels.ts` へ。`measure` に `readModel` ゾーンを足して分けて測れるようにした

副産物として **`saved` がロード後の読み（「もっと見る」）を実装した**。
`Perform` が id しか返せなかった間、Spacta は**書けるが読めなかった**。それが解消した。

### 数字 [確立]

```

        sharedUi 15f/404L   dataAdapter 7f/1250L   sharedOther 2f/88L   framework 24f/830L
```

`contract` が 199 → 37 に落ちたのが v0.11 の可視的な到達点である。

## 2. 今日いちばん重要だったこと [確立]

作業そのものより、**「穴を植えて落ちるのを見る」工程が毎回何かを見つけた**ことである。

| 植えた穴 | 判明したこと |
|---|---|
| `feature-internal` が L2 を主張 | ファイル0件の役割は `roleCoverage()` が**検算ごと飛ばしていた**。`perform.ts` 6枚が「主張だけあって検算のない役割」にいた |

**5つ植えて5つとも見つかった。**

3つ目が最も重い。往復という機構が存在する唯一の理由が、**機能の全期間にわたって一度も検算されていなかった。**
tempId のまま残る trace は完全に決定論的なので、リプレイは自分自身と一致する。

### 2.5 原理が1つ更新された [確立] — **これは失われやすい**

`archive/tmp-for-ai/spacta-fukuzatsusei-no-gyoshuku.md`（v0.9 期）は「複雑性の凝縮」の

## 3. 今日追加した仕組み [決定]

### 3.1 `tools/mutate.mjs`

`verify` に段位を訊き、T3 機能の `core.ts` に往復を壊す変異を2種植え、行動ゲートを回して
**生き残り（= 無検査）を報告する**。「一度も落ちるのを見ていない検査は検査ではない」の機械化。

- `finally` で必ず復元し、`replay-sessions/` を前後で退避する
  （検査を確かめる道具が証拠を汚してはならない）
- 変異箇所が一意に定まらなければ**推測せず停止**する
- **`tsc` を意図的にゲートから外している** — 挿入した `return` の後ろが到達不能になるので、
  tsc は「捕まえた」ように見えて実は変異の作り方を検出しただけになる（偽の安心）
- `verify` は回すが**殺し手には数えない** — 静的解析なので原理的に捕まえられない。
  それでも印字するのは「verify 緑は振る舞いの正しさを意味しない」を毎回目にするため
- exit 1 は**故障ではなく測定結果**である

### 3.2 「掟ではないが緑を止める検査」という第3の区分

散文だけが守っていた2つの性質を検査にした。**掟は10本のまま。**

```
✓ Laws (L1, L2, L3, L4, L5, L7, L9, L10): No violations
✓ Blocking checks that are not Laws (engine-portability, data-layer-import): No violations
```

| 検査 | 守るもの | 設計上の判断 |
|---|---|---|
| `engine-portability` | エンジンに `react`/`next` が入らない | **fail-closed** — `shared/spacta/` のうち `react.ts` 以外を全部歩くので、エンジンにファイルが増えたら既定で検査対象 |
| `data-layer-import` | 機能がデータ層を import しない | **`import type` も落とす** — 実行時依存は増えないが、守っているのは参照範囲だから |

`law: "—"` + `severity: "err"` で登録した。片方は1ファイルの設計上の約束、
もう片方は `SPACTA.md` §3 が**既に事実として書いている**文の機械化であり、
どちらも Spacta が普遍的に主張する新しい性質ではない。だから11本目の掟にはしていない。

検体4つ + L6 自己テスト4件つき。`--write-docs` を忘れたら `docs-drift` が exit 1 で止めた
——レジストリと文書が食い違えない仕組みが実際に働いた例である。

### 3.3 決定ログ `spacta-decisions.md`

**各エントリが「自分を守っている検査」を名指しし、無いときは「無防備」と書く。**
`SPACTA.md` の「穴があること自体は許される。穴を隠すことは許されない」を、
コードではなく**決定**に適用したもの。

引継書 §5 の不変条件は**全部同じ強さで書かれていた**ため、読む側は「守られている」と誤読する。
実測で仕分けたら**半分が無防備**だった。今日 5件 → **3件**になった。

残る3件は「掟10本」「膜語彙4つ」「答えの経路1本」で、**いずれも形ではなく*本数*についての約束**。
AST を歩いて見つける対象と種類が違うのが、これらが残った理由である。

## 4. Spacta の評価 — 私の判断 [仮説]

**私が見たのは1日分の作業なので、その範囲での判断である。**

### 強い（他ではあまり見ない）

1. **検証装置が自分自身を疑う構造になっている。** L6 自己テストに加え、
   **role-claim テスト**（表が主張する掟が本当にそのファイルを歩いているかの検算）がある。
   今日その恩恵を受け、**検証器自身の嘘**が露出した
2. **「穴を隠すことは許されない」が運用されている。** `NOT guaranteed` ブロック、
   `measure` の `die()`、crosscheck の「(4) は検証不能」。普通のツールは緑を出したら黙る
3. **AI に渡す契約が小さい。** `SPACTA.md` 79行。今日ほぼこれと引継書だけで作業でき、

4. **v0.11 の設計判断が正しい。** 「2つの画面を縛っているのはエンドポイントであって宣言ではない」

### 弱い

1. **一度も動いていない。これが最大の問題。** 正確には:

   | | |
   |---|---|
   | **実行される** | `engine/runtime.ts` と `core.ts` **5機能分**（テストが import するもの） |
   | **一度も実行されない** | 残り5機能の `core.ts`、**全 `shell.tsx`**、**全 `components/`**、**全 `perform.ts` の中身**、**全 `route.ts`**、`queries.ts`（**SQL 全部**）、`shared/ui/*`、`page.tsx` |

   今日 `queries.ts` にキーセット・ページネーションの SQL を書き、`route.ts` に GET を新設し、
   `perform.ts` を6枚書き直した。**このどれ一つも実行されていない。**
   型は合っている。SQL が構文的に正しいかは誰も確かめていない。

2. **装置の見かけが実際の覆いを上回っていた。** 5/5 の打率がそれを示した。
   `mutate` で機械化したが、**見ているのは T3 機能の2ケースだけ**である

3. **配布物として存在していない。** npm パッケージ無し、`starter/node_modules` 無し。
   版は揃えたが、外部の人は `npm create` できない

4. **検証台が小さい。** 10機能中 **T1 が4つ**——往復を一度もしない。
   目玉機構を実証しているのは T3 の5機能

5. **道具が掟の30倍ある。** `verify.mjs` 2500行超が `SPACTA.md` 79行を守る。単一実装・単一著者

### 実務で使うか [仮説]

- **思想は今日から使う。** Core の純粋性、Effect をデータとして返す、ループは1つ、
  correlationId、InitData は一度だけ。Spacta 無しでも任意の Next.js コードベースで主張できる
- **道具は、自分がメンテナになれるグリーンフィールドの社内プロジェクトなら使う。**
  クライアント案件では使わない（上流が無く、`verify.mjs` のバグは自分で直すことになる）
- **動かす前に本番投入はしない。** ブロッカーは設計ではなく「確かめていない」こと

**イエスに変わる条件は1つ。** `next dev` + DB + ブラウザで1回動かし、
React のバッチング問題（engine は `useSyncExternalStore` で外部ストアとして繋がっている）に
実測で答えが出ること。

| **`--write-docs` を忘れる**（今日追加） | CHECKS を触ったら `bun verify/verify.mjs --write-docs`。忘れると `docs-drift` が exit 1 |

## 8. 最後に — この文書を読む次の人へ

今日いちばん役に立った文書は `SPACTA.md` ではなく**引継書**だった。

掟は79行で学べる。しかし「**このプロジェクトが今どこにいて、何が決着済みか**」を
機械から引く手段が無く、前任者が手で書いた散文に依存していた。
それが無ければ D-003 や D-004 を平気で蒸し返していたはずである。

**次のアプリでは、この種の文書を最初から書くこと。**
作業の記録としてではなく、**作業の入力として。**

そのために今日、引継書を役割ごとに3枚へ分けた（冒頭の表）。**引継書を丸ごと渡さないこと。**
あれは作業指示として書かれており、新しいセッションには文脈が大きすぎる。

そして2枚を必ず更新すること。

- **`spacta-decisions.md`** —— 「守る検査が無いもの」の唯一の記録。
  更新されなければ、この文書が警告している当のもの
  ——権威ありげに見えて実態を写していない散文——になる
- **`spacta-open-questions.md`** —— 決着していないことの唯一の記録。
  **解決したら消さずに [解決] に書き換える。**「なぜそれが問題だったか」が消えると、
  次の人はその解決策が何を守っているのか分からなくなる

今日 §2.5 で1つ実例が出た。v0.9 期の文書が**成功例**として書いていた原理を v0.11 が覆したが、
その事実はどこにも書かれていなかった。あの文書を素直に読んだ AI は、
**今なら間違いになる原理を、成功例として適用する。**
情報を失わないとは、**古い知見を残すことと、それが古いと分かるようにすることの両方**である。
