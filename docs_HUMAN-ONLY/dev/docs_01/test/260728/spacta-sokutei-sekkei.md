# Spacta 隔離スケーリング測定 — 設計書

**著者専用。実装エージェント・機能追加エージェントには渡さないこと**（理由は §8-1）。
対応する改訂指示書: `docs/spacta-genzaichi-3.md`

---

## 0. この文書は何か

Spacta の中心命題が本当かどうかを、**機能を追加しながら測る**ための設計書。
何を測り、何を予測し、どういう結果なら命題が成立／不成立と判定するかを、**測る前に**確定させておくためのもの。

### テスト設計の基本 — 5つだけ

この種の作業をしたことがなくても、次の5つを守れば結果は信用できるものになる。

1. **測る前に予測を書く。** これが最も重要。人間（と AI）は、出た数字を見た後なら**どんな数字でも説明できてしまう**。「思ったより増えたが、これは機能が複雑だったからだ」という説明は、増えても減っても後から作れる。先に「この機能なら共有ファイル2〜3個の編集で済むはず」と書いておけば、外れたときに外れたと分かる。

2. **主指標を1つに絞る。** 指標が5つあると、5つのうち都合のいい1つを見て結論を出してしまう。主指標を1つ決め、残りは「解釈を助ける材料」として扱う。

3. **判定基準を先に決める。** 「どういう数字が出たら命題は不成立か」を先に書く。書けないなら、その命題は測定可能な形になっていない。

4. **測られる側に基準を教えない。** 実装するエージェントが「共有ファイルの編集数を測られている」と知っていると、無意識に共有ファイルを避ける設計を選ぶ。測りたかったのは「Spacta の構造がそうさせるか」であって「そう指示されたらできるか」ではない。

5. **測定中は他を変えない。** 測定期間中にリファクタリングを入れると、数字が動いた原因が「機能追加」なのか「リファクタ」なのか永久に分からなくなる。

### この実験に対照群は要らない

「Spacta あり vs Spacta なし」の比較は**しない。** 測りたいのは Spacta の有無による差ではなく、**Spacta 内部での傾き**（機能数が増えたときにコストが増えるか）だからである。同一コードベースの時系列を見ればよく、比較対象アプリを別途作る必要はない。**実験が桁違いに安くなる。**

## 1. 確かめたい命題

> **アプリが大きくなっても、1機能を追加・変更するのに必要な参照範囲は増えない。**

Spacta の他のあらゆる主張——コンテキスト隔離、複雑性の凝縮、AI との相性、規模に対する優位——は、すべてこの1つに乗っている。そして一度も測定されていない。

**この命題が偽なら、Spacta は「中規模アプリのための良い規律」という、はるかに小さい主張になる。**

## 2. 指標

### 主指標（これ1つで判定する）

> **新機能を1つ追加したときに、編集した「既存の共有ファイル」の数。**

- 対象は `src/shared/**` と `app/**` の**既存ファイル**のみ
- **新規作成は数えない。** 新しい機能ディレクトリや新しいルートが増えるのは当然であり、隔離が効いていれば負荷にならない
- 「編集」= 1行でも追加・変更・削除したファイル
- 補助として、その編集の**追加行数の合計**も記録する

**なぜこれが主指標か。** Spacta が再定義した予算は「行数」ではなく **「1タスクで参照しなければならない箇所の数」** である。既存共有ファイルの編集数は、その予算の直接の測定値である。`SPACTA.md` が67行でも90行でも、AI が1タスクで開くファイル数が変わらないなら支出はゼロに近い。逆に、幹を1行も増やさずに508行の共有ファイルを毎回触らせることは、毎タスク508行の支出である。

### 副指標（解釈を助ける材料。判定には使わない）

| # | 指標 | 何が分かるか |
|---|---|---|
| 副1 | ゾーン別のファイル数・行数の推移 | どのゾーンが育っているか |
| 副2 | `Effect` union のメンバ数 | L7 由来の構造的結合が線形に育つか |
| 副3 | 共有シンボルごとの消費者数（散らばり） | 「1つの複雑性が何箇所に散っているか」 |
| 副4 | 到達した段位（T0〜T3） | 新機能が Spacta のどこまでを必要としたか |
| 副5 | 実装 AI が1タスクで開いたファイル数・入力トークン数 | 参照範囲の別角度からの測定 |

副1〜4 は `npm run measure` が出す。副5 はセッションログから拾う。

## 3. 事前登録した予測 ★

**測定前に確定させる。数字を見た後にこの表を書き換えてはならない。**

### 3.1 主指標の予測

> **既存の共有ファイルの編集数は、機能を1つ追加するごとに 2〜4 個。そしてこの数は機能数が増えても増えない。**

内訳の予想:
- `shared/types.ts` … 1（読みモデル型の追加、書き込みがあれば `Effect` メンバの追加）
- `shared/source/queries.ts` … 1（読みがあれば）
- `shared/ui/*` … 0〜1（既存プリミティブで足りるはず。足りなければ1つ追加）
- `app/**` … 新規ルートは新規作成なので数えない

### 3.2 ゾーン別の成長率の予測

`n` = 機能数。

| ゾーン | 予測 | 根拠 | これが外れたら |
|---|---|---|---|
| `feature` | **O(n) 線形** | 機能が増えれば増える。**隔離されているのでこれは負荷ではない** | 予測通りでよい |
| `engine`（`shared/spacta/`） | **O(1) 完全不変** | 機構は機能に依存しない | **1行でも増えたら、機構に機能固有の判断が漏れている。設計の失敗** |
| `contract`（`types.ts`） | **O(n_write) 線形。** 書き込みのある機能1つにつき 1〜4 メンバ | L7 が `runEffect` に機能型の import を禁じる以上、`Effect` union は1ファイルに集まる。**構造的必然** | 予測通りなら、これは命題の**既知の反例**として確定する |
| `sharedUi` | **sublinear。後半ほど増分が減る** | 昇格は「2機能以上で実際に重複してから」なので、既存プリミティブの再利用率が上がるはず | 線形に増え続けるなら、昇格ルールが機能していない |
| `dataAdapter`（`source/`） | **O(n_read) 線形。1機能あたり 40〜80行** | 凝縮されていない既知の穴 | 予測通り。ここは驚きではない |
| `framework`（`app/`） | O(n_route) 線形 | ルートが増える | 予測通りでよい |

### 3.3 構成比の予測

現在: `feature` 48% / `shared` 31% / `app` 21%（6機能・81ファイル）。

> **予測: `shared` の割合は下がる。** 絶対量は増えるが、`feature` の増加のほうが速いため。

**重要な注意:** 「`shared` が増えないこと」は命題ではない。**増えてよい。** 命題は「1タスクの参照範囲が増えないこと」であり、`shared` が育っても、1回の機能追加で触るのがその中の2〜3ファイルに留まるなら命題は成立する。

### 3.4 段位の予測

> **追加した機能の過半数が T1 または T2 で済む。T3（往復あり）は相互作用型のみ。**

現在の分布（T1×3 / T2×2 / T3×1）と大きく変わらないはず。**変わるなら、Spacta の深い部分の必要頻度についての認識を改める材料になる。**

## 4. 手順

```
[t0] 現在地3 の変更①〜④ を完了 → npm run measure → metrics/baseline/ にコミット
      ↓
[t1] 機能 #7 を追加 → 記録テンプレート（§6）を埋める → measure → コミット
      ↓
[t2] 機能 #8 を追加 → 同上
      ↓
[t3] 機能 #9 を追加 → 同上
      ↓
[t4] 機能 #10 を追加 → 同上
      ↓
[判定] §7 の基準で 成立 / 不成立 / 保留 を決める
```

**各機能の追加は独立したセッションで行う。** 前の機能追加の文脈を持ち越さない（持ち越すと学習効果が交絡する）。

**推奨する機能数は4。** 3では傾きが読めず、5以上はコストに見合わない。4点あれば「増えている／増えていない」は判断できる。

## 5. 追加する機能の選び方

### 型を先に宣言する

**機能を実装する前に、その機能がどの型かを書き留めること。** 実装後に「これは特殊な機能だった」と分類し直すのは、都合のよい除外を許すことになる。

| 型 | 中身 | 想定段位 |
|---|---|---|
| **読み型** | 一覧・詳細・集計を表示するだけ。書き込みなし | T1 |
| **書き込み型** | フォーム送信など。Effect を出すが、結果を画面に反映する必要がない（送信→完了画面／リロード） | T2 |
| **相互作用型** | 楽観更新とロールバックが要る。押した瞬間に画面が変わり、失敗したら戻る | T3 |

### 推奨する構成

> **読み型 ×1、書き込み型 ×2、相互作用型 ×1。**

理由: 現在の分布（T1×3 / T2×2 / T3×1）と比率が近く、アプリの性格を途中で変えない。かつ最も難しい型（相互作用型）を必ず1つ含む。

### 候補（livingdoc の要件から自然に出るもの）

**読み型:**
- タイプ別の痕跡一覧（`stuck` だけを横断して見る）
- 材料ごとの統計ページ（痕跡数・参加者数の推移）
- 最近の活動フィード（既存の `listRecentActivity` の拡張ではなく新画面として）

**書き込み型:**
- 痕跡のブックマーク／後で読む
- ページ購読・通知設定
- 痕跡の編集（自分の投稿の修正）

**相互作用型:**
- 下書きの自動保存つきエディタ（保存中インジケータ、失敗時の復帰）
- コメントのインライン返信（楽観挿入 → サーバ採番 ID で置換 → 失敗ならロールバック）
- 痕跡の並べ替え／ピン留め（楽観的な順序変更）

**選定は著者が行い、実装エージェントには「この機能を作れ」とだけ渡す。型の分類は伝えない。**

### 順序

**型を混ぜた順序にする**（例: 読み → 相互作用 → 書き込み → 書き込み）。同じ型を続けると、学習効果と型の効果が区別できなくなる。

## 7. 判定基準

**測定前に確定。数字を見てから緩めない。**

### 成立

次の**すべて**を満たす。

- 主指標（既存共有ファイルの編集数）が、4回を通じて **増加傾向を示さない。** 具体的には、最後の2回の平均が最初の2回の平均を**上回らない**
- 各回の主指標が **4以下**
- `engine`（`shared/spacta/`）の行数が **1行も増えていない**

→ **Spacta は規模自由（scale-free）な隔離を実現している。** 他の誰も主張していないものを持っていることになる。

### 不成立

次の**いずれか**に該当する。

- 主指標が単調増加している
- 最後の回の主指標が、最初の回の **2倍以上**
- `engine` に機能固有のコードが漏れている

→ **「規模が増えても負荷が上がらない」は偽。** Spacta は中規模アプリのための良い規律であって、規模に対する主張は取り下げる。

### 保留

- 4回のばらつきが大きく（最大と最小が2倍以上開く）、傾向が読めない

→ **n を増やす**（あと2〜3機能）。ばらつきの原因が型の違いなら、型を揃えて再測定する。

### 判定できない条件（測定のやり直し）

- 測定期間中にリファクタリングが入った
- 実装エージェントがこの設計書または `genzaichi-3` を読んでいた
- 記録テンプレートの主指標欄が埋まっていない回がある

## 8. 交絡因子と対処

| # | 交絡因子 | なぜ問題か | 対処 |
|---|---|---|---|
| 1 | **実装者が測定基準を知る** | 「共有ファイルの編集数を測られている」と知れば、無意識に共有ファイルを避ける。測りたいのは「Spacta の構造がそうさせるか」であって「指示されたらできるか」ではない | **この文書と `genzaichi-3` を実装/機能追加エージェントに渡さない。** 渡すのは `SPACTA.md` と機能要件だけ |
| 2 | **学習効果** | 後の機能ほど実装が上手くなり、主指標が下がって見える | 型を混ぜた順序にする。各回を独立セッションで行う |
| 3 | **機能の性質のばらつき** | 簡単な機能ばかり選べば良い数字が出る | §5 で型を事前宣言し、相互作用型を必ず含める |
| 4 | **`queries.ts` の既知の穴が全体を支配する** | データアダプターが線形に育つのは既知であり、これだけで「増えている」に見えかねない | **ゾーン別に測るので分離できる。** 主指標は「編集したファイルの数」なので、`queries.ts` が何行育っても1ファイルは1ファイル |
| 5 | **同一著者・同一モデル** | n=1 の限界。他者・他モデルで再現するとは限らない | **認める。** この実験で言えるのは「この著者・このモデル・このアプリで、規模に対して傾きがあるか」まで。それでも今より情報は多い |
| 6 | **アプリの性格の偏り** | livingdoc は相互作用が密なアプリで、CRUD 寄りのアプリとは傾きが違う可能性 | 認める。結論を書くときに明記する |
| 7 | **「ついでのリファクタ」** | 機能追加のついでに共有コードを整理すると、次回の主指標が不当に下がる | **測定期間中はリファクタ禁止。** 気づいた改善は記録テンプレートの定性メモに書くだけ |

## 9. 測定を汚す行為 — 禁止事項

- 数字を見てから §3 の予測を書き換える
- 数字を見てから §7 の判定基準を緩める
- 都合の悪い回を「これは例外的な機能だった」として除外する（除外するなら、**測定前に**除外基準を書いておく）
- 測定期間中に `adapters/` への移動などのリファクタリングを入れる
- 実装エージェントに「共有ファイルはなるべく触らないで」と指示する（**それを言った時点で測定対象が消える**）
- 記録を後からまとめて書く（各回、その場で埋める）

## 10. 結果が出たあと — 何が変わるか

**この節を先に書いておくのは、「どちらに転んでも次の一手がある」ことを確認するためである。** 片方の結果でしか動けないなら、実験の設計が偏っている。

### 成立した場合

- Spacta の中心的な売り文句が、初めて数字で裏付けられる
- 次にやるべきは **段位の完成**（T0 だけで入れる入口を作る）と **エンジンの他プラットフォーム移植**。`shared/spacta/runtime.ts` が O(1) で不変だったことは、そのまま「移植面が小さい」の証拠になる
- `contract` ゾーンが線形に育っていた場合、それが唯一の構造的な負債として残る。L7 と単一ディスパッチ地点の関係を再設計する価値が初めて生まれる

### 不成立だった場合

- **「規模が増えても負荷が上がらない」は取り下げる。** 主張を「中規模アプリのための、機械的に施行される隔離規律」に縮める
- そのとき正直な選択は、製品を作り続けることではなく、**思想を文章として世に出すこと**——誠実さの機械化（検証器が自分の管轄範囲を申告する）、到達可能性の規律、hope-prompt の廃止。これらは Spacta という実装がなくても価値が残る。構造化プログラミングは製品ではなかった
- どのゾーンが命題を壊したかは記録に残るので、「Spacta のどの部分が規模に耐えなかったか」まで言える。これは他の人が別の宿主で実装する際の一次情報になる

### 保留だった場合

- ばらつきの原因を特定してから n を増やす。ばらつきが型由来なら、型を揃えて再測定

## 11. この設計書自体の弱点（正直に書いておく）

- **n=4 は少ない。** 傾きの有無は言えるが、傾きの大きさは言えない
- **「編集したファイル数」は粗い。** 1行の型追加と200行の書き換えが同じ「1」になる。だから追加行数も併記するが、判定には使わない（判定に2つの数を使うと、都合のいい方を見てしまう）
- **アプリが1つ。** 別の性格のアプリ（CRUD 寄り、管理画面）では違う傾きが出る可能性が高い
- **実装 AI の能力が変わると数字が動く。** モデルを記録する理由がこれ
- これらは**測定をやらない理由にはならない。** 今は傾きが分かっていないので、粗くても向きが分かれば前進する
