# Spacta 測定 — 実施手順書（著者用）

**著者専用。エージェントには §6 のテンプレート部分だけを貼り、この文書自体は渡さないこと。**

対応文書: `docs/spacta-genzaichi-3.md`（改訂指示書） / `docs/spacta-sokutei-sekkei.md`（測定設計書）

---

## 0. この文書の役割

測定 t1〜t4（機能を4つ追加する各セッション）を、**4回とも同じ条件で**実施するための手順。

条件が回ごとに違うと、数字が動いた原因が「機能追加のコスト」なのか「渡した情報の差」なのか分からなくなる。**この文書の存在理由はそれだけである。**

### 前提: 1機能 = 1エージェント = 1セッション

エージェントの分割粒度は **「縦のライン1本（＝1機能）＝1エージェント」** を既定とする。

コンポーネント単位でエージェントを立てない。コンポーネント1つの実装は多くの場合数十行であり、タスク仕様を書く・起動を待つ・出力を検証する・整合を確認するという**固定費が実装量に対して大きくなりすぎる**。ファイル分割の基準（再利用）とエージェント分割の基準（コスト対効果）は別の軸であり、一致させる必要はない。

**測定の観点でも重要:** 1機能を複数エージェントで分担すると、「1タスクの参照範囲」という主指標の単位が壊れる。

---

## 1. 主指標は git から外部的に取る

**これがこの測定設計の要である。** 主指標（編集した既存共有ファイルの数）は、エージェントの自己申告ではなく **`git diff` から取る。**

```bash
# 機能追加の前
cd /workspace/livingdoc && git rev-parse HEAD   # → BEFORE として記録

# 機能追加の後
git diff --stat BEFORE HEAD -- src/shared app   # → 編集された既存ファイルの一覧
git diff --name-status BEFORE HEAD              # → M(変更) と A(新規) の区別
```

- `M`（変更）かつ `src/shared/**` または `app/**` → **主指標にカウント**
- `A`（新規追加）→ カウントしない
- `src/features/**` → カウントしない（隔離されているので増えて当然）

**エージェントは自分が何を測られているか知らず、知る必要もない。** 測定は完全に外側で完結する。汚染の余地がない。

> **注意:** `/workspace/livingdoc` は現状 git 管理下にない可能性がある。**測定を始める前に `git init` してベースラインをコミットすること。** これができていないと主指標が取れない。

## 2. 各セッションで渡すもの — 固定リスト

| # | 渡すもの | 備考 |
|---|---|---|
| 1 | `/workspace/spacta/SPACTA.md` | 掟の正本。**これが Spacta についてエージェントが知る唯一の情報源** |
| 2 | 追加する機能の要件（§4 の書き方に従った文章） | 1機能分だけ |
| 3 | 作業ディレクトリ `/workspace/livingdoc` へのアクセス | コードは読ませてよい |
| 4 | 「`npm run verify` が緑、`tsc --noEmit` が0エラーになるまで直せ」 | `SPACTA.md` §4-4 と同じ |

**それだけである。**

### 渡してはいけないもの

- `docs/spacta-genzaichi-3.md`（改訂指示書）
- `docs/spacta-sokutei-sekkei.md`（測定設計書）
- **この文書**
- `docs/` 配下のあらゆる Spacta 設計文書（前版・参照文書・スピンオフ）
- `docs_HUMAN-ONLY/` の人間向けガイド類
- 前回の測定記録（`docs/measurements/**`）
- **前のセッションの会話文脈**

### なぜ人間向けガイドも渡さないのか

人間向けガイドには「Spacta が何を解決し何を解決していないか」の地図が書かれている。これを読んだエージェントは、**弱点を知ったうえでそこを避ける実装を選ぶ。** 測りたいのは「`SPACTA.md` 67行だけを渡されたエージェントが、構造に導かれてどう書くか」であって、「弱点を教えられたエージェントが避けられるか」ではない。

これは実運用の想定とも一致する。**`SPACTA.md` は AI が毎タスク読む唯一の幹であり、人間向けガイドは AI が読むものではない。**

## 3. セッションの手順

```
① 事前記録を書く（§5 のテンプレート「事前」欄）
      ↓  ここで型と予測を確定させる。実装後に書き換えない
② git rev-parse HEAD → BEFORE を控える
      ↓
③ §6 のテンプレートをエージェントに貼る
      ↓
④ エージェントが実装。verify 緑 / tsc 0エラーまで
      ↓  途中で誘導しない（§4 参照）
⑤ 変更をコミット
      ↓
⑥ npm run measure → metrics/NN.json に保存してコミット
      ↓
⑦ git diff --name-status BEFORE HEAD → 主指標を集計
      ↓
⑧ 記録テンプレートの「結果」欄を埋める（その場で。後回しにしない）
      ↓
⑨ セッションを閉じる。次の機能は新しいセッションで
```

**⑧ を後回しにしないこと。** 4回分をまとめて後から書くと、記憶が混ざり、都合のよい要約になる。

## 4. 要件文の書き方 — 誘導しないための禁止表現

要件文には **「何を作るか」だけを書く。「どう作るか」を書かない。**

### 禁止する表現

| 書いてはいけない | なぜ |
|---|---|
| 「共有ファイルはなるべく触らないで」 | **これを言った時点で主指標が測定対象でなくなる。** 測りたいのは構造がそうさせるかであって、指示されたらできるかではない |
| 「`shared/types.ts` に型を足して」 | 参照先を指定すると、参照範囲を測る意味がなくなる |
| 「既存の `TraceRecord` を再利用して」 | 同上 |
| 「この機能は他の機能と独立しているので」 | 隔離が成立するかどうかがまさに測定対象 |
| 「`core.ts` に純粋関数として書いて」 | `SPACTA.md` が言うべきことを人間が代弁している。**掟が伝わるかも測定対象である** |
| 「前回と同じやり方で」 | セッション間の独立性が壊れる |
| 「段位 T2 で作って」 | 到達段位は結果であって指示ではない |

### 書いてよい表現

- 画面に何が表示されるか
- ユーザーが何をできるか
- どのデータが必要か（**業務上の意味として。テーブル名や既存関数名を指定しない**）
- 既存のどの画面から遷移するか
- 失敗したときにユーザーに何が見えるべきか

### 例

**悪い例:**
> `shared/source/queries.ts` に `listTracesByType` を足して、`TraceRecord` を再利用して、タイプ別一覧ページを作って。共有ファイルは最小限の変更で。

**良い例:**
> 痕跡のタイプ（stuck / insight / resource / footprint）ごとに、そのタイプの痕跡だけを新しい順に一覧できる画面を追加してください。各痕跡には引用・本文・投稿者・投稿日時・賛同数を表示し、その痕跡が付いているページへ遷移できるようにしてください。ヘッダーから辿れる場所に置いてください。

## 5. 記録テンプレート

`docs/measurements/NN-<機能名>.md` に保存。**測定設計書 §6 と同じ内容。** ここには実施上の注意だけ補う。

- **「事前」欄は ② の前に書く。** 実装が終わってから書いた予測は予測ではない
- **「予測との差」欄は、言い訳ではなく仮説として書く。** 「複雑な機能だったから」ではなく「読みモデルを共有する機能だったため contract ゾーンの編集が発生した」のように、次の予測を改善できる形で書く
- **副指標5（開いたファイル数・入力トークン数）は取れる範囲でよい。** セッションログから確実に取れないなら空欄にする。**エージェントに自己申告させないこと**——「読んだファイルを報告して」と言うと、読む量を測られていると気づいて挙動が変わる

## 6. エージェントに貼るテンプレート

**以下をそのままコピーし、`<<< >>>` の部分だけを差し替えて使う。**

```
あなたは Next.js アプリ「Living Document」に機能を1つ追加します。

## 設計規律

このコードベースは Spacta という設計規律に従っています。
/workspace/spacta/SPACTA.md を読み、そこに書かれた掟に従って実装してください。

## 作業ディレクトリ

/workspace/livingdoc

## 追加する機能

<<< 機能の要件をここに。§4 の書き方に従い、実装方法を指定しないこと >>>

## 完了条件

1. 機能が動作すること
2. cd /workspace/spacta && node verify/verify.mjs ../livingdoc が緑になること
3. cd /workspace/livingdoc && npx tsc --noEmit が 0 エラーになること

2 と 3 は自分で実行し、緑になるまで自分で直してください。

## 注意

- /workspace/docs/ 配下のファイルは読まないでください
- /workspace/spacta/docs_HUMAN-ONLY/ 配下のファイルは読まないでください
- 既存機能のリファクタリングはしないでください。今回の機能追加に必要な変更だけを行ってください
```

**最後の「リファクタリング禁止」は測定の保護であり、誘導ではない。** 測定期間中に既存コードが整理されると、次回の主指標が不当に下がる。これは「共有ファイルを触るな」とは別のことで、**新機能のために共有ファイルを触るのは自由**である。
