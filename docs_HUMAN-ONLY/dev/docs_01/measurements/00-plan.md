### 予測の根拠（数字を見る前に書いている）

設計書 §3.1 の事前登録は「1機能あたり 2〜4個、機能数が増えても増えない」である。**operator の見積もりはそれより多い**ので、そのまま書き残す（都合よく丸めない）。

- **読み型 (t1) = 3**: 読みモデル型の追加で `shared/types.ts`、取得経路で `shared/source/queries.ts`、導線でヘッダー（`shared/ui/SiteHeader.tsx`）。新規ルートは新規作成なので数えない。
- **書き込みを伴う型 (t2/t3/t4) = 5**: 上の3つに加えて、`Effect` メンバ追加で `shared/types.ts`（同一ファイルなので重複カウントしない）、case 追加で `shared/runEffect.ts`、永続化で `shared/source/mutations.ts`。よって `types.ts` / `queries.ts` / `mutations.ts` / `runEffect.ts` / 導線1つ = 5。
- **この見積もりが当たると、設計書 §7 の成立条件「各回の主指標が4以下」は満たされない。** それでも下方修正しない。予測を実測に合わせて動かすのは §9 の禁止事項である。
- **構造的に避けられない2ファイル**: `shared/runEffect.ts` と `shared/types.ts` は、L4（単一ディスパッチ地点）と L7（`runEffect` は機能型を import できない）の帰結として、書き込みのある機能なら必ず編集対象になる。これは genzaichi-3 §8「共有予算」が既知の反例候補として挙げていたものである。

### db/ について

新機能がテーブルを必要とする場合 `livingdoc/db/schema.sql` を編集することになるが、`src/shared/**` でも `app/**` でもないため**主指標には数えない**（設計書 §2 の定義どおり）。副次的な事実として記録に残す。

## 2. 凍結した要件文（t1〜t4）

**実装エージェントにはこの文言をそのまま貼る。** 実施手順書 §4 の禁止表現（実装方法・参照先ファイル名・既存関数名・再利用指示・型や段位の指定）を含まないことを確認済み。**t1 の結果を見てから t2〜t4 の文言を書き換えない。**

### t1 — タイプ別の痕跡一覧（読み型）

> 痕跡のタイプ（stuck / insight / resource / footprint）ごとに、そのタイプの痕跡だけを新しい順に一覧できる画面を追加してください。各痕跡には引用・本文・投稿者・投稿日時・賛同数を表示し、その痕跡が付いているページへ遷移できるようにしてください。ヘッダーから辿れる場所に置いてください。

### t2 — 下書きの自動保存つきエディタ（相互作用型）

> 痕跡を書いている途中の内容が失われないように、下書きが自動的に保存される画面を追加してください。ユーザーは材料とページを選び、引用と本文を書きます。入力中は「保存中」なのか「保存済み」なのかがその場で分かるようにし、保存に失敗したときはそれが分かり、かつ書いた内容が消えないようにしてください。書き終えたら投稿でき、投稿すると下書きは残りません。前回の下書きが残っている場合は、次に開いたときに続きから書けるようにしてください。サインインしていない人には下書きを保存できないことが分かるようにしてください。

### t3 — あとで読む（書き込み型）

> あとで読み返したい痕跡を保存しておける仕組みを追加してください。痕跡を「あとで読む」に入れられ、入れた痕跡だけをまとめて見られる画面を用意してください。すでに入れてある痕跡は外せます。一覧では引用・本文・投稿者と、その痕跡が付いているページが分かるようにしてください。サインインしていない人には保存できないことが分かるようにしてください。

### t4 — 気になるページの登録（書き込み型）

> 気になるページを登録しておき、登録したページの一覧を見られる仕組みを追加してください。ページの画面から登録と解除ができ、登録した一覧では、それぞれのページに今いくつ痕跡があるかが分かるようにしてください。サインインしていない人には登録できないことが分かるようにしてください。
