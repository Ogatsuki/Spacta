## 1. 結論を先に

**設計書 §7 の判定基準を機械的に当てはめると「不成立」が発火する。** ただしそれを発火させたのは機能数ではなく**機能の型**であり、主指標そのものは機能数に対して**平坦**だった。両方を分けて書く。判定基準は数字を見た後に変更していない（§9）。

| | 判定 | 根拠 |
|---|---|---|
| **成立** | **不可** | 条件「各回の主指標が4以下」を t2/t3/t4 が破った（5 / 5 / 6）。条件「最後の2回の平均 ≤ 最初の2回の平均」も破った（5.5 > 3.5） |
| **不成立** | **発火** | 条件「最後の回が最初の回の2倍以上」に該当（t4=6 ≥ t1=2 の2倍）。ただし「単調増加」は厳密には不成立（t2=t3=5 で平坦） |
| **保留** | **同時に発火** | 「4回のばらつきが最大と最小で2倍以上」に該当（6 / 2 = 3倍）。設計書はこの場合の対処として「ばらつきの原因が型の違いなら、型を揃えて再測定」を指定している |

設計書は「不成立」と「保留」が同時に発火した場合の優先順位を定めていない。**どちらを採るかは著者の判断であり、operator は判定しない。** 判断材料として §3 と §4 を読んでほしい。

## 2. 主指標

**新機能1つを追加したときに編集した「既存の共有ファイル」の数**（`src/shared/**` と `app/**` の既存ファイルのみ。新規作成は数えない）。`git diff --name-status` から測定者が外部的に取得した。実装エージェントには指標の定義を渡していない。

| 回 | 機能 | 宣言した型 | 予測 | **実測** | 編集された既存共有ファイル |
|---|---|---|---|---|---|
| t1 | タイプ別痕跡一覧 | 読み型 | 3 | **2** | `queries.ts` / `SiteHeader.tsx` |
| t2 | 下書き自動保存エディタ | 相互作用型 | 5 | **5** | `types.ts` / `runEffect.ts` / `mutations.ts` / `queries.ts` / `SiteFooter.tsx` |
| t3 | あとで読む | 書き込み型 | 5 | **5** | `types.ts` / `runEffect.ts` / `mutations.ts` / `queries.ts` / `SiteHeader.tsx` |
| t4 | 気になるページの登録 | 書き込み型 | 5 | **6** | 上の5つ + `app/m/[material]/[page]/page.tsx` |

**この表の最も重要な性質は、数ではなく集合である。** 書き込みを伴う3回が触った共有ファイルは**毎回ほぼ同じ4ファイル**（`types.ts` / `runEffect.ts` / `mutations.ts` / `queries.ts`）＋導線1つであり、**機能数が6→10 に増えても集合は広がっていない。** 命題（§1「参照範囲が増えないか」）が問うているのはこの広がりであって、絶対値ではない。

一方、絶対値は事前登録された閾値（4以下）を最初から超えている。**その4ファイルのうち2つは構造的に避けられない**——L4 が単一ディスパッチ地点を要求し、L7 が `runEffect.ts` に機能型の import を禁じるため、書き込みのある機能は必ず `shared/types.ts` に `Effect` メンバを足し `shared/runEffect.ts` に case を足す。これは `genzaichi-3` §8 が「L1 の隔離が原理的に届かない、Law 同士の相互作用による結合」として**測定前に既知の反例候補として挙げていたもの**である。予測（書き込み型は5）はこの構造から立てられており、実測と一致した。

## 4. 測定によって判明した問題 — 3件

### 4-1. 主指標に盲点がある（最も重要）

設計書 §2 は `src/features/**` を「隔離されているので増えて当然」として主指標から除外している。**この除外は「機能ファイルは追加されるだけ」という前提に立っており、実測ではその前提が崩れた。**

| 回 | 編集した**既存機能**ファイル | 内容 |
|---|---|---|
| t3 | **5ファイル**（`pageview/core.ts` +33、`TraceCard` +11、`SpotCard` +8、`shell.tsx` +8、`types.ts` +2） | 既存の痕跡カードに「あとで読む」を置いた |
| t4 | **4ファイル**（`pageview/core.ts` +19、`types.ts` +6、`shell.tsx` +6、`PageMasthead`） | 既存のページ見出しに登録トグルを置いた |

`pageview/core.ts` は t3 の編集後 **596行**である。L1 違反ではない（他機能の内部を import したのではなく、`pageview` 自身に手を入れている）。しかし予算の定義が **「1タスクで参照しなければならない箇所の数」** である以上、596行のファイルを開いて編集したことは支出である。**主指標にはこれが1つも現れない。**

盲点を含めて数え直すと、1機能あたりの既存ファイル編集数は **t1=2 / t2=5 / t3=10 / t4=10** になる。後半2回で倍増しているが、その原因は機能数ではなく**「既存画面の上に操作を置く要件だったこと」**である（t2 は新規画面に閉じたので5のまま）。

**この事実は §7 の判定には使っていない。** 判定基準を後から変えないためである。次の測定では、主指標を「既存共有ファイル」ではなく **「編集した既存ファイル（機能内部を含む）」** に定義し直すことを推奨する。

### 4-2. 型の宣言基準が、実測と2回連続でずれた

t3・t4 はどちらも「書き込み型（送信して完了。結果を画面に反映する必要がない）」と宣言したが、**両方とも T3（往復あり）になった。** 理由は明白で、「入れる/外す」「登録/解除」という**既存画面上のトグル**は、押した瞬間に画面が変わることを要求し、失敗したら戻す必要があるからである。これは設計書 §5 の定義では相互作用型である。

つまり実際に実施できた型の配分は「読み型×1 / 相互作用型×3」であり、事前に決めた「読み型×1 / 書き込み型×2 / 相互作用型×1」ではなかった。**型の宣言は要件文を書いた時点で決まるので、要件文の中に「既存画面上のトグル」が入っていれば相互作用型として宣言すべきだった。** 次の測定への具体的な改善である。

### 4-3. 段位の梯子に穴がある（`T?`）

t1 の `tracetype` は `T?` と判定された——`core.ts` が型パースとラベルという純粋ヘルパだけで `init(initData)` を持たないため、T0（`core.ts` なし）でも T1（`InitData` を受ける）でもない。**読み取り専用画面に状態機械は要らないので掟に反していない実装であり、梯子側の穴である。**

verify はこれを黙って T1 に丸めず、理由を印字した（`? tracetype: core.ts takes no parameter typed *InitData, …`）。**設計の意図どおりの挙動ではあるが、梯子が読み型を1段として持っていないことは事実である。** 修正案は `genzaichi-3` §5 に記録した。**測定期間中に判定器を変えると数字が動いた原因が交絡するため、修正していない。**

## 5. 測定の妥当性

実施手順書 §7 のチェックリスト:

- [x] 4回とも固定リスト以外を渡していない（`SPACTA.md` / 要件文 / 作業ディレクトリ / 「緑になるまで直せ」）
- [x] 4回とも同じテンプレートを使った（要件文以外を変えていない。node→bun の置換は4回すべて同一）
- [x] 4回とも独立したセッション（毎回新規の sonnet。前の回の内容も結果も渡していない）
- [x] 型を混ぜた順序で実施した（宣言上は 読み→相互作用→書き込み→書き込み。**実測の型は §4-2 のとおりずれた**）
- [x] 各回の「事前」欄を実装開始前に書いた（`00-plan.md` に4回分を t1 開始前に凍結）
- [x] 測定期間中にリファクタリングを入れていない（`clone` info 0→2、`export-ownership` info 0→2、`types.ts` 予算超過 info が出ているが、いずれも触っていない）
- [x] 主指標を `git diff` から取った（実装エージェントの申告ではない）

設計書 §7「判定できない条件」には**該当しない**（リファクタなし / 実装エージェントは設計書も `genzaichi-3` も読んでいない / 主指標欄は4回すべて埋まっている）。

限界として記録すべきこと:
- **副指標5（実装 AI が開いたファイル数・入力トークン数）は取得していない。** 自己申告させると読む量を測られていると気づいて挙動が変わるため（手順書 §5）、セッションログから確実に取れない以上は空欄とした。
- **実行時確認ができない環境である。** `workerd` が動かないため dev サーバと D1 を起動できず、4回すべて「verify 緑 + tsc 0エラー」だけがゲートだった。t4 の実装者のみ `bun:sqlite` で SQL を直接検証している（条件がこの1点で不均一）。
- n=4、アプリ1つ、著者1人、モデル1つという設計書 §8-5 / §8-6 の限界はそのまま残る。

## 6. 著者に決めてもらう必要があること

1. **§7 の「不成立」と「保留」が同時に発火した場合、どちらを採るか。** 機械的には「不成立」の比率条件が該当し、同時に「保留」のばらつき条件も該当する。設計書は優先順位を定めていない。判断材料: 主指標の**集合**は機能数に対して広がっておらず（§2）、ばらつきの原因は型であることが特定できている（§4-2）。設計書 §7 の保留枝はこの場合の対処として「型を揃えて再測定」を指定している。
2. **主指標の定義を §4-1 のとおり改めるか。** 改めるなら、それは**次の測定**の定義であり、今回の4点を遡って再判定してはならない（§9）。
3. **段位の梯子（§4-3）をいつ直すか。** 測定が終わった今なら直せる。
4. **`types.ts` が 257行になり、verify が予算超過の info を出し始めた。** これは `contract` ゾーンの線形成長が閾値に到達したという信号であり、設計書 §10「成立した場合」が挙げていた「L7 と単一ディスパッチ地点の関係を再設計する価値」がここで実際に発生している。
