# Living Document 要件定義草案

このドキュメントはゆーざーの思いつきをまとめた粗いもの。これからブラッシュアップしていく必要がある。

## まず始めに、アプリを作るには、こういうものがあればいいと聞いた

### 呼び方・使い分け
要件定義（要件定義書)：「何を作るか」を決める工程・成果物。技術やサービスの話は含まず、「ユーザーが何をできるべきか」「システムは何を満たすべきか」を言語化するもの。あなたが今作りたいのはこれに近いです。
機能要件：システムが「持つべき機能」（例：ユーザー登録、検索、通知など）
非機能要件：機能以外で満たすべき性質（速度、セキュリティ、対応端末など）
基本設計（外部設計）：要件を元に、画面構成やデータの流れなど「どう実現するか」の大枠を決める工程（ここから多少技術寄りになる）
詳細設計：さらに実装レベルまで落とし込む工程（DB設計、API設計など）
仕様書：要件・設計を含めた「このアプリはこう動く」という具体的な取り決めをまとめたもの

## 要件定義書に入れるべき項目
一般的にはこういう項目立てが使われます。

背景・目的：なぜこのアプリを作るのか、誰の・どんな課題を解決するのか
想定ユーザー：誰が使うのか（ペルソナ、利用シーン）
スコープ（範囲）：今回作る範囲、あえて作らない範囲（「やらないことリスト」も超重要）
機能要件：

必須機能（MVPとして絶対必要なもの）
あったら嬉しい機能（後回しでもOK）
各機能ごとに「誰が」「何をして」「何が起きるか」を書く（例：ユーザーストーリー形式「〜として、〜したい、なぜなら〜」）


画面一覧・画面遷移（大まかでOK）：どんな画面があり、どう繋がるか
データ要件：アプリが扱う主な情報（ユーザー情報、投稿データなど）を大まかにリストアップ
非機能要件：

パフォーマンス（例：レスポンス速度）
セキュリティ（例：ログイン方式、個人情報の扱い）
対応環境（PC/スマホ、ブラウザなど）


制約条件：予算、期限、使えるリソースなど
成功基準（KPI）：何をもって「うまくいった」と言えるか

## 失敗談
一度、日本の「宅建」の勉強用に、youtube埋め込み型のアプリを作ったことがある。そのときある機能はただ「youtubeの埋め込みにタイムスタンプ付きの付箋を貼るだけ」だった。
しかし、これはユーザーにyoutubeからアプリへの移動を促す仕組みだった。本家の学ぶ場所と、このアプリにメイン-サブの関係があり、メインと競合しないようにあえてサブの道を選んだ。しかし結果としてスマホではアプリを毎回切り替える必要がうまれたり、youtubeでもシームレスでなかった。

元々は大学で教授が教材のブラッシュアップで使えるように考案した。この領域では集合知とLiving Documentがいきるだろう。しかし営業コストの関係から、今はRustなとプログラミング言語での使用を考えている。
なお、できたらRedditのRustコミュニティで言ったりすれば最低限テスターは集まると考えている
