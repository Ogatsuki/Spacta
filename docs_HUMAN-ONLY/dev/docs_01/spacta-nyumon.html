SPACTA 入門

AIと一緒に作るための、
アプリの世界地図

Spacta（スパクタ）は、Next.js アプリを「AI が安全に手を入れられる形」に整えるための 設計ルール＋小さなランタイム＋検査 CLI のセットです。 このページは React / Next.js を学習中の人向けに、その全体像を地図として説明します。

01解こうとしている問題

Next.js で大きなアプリを作ろうとすると、2つの壁にぶつかります。

壁① 密結合
Next.js は UI と状態管理を密結合させるので、1つの機能変更が離れた場所に波及しかねません。 しかも「波及していないこと」を機械的に確かめる手段がありません。 頼れるのは部分的な型チェックだけです。
壁② コンテキスト肥大
密結合の構造上、小さなタスクでも大量の関連コンポーネントを読む必要が出ます。 コンテキストウィンドウが足りなくなるし、 小さな修正のために大規模なコードを読み解く非効率も生まれます。

ここで重要なのは、壁②はモデルが賢くなっても消えないということです。 将来コードベース全体をコンテキストに収められるモデルが出ても、 「すべて読める」ことと「変更が状態管理をひそかに壊していないと保証できる」ことは別の問題だからです。

SPACTA が賭けている一つの命題

機能を足しても、「1機能を触るために読む量」は増えないようにできる。

先に、この3語だけ具体的に決めておきます
エンジン（ランタイム）
src/shared/spacta/ にある約290行の TypeScript。 全機能が共通で使う「処理の順番待ち」と「サーバーとの往復」を担当します。
検査（verify）
npm run verify で走らせる CLI。ESLint に近い立ち位置で、 リポジトリを AST として読んでルール違反を報告します。 違いは、末尾に「この緑が保証していないこと」まで印字する点。
型で守る
この文書で「構造で守る」と書いたら、多くの場合 tsc がコンパイル時に落ちるという意味です。 実行するまで分からないバグを、書いた瞬間の型エラーに変換する、ということ。

02なぜ今さらこんな分割をするのか

よくある疑問

今までも個人開発は十分できていた。なぜわざわざこんな制約を入れるの？

まず、その感覚は正しいです。Spacta が使っているパターン自体は、何も新しくありません。 純粋な関数にロジックを閉じ込める設計も、Elm や Redux のループも、20年前からある考え方です。 そして主流にはなりませんでした。理由も単純で、 人間が書くには冗長すぎて割に合わなかったからです。

網羅的な switch 文。あらゆる分岐に対する明示的な型定義。 これらは「あとから検証しやすくする」ための投資ですが、 その対価として人間が払う筆記コストが高すぎました。 だから多くの人は、素直に useState と fetch をコンポーネントに書いてきたわけです。

生成AIが、この取引のレートを変えた

AI にとって、反復的で明示的な構造は書くコストがほぼゼロです。 それどころか、これまで無数に見てきた密で機械的なパターンなので、 最も正確に再生産できる得意分野にあたります。

Spacta を一文に畳むと

AI 時代に、「書くコスト」と引き換えに「検証可能性」を買う取引のレートが劇的に変わった。
その新しいレートで、設計をやり直す。

書き手のコストが消えた瞬間、検証可能性だけが残って純利益になります。 つまり「人間には割に合わなかったから流行らなかった設計」が、 書き手が AI に替わった今、初めて元が取れるようになった——これが最大の動機です。

もうひとつ、AI が持ち込んだ新しい問題

「このファイルに fetch を書かないで」とプロンプトで頼むのは、 Spacta の言葉では hope-prompt（祈るように頼むだけの指示）です。 守られる保証がありません。しかも悪いことに、 禁止事項を並べるほど LLM の注意機構は分散し、回答精度が落ちます。

この設計思想の中心にある認識

Attention はリソースである。

注意が薄く広がれば、その "祈り" 自体を取りこぼす確率が上がります。 Spacta はこれを rule-prompt に置き換えます—— AI はルールに沿って書き、npm run verify が緑になるまで自分で直すだけ。 境界が守られていることは、記憶や祈りではなくスクリプトが実際のコードを読んで保証します。 その結果、AI は注意を目の前のタスクだけに集中させられます。

ここは Rust に例えると分かりやすいところです。AI に Rust を書かせると 「borrow checker が通るまで直す」というループが自然に発生します。 AI と Rust の相性が良いと言われる本当の理由はこれで、 Spacta の「緑になるまで直す」は、それを Next.js の上に後付けで作ったものです。

03中心にある分割 ——「決める」と「やる」を分ける

ふつうの React コンポーネントでは、ボタンのハンドラの中に 「バリデーション → setState → fetch → 返ってきたらまた setState」が まとめて書かれます。Spacta はこれを役割ごとに3つに割ります。

コア — 決める人
バリデーション、状態の更新、失敗時の巻き戻し。判断はすべてここ。 ただし fetch も Date.now() も呼びません。 引数だけを見て答えを返す純粋関数です。
機能ごとに1つ。features/○○/core.ts
実行係 — やる人
実際に fetch を投げる係。判断は一切しません。 渡されたものを送り、返ってきたものをそのまま返すだけ。
アプリ全体で1ファイル。shared/runEffect.ts
エンジン — つなぐ人
コアが出した「やってほしいこと」を実行係に渡し、 結果を必ずコアに返す。この往復を絶対に落とさないのが仕事。
全機能で共通。shared/spacta/runtime.ts

肝は、コアは命令を実行しないことです。 「保存して」というオブジェクトを return するだけで、その場では何も起きません。 実行するのは実行係で、橋渡しをするのがエンジンです。

なぜここまで分けるのか。コアが純粋関数になると、 そのファイルを読むだけで機能の全挙動が確定するからです。 「この関数、裏で API 叩いてるかも」という疑いが原理的に消えます。 AI が読む量を減らす効き目は、これが一番大きい。

04国境を越えられる言葉は、4つだけ

コアと外の世界のあいだには膜があります。 ここを通れるのは4種類のデータだけ。これが Spacta で最も硬いルールです。

図1 — 膜を通れる4つの型
型意味React でいうと
InitData最初に一度だけ渡す初期データサーバーから受け取る props
State今どうなっているかuseState の中身にあたるもの
Action何かが起きた、という知らせreducer に dispatch するやつ
Effect外にやってほしいことの宣言近いものがない。ここが Spacta 固有

4つとも「ただのデータ」で、関数やコールバックは膜を越えません。 だから「渡した先で勝手に何かが動く」ということが起こりえない。 これが後で出てくる「型で守る」の土台になります。

05Spacta 世界地図

実際のアプリを領域として描くとこうなります。 横に引かれた点線が国境で、そこを越えると何が使えるかが変わります。

図2 — Spacta 世界地図。features/○○/ は機能ごとに増える領土、 shared/ は全機能で共有する領土

この地図から読み取ってほしい3つのこと

① 国境①より下には React が存在しない。 エンジン・コア・実行係には import ... from "react" が一行もありません。 偶然ではなく、コードに明記され、検査でも見張られています。 おかげで、React が新しい API を出しても直すのは関所ひとつだけで済みます。

② コアと実行係のあいだに直通の道がない。 地図の中央の ✕ がそれです。コアは fetch を呼べません—— 呼びたければ「Effect」というデータを返して、エンジンに頼むしかない。 この迂回が、コアを純粋関数のまま保っている仕掛けです。

③ エンジンだけが両側とつながっている。 だからエンジンは「往復が完了したか」を唯一知っている立場にあります。 ここが次のセクションの主役です。

06クリックが一周する旅

「いいね」ボタンを押したとき、データが地図をどう移動するか。 同じ地図に、往路（オレンジ）と復路（緑）を描き込みます。

図3 — 書き込みは「行きっぱなし」ではなく、地図上をぐるりと一周する
#場所起きること
1画面クリックが { type: "TOGGLE_VOTE" } のようなただのデータに変換される。ここから先、DOM イベントは流れない
2エンジン知らせを FIFO に積む。同時に来ても必ず一件ずつ処理する
3コア画面をどう変えるか決め、同時に「保存して」という Effect を返す。通信を待たず、画面はもう「いいね済み」になる（楽観的更新）。ただし「保存待ち」の控えを内部に残す
4実行係Effect を実際の fetch に変換して送信。アプリ全体でネットワークが動くのはこの1箇所だけ
5エンジン成功でも失敗でも、結果を必ず Action に包んで持ち帰る。ここに分岐はなく、返事を捨てる道が存在しない
6コア成功なら控えを消す。失敗ならいいねを取り消す。巻き戻しの判断もコアの仕事で、エンジンも実行係も何を戻すべきか知らない
7画面更新された State が反映される。ここで初めて React が再登場する
この設計の合言葉

書き込みは出発ではなく、往復である。

よくあるバグは ④と⑤のあいだで返事を落とすことです。 実際 livingdoc でも、以前はこの往復ループが機能ごとに3回も手書きされていて、 そのうち2つが返事を捨てていました。しかも誰も気づいていませんでした。

07検査で守る → 型で守る

その「返事を捨てていた」問題に、どう対処したか。ここが設計思想の核心です。

以前 — 検査で守る（verify に任せる）
  • CLI がソースを AST として走査し、違反を探す
  • しかし await runEffect(e); と書いて戻り値を捨てるのは TypeScript として完全に合法
  • AST から見ると「捨てた」と「そもそも受け取る必要がない（画面遷移など）」が同じ構文に見える
  • 結果、verify は緑を出し続けた
現在 — 型で守る（tsc に任せる）
  • エンジンが結果を返す処理に分岐が1つもない。捨てる経路がコード上に存在しない
  • 結果を受け取る口を用意していない機能は、エンジンに渡す時点で型が合わず tsc が落ちる
  • さらに assertNever で、case を書くこと自体をコンパイラが強制する
  • ループの実装が1つしかないので、それが正しければ全機能が正しい
考え方の転換

「間違いを見つける検査」を強くするのではなく、
「その間違いを書けない型」に作り替える。

ただし全部が型で守れるわけではありません。「コアが純粋関数であること」は tsc では検出できないので、今も verify という CLI に頼っています。 Spacta の改良とは、おおむね「検査に頼っていた部分を、型で守れる形に移していく」作業のことです。

08「並列開発」と「直列化」は別のレイヤーの話

よくある疑問

「複数の AI で並列開発できる」と聞いた。でも「直列化」と書いてある。できないということ？

どちらも正しく、矛盾していません。まったく別の時間軸の話だからです。

図4 — 左は「誰がコードを書くか」、右は「実行中に処理がどう流れるか」。層も時間の単位も違う
並列開発直列化
いつの話開発しているときアプリが動いているとき
時間の単位数日〜数週間ミリ秒
何が並ぶ/並ばないか機能（catalog / search / profile）1機能の中の書き込み（投票・コメント）
何のため開発を速くするデータの取りこぼしを防ぐ

並列開発が成立する条件（ここは正確に）

「複数の AI で並列実装して衝突ゼロだった」は初期評価で実際に起きたことですが、 その成功の理由を取り違えないことが重要だと設計文書は念を押しています。

衝突を防いだのは何だったか

衝突を防いだのは、機能同士を切り離すルールではない。
契約（types.ts）を人間が事前に凍結したことである。

ルールが止めるのは機能↔機能の結合ですが、 並列で動く AI が実際にぶつかるのは共有部分（shared/ui のボタン部品や、 共通の型定義）です。ルールの役割は「合流点を、名前のついた少数の場所に限定すること」であって、 凍結そのものではありません。

したがって実務上の手順はこうなります—— ①共有部分（型・UI部品）を先に実ファイルとして確定させる → ②機能ごとに AI を並列で走らせる → ③画面の統合を最後にまとめて行う。 この順番を守らずに並列化すると、共有部分の取り合いで普通に壊れます。

直列化のほうは、代償もある

エンジンは1つの機能インスタンスにつき、飛行中の書き込みを常に1件に制限します。 これが「投票の返事が着地したらコメントが消える」という種類のバグを構造的に消しました。 ただし互いに独立した書き込みまで待たされます。 正しさのために並行性を捨てた選択であり、採用する側が知っておくべき性質です。

09AI は何を書き、何を書かないのか

よくある疑問

エンジンやアダプターがパッケージ化されるなら、AI に書かせる量は減るの？　結局、何を書かせていくの？

まず前提として、Spacta の方針は「コードベースの全部を AI が書く」です。 core.ts のロジックも、shell.tsx の配線も、components/ の見た目も、全部です。 人間の介入は任意——AI の生成物が問題なく動くならそのまま出荷して構いません。

その上で、地図のどこを AI が書くのかを塗ってみます。

図5 — 機能追加のたびに AI が書くのは、コアと画面。エンジンと関所は触らない
場所誰が書くか機能を1つ足すと
コアAI（判断ロジック全部）1ファイル増える
画面・部品AI（人間が見た目を調整することも）数ファイル増える
型の契約人間が先に凍結し、AI が従う1ファイル増える
実行係AI（case を1つ足すだけ）数行増える
エンジン誰も書かない1行も増えない
関所誰も書かない1行も増えない

実測では、エンジンは4つの機能を追加するあいだ 292 行から1行も動きませんでした。 パッケージ化の意味はここにあります——書く量が減るというより、 「毎回書き直していたせいで壊れていた部分」が、書く対象から消えるということです。

実際、あの「往復ループが3回手書きされ、2つが返事を捨てていた」事故は、 共通化されていなかったから起きました。 同じものを3回書けば、3回とも正しく書ける保証はどこにもありません。

ちなみに現時点でエンジンはまだ npm パッケージになっておらず、3つのリポジトリに同じ内容がコピーされています。 苦しまぎれに「3つがバイト単位で一致しているか」を自動テストで確認している状態で、 止血であって解決ではないと設計文書に明記されています。

10結局、どのくらい効くのか

よくある疑問

具体的にどのくらいエラーが減るの？　保守性はどのくらい上がるの？

正直に答えると、「エラーが何％減る」という数字は測られていません。 そもそも Spacta が減らすのは、エラーの数ではないからです。

verify が緑のとき、何が言えるのか

バグがない　　　　　　　　　　❌
バグがあっても、それは局所的・明示的・決定的である　✅

count + 1 と書くところを count + 2 と書き間違えたコードは、 緑のまま通ります。ロジックの間違いは検出されません。 減るのは「バグを探す範囲」のほうです。 密結合な Next.js では「これは正しいか？」がアプリ全体を見ないと答えられない問いになりますが、 Spacta ではそれが「1つの純粋関数を読めば答えられる問い」に縮みます。

実際に測られている3つのこと

  • 0件 並列実装での衝突 契約を凍結した上で、複数の独立した AI エージェントが別々の機能を同時に実装し、 衝突ゼロで統合できました（初期評価）。
  • 12/12 リプレイの一致 「操作の記録だけから、画面の状態を完全に再現できる」かを12セッションで検証し、全一致。 同じ検証を改良前のコードで走らせると1個目・5個目の操作で食い違います—— つまり改良前には実在したバグが、実測で閉じたことが確認されています。
  • 292行 エンジンの不動 機能を4つ追加するあいだ、共通エンジンは1行も変わりませんでした。 機能追加のコストが共通部分に波及していないことの実測値です。

逆に、正直に増えるもの

設計文書自身が注記しているところですが、この設計には逆向きに働く2つの力があります。

減るもの — AI が読む量
  • 1機能を触るのに読むのは、その機能のディレクトリだけ
  • 「この関数、裏で API 叩いてるかも」という追跡が不要
  • 状態がどこで書き換わるか探す作業が消える
増えるもの — AI が書く量
  • 全分岐に明示的な型定義が要る
  • 網羅的な switch を書く必要がある
  • 1つの操作に Action と Effect の往復が要る

総体として安くつくのか高くつくのかは、まだ計測されていません。 設計文書はこれを「決着した主張」ではなく「未解決の問い」として書き留めています。 ただし、書き手が AI である以上、 「書く量が増える」側のコストは人間が払うものではない—— これが 02 で述べた取引レートの話につながります。

11まだ解けていないこと

この設計のいちばん特徴的な性質は、 道具が「自分が保証していないこと」を毎回出力に含めることです。 verify を走らせると、違反一覧のあとに NOT guaranteed by this green: という 見出しで9項目が印字されます。

  • データ経由の結合は消えていない 機能同士が import し合うことは禁止できますが、 同じ DB テーブルを読んでいることによる結合は残ります。 実測では読み取りクエリのファイルが 508 行まで育ち、3機能が同じ定数を共有しています。 テーブルに列を1つ足す判断が3機能に同時に波及しますが、ルールはどれも反対しません。
  • 共有部分が線形に育っている 冒頭の命題への、実測された反例。ルール同士の組み合わせの都合で、 書き込み機能を1つ足すと共有の型定義が1〜2行ずつ膨らみます。 計測ツール自身が閾値超過を検知し、警告を出し始めました。
  • Next.js 自身の暗黙性は素通し キャッシュの意味論、再検証のタイミング、サーバー／クライアント境界のシリアライズ。 Next.js 最大の「追跡不能」はここにあり、Spacta のルールはほぼ手を出していません。
この設計が守っている一線

穴があること自体は許される。
穴を隠すことは許されない。

verify が緑を出すとき、それが何を意味していて何を意味していないのか。 Spacta はそれを毎回明示します。 「緑だから安心」ではなく「緑はここまでを保証し、ここから先は保証しない」と言い切る—— これが、この設計で最も評価されている点です。

12まとめ

  • 動機 — AI 時代に「書くコスト」と「検証可能性」の交換レートが変わった。昔は割に合わなかった設計が、今なら元が取れる
  • 地図 — React を知る領域と知らない領域を国境で分け、コアと fetch のあいだに直通の道を作らない
  • 通行証 — 国境を越えられるのは InitData / State / Action / Effect の4つのデータだけ
  • 往復 — 書き込みは必ず一周して戻る。返事を落とす経路を構造から取り除いた
  • 並列と直列 — 開発は並列にできる（契約を先に凍結すれば）。実行時の書き込みは直列（取りこぼしを防ぐため）
  • 効果 — バグの数は減らない。減るのはバグを探す範囲。「アプリ全体を見る問い」が「1関数を読む問い」になる
  • 誠実さ — 解けていない部分を、道具自身に毎回言わせ続けている
