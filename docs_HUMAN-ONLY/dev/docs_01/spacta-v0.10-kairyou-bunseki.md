## 2. 改良の骨格 — 3つの移動

### 移動1: 往復の保証が「検査」から「構築 + 型」へ [確立]

対応: genzaichi-3 §2.5 / §3.3 / §4-① / §5.2

#### 何が壊れていたか

`drain`（Effect キューを回す機構）が**1プロジェクト・1著者の中で3つに手書きされ、うち2つがサーバの答えを捨てていた**。捨てていた2つ（`materialrequest` / `moderation`）の Effect は `correlationId` を持たないため L3 の受け皿検査が発火せず、**verify は緑のままだった**。

これは「掟の穴」ではない。`SPACTA.md` は `runEffect` を**誰がどう呼ぶか**を一言も規定していなかった（§3.3）。**機構の不在**である。

#### 何に変わったか

`src/shared/spacta/runtime.ts`（212行）+ `react.ts`（80行）= **292行**。ループの実装はこの1つだけになった。

**重要なのは、往復の施行が AST 検査に一切依存していないこと。** 3層で、どれもコンパイラか構造である。

| 層 | 実体 | 何を不可能にするか |
|---|---|---|
| **1. 無条件 dispatch** | `runtime.ts:191` の `inbox.push(outcome)` に分岐が1つもない | **答えを落とす経路が存在しない。** 識別子を持たない Effect（`NAVIGATE` / `LOG`）にも outcome が飛ぶ |
| **2. 型** | `Update<S,A,E>` の action 引数が `A \| EffectOutcome`（`runtime.ts:30`） | 受け皿のない機能は **`useSpacta` の呼び出し地点で tsc が落ちる**。「往復を書き忘れた」が沈黙ではなく型エラーになる |
| **3. 網羅性** | `core.ts` の `assertNever` | 受け皿があるだけでなく、**case を書くことを強制する** |

> **これが v0.10 で最も本質的な一手である。** 指示書 §4-① が「検査を足すのではなく機構を提供する」と決めた理由——`await runEffect(e);` と書いて戻り値を捨てるのは TypeScript として合法であり、AST からは「捨てた」と「元々受け取る必要がなかった」が同じ構文に見える——は正しく、そして**唯一の実装が正しければ往復は検証する対象ではなくなる**。

#### 副産物: lost-update が閉じた [確立]

エンジンは1つの権威ある `state`、1つの Action FIFO、1つの Effect FIFO を持ち、`apply()` と `drain()` の両方に再入ガードがある。旧シェルは React クロージャから `state` を読み、state オブジェクト全体を `setState` で戻していたため、**投票の答えがコメントの飛行中に着地するとコメントが消えた**（§2.6）。

**実測で前後が分かれている**（`bun replay/crosscheck.mjs`）:

```
S2  legacy  pageview   diverged at #1 TOGGLE_VOTE        （旧ループ）
S2  engine  pageview   replays                            （エンジン）
S3  legacy  pageview   diverged at #5 EFFECT_SUCCEEDED   （旧ループ）
S3  engine  pageview   replays                            （エンジン）
```

指示書 §4-⑤ が要求した「①の前で失敗し後で通ること」が、**旧ループを転写して残す**という形で満たされている。捨てずに残したのは正しい判断で、これがなければ「直列化が効いた」は主張にすぎなかった。

### 移動2: 定理が「主張」から「検算」へ [確立]

対応: genzaichi-3 §4-⑤

Spacta は「verify が緑なら、バグは (1) 機能内に閉じ、(2) `(initData, actions[])` だけから再現でき、(3) 隠れた入力を持たない」と主張していた。**一度も検算されていなかった。**

#### 設計上、注目に値する3点

**① `Recorder<A>` に `S` の型引数が存在しない**（`runtime.ts:91`）。

これは規律ではなく**型による保証**である。State を記録できる記録器があれば、照合は状態を自分自身と比べて必ず一致し、緑に見えながら何も検証しない。**型引数を持たせないことで、その失敗が書けなくなっている。** 指示書 §4-⑤ は「記録した State を読んで比較してはならない」と**禁止事項として**書いたが、実装は禁止を**表現不能**に変えた。

**② 記録が付く場所が1行だけ**（`runtime.ts:163`、`apply()` の中）。

すべての機能のすべての Action がこの1行を通る。**7つ目の機能はこのファイルに0行、自分自身にも0行を足す。** 指示書 §4-⑤「配置」が要求した「機能数に対して O(1)」が、位置の選択だけで達成されている。実測でも `engine` ゾーンは4機能追加を通じて **292行から1行も動いていない**。

**③ `record` がエンジンの引数である。** エンジンに `process` も `import.meta` も「開発ビルド」の概念も入っていない。コメントいわく「入れたらエンジンにプラットフォームを与えることになる」。**移植単位の純度を、便利さより優先した判断。**

#### ハーネス自身に自己テストがある [確立]

L6（検証器自己検証）の発想を1階層上に適用したもの。`bun replay/harness.selftest.mjs` で12件。特筆すべきは:

> `ok  dropping an Action and trimming the run's trace to match is still rejected — the states are compared, not counted (12/12 positions caught)`

**ハーネスを騙す最も自然な方法**（Action を1つ落とし、辻褄合わせに trace も削る）を先回りして潰している。指示書 §4-⑤ は「既知の発散を埋めて検出を assert せよ」としか言っていない。**実装が指示より強い箇所。**

#### 結果

- **(2) 再現性は、エンジン駆動の12セッションすべてで成立した。**
- **(4) 他機能への波及は「検証できない」と毎回印字される。** データ層の共有はプロセス内 Action ログに現れないため。
- **(*) S_live が React を通っていない**ことも毎回印字される（§4-4 参照）。

### 移動3: 緑が「一枚岩」から「段位つき」へ [確立]

対応: genzaichi-3 §4-③

**改良前の状態は、穴より悪かった。** Spacta を途中まで採用したプロジェクトは、**採用しなかった部分について何も保証しない緑**を受け取っていた。

改良後、verify は機能ごとに T0〜T3 を印字する。実測:

```
Tiers: pageview T3, draft T3, saved T3, watchlist T3, moderation T2,
       materialrequest T2, catalog T1, search T1, profile T1, tracetype T?
  T2 features declare Effects but do not receive their results — the write-path
  round trip is NOT verified for them.
```

**段位は赤にならず、exit code に影響しない。** 指示書の判断——「往復を必要としない機能に往復を強制すると、利用者に無視リストへ手を伸ばす訓練をさせることになる。**口に出すのが解決であって、走るのを拒むことではない**」——がそのまま実装されている。

そして `tracetype` の `T?` は、**判定器が丸めずに理由を印字した**実例である（§5-3）。

### 補: 主張が測定可能になった [確立]

対応: genzaichi-3 §4-②

`metrics/measure.mjs`（660行）。設計原則が明快で、**「検知は verify、測定は measure、変換は garden」** という目と手の分離をツール構成にまで貫いている。

## 4. 弱いまま残った点 — 6件

### 4-1. `contract` の線形成長が、v0.10 唯一の構造的負債 [確立]

L4（エンジンが唯一のディスパッチ地点）と L7（`runEffect.ts` は機能型を import できない）の**相互作用**により、`Effect` union は全機能で共有される1ファイルに集まる。「機能 A に Effect を1つ足す」が「機能 B の依存先の編集」になる。

**これは L1 の隔離が原理的に届かない結合である。** genzaichi-3 §8「共有予算」が測定前に既知の反例候補として名指ししていたものであり、測定 t1〜t4 で実測された:

```
Effect union:  9 → 11 → 12 → 13     （書き込み機能1つにつき +1〜2）
types.ts:    209 → 246 → 249 → 256行
```

そして `types.ts` が **257行**（verify の数え方）に達し、**予算超過の info が発火し始めた**。

> **v0.10 の到達点は、「自分の唯一の構造的弱点を、自分の測定器が見つけて自分で申告する」ところまで来たことである。** ただし解決はしていない。genzaichi-3 §10「成立した場合」が挙げていた「L7 と単一ディスパッチ地点の関係を再設計する価値」が、ここで実際に発生した。

### 4-2. エンジンが3部に重複している [確立]

`shared/spacta/{runtime,react}.ts` は starter / livingdoc / `livingdoc/verify/starter/`（参照コーパス）の**3箇所に同一内容で存在する**。byte 一致 assert は止血であって解決ではない——**エンジンを1箇所で進化させられない。** genzaichi-3 §5 に記録済み。測定ゾーンの構成比を切断するため測定完了まで保留された。**測定は完了したので、これは今やれる。**

### 4-3. 「答えは返るが、名指しできない」ケースが残った [確立] — この文書の独自指摘

無条件 dispatch は**沈黙を消した**。しかし `correlationId` を持たない Effect は、答えを受け取れても**答えを使えない**。実例が `moderation/core.ts:108`:

```ts
case "EFFECT_SUCCEEDED":
  // Deliberately nothing. (…) It would be right to drop the confirmed id from
  // `pending`, but the answer does not say which id it is about — `MODERATE` carries
  // no `correlationId`. The gap is stated here rather than guessed at.
  return [state, []];
```

結果として `moderation` は**成功したコマンドの行を `pending` に残したままにする**（既存の不具合、genzaichi-3 §5 に記録済み）。

> **「沈黙を、意図的な記述に変える」は達成された。ただしその記述の中身が「何もできない」であるケースが残っている。** 施行の観点では前進（穴が可視化された）だが、機能の観点では未修正のバグである。修正には `MODERATE` に識別子を持たせる必要があり、それは段位判定（T2→T3）を動かすため測定期間中は禁じられていた。**これも今やれる。**

### 4-4. リプレイ照合が React を通っていない [確立]

`S_live` はエンジンと実 `core.ts` を直接駆動して作られており、`perform` はスタブ。**React の batching / Suspense / 再描画タイミングは一度も通っていない。** 同じ理由で `useSpacta` の `record` 受け渡しは React 経由で一度も走っていない。

**照合の出力に毎回印字されるので、隠されてはいない。** 閉じるには Testing Library か実ブラウザ＝依存の追加が要る。

### 4-5. 段位の梯子に穴がある（`T?`）[確立]

`tracetype` の `core.ts` は型パースとラベルという純粋ヘルパだけで `init(initData)` を持たないため、T0（`core.ts` なし）でも T1（`InitData` を受ける）でもない。**読み取り専用画面に状態機械は要らないので掟には反していない。梯子側の穴である。**

加えて **T0 は実プロジェクトで一度も発火していない**（`core.ts` を持たない機能が starter にも livingdoc にも存在しない）。フィクスチャ経由でしか検証されていない段が1つある。

### 4-6. 直列化の代償が、どこにも記録されていない [仮説] — この文書の独自指摘

`drain()` の再入ガード（`runtime.ts:176` の `if (draining) return;`）は、**1機能インスタンスにつき飛行中の Effect を常に1つに制限する。**

これは lost-update を閉じたが、**同時に並行性を全部捨てている。** 互いに独立した3つの書き込み（別々の痕跡への3つの投票など）も厳密に直列で待つ。genzaichi-3 §5 は「同一機能の2インスタンスを競合させるシナリオが未設計」と書いているが、**より根本的な問題は、直列化が正しさのために並行性を捨てる選択だったという事実が、指示書にも実装コメントにも書かれていないこと**である。

現状の livingdoc は書き込みが軽いので問題にならない。**ただし「1機能インスタンスの書き込みは直列である」は Spacta を採用する側が知るべき性質であり、`SPACTA.md` §4-3 か `HUMAN_GUIDE` に1行あるべき。**

**関連する小さな穴 [仮説]:** `update` が throw すると `apply()` の例外が `dispatch` の呼び出し元まで伝播し、`announce()` と `drain()` がスキップされる。inbox に残った Action と queue に残った Effect は**次の dispatch まで適用されない**。回復可能ではあるが、静かに遅延する。

## 5. v0.10 の性格 — 自分の弱点を自分で印字する

**この版で最も評価すべきなのは、個々の改良ではなく、4つの道具すべてが「自分が保証しないこと」を出力に含めるようになったことである。**

| 道具 | 自己申告している内容 |
|---|---|
| `verify` | `NOT guaranteed by this green:` 9項目。0ファイル走査の検査は `NOT verified (0 files matched)` と印字し、緑に混ぜない |
| `replay/crosscheck` | `(4) 他機能への波及は検証不能` / `(1) 局所性は部分的` / `(*) React を通っていない` |
| `measure` | 数字だけを出し、判定しない。比較器を意図的に持たない |
| **段位** | `T?` を T1 に丸めず、判定できない理由を印字（`core.ts takes no parameter typed *InitData`） |

genzaichi-3 §6.4「穴があること自体は許される。穴を隠すことは許されない」が、**4つの道具すべての出力形式にまで降りてきている。** これは規律が文書から実装に移った証拠であり、v0.10 の最大の成果だと考える。

## 6. 二本脚モデルへの帰結 [確立]

genzaichi-3 §8「二本脚モデル」（第1の脚＝構造 / 第2の脚＝検証）に対して、v0.10 は次の3つを実物で示した。

1. **変更① は verify を1行も必要とせずに往復問題を閉じた。** 施行は構築（唯一のループ）と型（`A | EffectOutcome`）だけで済んでいる。**帰結: 「Spacta in X」は検証器ゼロで出荷できる。**
2. **エンジン292行が、4機能・うち T3 が3つを追加してなお1行も動かなかった。** これはそのまま**移植面が O(1) である証拠**になる。SwiftUI / Compose への展開は、この292行を書き直す作業として見積もれる。
3. **規律 / 機構 / アダプターの3分類が実物で確認できる形になった。** `runtime.ts` に `react` も `next` も1文字も入っていない（機構＝移植される部分）。`react.ts` が React と非決定性採取を独占する（アダプター＝書き直される部分）。掟10本は依然として検証器でしか届かない（規律＝ライブラリ化不可）。

## 7. 次に効く順番 — 提案

測定が完了した今、genzaichi-3 §5 の保留リストのうち**解禁されたもの**を、効果の大きい順に。

| 順 | 項目 | なぜこの順か |
|---|---|---|
| 1 | **`contract`（`types.ts`）の再設計** — L7 と単一ディスパッチ地点の関係 | **唯一の構造的負債であり、予算超過 info で閾値に到達した**（§4-1）。放置すると機能数に比例して悪化する唯一の箇所 |
| 2 | **エンジンのパッケージ化** — 3部重複の解消 | 測定ゾーンの制約が外れた。**1と独立に進められる**。参照コーパスがエンジンのコピーを持つ必要もなくなる |
| 3 | **段位の梯子の修正** — T1 を「`core.ts` が存在し純粋である」に緩める | 判定器を変えても交絡しなくなった。**読み型が段位を持てるようになる**（§4-5） |
| 4 | **`moderation` に識別子を持たせる** | 3 の後。既知の不具合が閉じ、同時に「答えを名指しできない」ケースが1つ減る（§4-3） |
| 5 | **`SPACTA.md` / `HUMAN_GUIDE` に直列化の代償を1行** | 採用者が知るべき性質が未記載（§4-6） |
| 6 | **`adapters/` 新設と `shared/source/` の移動** | 測定完了で解禁されたが、**効果は §5 が自ら「過大評価されている」と書いている**。優先度は低い |
