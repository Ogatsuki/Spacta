# Spacta モード分離 — 契約決定を「誰が」から「どのモードか」へ

**この文書の位置づけ:** `spacta-genzaichi-2.md`未収録の新規論点。並列構築（縦のライン=component/feature/page の同時実装）を検討する対話から生まれた。確信度タグは genzaichi-2 と同じ規則（[確立]/[仮説]/[着想]/[決定]）。

---

## 問いの出発点

縦のライン（component → feature → page/layout、import の向きに沿った1本）を複数のAIで並列実装しようとしたとき、「型契約を誰が最初に決めるのか」という問いが生まれた。componentの実装を知らなくても、型契約さえ凍結されていればfeatureは書ける——という前提（§7の「意図の型」と同型）に立つと、残る問題は「誰が・いつ契約を凍結するか」だけになる。

## 第1段階の答え：2フェーズ論 [出発点、後に一般化]

- **構築フェーズ**: 統括AIがアプリ全体を見渡し、その後並列エージェントが独立に実装する
- **保守フェーズ**: Spactaのコンテキスト隔離のおかげで単一機能に閉じて作業できるので、単一のエージェントが縦のラインを1人で見る。並列も統括も不要

この段階での結論：構築フェーズだけ「全体を見渡す主体」が要る。保守フェーズはそもそも契約が既に凍結済みなので問題が消える。

## 第2段階の一般化：フェーズ（暦）からモード（タスクの種類）へ [仮説]

2フェーズ論を精査すると、本質は「いつ（構築期か保守期か）」ではなく「**今、共有契約に触る必要があるかどうか**」だと分かる。これはカレンダー上のフェーズではなく、**タスクごとに出入りするモード**として捉え直せる。

- 保守中の単一エージェントであっても、途中で型契約の変更が必要だと気づいた瞬間、一時的に「契約変更モード」に入ればよい。統括AIという役職を常設する必要がなくなる
- 「誰が決めるか」という問いは、「**その瞬間にアプリ全体（あるいは対象の共有契約の全消費者）を見渡している主体が、共有部分だけを決める**」という形に統一できる。これは§3のアダプター概念（2機能以上での共有が凝縮の対象になる）と同じ基準——**共有されていなければ、そもそも契約凍結の対象にすらならない**

## モードの排他性というアイデア [仮説]

「契約変更モードの間は通常実装をしない、通常実装モードの間は契約変更をしない」という排他性を課すことで、AIのアテンションリソースを節約できるのではないか、という着想。

- **人間の文脈切り替えコストとの違いに注意**: 人間はモードを切り替えると注意・記憶が失われるが、単一の連続したコンテキストを持つLLMエージェントは何も忘れない。モードとは記憶の境界ではなく**自分に課すルールセットの切り替え**でしかないので、切り替えコスト自体はほぼゼロに近いと考えられる
- したがって排他性を課すこと自体は負担というより、Spactaの一貫した思想（「気づける」をAIの自制心に依存させず、構造で強制する。§10-④、L1〜L10がすべて`verify`で機械施行されている理由と同型）に沿った安全策になりうる

## 「構造の開示」と「読み込みの深さ」を分離する [確立]

前段の議論で出た懸念——「契約変更モードに入ったAIが、その共有契約の他の消費者の存在を知らなければ、§7が解こうとした『気づかれずに壊れる』問題が再発する」——に対して、次の分離が有効だと判明した。

| 部分 | 何を保証するか | 階層 |
|---|---|---|
| 消費者の**存在**の開示 | 「pageview/search/profileがこの共有ファイルをimportしている」という事実の一覧 | **機械的に保証可能**（Law/Advice） |
| その消費者を**どこまで読むか・どう判断するか** | 型変更が意味的に安全か | **判断に委ねる**（Judgment、ルールプロンプト） |

「本当に読んで理解したか」を検証スクリプトでチェックするのは原理的に不可能であり、それを目指すのは§8-2「潔癖症になりすぎない」に反する——ここは当初の提案の誤りだった。一方で「消費者が存在するという事実」は`grep`や依存グラフ解析で100%機械的に検出可能であり、これは`nextjs.mjs`の名前→役割マッピングや`garden`のinfo→指示書変換と同じトリックの応用にすぎない。

**具体案**: 契約変更モードに入ったら最初にすることを「このスクリプトを走らせる」とルールプロンプトに書き、そのスクリプトが最低限必要なディレクトリ構造・消費者一覧を機械的に開示する。これは新しい機構ではなく、`SPACTA.md`§4「④ `npm run verify`を自分で走らせろ」と同種の追加エントリーポイントとして実現できる。

読み込みの深さ（消費者一覧の中身をどこまで実際に開くか）は**強制チェックリストではなく利用可能なメニュー**として扱う方向に傾いている——ここもJudgment階層に留め、機械強制はしない。

## 未解決・保留事項

1. **モードの列挙**: どのモードが存在するか（通常実装モード／契約変更モード／並列委任モードなど）を正確に定義する作業は、意図的に後回しにしている。別セッション・別AIでの検討を予定
2. **モード軸は層に依存しない直交軸である**: モード（通常/契約変更）は feature/UI だけでなく core・状態管理・API にも横断的にかかる。ただし「層×モード」の組み合わせを明示的に命名する（例:「通常実装モード・core」）のは組み合わせ爆発を招くため避けたい、という直感がある。「末端ファイルのみ編集可」のような精密な定義を与えることも、AIのアテンションを逆に分散させるリスクがあるため、今は保留する（§8-2 潔癖症回避と同型の判断）
3. 契約変更モードと並列委任モードが同一なのか、後者が前者を包含する関係なのかは未整理
