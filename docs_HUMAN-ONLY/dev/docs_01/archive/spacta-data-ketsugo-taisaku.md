# データ経由の結合への処方箋

対話(著者とAI)の結論。`spacta-genzaichi.md` §4「データ経由の結合 —— 最大の穴」に対して、`spacta-fukuzatsusei-no-gyoshuku.md`(複雑性の凝縮)と `spacta-adapter-bunrui.md`(データアダプター・物理ディレクトリ分離)を組み合わせて処方する。

**結論を先に書く: 完全解決ではない。ただし「気づかれない事故」を「見える単一の確認ポイント」に変換するところまでは持っていける。** これはSpactaが書き経路の戻り問題(v0.9.3)ですでに達成したのと同じ水準・同じ形の解決である。

---

## 問題の再確認 [確立]

`livingdoc/src/shared/source/queries.ts` の `TRACE_SELECT` を、pageview / search / profile の3機能が共有している。`traces` テーブルに列を1つ足す・意味を変える判断は3機能の読み経路に同時に波及するが、**`verify`のL1は緑のまま**。カバレッジではなく「エージェントは自分のfeatureだけ読んでタスクを完了できるか」という指標で見たとき、データ形状のタスクだけがここで破綻する。

## なぜ今まで危険だったか [確立]

`queries.ts`は`shared/`(Spacta所有の名前空間)の中に、他のSpacta所有コードと同じ顔をして埋まっている。pageviewだけを直すつもりのAIが、**自分が3機能共有のコードを触っていることに気づけない。** 危険の本体は「共有されていること」自体ではなく、「共有されていることが構造から見えないこと」にある。

## 処方 [仮説]

### 1. 物理ディレクトリで「触っている」ことを可視化する

`spacta-adapter-bunrui.md`で決定した`adapters/`ディレクトリに`queries.ts`を移す。pageviewの機能修正タスクなら`features/pageview/`だけで完結し、`adapters/`に触れる理由がそもそも無い。触る必要が生じたら、その場所にいるという事実だけで「これは複数機能に影響する変更だ」と構造的に気づける。role-claim的な検査ロジックに頼らず、ディレクトリ配置だけで実現する。

### 2. 語彙を型定義として1箇所に凝縮し、構築を機能ごとに局所化する

`spacta-genzaichi.md` §3「第5の膜語彙を作らなかった」で実測されたパターン——**型は大域的でも構築は機能ごと、カスケードは起きなかった**——を読み経路に輸入する。

```
今: 3機能が同じ関数(TRACE_SELECT)を直接共有
  pageview → listTracesForPage() ─┐
  search   → searchTraces()      ─┼─→ 全部 TRACE_SELECT を呼ぶ
  profile  → listTracesByUser()  ─┘

処方後: 各機能は「意図」を型で宣言し、データアダプターが個別に組み立てる
  pageview の意図 = { fields: ["id", "page_id", "quote", "author"] }
  search    の意図 = { fields: ["id", "quote", "votes"] }
  profile   の意図 = { fields: ["id", "author"] }
  → 型定義された意図に対して、データアダプター側の汎用ビルダーがそれぞれ独立にSQLを組み立てる
```

意図の型に無いフィールドを機能側が要求すればコンパイルエラーになる。これにより:

- pageviewが新しいフィールドを必要としても、pageviewの意図だけを変更すればよく、search/profileのコードに触れない
- 3機能が同じ文字列を共有しなくなるので、1機能の変更が他の2機能に波及しなくなる
- 機能側が語彙を勝手に拡張・独自解釈する(「5つ目の重複実装」)リスクが構造的に塞がる。語彙の定義は1箇所にしかなく、機能側はそこから選ぶだけになる

## この処方で解決する部分・しない部分 [確立]

型定義は「形(shape)の整合性」を保証するが、「意味(業務ルール)が全消費者にとって正しいか」までは保証しない。例えば`hidden`フラグの判定ロジック自体の意味が変わったとき、型チェックはそれを検出できない。

ただし処方後は、この判定ロジックの実装自体がデータアダプター内の**1箇所**に凝縮されているため、失敗モードの性質が変わる。

| | 処方前 | 処方後 |
|---|---|---|
| リスクの所在 | 3箇所に散らばった呼び出し元のどれかが更新漏れ(**見えない**波及) | 1箇所(データアダプター実装)の変更が3機能にとって正しいか(**見える**単一の確認点) |
| 機械的な検知 | なし。`verify`も`tsc`も緑のまま | フィールドの過不足はコンパイルエラー。共有コードへの接触自体は`adapters/`という配置で可視 |
| 残るリスク | 気づかれずに壊れる | 気づいた上で、実際に正しいかは人間かAIがレビュー・テストする必要が残る |

**「隠れた地雷」から「見える単一の確認ポイント」への変換**——これは書き経路の戻り問題(v0.9.3)で`verify`が受け皿の存在を保証しつつ「往復そのものは追跡していない」と正直に書いたのと同じ、Spactaの誠実さの機械化の水準に、この穴も引き上げるということである。完全な解決だと主張しないことが、`spacta-genzaichi.md` §5判断基準2「潔癖症になりすぎない」に沿う。

## 未解決のまま残るもの

- 型定義された「意図」から実際のSQLを組み立てる汎用ビルダー(データアダプターの中身)自体の設計は未着手
- データアダプター内の実装変更が3機能すべてにとって振る舞い的に正しいかの検証(テスト)は、型システムの外側の話として別途必要
- `traces`テーブルの物理スキーマそのものが複数機能から参照されている事実は、どんなアダプターでも消せない。カラムのリネーム・型変更は結局「誰が読んでいるか全員把握している人」が要る
