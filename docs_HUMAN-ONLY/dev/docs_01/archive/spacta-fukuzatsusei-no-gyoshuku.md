# 複雑性の凝縮 — もぐら叩きを止める原理

対話(著者とAI)で命名した概念。**複雑性を1箇所に凝縮し、他の場所がそれに振り回されないようにする**という設計原理。Spactaが個別に解決してきた問題群に共通する、より上位の一般原則として取り出す。

確信度タグは `spacta-genzaichi.md` に合わせる。

---

## 定義 [確立]

> ある種類の複雑性・変化・多様性を、コードベース中の**1箇所(1ファイル、1つの型定義、1つの構築点)に集約**し、それ以外の場所はその1箇所を経由してのみ複雑性に触れるようにする。エラーが起きたとき、見るべき場所が1つで済む状態を作ること。

これにより2種類の「もぐら叩き」が同時に止まる。

1. **外側の変化への追随によるもぐら叩き。** フレームワークが新しい規約を追加するたびに、検査側がその規約を1つずつ後追いで足していく必要がなくなる。
2. **内側の再発明によるもぐら叩き。** 同じ意味のものを、機能やプロジェクトごとに独自に(しばしば少しずつ間違えて)再実装してしまう事故がなくなる。

`spacta-genzaichi.md` 自身の言葉を借りれば、これは **§6「コンテキスト隔離の機構」** の「このファイルだけ読めば分かる」を、Core内部だけでなく**Coreの外側(境界を横切る先)にも一般化したもの**である。

## すでに実測されている実例 [確立]

### 実例1: フレームワーク名の列挙をやめる(v0.9.4)

`spacta-genzaichi.md` §3。`layout.tsx` / `middleware.ts` と個別にファイル名を検査に足していく方式(=もぐら叩き)をやめ、`verify/platform/nextjs.mjs` が「名前 → 役割」の対応を1箇所に凝縮した。`CHECKS` は役割だけを語るようになり、Next.jsが新しい規約を追加しても、役割さえ引ければ即座に対応できる。**複雑性の凝縮がもぐら叩きを止めた、文書内で唯一実測済みの成功例。**

### 実例2: 書き経路の戻り(v0.9.3)

`spacta-genzaichi.md` §3「第5の膜語彙を作らなかった」。`Effect` の型定義は `shared/types.ts` の単一unionとして**大域的に1箇所に凝縮**されているが、実際に構築する場所(`core.ts`)は機能ごとに局所的。実測で「型は大域的でも構築は機能ごとだった。カスケードは起きなかった」と確認されている。**「語彙の定義を1箇所に凝縮し、使用は局所に任せる」というパターンがすでに機能した実例。**

この2つの実例から、複雑性の凝縮には少なくとも2つの実装形がある。

- **役割マッピング型**(実例1): 「名前 → 役割」の対応表を1箇所に持つ
- **語彙定義型**(実例2): 「意味のある型」を1箇所に持ち、構築は各所に散らす

## まだ手つかずで、凝縮が有効そうな候補 [仮説]

### 機構(mechanism)のライブラリ化 — 最も緊急性が高い

`spacta-genzaichi.md` §6「規律/機構/束縛の三分割」。`drain` / Effectキュー / correlationId / Actionログは、**すでに実害が出ている**。

> livingdocの`drain`はstarterに無かったので実装者が発明し、その発明版が結果を握りつぶしていた。ライブラリなら間違えられなかった。

これは「同じ意味のものをプロジェクトごとに再発明し、しばしば間違える」という複雑性の凝縮が防ぐべき事故そのものが**実際に起きた**ケース。`spacta-genzaichi.md` §9の優先順位表では4番目(v0.10以降)だが、実害の実例がある分、傍証としては最も強い。

### correlationIdのオプトイン問題

`spacta-genzaichi.md` §4「その他の未解決」。correlationIdを使わない機能は無保証・無警告。Effectを作る場所を1つの強制ファクトリ関数に凝縮すれば、「付け忘れ」というもぐらは構造的に発生しなくなる(`spacta-adapter-bunrui.md` の型定義ペアリングの話と直結)。

### データ経由の結合

`spacta-genzaichi.md` §4の最大の穴。詳細な処方は `spacta-data-ketsugo-taisaku.md` に分離した。

### 将来の他プラットフォームアダプター

`spacta-genzaichi.md` §7②で言及されている隣接市場(SwiftUI / Flutter / Compose)。まだ実装されていないが、実例1(`nextjs.mjs`)と同じ「名前 → 役割」パターンをテンプレート化しておけば、新プラットフォームが出るたびに一から作り直す未来のもぐら叩きを先回りできる。

## 対象外と判断したもの

縦の依存(`components`/`shell` → `shared/ui`、約30ファイル)は `spacta-genzaichi.md` §4で著者判断により「hope-promptでよい」とすでに見送られている。理屈上は凝縮が効きうるが、著者がすでに下した判断を蒸し返す場所ではない。
