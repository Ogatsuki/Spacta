## 1. この版の目的 — 1文で

> **Spacta の中心命題「アプリが大きくなっても、1機能を追加・変更するのに必要な参照範囲は増えない」が本当かどうかを、測れる状態にする。**

### これが何を意味するか

Spacta の他のあらゆる主張——コンテキスト隔離、複雑性の凝縮、AI との相性——は、すべてこの1つの命題に乗っている。そしてこの命題は **一度も測定されていない。** 検証台アプリ（livingdoc）は6機能で止まっており、6機能の時点のスナップショットしかない。**傾きが分からない。**

したがって v0.10 の作業は「機能を増やすこと」でも「穴を塞ぐこと」でもない。**測定を可能にすることである。**

### この目的が課す制約 — 最も重要な指示

> **測定のベースラインを壊す変更を入れてはならない。**

ファイルを移動・改名する種類のリファクタリング（例: `shared/source/` を `adapters/data/` に移す）は、**それ自体は正しくても、ファイル数と構成比の連続性を切断するため今回は禁止する。** 測定が終わってから行う。

§4 の変更が「4つだけ」に絞られているのはこの理由による。**やりたくなった改善は §5 の保留リストに追記して、実装しないこと。**

## 4. 今回入れる変更 — 4つだけ

### 変更① 機構をエンジンとして抽出する [決定]

**問題:** `shell.tsx` は4つの別物が1つの名前を着ている。

| | 中身 | 機能固有か | React 固有か | 行き先 |
|---|---|---|---|---|
| **A** | `drain` — Effect キュー、`runEffect` 呼び出し、結果→Action 変換、再投入 | **ゼロ** | **ゼロ** | **エンジン** |
| **B** | 非決定性の採取（`new Date()` / `crypto.randomUUID()`） | ゼロ | プラットフォーム固有 | **束縛アダプター** |
| **C** | `useState` / `setState` による状態保持と再描画起動 | ゼロ | **React そのもの** | **束縛アダプター** |
| **D** | JSX 配線（state を props へ、callback を dispatch へ） | **全部** | JSX | **機能に残る** |

**A には Next.js も React も1文字も入っていない。** `pageview/shell.tsx` の `drain` のコメントは著者自身がこう書いている——*"Mechanism, not judgement. (…) Do not add an `if` about traces, votes or reports to this function."* **編集されたくないと宣言されているコードである。**

判断基準は **「AI が編集すべきものは starter に、編集すべきでないものはライブラリに」**。A/B/C はこの基準でライブラリ側にある。

#### やること

`src/shared/spacta/` を新設し、A + B + C を移す。**D だけが `shell.tsx` に残る。**

推奨する構成（署名は実装者の裁量。**下の「不変条件」だけが必須**）:

```ts
// src/shared/spacta/runtime.ts — エンジン。フレームワーク非依存。
//   ここに React も Next.js も入れないこと。将来 SwiftUI / Compose に移植する単位である。

export type Update<S, A, E> = (state: S, action: A) => [S, E[]];

/** すべての機能の Action union に、この2つが含まれなければならない。 */
export type EffectOutcome =
  | { type: "EFFECT_SUCCEEDED"; ref: string; id?: string }
  | { type: "EFFECT_FAILED";    ref: string; message: string };

/** 直列化された Effect キュー。エンジンの本体。 */
export async function drain<S, A, E extends { ref?: string }>(...): Promise<void>;
```

```ts
// src/shared/spacta/react.ts — 束縛アダプター。React 固有。
//   Next.js / React の変化が着地する唯一の場所。ここ以外に React 固有の機構を書かない。

export function useSpacta<S, A, E>(opts: {
  init: () => S;
  update: Update<S, A, E>;
  perform: (effect: E) => Promise<{ id?: string } | null>;  // = runEffect
}): [S, (make: (mint: Mint) => A) => void];

export type Mint = { now: string; id: () => string };  // 非決定性の供給。L3 は不変
```

#### 不変条件 — これらは必須 [決定]

1. **`drain` の実装は1つだけ。** 機能側に Effect ループを書かない
2. **エンジンは結果を必ず Action に変換して dispatch する。捨てる経路が存在しない**
3. **各機能の `Action` union は `EffectOutcome` を含み、`core.ts` の switch は網羅的でなければならない**（`assertNever`）。これにより、**往復を処理し忘れると `tsc` が落ちる**
4. **同一機能インスタンスの `drain` は同時に走らない**（直列化）。§2.6 の lost-update を閉じる
5. **非決定性の採取はアダプター側で行い、`core.ts` は値として受け取る。** L3 は変更しない
6. **膜の語彙を5つ目に増やさないこと。** 膜を越えてよいのは `State` / `Action` / `Effect` / `InitData` の4つだけである。`EffectOutcome` は**膜語彙ではなく `Action` の一種**であり、`runEffect` の戻り値の型（`{ id?: string }`）は膜を越えない——アダプターがそれを `Action` に変換し、**越えるのは `Action` である。**「第5の膜語彙」という発想が出たら、それは圏を間違えている

#### 命名について [決定]

`correlationId` を `ref` に改名するかは実装者の裁量とする。ただし**どちらを選ぶにせよ、次の性質を満たすこと**——エンジンが outcome を**無条件に**dispatch し、識別子を持たない Effect（`NAVIGATE` 等）についても機能側が「何もしない」という case を**明示的に書く**ことになる形にする。現行の `correlationId` はオプトインで、付けない機能は無保証かつ無警告だった。**沈黙を、意図的な記述に変えることが目的である。**

#### なぜ「検査を足す」のではなく「機構を提供する」のか

`runEffect` の戻り値が Core に届いているかを AST で検査することは**しない**。理由:

- `await runEffect(e);` と書いて戻り値を捨てるのは **TypeScript として完全に合法**であり、AST からは「捨てた」と「元々受け取る必要がなかった（`NAVIGATE` 等）」が同じ構文に見える
- 区別するには `await` を跨いで値を追い、クロージャを抜け、`setState` まで追跡する**手続き間データフロー解析**が必要になる
- そして React / Next.js が新しい非同期イディオム（`useActionState`、`useOptimistic`、Server Actions、`startTransition`）を出すたびに、追跡ルールを1件ずつ足すことになる

> **これは、`verify` が v0.9.4 で捨てた「フレームワークの名前を列挙する設計」と完全に同型である。ランタイム側で同じ過ちを始めてはならない。**

**唯一の実装が正しければ、往復は検証する対象ではなくなる。** 検証問題を構築問題に置き換える。これが第1の脚（構造）で解くということである。

#### 今回やらないこと（この変更のスコープ境界）

- **`InitData` の受け渡しや Server Actions の輸送をエンジンに飲み込まない。** 読み経路は §3.2 の通り設計が未確定であり、`app/` はフレームワーク所有と決めた領域である
- **`shared/source/` を移動・改名しない**（§1 の制約）

#### 受け入れ条件

- `features/*/shell.tsx` に `runEffect` の直接呼び出しと `drain` 定義が1つも残っていない
- 3機能すべてが同じエンジンを通り、`materialrequest` / `moderation` も結果を Action として受け取る
- `pageview` の連続 dispatch で先発の結果が失われない（テストで示すこと）
- `verify` が緑、`tsc --noEmit` が0エラー

```jsonc
    { "symbol": "TraceRecord",       "file": "shared/types.ts",         "consumers": ["pageview","search","profile"] },
    { "symbol": "listTracesForPage", "file": "shared/source/queries.ts","consumers": ["app/m/[material]/[page]"] }
    // …consumers 数の降順
  ],

  // ④ 機能ごとの段位（変更③と同じ判定を使う）
  "tiers": { "pageview": "T3", "moderation": "T2", … }
}
```

> **実測メモ（v0.10 で `measure` を実装した結果 — 上の例の行は symbol 単位では誤りだった）。** `TraceRecord` の consumers は **`pageview` のみ**（4ファイル）で、`search` / `profile` が消費しているのは `TraceWithPage`（5ファイル）である。§2.4 の「読みモデル型 `TraceRecord` / `TraceWithPage` を3機能の9ファイルが消費」は**正しい**——ずれているのは「1つの symbol が3機能から読まれている」と読める上の例だけである。**`measure` をこの例に合わせて直さないこと。** また `TRACE_SELECT` は `queries.ts` のモジュール内 `const` であって export ではないため `spread` には原理的に現れない。`spread` が測るのは共有予算からの**流出**であり、共有予算の内部構造ではない。

**③ の `spread` は測定であると同時に道具である。** 共有シンボルを編集しようとするエージェントに「これは3機能から読まれている」と機械的に開示できる。ディレクトリの配置は「共有されている」ことしか伝えないが、この数字は**何箇所に散っているかを伝える。**

#### 受け入れ条件

- `npm run measure` が starter と livingdoc の両方で走る
- 出力が決定論的（同じコミットなら同じ JSON）
- **変更①〜④をすべて入れ終えた直後のベースラインを `metrics/baseline/` にコミットする**

### 変更③ 段位を verify が申告する [決定]

**問題:** Spacta は今、深い部分（Effect の往復）を採用しない機能に対して**嘘の緑を出す。** `materialrequest` と `moderation` は結果を捨てているが、`correlationId` を使っていないので L3 が発火せず緑になる（§2.5）。

部分的に採用したユーザーが受け取るのは「動いていない安心」である。**これは穴より悪い。** 誠実さの機械化を掲げる道具として、ここは矛盾している。

#### 段位の定義

| 段位 | 条件 | 何が保証されるか |
|---|---|---|
| **T0** | `page.tsx` → `components/` のみ。`core.ts` なし | L9 / L10 のみ |
| **T1** | + `core.ts`（純粋な状態機械）。`InitData` を受ける | + L2 / L3(inbound) |
| **T2** | + `shell.tsx`。Effect を宣言する | + L1 / L4 |
| **T3** | + 往復（Effect が `ref` を持ち、`core.ts` が `EFFECT_SUCCEEDED` / `EFFECT_FAILED` を処理する） | + L3(outbound) |

#### やること

`verify` が **機能ごとの段位を印字する。** 役割カバレッジ表と同じ場所・同じ形式でよい。

```
  Tiers: pageview T3, moderation T2, materialrequest T2, catalog T1, search T1, profile T1
    T2 features declare Effects but do not receive their results — the write-path
    round trip is NOT verified for them.
```

**赤にしないこと。** T1 や T2 は正当な状態である。往復を必要としない機能に往復を強制すると、判断基準2「潔癖症になりすぎない」に反し、かつ「無視リストに手を伸ばす訓練」を利用者にさせることになる。**口に出すのが解決であって、走るのを拒むことではない。**

#### なぜこれが今回必要か

1. **誤用への耐性がこの道具の最大の弱点である。** 途中まで採用したユーザーが嘘の緑を受け取る限り、この道具は信用されない
2. **測定の解釈に要る。** 機能を追加したとき、それが T1 で済んだのか T3 まで要ったのかは、**「新機能1つあたりのコスト」の中身そのもの**である
3. **入口が浅くなる。** T0/T1 だけを使いたい利用者が、往復機構を飲まずに入れる

#### 実装上の落とし穴 — 過去に踏んだもの [確立]

段位の判定は役割表と L3 の検査に触れる。**過去に一度ずつ踏んだ罠が2つあるので、繰り返さないこと。**

1. **役割表の catch-all は貪欲にしてはならない。** かつて `/^src\/.+\.tsx?$/` という catch-all を置いた結果、それが `src/app/page.tsx` を飲み込み、**塞いだばかりの穴をその一般解を書いている最中に再度開けた。** catch-all は必ず app router のルート群を除外すること。これは L6 の分類器自己テストが捕まえた

2. **「受け皿となる Action が存在すること」だけでは検査が空虚である。** Shell は識別子を**要求する側の Action**（`INCREMENT` 等）に既にそれを載せているので、受け皿の存在だけを見ると条件が満たされてしまう。**受け皿は「書き込みを要求する Action ではないもの」でなければならない。** 変更① でエンジンが outcome を dispatch する形にすれば構造的に満たされるが、L3 の検査を触る場合はこの性質を壊さないこと

#### 受け入れ条件

- starter と livingdoc の両方で段位が印字される
- §2.2 の表と一致する（pageview のみ T3、shell なし3機能が T1）
- 段位が理由で exit code が非ゼロにならない

### 変更④ `SPACTA.md` の最小改訂 [決定]

### 変更⑤ 定理のリプレイ照合を実装する [決定]

**変更① に依存する。① の完了後に着手すること。**

#### 問題

`verify` が検証しているのは **「掟が守られているか」** であって、**「掟が主張する性質が実際に成り立つか」** ではない。Spacta は次の定理を主張している。

> **verify が緑なら、機能 F のバグは (1) F の中に閉じ、(2) `(initData, actions[])` だけから再現でき、(3) 隠れた入力を持たない。**

**この定理は一度も検算されていない。そして既に反例が1つある**——§2.6 の非直列 `drain` により、Action ログをリプレイした最終状態とユーザーが実際に見た状態が一致しない。**(2) が偽である。**

Rust の借用チェッカが価値を持つのは、チェッカ自体ではなく **「この構造的性質が成り立つなら、このバグのクラス全体が不可能になる」という定理が証明されているから**である。Spacta の定理は主張されているだけであり、**この状態で「緑なら局所・再現可能」と書くことは、`verify` が捨てたはずの過大主張と同種である。**

#### やること

1. **エンジンが `initData` と Action の列を記録できるようにする。** 開発・テスト時のみ有効なオプトイン。本番経路では無効
2. **記録から状態を再導出して照合するハーネスを作る**
3. **livingdoc の主要シナリオで照合し、結果を記録する**

```
実走行:   init(initData) → 本番の経路で update を適用 → S_live
リプレイ: init(initData) → actions.reduce(update)      → S_replay

S_live ≠ S_replay ⟹ 定理が破れている。破れた地点が Action 単位で特定できる
```

#### 不正な実装の禁止 — これを守らないと照合が無意味になる

- **記録した `State` を読んで比較してはならない。** 記録するのは `initData` と Action の列**だけ**である。`State` を記録すると照合が自明に成功し、何も検証しない
- **リプレイは `init` と `update` だけを使って状態を再導出すること。** エンジンの内部状態やキャッシュを覗かない
- **照合は最終状態だけでなく、各 Action 適用後の中間状態でも行うこと。** 最終状態だけだと、途中で発散して偶然戻った場合を見逃す

#### 配置 — 測定ゾーンを汚さないこと

| 何を | どこに | 理由 |
|---|---|---|
| **記録機能** | `livingdoc/src/shared/spacta/`（エンジン内） | 機能数に対して **O(1)**。機能を増やしても1行も増えないこと |
| **照合ハーネス** | `/workspace/spacta/replay/`（ツール側） | livingdoc の測定ゾーンに入れない |
| **記録したセッション** | `livingdoc/replay-sessions/` | `src/` でも `app/` でもない。**変更② の `measure.mjs` はこのディレクトリを除外すること** |

**これを間違えると、測定の予測（`engine` ゾーンは O(1)）が実装の都合で壊れる。**

#### この検証が確かめられるもの・確かめられないもの

| 定理の項 | リプレイ照合で | 備考 |
|---|---|---|
| **(2) 再現性** | ✅ **直接検算できる** | これが主目的 |
| **(3) 隠れた入力の不在** | ✅ **検算できる** | `update` が時刻や乱数を隠れて読んでいれば、リプレイが発散する |
| **(1) 局所性** | ⚠️ **部分的** | 1機能のセッションを単独でリプレイして一致するなら傍証になる |
| **(4) 他機能への波及の不在** | ❌ **できない** | データ層の共有（§2.4）はプロセス内のログに現れない |

**「できない」を印字すること。** 照合が通ったときの出力に、**この表の (4) が未検証であること**を必ず含める。§6.4「穴を隠さない」の適用である。

#### 走らせるシナリオ

**「通るシナリオを1つ流して緑でした」では検証にならない。定理を壊しにいくシナリオを作ること。**

| # | シナリオ | 狙う項 | 期待 |
|---|---|---|---|
| S1 | 単純な直列操作（投稿 → 表示） | (2)(3) | 通るべき |
| S2 | **投票の連打**（同一対象へ高速に複数回） | (2) | 変更①前は失敗し、後は通るべき |
| S3 | **投票と投稿の重ね**（in-flight 中に別の dispatch） | (2) | **§2.6 の反例の直撃。変更①の検算** |
| S4 | **書き込みの失敗注入**（サーバが 500 を返す） | (2)(3) | 補償が Action 経由なら通る |
| S5 | **成功と失敗の混在**（3件中2件目だけ失敗） | (2) | 順序依存の補償が正しいか |
| S6 | 時刻をまたぐ操作（日付境界） | (3) | `update` が時計を隠れて読んでいれば発散 |
| S7 | 複数機能を同一セッションで操作 | (1) | 各機能を単独でリプレイして一致するか |
| S8 | **同じ Action 列を2回リプレイ** | (3) | 2回目が1回目と一致しなければ `update` が非決定的 |

**S2 / S3 は変更① の前後で両方走らせること。** 前で失敗し後で通ることが、直列化が効いた証拠になる。**前でも通ってしまうなら、シナリオが反例を再現できていないので作り直すこと。**

#### 照合ハーネス自身の自己テスト

L6 と同じ問題が1階層上で再発する——**「照合ハーネスが本当に発散を検出できるか」は誰も検証していない。**

`verify` の fixtures と同じ発想で、**既知の発散を意図的に埋めた記録**（例: Action 列の途中を1つ落としたもの、`update` に隠れた `Date.now()` を混ぜたもの）を用意し、**ハーネスが必ずそれを検出することを assert すること。** 検出できなければ、照合が緑でも意味がない。

#### 位置づけ — フライトレコーダーの再解釈

`HUMAN_GUIDE` §6.4 は Action ログからの決定的リプレイを「監査可能性」という**製品機能**として書いているが、**本来の第一用途は Spacta 自身の定理の検算である。** 監査可能性は副産物として付いてくる。**§6.4 の記述をこの順序に直すこと。**

またこれは、変更① の不変条件4（直列化）が正しく入ったかの検算そのものでもある。**直列化が入っていなければ、この照合は必ず失敗する。**

#### 受け入れ条件

- `initData` と Action 列だけが記録され、`State` は記録されていない
- リプレイが `init` + `update` だけから状態を再導出している
- 中間状態でも照合している
- livingdoc の `pageview` で、**投票と投稿を意図的に重ねたシナリオ**の照合が通る（§2.6 の反例が閉じたことの証明）
- 照合の出力に「(4) 他機能への波及は未検証」が印字される
- `livingdoc/replay-sessions/` が `measure.mjs` のゾーン集計から除外されている
- **照合が失敗した場合は、失敗したまま報告すること。** 定理を黙って弱めない（詳細は著者が別途管理する定理検証設計書に従う）

| **パス語彙が verify と measure で二重に存在する** | **v0.10 の変更② で残した重複。** `measure` は path→zone の表を、`verify` は path→role の表を別々に持ち、共有しているのは `APP_ROOTS` だけ（フレームワーク名の凝縮は §6.1 のため1箇所に保った）。本来はパス語彙を1モジュールが所有すべきだが、それは `verify/` の編集になるため測定完了後 |
| **`lines` が物理行数であること・差分モードの不在** | **v0.10 の変更② の設計判断（意図的）。** `lines` は `wc -l` 相当なので、コメント密度の違うファイル間では比較できない（例: engine の 292行は大半が自身の説明）。傾きの読み取りに定義を1つに保つことを優先した。また `measure --against <baseline>` のような比較モードは**意図的に作っていない**——比較は `metrics/baseline/*.json` の git diff で行う。組み込みの比較器は成績表への第一歩になる |

| **React で描画した実走行によるリプレイ照合** | **v0.10 の変更⑤ で残した限界。** 照合の `S_live` はエンジンと実 `core.ts` を直接駆動して作っており、React の batching・Suspense・再描画タイミングは通っていない（この限界は照合の出力に毎回印字される）。閉じるには Testing Library か実ブラウザ＝依存の追加が必要。同じ理由で `useSpacta` の `record` 受け渡しは React 経由で一度も通っていない |
| **同一機能の2インスタンスを競合させるシナリオ（より強い S3）** | **v0.10 の変更⑤ で判明した構造的事実。** エンジンは1機能インスタンスにつき常に1つの Effect しか飛ばさないため、単一機能のシナリオでは「答えの順序が入れ替わる」状況を作れない。逆順の着地は S7（3機能同時）でしか発現しない。同一機能を2つ立てて競合させる方が強い検査になるが、シナリオ設計が未確定 |

**作業中に「これも直したい」と思ったものは、実装せずにこの表に追記すること。**

### 5.1 モード概念の現在の扱い

「契約変更モード / 通常実装モード」という着想は、**2つの部分に分かれ、片方だけが今回に入っている。**

| 部分 | 何を保証するか | 階層 | 今回 |
|---|---|---|---|
| 共有契約の**消費者の存在**を開示する | 「pageview / search / profile がこの共有シンボルを使っている」という事実の一覧 | **機械的に保証可能** | **変更② の `spread` として実装する** |

| モードの**列挙と排他性**（どのモードが存在し、モード中は何を禁じるか） | — | 未確定 | **保留** |

## 6. やってはいけないこと — 美しさの基準 [決定]

著者が「美しい」と呼ぶものの定義。**方針に迷ったらここに戻る。**

### 6.1 もぐら叩きをしない

> **「Next.js にこういう機能があるから、これをこういう実装で潰す」を1件ずつ積み上げる設計は、どれだけ動いても採用しない。**

フレームワークが新機能を出すたびに追随が要る構造は、掘れば掘るほど修正箇所が出てくる。**名前を足すべき場所には概念を置く。**

具体的な禁止:
- `verify` に**フレームワークのファイル名を列挙しない**。名前 → 役割の対応は `verify/platform/nextjs.mjs` の1箇所だけが引き受け、`CHECKS` は役割だけを語る
- **Effect の往復を AST で追跡する検査を書かない**（§4-① の理由）
- React / Next.js の非同期イディオムごとに分岐を足さない。**React 固有の機構は `shared/spacta/react.ts` の1ファイルに閉じる**

### 6.2 潔癖症にならない

- **すべてを検査に落とす必要はない。** あらゆるファイルに意見を持とうとせず、知らないものは知らないと言う
- カバレッジ%を最大化する設計より、**検証器自身の無知を可視化する設計**を優先する
- `laws: []` は穴ではなく**宣言された弱さ**である。役割が引けたファイルは、掟が弱くてもその弱さを印字できる。**役割が引けないファイルだけが本当の穴である**
- `INCONCLUSIVE` は「これが何か分からない」にだけ使い、「専用の役割が無い」には使わない

### 6.3 開発者は AI である

- **人間が `verify` / `garden` を走らせる前提で設計しない**
- **「気づける」を人間の注意力に依存させる設計はすべて無効。** 構造か、コンパイラか、印字のどれかで表現されていなければ存在しないのと同じである。レビュー時の注意喚起やコメントは成果として数えない
- **赤と exit 2 は、それを受け取ったエージェントが自分のタスクの中で解消できなければならない。** 解消できない非ゼロ終了は、ループか回避策の捏造を招く

### 6.4 穴を隠さない

- **穴があること自体は許される。穴を隠すことは許されない**
- `verify` は毎回「この緑が保証すること / しないこと」を印字する。この性質を減らす変更をしない
- 0ファイルの検査を「Guaranteed」に載せない
- 未知の rule を黙って落とさない（`garden` の `kind:"unknown"`）

### 6.5 検証器自身が検査対象である [確立]

`verify` に手を入れるとき（変更③）、**検査が「何かに向いていること」を必ず証明すること。**

過去にこれを怠って踏んだ穴: L6 の自己テストは checker **関数**にテキストを直接渡していたため、`CHECKS` の glob（`root` / `match`）を**一度も通らなかった。glob を書き間違えて0ファイル走査になっても、自己テストは緑・本スキャンも緑**という状態が成立していた。

現在は3層で塞がれている。**新しい検査や役割を足したら、3つとも維持すること。**

| 層 | 何を保証するか |
|---|---|
| **L6 自己テスト** | 参照コーパスに埋めた既知の違反を、検証器が必ず拒否する |
| **L6 wiring テスト** | 各 glob が参照コーパスに対して **1件以上**選ぶ（判定は `> 0`。調整された閾値ではない） |
| **role-claim テスト** | 役割表が「この役割は L5 が統治する」と主張するなら、**実際に L5 がそのファイルを走査している**ことを実走査で検算する |

3つ目は実際に穴を見つけた実績がある——役割で語らせた瞬間、`layout.tsx` は表では L5 が統治すると称しているのに**実際の L5 は走査していない**ことが露見した。

**また、走査したファイル数が0件の検査を「Guaranteed」に載せないこと。** 0件は緑ではなく `NOT verified in this project (0 files matched)` として、走査した root 付きで印字する。**赤にはしない**——`app/` や `components/` がまだ無いプロジェクトは正当であり、fatal にすると正直な状態が表現不能になる。

### 6.6 既存仕様に縛られない

検証過程のブランチでは柔軟に方針を変えてよい。**ただし §5 の保留リストは今回の測定を守るための制約であり、これには従うこと。**

### 順序

1. 変更① 機構の抽出 → `verify` 緑 / `tsc` 0エラー / 直列化のテスト
2. **変更⑤ リプレイ照合**（① に依存。ここで直列化が本当に入ったかが検算される）

**変更② を最後に置く理由:** ①③⑤ でゾーン構成（`shared/spacta/` の新設、`replay-sessions/` の除外）が変わるため。**ベースラインは全変更を入れ終えた状態で取る。**

**⑤ の照合が失敗したまま先へ進んでよい。** ただし失敗を隠さず、どのシナリオでどう発散したかを報告に含めること。**定理が偽であることが分かるのは、この版の成果である。**

### `docs/spacta-sokutei-sekkei.md` を開いてはいけない理由

測定設計書には、**この後に追加される機能を評価する基準と、事前に登録された予測**が書かれている。

実装するエージェントがその基準を知っていると、意識的でなくとも基準に有利な設計を選んでしまう（測定される側が測定基準を知ると、測ろうとしていたものではなく基準そのものを最適化してしまう）。**この文書に書かれた設計判断は、測定基準ではなく §6 の美しさの基準だけを根拠に下されなければならない。**

同じ理由で、**この後に機能を追加するエージェントにも測定設計書を渡さない。** 著者が別途管理する。

## 8. 用語 — この文書で使う言葉の定義

前版までの文書で命名された概念のうち、本文書で使うものだけを定義する。**由来を辿る必要はない。**

### 複雑性の凝縮

> ある種類の複雑性・変化・多様性を、コードベース中の**1箇所**（1ファイル、1つの型定義、1つの構築点）に集約し、それ以外の場所はその1箇所を経由してのみ複雑性に触れるようにする。**エラーが起きたとき、見るべき場所が1つで済む状態を作ること。**

止まるもぐら叩きは2種類。**外側の変化への追随**（フレームワークが規約を足すたびに検査側が後追いする）と、**内側の再発明**（同じ意味のものを機能・プロジェクトごとに、しばしば少しずつ間違えて再実装する）。§2.5 の3つの `drain` は後者の実例である。

実装形は3つ:

| 形 | 何を1箇所に置くか | 実例 |
|---|---|---|
| 役割マッピング型 | 「名前 → 役割」の対応表 | `verify/platform/nextjs.mjs` |
| 語彙定義型 | 「意味のある型」。構築は各所に散らしてよい | `shared/types.ts` の `Effect` union |
| 目と手の分離型 | 「検知」を1箇所に置き、他は変換・実行だけ | `verify` → `garden`。今回 `measure` を足す |

**凝縮の目的は「人間が把握できる量に減らすこと」ではなく「1エージェントの1コンテキストに収まる量に減らすこと」である。**

### アダプター（傘概念）

Spacta の外側にあって、Spacta の語彙に翻訳する層。2種ある。

| | 何を吸収するか | 具体例 |
|---|---|---|
| **束縛アダプター** | フレームワークへの配線 | `verify/platform/nextjs.mjs`、**変更① の `shared/spacta/react.ts`** |
| **データアダプター** | データ取得・永続化 | `shared/source/queries.ts` |

**重要な非対称性:** ライブラリは**能力**を提供するので隠せる。Spacta が提供するのは**制約**であり、制約の価値は「あなたが書くコードに適用されること」から来る。

> **アダプタは Next.js を Spacta から隠せる。Spacta を Next.js から隠すことはできない。**

### コンテキスト隔離の機構 — どの掟が本体か [確立]

**これは変更① の設計を左右するので、誤解しないこと。**

> **import の隔離は必要条件であり、かつ最も簡単な部分である。**

| | 止めるもの | 難易度 |
|---|---|---|
| **L1 / L7** | **見える結合**（import グラフの静的な辺） | 簡単。ESLint でも8割できる |
| **L2 / L3 / L9 / L10 + 4語彙** | **見えない結合**（共有可変状態、環境からの暗黙読み取り、末端からの IO） | **難しい。ここが Spacta の実質** |

本丸は **L2**。`(state, action) => [state, effects]` が純粋なら、機能の全挙動が自分の引数だけの関数になり、「このファイルだけ読めば分かる」が真になる。**L10 は「状態がどこにあるか探す」作業を消し、L9 は葉から伸びる隠れた IO の辺を消す。**

**帰結:** 変更① で状態保持をエンジンへ移すことは、L10 の精神（状態の在処を1箇所にする）を `shell.tsx` にまで拡張する作業である。**「import さえ切れていればよい」という設計判断をしないこと。**

**そしてデータ経由の結合は、この表に載っていない第3の列である**——import の辺でもなく、プロセス内の共有可変状態でもなく、**同じテーブルを読んでいるという事実**による結合。だから L1〜L10 のどれにも引っかからない（§2.4）。

### 規律 / 機構 / アダプター — ライブラリ化の可否 [確立]

**変更① の根拠となる分類。** Spacta の中身は3種類に分かれ、**ライブラリにできるのは1つだけである。**

| | 中身 | ライブラリ化 |
|---|---|---|
| **規律** | L1 / L2 / L7 / L9 / L10、膜語彙 | ❌ **検証器でしか届かない。** ライブラリの向こうに隠せない |
| **機構** | `drain` / Effect キュー / 識別子 / **Action ログ** | ✅ **可能。しかもすべき**（§2.5 に実害の実例） |
| **アダプター** | 束縛（React 配線・`app/` の解釈）+ データ（取得・永続化） | ✅ これが本当のアダプタ |

**判断基準は「AI が編集すべきものは starter に、編集すべきでないものはライブラリに」。** 代償は「Spacta が書き方から依存先に変わる」ことであり、これは避けられない。

副次的な効果が3つある——並行制御が一度だけ正しく解ければ済む、**フライトレコーダーがタダで手に入る**（エンジンが全 Action を見るため）、starter が薄くなる。

### 名前は説明ではなく、探索範囲の指定である [確立]

**この文書で最も繰り返し効いている教訓。**

前版は `queries.ts` の層を `edge` という独自の圏として置いていた。その瞬間、束縛アダプター側で既に解けている前例（役割による凝縮、型付き `Action`、L6 自己テスト、role-claim テスト）が**見えなくなった。**「安価な検査が見つかっていない」と書いていたのは、圏を分けていたせいで前例が見えなかったからである。**アダプターという傘に入れ直すだけで、処方が既存パターンの移植に変わった。**

同じ罠を §3.2 でも踏んでいる——「書き経路の実測が読み経路に移植できる」という誤りは、**両者を同じ名前（凝縮）で呼んだせいで、性質の違い（構築の共有 vs 消費の共有）が見えなくなった**ことによる。

> **名前を付けるときは、それが何を説明するかではなく、それが次にどこを探させるかを考えること。**

### 共有予算（非隔離ゾーン）

`src/shared/**`。L1 の隔離が及ばない層。ここが機能数とともにどう育つかが §1 の命題そのものである。

**構造的な注意 [確立]:** L7 により `shared/runEffect.ts` は機能側の型を import できない。したがって単一ディスパッチ地点を保つ限り、`Effect` union は全機能で共有される1ファイルに集まる。「機能 A に Effect を1つ足す」操作が、機能 B の依存先の編集になる。**これは L1 の隔離が原理的に届かない、Law 同士の相互作用による結合である。** §1 の命題に対する既知の反例候補であり、変更② の `effectUnion` はこれを追跡するために測る。

### 散らばり

「1つの複雑性が何箇所に散っているか」。カバレッジ% の代替指標。

カバレッジ% は分母が「全ファイル」なので、意見を持つ必要のないファイルにまで意見を持たせる圧力を生む（＝§6.2 に反する）。**散らばりの数は分母を持たず、ゼロにはできないが数えられ、減らすべき対象を名指しできる。** 変更② の `spread` がこれである。

### 二本脚モデル

- **第1の脚（構造）** `SPACTA.md` + starter + 4語彙 + **エンジン**。これが AI 開発を成立させている部分
- **第2の脚（検証）** `verify` + `garden` + `measure`。構造が破れていないことの証明と、破れの回収

**検証器は商品ではない。構造が商品で、検証器はその保証である。** 帰結として「Spacta in X」は検証器ゼロで出荷できる。**変更① は第1の脚だけで往復問題を閉じる——検証器を1行も必要としない。**

### 名前の所有権

「フレームワーク非依存 vs 依存」は雑な切り方。規則の文言はタダで、価値は施行にあり、施行は必ず実ファイルを見る。実務的に効く線は **「その名前を所有しているのは誰か」**。

| Spacta 所有 | フレームワーク所有 |
|---|---|
| `core.ts` / `shell.tsx` / `features/` / `shared/` | `app/` / `page.tsx` / `layout.tsx` / `middleware.ts` |
| 誰にも動かされない | リリースで動く。追随が要る |

実測: livingdoc 81ファイル中 `app/` は17（21%）。**残り8割は Spacta が名前を所有する内側。** アダプタが小さく済む根拠。

### sink / source — 逃がし口の判定基準

> **外に置いてよいのは Spacta の状態から「受け取る」もの（sink）だけ。状態に「書ける」もの、Core に値を注入できるもの（source）は外に置けない。**

**輸送は外でよい、判断は出せない。** データアダプターは定義上 source（Core に値を注入する）なので、「外」ではなく Spacta の管轄内に置かれなければならない。

### err と info の選別基準

**「重要か」ではなく「失敗が沈黙するか」。** L2 が err なのは重要だからではなく、失敗が沈黙するから（テストも tsc も画面も通る）。

そして受け手は人間ではないので:

> **err = 誰も回収しない失敗。info = `garden` が回収する失敗。**

L8（色の直書き）が info でよいのは「人間が画面を見れば気づくから」ではない（**AI は画面を見ない**）。`garden` が verify の info/warn を AI が消化できる指示書に変換して回収するからである。

## 10. 判断基準 — 迷ったらここに戻る [決定]

1. **小手先の解決でないこと。** 名前を足すべき場所に概念を置く
2. **潔癖症になりすぎないこと。** すべてを検査に落とす必要はない。知らないものは知らないと言う
3. **美しいこと。** 検証器自身の無知を可視化する設計を、カバレッジを最大化する設計より優先する
4. **既存仕様に縛られない。** 検証過程のブランチでは柔軟に方針を変えてよい
5. **AI が開発者である。** 人間の目・注意力・レビューを当てにした設計をしない
6. **vibe coder にとって最重要はアプリの質、次にコスト。** 出力トークンの1.5倍はノイズ
7. **予算は行数ではなく「1タスクで参照しなければならない箇所の数」である。** `SPACTA.md` が67行でも90行でも、AI が1タスクで開くファイル数が変わらないなら支出はゼロに近い。逆に、幹を1行も増やさずに508行の共有ファイルを触らせ続けることは、毎タスク508行の支出である

### 補足1: 複雑性には2つの軸がある [確立]

予算を「参照箇所の数」に置き換えたとき、**もう1つの次元が残る。**

- **振る舞いの複雑性** — 分岐・副作用・データ形状の推論。**膜はこの軸を切り離すために存在する**
- **分量の複雑性** — JSX の行数、CSS のバリエーション、アニメーションの状態数、レスポンシブの分岐。**state / API を追い出しても、この軸は一切減らない**

「UI 層が純粋（振る舞いが単純）」と「UI 層が小さい（分量が少ない）」は別の主張であり、前者が成り立っても後者は自動的には成り立たない。**同じ「1箇所」であっても、その箇所自体の生の分量は別の予算次元であり、凝縮（参照箇所を減らす原理）ではこの軸は縮まらない。**

緩和は `SPACTA.md` §2「Layouts Go Up, Components Go In」が既に担っている——共通の枠は `app/layout.tsx` / `shared/ui/*` へ上がり、feature 固有 UI は `features/<name>/components/` に留まり、**重複は結合より推奨される。この分割ルールを弱める変更をしないこと。**

### 補足2: 循環する論法に注意 [確立]

> 「AI は隔離のおかげで小さい範囲しか見ないから、その推論を信じてよい」——**この論法は、その隔離を作っているのが L1 / L7 / L2 なので循環する。**

したがって、この論法を根拠に**隔離を作っている掟（L1 / L2 / L7）を緩めてはならない。** 緩和を検討してよいのは、隔離を**消費**している掟（L8 / L9 / L10）だけである。

### 補足3: 保証の階段のどこにいるか [確立]

ソフトウェアの保証には階段がある: **構文的な境界検査（リント）→ 静的解析 → property-based testing → モデル検査 → 形式的証明**。

**`verify` は一番下の段（構文的境界検査）にいる。** これは恥ずかしいことではなく、コストが最も低く AI のループに組み込みやすい段だからこそ選んでいる。**ただし自分がどの段にいるかの自覚は持つこと。**「verify が緑」を上の段の保証であるかのように書かないこと。

上の段への道は構造的に開いている——`core` が純粋なステートマシンであることは、property-based testing やモデル検査の入力に**そのまま使える**ことを意味する。
