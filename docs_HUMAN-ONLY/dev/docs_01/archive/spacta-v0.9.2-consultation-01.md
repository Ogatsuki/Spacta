## 3. Q1 【最重要】書き経路の戻りをどう定めるか

### 3.1 症例 — livingdoc で実際に起きていること

`verify` 緑・`tsc` 0エラー・E2E 通過のまま、以下が成立している。

```
shell.tsx:69   tempId: `temp_${crypto.randomUUID()}`     ← 仮ID を縁で採番 (ここは L3 に忠実)
core.ts:244    id: action.tempId                          ← state に楽観挿入
runEffect.ts   SAVE_TRACE → POST /api/traces              ← 本ID はサーバが採番
               ...戻り経路が存在しない
core.ts:318    TOGGLE_VOTE → Effect{ targetId: "temp_…" } ← 仮ID がそのままサーバへ飛ぶ
core.ts:388    case "FAILED": return [{...state, notice: action.message}, []]
                                                          ← 補償なし。失敗した投稿が画面に残る
shell.tsx:26   drain: 失敗しても次の effect へ進む
```

実害: 投稿直後の trace への投票・コメント・通報がすべて失敗する。失敗時は存在しない trace が残る。
**3つのゲート (verify / tsc / E2E) が同一の一点で同時に盲目になっている。**

### 3.2 なぜこれが「バグ1件」ではないのか

`SPACTA.md` の L3 は既に「サーバ採番 ID も含めて非決定性は値として注入せよ」と書いており、**この症状は L3 違反である。** にもかかわらず検出されない理由は、L3 が自前の走査を持たず、施行が L2 (core.ts しか見ない) に委ねられているためで、**「Core が生成しないこと」の半分だけが施行され、「外から入るものが Action を通ること」の半分が空いている。**

さらに重要な含意: `HUMAN_GUIDE` §6.4 のフライトレコーダー構想 (Action ログだけで決定的リプレイ) は、**IO の結果も Action として膜を通ることが前提**である。この穴がある限り §6.4 は実装不可能な構想であり、同ガイド §8.2 が挙げるエージェント版 Spacta の価値提案 (実行の全リプレイ可能性) も根拠をここに置いている。**Q1 は成長経路そのものの前提条件である。**

### 3.3 既存の設計案 (04 §3.5) — 再設計は求めていない

**必ず `spacta-v0.9.1-edit-plan-04.md` の §3.5 (436〜588行) を全文読んでほしい。** 要点のみ:

- `shared/types.ts` に `EffectResult = { id?: string }` を置き、戻りを持つ Effect は `correlationId` を必須にする
- `runEffect` は成功時に `EffectResult | null` を返し、失敗時は throw する
- feature の `Action` union に `EFFECT_SUCCEEDED` / `EFFECT_FAILED` を足す
- **要点**: `core.ts` の `update` は既に `default` に `never` 終端を持つので、**この2メンバーを union に足した時点で tsc が両方の処理を強制する。verify に検査を足す必要がない。新しい掟ゼロで prevent-strong が得られる**
- `shell.tsx` の `drain` をキュー方式にし、戻りの Action が生んだ Effect も取りこぼさない

この設計は4文書 (report-00 / review-01 / reply-02 / 04) が同じ結論に収束したものである。**あなたに求めるのは、以下の未決点の裁断である。**

### Q1-a. 膜語彙を5つ目に増やすか

現在の膜語彙は `State` / `Action` / `Effect` / `InitData` の4つ。04 §3.5 の設計は `EffectResult` を **`shared/types.ts` の一型として**置き、正式な膜語彙には昇格させていない。04 自身の判断根拠 (784行付近):

> **第5の膜語彙 (`Outcome` 等) の正式化**: 「語彙は検査可能性を生む」に同意するが、**検査器なしで語彙だけ増やすと hope が1つ増える**。§3.5 の設計は tsc に施行させることで、語彙を増やさずに prevent-strong を得ている。正式な膜語彙への昇格は、検査器の目処が立ってから

一方 reply-02 は「第5の語彙を増やすことに賛成」と表明済みで、**ここが割れている唯一の点**である。

- **案A (04)**: 語彙は4つのまま。`EffectResult` は実装上の型にとどめ、施行は tsc に任せる。`SPACTA.md` への追加は L3 の施行欄1行の修正のみ
- **案B (reply-02)**: `Outcome` (仮) を第5の膜語彙として `SPACTA.md` §2 の「Discriminated Unions」に明記する。`types.ts` に置くべき語彙が5つになる

**判断してほしい。** 併せて、案Bを採る場合に **検査器なしで語彙を増やすことが hope を1つ増やす行為にならない理由**を示してほしい (Spacta が自分で名指しした失敗モードなので)。

### Q1-b. `drain` の判断を shell に残すか、core へ移すか

これは**04 が扱っていない、今回の分析で見えた論点**である。

04 §3.5 の `drain` は shell に置かれ、そこには **エラー方針 (throw を Action に変換する)・順序方針 (キュー FIFO)・継続方針 (失敗しても続行するか)** が入る。これは `SPACTA.md` §2 の

> Move all pure judgments (save triggers, status transitions, threshold checks) from `shell.tsx` into pure functions in `core.ts`.

に触れる。しかも `verify` の `NOT guaranteed` は "Judgement kept out of shell.tsx → not checked" と印字しており、**この穴に新しい判断を意図的に置く**ことになる。

- **案A**: 残す。`drain` は「Effect を Action に変換する配線」であって判断ではない、と位置づける。starter は薄いままで済む
- **案B**: 方針を core に持たせる。例えば `update` が `EFFECT_FAILED` を受けたときに返す `Effect[]` でリトライを表現し、shell はキューを回すだけにする。純粋層が厚くなるが、リプレイ可能性 (§6.4) は完全になる

**§6.4 を成長経路の中心に掲げる以上、案B が筋に見える。だがそれは starter を重くする。** 裁断を求める。

### Q1-c. 並行制御を starter に載せるか

04 §3.5 (577行) が自分で「塞がらないもの」として挙げた点。`drain` は開始時の state を起点にするので、`await` 中の別操作と競合する。04 の推奨 (806行):

> **私の推奨: 載せない。コメントで制約を明示し、`HUMAN_GUIDE` の「潰せていないもの」に1行足す。** starter は正しさの見本であって完成品ではない、という位置づけを保つため

**この推奨に同意するかどうかだけ答えればよい。** ただし注意: livingdoc の現行 `shell.tsx:36-40` の `dispatch` は既に**レンダー時クロージャの `state`** を読んでおり、同一 tick 内の連続 dispatch を落としうる。「starter が見本にとどまる」判断は、この種の欠陥が写されることを許容する判断でもある。

### Q1-d. 戻り経路を verify で走査可能にするか。それは L3 の拡張か、新しい掟 (L11) か

04 は「戻りが Action を通っているかを AST で判定する安価な方法が無い」として、v0.9.1 では **hope に留まることを宣言する** (= `NOT guaranteed` に明記する) 方針を採った。これは既に実装済みで、`verify` は毎回こう印字している。

```
  NOT guaranteed by this green:
    - Effect results travelling back into Core            → not checked
```

しかし安価な部分検査は考えうる。例えば:

- `runEffect` の戻り型が `Promise<void>` のとき info を出す (= 戻りを捨てる設計であることを表示する)
- feature の `Action` union に `EFFECT_FAILED` 相当のメンバーが無いのに、その feature の `Effect` が `correlationId` を持つ場合に err

**これらは「宣言に走査を追いつかせる」の型に乗るか、それとも命名規約への依存 (= 脆い hope) か。** 判断を求める。**「今回は入れない」も正当な答え**だが、その場合 §6.4 が hope の上に立ち続けることを `HUMAN_GUIDE` にどう書くかまで示してほしい。

## 5. Q3. shell に溜まる判断を掟にするか (L11?)

`verify` の `NOT guaranteed` の2行目:

```
    - Judgement kept out of shell.tsx  → not checked (L10 covers components, not shells)
```

現状の穴の実例が Q1-b の `drain` である。L10 (Component Statelessness) は `features/*/components/*` しか見ておらず、`shell.tsx` は対象外。

- **案A**: 掟にしない。「判断が shell に溜まっていないこと」は AST で判定できない (何が判断かを構文で決められない) ので、`NOT guaranteed` に留める。**現状維持**
- **案B**: 安価な代理指標で掟にする。例: `shell.tsx` の行数、`if`/三項演算子の数、`shell.tsx` 内の `switch` 禁止 (L4 は既に effect switch を見ている)
- **案C**: L10 の走査範囲を `shell.tsx` へ拡張する。ただし shell は `useState`/`useReducer` を正当に持つので、禁止集合を変えねばならず「L10 は一様・例外なし」という現在の美点を壊す

**注意**: 05 §4.1 は L10 の成長経路として「C1 (`setState` は core 由来に限る) を L10 の走査範囲拡張として自然に収める」ことを想定している。案C を採るならその成長経路との整合を示してほしい。

**私の見立ては案A (現状維持) だが、Q1-b で案B (方針を core へ) を採るなら、案Aのままでも実質的に穴は小さくなる。** この連動を踏まえて裁断してほしい。

## 7. Q5 【小】`verify/README.md` の表を生成物にするか

本セッションで表を実装に手で同期させた (§2.2)。だが**手書きの表はそれ自体が hope である** (alpha-evaluation の指摘) — 実際、v0.9.1 で L4 の走査根と L9/L10 を追加した際、この表は放置されて実装と乖離した。

**実装の抜け道 (要修正):** `verify.mjs:1252-1255`、コーパスが無いとき `runWiringTest()` が `null` を返し、**SKIPPED を印字して処理が続行し、そのまま Green で終われる。** コメントは「呼び出し側が skip を必ず申告する (黙って通すのが穴そのもの)」と正しく書いているが、**申告が info であれば実質的に案B と同じ抜け道**である — `starter/` を消せば配線テストは消える。v0.9.1 で確立した「空スキャン → `INCONCLUSIVE` (exit 2)」の処方をここにも一貫適用する。1行の修正で、Q7 で最も価値のある変更。
**赤のメッセージ:** 現状は0件の check を列挙するだけで、案A の運用方針が利用者に届いていない。「Form をカスタマイズしたなら `starter/` も同じ Form に更新せよ」を赤の本文に含める。

## 10.1 実装順序

**Q1-a を先に固定する。** 依頼書は Q1-a と Q1-b が相互依存すると見ているが、**依存は一方向**である — Q1-b で判断がどこに住もうと、その判断は `State` と `Effect` で表現されるので新語彙を要求しない。逆に第5の語彙を作ると、それがどこに住むかが Q1-b を拘束する。語彙を先に閉じるのが正しい。

| # | 作業 | 依存 |
|---|---|---|
| 1 | **Q1-a 確定** (語彙4つのまま。文書上の宣言のみ) | — |
| 2 | **Q1-b 確定** (drain の形。04 §3.5 のコードを採用) | 1 |

## 11.1 【記録】文書の正しい導線は README ハブ型である

**著者による補足。** 本来の設計意図は次のとおり。

```
ルート README.md  ←── AI も人間もここだけを参照する唯一の入口
  ├─ SPACTA.md               (AI 用の幹)
  ├─ docs_HUMAN-ONLY/ja/…    (人間用・日本語)
  └─ docs_HUMAN-ONLY/en/…    (人間用・英語) ← 現在存在しない
```

**現状は AI が `SPACTA.md` しか読まないため、人間用文書との間に認識の乖離が生じている。** これは Q6 の位置づけを変える — 英語版は「末端の付録」ではなく**入口の片翼**である。ただし **v0.9.2 の主眼は文書生成ではなく Spacta の実装修正**であるため、この整理は後続タスクとする。§10 の Q6 裁断 (`OVERVIEW.md` を対応関係なしの独立文書として置く) はこのハブ型と矛盾しないので、そのまま有効。

## 11.2 【要検討】Next.js への押し込みと「もぐらたたき」の懸念

**著者から提起された、v0.9.2 より上位の設計懸念。** 要旨: Spacta は FCIS の形に Next.js を無理やり押し込めており、対応が対症療法の連続になっていないか。美しい解決は、Next.js の将来の発展や新機能と衝突しないベクトルから検証可能性を持ち込むことではないか。

これは v0.9.2 の範囲を超えるが、**§10 の裁断を無効化しないこと**を先に述べておく (Q1 の Law 部分「IO の結果は Action として膜を通る」はフレームワーク非依存であり、Next.js が何を出そうと成立する)。詳細な分析と提案は別文書に分ける。要点のみ:

- **掟は2種類に分かれる。** L1/L2/L4/L7/L9 は**フレームワーク非依存** (モジュールグラフと純粋性の話で、規則としては Remix でも Rails でも CLI でも成立する。ただし施行コストは言語ごとに発生し、L10 は React 固有で機構としては移植できない — §11.3)。一方 **L5 と `shell.tsx`/`runEffect` の Form は Next.js のファイル名と実行モデルに直結している。もぐらたたきの表面はここに局在している。**
- **証拠は CHANGELOG にある。** L5 が `page` → `page|route` に広がり、L4 の glob が広がったのは、まさに Next.js の規約を追いかけた動きである。**著者の直感は正しく、既に一度起きている。**
- **構造的な処方: 「フレームワークのファイル名を列挙する」のをやめ、「役割で分類する」に変える。** `CHECKS` から Next.js アダプタ (`join(r,"app")` / `/(page|route)\.tsx?$/`) を分離し、掟は役割 (Source / Shell / Core / Component / SharedUI) だけを語る。Next.js が新規約を出したらアダプタ1ファイルの更新で済み、掟は動かない。
- **最も価値の高い単発の変更:** 現状、**Spacta が知らない Next.js のファイル規約 (`default.tsx` / `error.tsx` / `template.tsx` / `middleware.ts` 等) はどの glob にも掛からず、黙って未走査のまま緑になる。** これは「空スキャン Green」のフレームワーク版であり、*将来の Next.js 機能が静かに検証を逃れる経路そのもの*である。処方は同じ: `app/` 配下を列挙して各ファイルを役割に分類し、**未分類が1つでもあれば `INCONCLUSIVE`**。「Next.js が進化して Spacta が気づかなかった」を静かな穴から大きな音に変える。
- **書き経路については、フレームワークと競合せず、その上で膜を定義する。** 不変条件は「Core に入る値はすべて Action / IO はすべて Core が宣言する」であって、それを実行するのが `runEffect` か Server Action か `useOptimistic` かは **Form の問題**である。§10 の Q1 は Form (`drain`) と Law (戻りは Action を通る) を同時に決めているので、**`SPACTA.md` には Law をフレームワーク中立な言葉で書き、`drain` は starter 側で Form (可変) と明示的にラベルする。** そうすれば Server Actions が成熟したとき `drain` の差し替えが掟に触れない。
