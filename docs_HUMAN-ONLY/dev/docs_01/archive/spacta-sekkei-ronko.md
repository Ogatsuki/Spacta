## コンテキスト隔離の機構 [確立]

**Spacta のコンテキスト隔離を成立させているのは import の隔離ではない。** import の隔離は必要条件であり、かつ**最も簡単な部分**である。

著者の証言（この認識の由来）:

> 私はスパクターを開発する上で一番最初にインポート、エクスポートの分離、隔離を実現したが、これは極めて簡単だった。何が難しかったというと、状態管理など、そういった含むものをちゃんと隔離すること。

切り分けると:

| | 止めるもの | 難易度 |
|---|---|---|
| **L1 / L7** | **見える結合** — import グラフ上の静的な辺 | 簡単。ESLint の `no-restricted-imports` でも8割方できる |
| **L2 / L3 / L9 / L10 + 4語彙** | **見えない結合** — 共有可変状態、環境からの暗黙読み取り、末端からの IO、参照経由の変異 | 難しい。**ここが Spacta の実質** |

import グラフは静的結合しか捉えない。「他を読まずに実装できるか」を壊すのは大半が動的結合である — グローバルストアがあれば A の書き込みが B の読みに届き、A と B が同じ API を叩けば payload の変更が伝播し、コンポーネントが Context を読めば挙動がツリー全体に依存する。**import をゼロにしてもこれらは1つも消えない。**

実際に隔離を成立させている機構:

- **L2（core 純粋）— 本丸。** `(state, action) => [state, effects]` が純粋なら、機能の全挙動が自分の引数だけの関数になる。環境からの読み取りがゼロなので「このファイルだけ読めば分かる」が真になる
- **L10（コンポーネント無状態）** — 状態が1箇所しかないので、「状態がどこにあるか」を探す作業自体が消える
- **L9** — 末端が fetch しないので、葉から伸びる隠れた IO の辺がない
- **L3 + `InitData` / `Effect`** — 機能が世界から受け取るものと世界へ出すものが、**型として列挙可能**になる

### 認識を変えた要因（次のAIが同じ誤りに戻らないために）

**AI (Opus 5) は当初「L1/L7 がコンテキスト隔離を作っている」と述べ、さらに「L1/L7 は最も移植しやすいので、中核価値と移植容易性が一致している。良い偶然だ」と主張した。これは誤りである。** 著者の実装経験による指摘で撤回された。

**誤りの出どころも特定されている。** `HUMAN_GUIDE_tactical_20260725-modify.md` §0-1 は、問題1 を「Next.jsは UI と状態管理を密結合させる」と正しく立てているのに、答えの記述が

> **Spactaの答えは物理的な隔離です。** すべての機能は専用ディレクトリ（`core.ts` / `shell.tsx` / エッジファイル群）に閉じ込められ、他の機能の内部を import できません。

となっており、**状態側をどう隔離したかの機構（L2 / L10）が答えの段落に書かれていない。** 文書のこの欠落が読み手を L1/L7 に誘導する。→ `HUMAN_GUIDE` §0-1 の修正候補として未解決に残す。

### 含意

**安い部分は価値が薄く、価値のある部分が言語ごとのコストを持つ。** → 「言語横断の移植性」へ接続。

## 名前の所有権による切り分け [確立]

「フレームワーク非依存 vs 依存」という切り方は雑である。規則の文言はタダで誰でも書けるので、**文言が非依存でも意味がない。Spacta の商品価値は施行にあり、施行は必ず実ファイルを見るのでフレームワークに触る。**

実務的に効く線は **「その名前を所有しているのは誰か」** である。

| Spacta が名前を所有 | フレームワークが名前を所有 |
|---|---|
| `core.ts` / `shell.tsx` / `features/<name>/` / `shared/` / `components/` | `app/` / `page.tsx` / `route.ts` / `layout.tsx` / `middleware.ts` |
| L1, L2, L4, L7, L9, L10 の施行対象 | L5 の施行対象 |
| **誰にも動かされない。永久に安定** | **Next.js のリリースで動く。追随が要る** |

L2 の施行は「`core.ts` という名前のファイルを探して AST を見る」だが、**この `core.ts` という命名は Spacta 自身の発明**である。Next.js はこれを知らないし今後も知らない。だから L2 の施行は「フレームワーク非依存」というより **「Spacta が自分で立てた柱の上に立っている」** — 動かされる心配がない。

**実測（分量）:** starter 15ファイル中 `app/` は2つ。livingdoc 81ファイル中 `app/` は17（約21%）。**残り8割は Spacta が名前を所有する内側。**

→ **アダプタの仕事は「他人が所有する名前を、Spacta が所有する役割に翻訳すること」だけ**であり、アダプタが小さく済む根拠がここにある。

## もぐらたたきの局在 — 診断 [確立]

著者の懸念（この論点の由来）: Spacta は FCIS の形に Next.js を無理やり押し込めており、対応が対症療法の連続になっていないか。

**懸念は正当であり、証拠は既にコードとリリース履歴にある。** ただし汚染は全体ではなく**一箇所に局在している**。

### 既に一度叩いている

- L5 は当初 `page.tsx` しか見ておらず、`route.ts` に広げた
- L4 は `shell.tsx` だけだったのを `src/**` に広げた（`CHECKS` の L4 エントリのコメントに経緯が残っている）

**これらは思想の深化ではなく、Next.js の規約を後追いした動きである。**

### 現時点で既に出ているモグラ（未発見だったもの）

**`app/layout.tsx` は、err レベルの検査を1つも受けていない。**

- L5 の `match` は `(page|route)\.tsx?` なので `layout.tsx` に掛からない
- L1/L2/L4/L7/L9/L10 は全部 `root` が `src/` 配下。**`app/` は `src/` の外にある**

つまり `app/layout.tsx` に `Math.random()` / `new Date()` / 直書き `fetch` を書いても `verify` は緑である。そして **livingdoc の `app/layout.tsx` は実際に `await readViewer()` をしており、機能的には完全に Source 境界である。** L5 が守るべき役割を果たしているファイルが、L5 の glob の外にいる。`error.tsx` / `template.tsx` / `default.tsx` / `middleware.ts` も同じ状態。

**これが「ファイル名を列挙する」設計の本質的な欠陥である。役割は存在し、ファイルはその役割を演じているのに、glob が名前を知らないから見えない。Next.js が次に出す規約は自動的にこの穴に落ちる。静かに、緑のまま。**

## もぐらたたきの処方 — 役割分類とアダプタ分離 [仮説]

未実装。v0.9.2 の範囲外。

**(1) 掟からフレームワークアダプタを分離する。** 現在 `CHECKS` に `join(r,"app")` と `/(page|route)\.tsx?$/` が直接埋まっている。これは**掟のレジストリに Next.js アダプタが密輸されている**状態。`platform/nextjs.mjs` に切り出し、「この framework では、これらのパスが Source / Shell / Component / SharedUI」と宣言させる。掟の側は**役割**だけを語る。

効果: Next.js が新規約を出してもアダプタ1ファイルの更新で済み、掟は動かない。**もぐらたたきが「掟の劣化」ではなく「アダプタのドリフト」として可視化される** — 叩くこと自体は避けられないが、叩く場所が1ファイルに閉じ込められ、掟の純度が汚れなくなる。

**(2) 単発で最も価値が高い変更: 未分類を `INCONCLUSIVE` にする。** `app/` 配下を列挙し各ファイルを役割に分類、**どの役割にも分類できないファイルが1つでもあれば `INCONCLUSIVE` (exit 2)**。

これは Spacta が自分で確立した処方の一貫適用である。v0.9.1 で「空スキャン → INCONCLUSIVE」、v0.9.2 で「glob が0件 → 赤」（L6 配線テスト）を入れた。**その次の段が「フレームワークに Spacta の知らないファイルがある → 判定不能」である。**

> これで「Next.js が進化して Spacta が気づかなかった」が、静かな穴から大きな音に変わる。もぐらたたきは終わらないが、**モグラが出たことが分かるようになる。**

なぜ仮説どまりか: 役割分類が `app/` 配下の全ファイルに対して過不足なく定義できるか未検証。偽陽性（分類の必要がないファイル）の量も未計測。

## 二本脚モデル — 構造と検証 [確立]

**Spacta には脚が2本ある。**

- **第1の脚（構造）** — タスクを小さく閉じたものにする。`SPACTA.md` + starter + 4語彙。**これが AI 開発を成立させている部分**
- **第2の脚（検証）** — その構造が破れていないことを証明する。`verify`

### 認識を変えた要因

**AI (Opus 5) は議論を通じて一貫して検証器を Spacta の商品として扱い、「Spacta の創業観察は hope-prompt 問題である」と繰り返した。これは重み付けの誤りである。**

`HUMAN_GUIDE` §0 は既に4本立てになっている: ①コンテキスト隔離 ②明示的構造による複雑性の低減 ③契約駆動 ④機械的検証（hope-prompt 排除）。**hope-prompt は4本のうち1本にすぎない。**

著者の指摘:

> だからスパクタはホーププロンプトを解決しているだけではない。数字で見れば失敗率は3%だけど、後々の保守性や、そもそもの実装難易度、修正難易度の低下。そもそもスパクタ自身がAIでの開発を大前提にしているものだから。

**著者の整理は構造を商品に置き、検証器をその保証として置く。こちらが正確である。**

### 含意 — これが最も実用的な帰結

**「Spacta in X」は検証器ゼロで出荷できる。** 第1の脚（隔離・小さいタスク・影響範囲の限定）は `SPACTA.md`-for-X と starter-for-X だけで初日から手に入る。検証器は「500タスク回したときの漂流を止める」ためのもので、day-one の価値には要らない。

**したがって「言語ごとに AST 検査器を書き直すコスト」は参入コストではなく持続コストである。入口はずっと安い。**

## 言語横断の移植性 [仮説]

### 層と移植性

| 層 | 移植性 | 言語ごとのコスト |
|---|---|---|
| **方法論**（hope→検査に落とす / NOT guaranteed を宣言する / 幹の行数予算） | 完全に不変 | ゼロ |
| **役割の分解**（Source / Core / Shell / Component / SharedUI） | UI アプリなら不変。**サーバのみなら Source / Core だけ**（Shell も Component も存在しない） | ゼロ |
| **検査器** | ❌ 移植できない | **言語ごとに書き直し**（パーサが違う） |
| **アダプタ** | フレームワークごと・バージョンごと | 小 |

**「Spacta in Rust」はプラグインではなく仕様を共有した別実装になる。** ESLint と Clippy と golangci-lint の関係と同じで、思想は共有されるがコードは共有されない。

### 掟ごとの移植性

| 掟 | 移植性 | 理由 |
|---|---|---|
| L1 / L7（モジュールグラフ） | 9割 portable | import 文が読めれば言語を問わず同じロジック。**ただし価値は薄い**（→ コンテキスト隔離の機構） |
| L2 / L9 / L5（純粋性） | エンジンは共有、**禁止構文リストは言語ごと** | Go なら `time.Now` / `rand` / `os` / `net/http`、Rust なら `Instant::now` / `rand::` / `std::fs` |
| L4（網羅性） | **言語による** | Rust の `match` は言語が既に強制（Spacta 不要）。Go は `switch` に網羅性がなく**価値が高い**。TS は現状どおり |
| L10（コンポーネント無状態） | ❌ **React 固有。機構としては移植できない** | ただし**目的**（状態が1箇所にある）は移植する。サーバ言語なら「パッケージレベルの可変状態を持たない」が対応物 |

### 認識を変えた要因 — バックエンド言語の評価を下方修正

**AI は当初「Go は価値が高い」と述べた。取り下げられている。**

理由: **バックエンドでは状態がプロセス内にない。DB にある。** A ハンドラと B ハンドラの結合の主要因は共有テーブル・共有スキーマ・共有クエリであり、**これは Spacta が「解決していない」と明言している結合そのものである。**

`HUMAN_GUIDE` §6.2 の「データを経由した結合」、実例が livingdoc の `queries.ts` 508行、`TRACE_SELECT` を pageview / search / profile の3機能が共有、そして **L1 は緑のまま**。

> つまり「Spacta in Go」は、Spacta の最大の既知の穴を、副次的な問題ではなく**主要な問題として相続する。**

**逆に価値が高いのはプロセス内クライアント状態を持つ領域** — SwiftUI / Flutter / Compose / 他の Web フレームワーク。ここは livingdoc と同じ構造の問題を持ち、Spacta の答えがそのまま効く。

> **隣接市場は他言語のバックエンドではなく、他プラットフォームの UI である。**

なぜ仮説どまりか: いずれの言語でも実装も計測もされていない。上表は言語仕様からの演繹にすぎない。

## 層モデル [確立]

```
[Next.js 領域]  app/ — フレームワークが名前を所有
      ↕ アダプタ  ファイル名 → 役割の翻訳
[Spacta 領域]   src/ — Spacta が名前を所有。ここで import・状態・IO の複雑性を廃す
      ↑ 検証器  隔離が破れていないかを観測する
```

**検証器は Spacta 領域と並ぶ層ではなく、直交する観測者である。** そして**検証器はアダプタに依存する**（境界ファイルがどこかを知る必要があるため）。依存の向きは「検証器 → アダプタ → フレームワーク」であり、**Spacta 領域自体はどこにも依存しない。**

これが移植可能性の根拠であり、「検証器ゼロで出荷できる」の理由でもある。

**可搬な成果物は `SPACTA.md` である** — 検証器でもアダプタでもなく。67行のあの文書と starter が、言語をまたいで運ぶ実体になる。

## err と info の選別基準は「沈黙するか」 [仮説]

著者の提起: 潔癖症のように全てをスクリプトで検証可能にするのは必須ではないのではないか。重大なもののみ検査で、あとは info / 警告でよいのでは。AI の推論を信じてよいのでは。

**賛成。ただし選別基準は「重要度」ではなく「失敗が沈黙するか」である。**

- **L8（色の直書き）が info でよい理由**は、重要でないからではなく **失敗が見えるから**。人間が画面を見れば30秒で気づく。AI を止める必要がない
- **L2（core の純粋性）が err である理由**は、重要だからではなく **失敗が沈黙するから**。テストは通り、`tsc` も通り、画面も正しく見える。そして他の全保証がその上に乗っている

**Spacta は既にこの基準で動いているが、明文化されていない。** だから err/info の振り分けが直感になっており、直感は必ずぶれる。→ 明文化の候補（`verify/README.md` か `CHECKS` のコメント。`SPACTA.md` の幹は太らせない）。

### 循環への注意 — これが最も重要

**「AI はコンテキスト隔離のおかげで小さい範囲しか見ないから推論を信じてよい」は、そのままでは循環する。その隔離を作っているのが L1/L7/L2 だからである。**

- **隔離を生産している掟（L1 / L7 / L2）** → 緩められない。緩めると前提そのものが消える
- **隔離を消費している掟（L8 / L9 / L10 / L5 の一部）** → **緩和の候補はここだけ**

hope-prompt 問題との整合: あれは AI の**能力**の話ではなく**500タスク中3%の失敗率**の話である。3% が許容できるかは「その失敗が誰にいつ見つかるか」で決まる。**だから「沈黙するか」が基準になり、創業観察と矛盾せずに緩和を正当化できる。**

なぜ仮説どまりか: 基準として提案されただけで、既存の err/info 振り分けを全件この基準で再検証してはいない。

## 膜語彙の圏 — なぜ第5の語彙を作らないか [確立]

v0.9.2 Q1-a の裁断根拠だが、概念として独立の価値がある。

`State` / `Action` / `Effect` / `InitData` は膜を**越える**語彙である。しかし書き経路の戻り値（`EffectResult`）は**膜を越えない** — **膜を越えるのは `EFFECT_SUCCEEDED` / `EFFECT_FAILED` という `Action` であり、`EffectResult` は `runEffect` → `shell` 間、つまり縁の内側で完結するペイロード形である。**

したがって「第5の**膜**語彙」という命名が最初から成立していない。第5の語彙を作る案は、語彙表に非-膜語彙を混ぜる操作であり、**「膜を越えるものの名前」という語彙表の意味を薄める。**

補助的な根拠（edit-plan-04 由来）: 検査器なしで語彙だけ増やすと hope が1つ増える。

## L5 とサーバ採番 ID の衝突 [確立]

**L5 は `route.ts` での ID 生成を err にしている。一方、書き経路の戻り設計は「サーバが ID を採番する」を前提にする。字面上は矛盾する。**

解決は starter の実例が担う: **route.ts のアプリコードが `crypto.randomUUID()` を書くのではなく、DB（`@default(cuid())` 等）が採番したものを読んで返す。**

```ts
const created = await prisma.sample.create({ data: {...} });
return Response.json({ id: created.id });   // 採番は DB。route は運ぶだけ
```

これは L5 の精神（境界で非決定性を発明するな）と完全に整合し、実務的にも正しい。

**この衝突は starter に `route.ts` が無かったから顕在化していなかっただけである。** → 「規範が無い場所は必ず埋められる」の実例。livingdoc の `post()` が `Promise<void>` になっていたのも同じ機序。

## 書き経路 — 「きれいでない」の3種類 [確立]

分けて扱う必要がある。timescale も解決経路も違う。

**(a) Law としてはきれいである。** 「IO の結果は Action として膜を通る」は完成しており、フレームワークにも言語にも依存しない。片付いた。

**(b) 施行が部分的である。** 採用した検査は「Action union に受け皿があること」しか見ず、「戻りが実際に往復していること」は追跡しない。`tsc` が「受け皿を処理すること」を強制するので実用上は強いが、**`runEffect` の結果を握りつぶして Action を作らない shell は今も書けて、緑になる。** 安価な AST 検査は現時点で見つかっていない → 未解決へ。

**(c) Form がフレームワークと競合している。ここが本命。** `drain` は React の `useOptimistic` / `useActionState` / Server Actions を手で再実装したものである。両方とも動くが**合成できない** — 片方を選ぶと片方が使えない。

**(c) に理論的な解決がない理由は、根が1つの対立にあるからである:**

> `useOptimistic` のロールバックは暗黙で、Action ログに現れない。フレームワークは「開発者が書く量を減らす」ために暗黙化し、Spacta は「後から因果を追える」ために明示化する。**この2つは同じ軸の逆向きであり、技術的な工夫で両立するものではない。**

したがって (c) の正しい扱いは「解決する」ではなく **「選択であることを明示し、乗り換え可能にしておく」** — `SPACTA.md` には Law をフレームワーク中立な言葉で書き、`drain` は starter 側で Form（可変）と明示的にラベルする。将来 React 側が「ロールバックを観測可能にする API」を出せば対立は消えるが、それは待つ話であって設計で先回りできる話ではない。

**副次的に必要な作業:** `HUMAN_GUIDE` §6.2 に「なぜ `useOptimistic` を使わないか」を1項目足す。現状これは書かれておらず、書かれていないと読者は「作者は React の標準機能を知らないのでは」と受け取る。理由を書けば意図的な差異になる。
