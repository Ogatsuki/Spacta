# アダプターの分類 — 束縛アダプター / データアダプター

対話(著者とAI)で決定した方針。「アダプター」という言葉の意味を整理し、物理配置を決める。**ここに書かれた分類・ディレクトリ方針は決定事項**であり、提案ではない。

---

## 用語の整理 [確立・決定]

`spacta-genzaichi.md` では「アダプター」という語が**束縛(binding)層**を指すものとしてすでに使われている一方(§6「規律/機構/束縛の三分割」で「束縛 = Reactへの配線、`app/`の解釈」が「本当のアダプタ」と呼ばれている)、データ取得層は「**edge**」という役割名で別に呼ばれていた(§4の役割分類表)。この2つは実は同じ性質——**Spactaの外側にあってSpactaの語彙に翻訳する層**——を持つため、対話の中で用語を統合した。

> **「アダプター」を傘概念とし、その下に「束縛アダプター」と「データアダプター」の2種を置く。**

| | 旧称 | 何を吸収するか | 具体例 |
|---|---|---|---|
| **束縛アダプター** | (すでに「アダプタ」と呼ばれていた対象) | フレームワークへの配線 | `verify/platform/nextjs.mjs`(名前→役割)、React配線、Server ActionsをEffect輸送路に使う話 |
| **データアダプター** | `edge`(役割分類表) | データ取得・永続化 | `shared/source/queries.ts`、`TRACE_SELECT` |

**`spacta-genzaichi.md` を今後改訂する際は、役割分類表の「edge」という表記を「データアダプター」に置き換える対象として扱ってよい。**

## ディレクトリ方針 [確立・決定]

> **`adapters/` という新しい物理ディレクトリを作る。**

現状の名前の所有権の切り分け(`spacta-genzaichi.md` §6)は次の2区分だった。

| Spacta所有 | フレームワーク所有 |
|---|---|
| `core.ts` / `shell.tsx` / `features/` / `shared/` | `app/` / `page.tsx` / `layout.tsx` / `middleware.ts` |

ここに **第3の区分としてアダプター専用の物理領域を追加する。**

| Spacta所有 | フレームワーク所有 | アダプター |
|---|---|---|
| `core.ts` / `shell.tsx` / `features/` / `shared/` | `app/` / `page.tsx` / `layout.tsx` / `middleware.ts` | `adapters/`(束縛アダプター・データアダプター) |

**理由:** `spacta-genzaichi.md` §6「名前の所有権による切り分け」がすでに述べている通り、見える結合の分離は「簡単。ESLintでも8割できる」——物理ディレクトリという構造的な区分けは、この安価な層をそのまま強化する。今`queries.ts`は`shared/`(Spacta所有の名前空間)の中に他のコードと同じ顔をして埋まっており、機能単体の修正のつもりで触っているAIが「これは複数機能に影響する共有コードだ」と気づけない。`adapters/`という別ディレクトリに出すことで、**その場所にいるという事実だけで「ここは特別扱いが要る」と構造的に伝わる。** これは `spacta-fukuzatsusei-no-gyoshuku.md` の実装形の1つでもある。

既存の粒度(`app/` / `features/` / `shared/` / `core.ts` / `shell.tsx`)に対し `adapters/` を1つ足すだけなので、過剰なラベリングではなく既存の粒度に自然に収まる追加、と判断した。

## 型定義とのペアリング原則 [仮説]

対話の中で出た問い:「アダプターには型定義をセットにすべきか」。答えは**アダプターの種類によって異なる**——束縛アダプターは一枚岩ではなく、性質の異なる2つの仕事が混在しているため。

### データアダプター: 型定義のペアリングが全面的に有効

データアダプターの仕事は「値を取ってくる」ことなので、**「どんな値を要求できるか」を型で縛ることがそのまま機能する。** 各機能は共有SQL文字列を直接書くのではなく、型定義された「意図」を宣言し、データアダプターがそれをもとに実際の問い合わせを組み立てる。詳細と、これがデータ経由の結合にどう効くかは `spacta-data-ketsugo-taisaku.md` に分離した。

### 束縛アダプター: 「値の輸送」と「ファイルの分類」で扱いが割れる

- **値がSpactaの語彙に流れ込む部分**(例: Server Actions経由のEffect結果輸送)には、型定義のペアリングがすでに機能している。書き経路の`Action`union型と`tsc`の`never`終端チェックが、まさにこれ(`spacta-genzaichi.md` §3)。輸送されてきた結果は必ず`EFFECT_SUCCEEDED`/`EFFECT_FAILED`という型付きの`Action`でなければならず、コンパイラが網羅性を担保する。
- **ファイルを役割に分類する部分**(例: `nextjs.mjs`の名前→役割マッピング)は、データの形の話ではなくファイルパスの分類ロジックなので、**型定義は噛み合わない。** ここは別の機構(L6の自己テスト——globが最低1件マッチすることをassert、role-claimテスト——表の主張を実走査で検算)がすでに担っており、これはこれで正しい設計。

**まとめ:** 「束縛アダプターに型定義は要るか」という問いは一段分解する必要がある。値が流れ込む場所には要る(すでにある)。ファイルを分類する場所には効かない(別の機構がすでにある)。
