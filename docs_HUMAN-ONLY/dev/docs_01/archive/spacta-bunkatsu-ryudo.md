# Spacta 分割粒度 — ファイル分割とエージェント分割は別の軸

**この文書の位置づけ:** `spacta-genzaichi-2.md`未収録の新規論点。「縦のラインをAIで並列実装する際、コンポーネントごとにエージェントを立てるべきか」という疑問から生まれた。確信度タグは genzaichi-2 と同じ規則。

---

## 問いの出発点

初期の実験では、コンポーネント1つにつきAIエージェントを1体割り当て、20数体を並列に走らせたことがあった。しかしコンポーネント1つの実装は多くの場合数十行程度の小さな仕事であり、それに専用のエージェントを1体起動するコスト（タスク仕様を書く・起動を待つ・出力を検証する・他との整合を統括側が確認する）は、その数十行を統括AI自身がその場で書くコストより高くつくのではないか、という疑いが生じた。

## 核心の気づき：2つの軸を混同していた [確立]

**「コードをどう分割するか（ファイル/モジュール粒度）」**と**「AIをどう分割するか（エージェント委任粒度）」**は本来別の判断であり、一致させる必要はない。

### 軸A: ファイル分割の基準 = 再利用

これは既に `SPACTA.md` §2 の Form ガイドラインとして明文化済み。

- Header/Nav/ページレイアウトのような共通の枠は `app/layout.tsx` / `shared/ui/*` に上げる
- feature固有のUI（Hero sectionなど）は `features/<name>/components/` に留め、**重複は許容・むしろ結合より推奨**
- `shared/ui` への昇格は、**同じ形が実際に2つ以上のfeatureで重複した後にのみ**行う。`verify`が出す`clone` infoはそれ自体が昇格の指示ではない

→ 1箇所でしか使われないコンポーネントは、そもそも切り出す理由がない。featureに一体化してよい。

### 軸B: エージェント委任の基準 = コスト対効果

並列化が経済的に見合うのは次の3条件が揃ったときだけ。

1. 各断片が本当に独立している（互いの実装詳細を知る必要がない）
2. 契約の言語化コスト（interfaceを書く手間）が実装コストに比べて小さい
3. 統合・検証コストが、並列化によって浮く時間より小さい

小さいコンポーネント1つはこの条件を満たしにくい。**契約の言語化・起動・検証・統合という固定費が、実装量に対して相対的に大きくなりすぎる。**

## 24並列エージェント実験の再解釈 [仮説]

この実験は「ファイル分割の基準（軸A: 再利用）」を「エージェント分割の基準（軸B: コスト対効果）」に無反省に横滑りさせていた可能性が高い。「コンポーネントごとに分けるのが正しい構造」という判断と「コンポーネントごとにエージェントを立てるのが正しい実行戦略」という判断は別物であり、前者が正しくても後者が正しいとは限らない。

ただし、この実験自体が「Spactaの隔離が本当に並列構築を許すか」という**仮説検証**として意味を持っていた可能性はある——常設の作業フローとして採用すべきという結論とは別に評価すべき。

## 推奨される既定 [仮説・未実測]

- **エージェント委任の既定粒度は「縦のライン1本（あるいは1feature）= 1エージェント」**とする
- エージェントを分割するのは、**そもそも契約凍結が必要な境界（軸Aで既に切り出す判断がされた、真に共有されている箇所）に沿ってのみ**行う。共有されていない内部の都合だけでエージェントを割る理由はない
- これにより、ファイル分割の判断基準とエージェント分割の判断基準が**「共有されているか」という単一の基準に収束**し、2つの独立した判断を毎回下す必要がなくなる

## 未解決・保留事項

「縦のライン1本 = 1エージェント」という既定粒度が、実際に1エージェントのコンテキストに収まるかどうかは未検証。これは分量の複雑性軸の問題であり、詳細は `spacta-fukuzatsusei-jiku.md` を参照。genzaichi-2 §12 優先3（n=2実測）と同じく、実測してみないと分からない部類の問い。
