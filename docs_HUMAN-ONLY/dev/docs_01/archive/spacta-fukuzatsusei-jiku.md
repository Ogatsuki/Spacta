# Spacta 複雑性の2軸 — 振る舞いの複雑性と分量の複雑性

**この文書の位置づけ:** `spacta-genzaichi-2.md`未収録の新規論点。「Amazonのような密度の高いUIでも縦のライン1本を1エージェントが持てるか」という疑問から生まれた。確信度タグは genzaichi-2 と同じ規則。

---

## 問いの出発点

Spactaは state/API管理をUI層から追い出しているため、一般的なNext.jsアプリより実装の複雑性・タスク難易度は低いと言える。しかし、CSSアニメーションや装飾の多い密度の高いUI（Amazonのようなページ）を書く場合、この「UI層は単純」という前提は本当に成り立つのか、という疑問が生じた。

## 核心の区別：振る舞いの複雑性と分量の複雑性は別の軸 [確立]

- **振る舞いの複雑性**: 分岐・副作用・データ形状の推論（状態管理・API呼び出し）。Spactaの膜（§1「膜をデータだけが越える」）はまさにこの軸を切り離すことを目的にしている
- **分量の複雑性**: JSXの行数・CSSのバリエーション・アニメーションの状態数・レスポンシブの分岐。state/APIを追い出しても、**この軸は一切減らない**

「UI層が純粋（振る舞いが単純）」であることと「UI層が小さい（分量が少ない）」であることは別の主張であり、前者が成り立っても後者が自動的に成り立つわけではない。Amazon的な密度の高いUIは、状態管理がゼロでも見た目の情報量だけでコンテキストを圧迫しうる。

## 既存の分割ルールによる緩和 [確立]

`SPACTA.md`§2「Layouts Go Up, Components Go In」により、この分量軸の懸念は当初想定より緩和される。

- Header/Nav/ページ全体のレイアウトは `app/layout.tsx` / `shared/ui/*` に上がる
- Hero sectionのようなfeature固有のUIは `features/<name>/components/` に留まり、重複は許容・結合より推奨される

この結果、部分的な変更をする際にページ全体が強制的にロードされるわけではなく、該当のcomponent/feature＋上位のlayout/pageだけを見ればよい。さらに、**「縦のライン1本」という構築単位自体が、既存の分割ルールのおかげで「ページ丸ごと」から「1つのHero section＋それを使うfeature」程度まで自然に小さくなる**——これは§4の懸念（縦のライン1本を1エージェントが持てるか）を和らげる副次的な効果になる。

## 未解決・保留事項

分量軸の緩和は方向として正しそうだが、**実測されていない**。特にアニメーションを多用する密度の高いコンポーネント1つが、実際に1エージェントのコンテキストに快適に収まるかどうかは、推測ではなく実測で確認すべき事項。genzaichi-2 §12 優先3（n=2実測）と同じ「やってみないと分からない」カテゴリーに属する——安上がりな予備テストとして、想定するアプリの1画面分（アニメーション込み）のJSX+CSSを想定して行数・トークン数を概算することは今すぐでもできる。

## genzaichi-2 との接続

- §4「予算の再定義」（幹の行数ではなく「1タスクで参照する箇所の数」が予算）に、もう1つの軸を追加する形の補足——**同じ「1箇所」であっても、その箇所自体の生の分量は別の予算次元であり、凝縮の原理（参照箇所を減らす）だけではこの軸は縮まらない**
- §12 優先3（n=2実測）の自然な検証対象として直結する
- `spacta-bunkatsu-ryudo.md`（分割粒度）の前提となる論点——「縦のライン1本 = 1エージェント」という既定粒度が成立するかどうかは、ここで扱う分量軸の実測結果に依存する
