- 作成日: 2026-07-25
- 書いた人: Claude (Opus 5) — 本レポートの筆者は、Living Document MVP を Spacta 上で実装した当人
- 対象: `spacta/SPACTA.md` v0.9 / `spacta/verify/verify.mjs` / `spacta/starter/`
- 題材: `livingdoc/` (Next.js 15 + D1、app/src 合計 4,722 行、22 コンポーネント、17 ルート)
- 立場: Spacta の作者ではなく、Spacta を渡されて 1 アプリを完成させた実装者
- 前提: 私はこのアーキテクチャを本件で初めて使った。以下は「1 プロジェクト・1 回」の経験に基づく所見であり、長期運用の知見ではない

---

## 0. 要約

**証明の道具としては優秀、指導の道具としては未完成。**

Spacta は「IO をどこに置いてはいけないか」を機械的に証明する。これは非常によく効く。
一方で「思考をどこに置くべきか」は証明しない。私の shell が薄いのは私がそう決めたからで、
Spacta がそう強制したからではない。

そして本件で最大の効用は、ドキュメントが謳っている「1 機能を全体を把握せずに実装できる」ではなかった。
**「複数のエージェントに並列で投げても、成果物が絡み合わないことを機械的に保証できる」** ことだった。
これは README にも SPACTA.md にも書かれていない。私はこれが Spacta の本命の用途だと考える。

## 1. 何が起きたか (事実の記録)

意見を述べる前に、検証可能な事実を置く。

| 事実 | 数値 |
|---|---|
| `bun run verify` の初回実行 | **一発で Green**。L1/L2/L4/L5/L7 違反 0 |
| 初回に出た info | 2 件のみ (`single-owner-export` ×2)。両方とも指摘は妥当で、5 分で解消 |
| clone 検知 | 0 件 (4 体のエージェントが書いた 22 コンポーネントを横断して) |
| L8 提示純度 | 0 件 |
| `tsc --noEmit` | エラー 0 |
| 並列サブエージェント | 4 体 (UI プリミティブ / pageview / catalog+search+profile / moderation+materialrequest) + カタログ SQL 1 体 |
| サブエージェント成果物の手直し | 1 箇所 (番号なしページで `. タイトル` と表示されるバグ。Spacta とは無関係の表示バグ) |

**重要な留保**: 私は SPACTA.md の中心的なループ —— §0 の「掟を暗記することではなく、`verify` が緑になるまでコードを直すこと」
—— を**一度も経験していない**。赤を出して直した回数はゼロである。したがって本レポートは
「fix-until-green ループの使い勝手」については何も語れない。語れるのは「設計段階で掟を内面化した場合に何が起きるか」だけである。

なぜ一発で緑になったか。掟のほとんどは**配置の規則**であり、私は配置を先に決めてから書いたからだ。
`readNow()` / `newId()` を `source/ids.ts` に置いたのは、L5 が route.ts での生成を弾くと**書く前から知っていた**からで、
弾かれてから直したのではない。つまり掟は私にとって**事後の矯正器ではなく事前の設計制約**として働いた。
これは Spacta の想定と少しズレるが、悪いズレではないと思う。

## 2. 良かった点

### 2.1 L6 (検証器の自己検証) — この文書で最良のアイデア

`verify` は本スキャンの前に `verify/fixtures/` の「わざと壊した検体」を全部弾けるか自己テストし、
落ちたら他の結果を一切信用させずに終了する。

これがなぜ効くか。**私はサブエージェントが書いた 22 個のコンポーネントを一行も精読していない。**
`✓ L6 self-test` を見た上での `verify: Green` と `tsc: 0 errors` を、受け入れテストとして信用したからだ。
もし L6 がなければ「緑が出た」は「チェッカが壊れていて何も見ていない」と区別がつかず、
私は 22 ファイルを読む羽目になっていた。

世の中の「アーキテクチャ強制」の大半は、誰も再検証しない lint 設定である。
**自分が赤を出せることを証明できない限り緑を名乗らない**というのは、
私が知る限り他所であまり見ない設計で、しかも委譲の文脈で直接的に金銭的な意味を持つ。
L6 は Spacta の中で唯一「メタレベルの誠実さ」を担保している掟であり、他の 7 つの掟の価値はすべてこれに乗っている。

### 2.2 L2/L3 (Core 純度と注入) が、狙っていないバグを 1 クラス消した

`core.ts` で `new Date()` が書けない。だから相対時刻の整形は `formatRelative(now, iso)` になり、
`now` は必ず引数として外から入る。

その副作用として、**SSR とハイドレーションの時刻ズレが構造的に発生しなくなった**。
サーバで「3h ago」と描いた文字列は、クライアントで再計算されても同じ `now` を使うので必ず一致する。
私はこの問題を解こうとしていない。掟に従ったら勝手に消えた。

同じことがより大きな規模で起きたのがスポット導出である。
`buildSpots()` が純関数なので、**サーバの SSR とブラウザの楽観的更新が文字通り同じ関数を呼ぶ**。
「投稿直後にクライアントが計算したグルーピング」と「次のリロードでサーバが計算したグルーピング」が
食い違う余地がない。楽観的 UI の典型的な地雷 (クライアント側の簡易ロジックとサーバ側の本物のロジックの乖離)
が、選択の余地なく塞がれている。

これは Spacta の宣伝文句である「文脈節約」よりもずっと実利的な効果だと思う。
純度は**節約のため**ではなく、**同一性を保証するため**に効いている。

### 2.3 L5 が非決定性の表面積を 1 ファイルに畳んだ

route.ts で `crypto.randomUUID()` が書けない。書いている最中は正直「なぜ直に呼ばせない」と思った。
結果として、このアプリで時刻・ID・乱数が生まれる場所は `src/shared/source/ids.ts` の 3 関数だけになった。

セキュリティレビューの観点でこれは大きい。「このアプリの非決定性を全部見せろ」に対して
1 ファイル 20 行を指させる。9 本の route ハンドラを読む必要がない。
瞬間的な摩擦と引き換えに、監査可能性が跳ね上がっている。良いトレードだった。

### 2.4 export 所有状況の検査 (dead-export / single-owner-export) が新鮮

初回に出た info はこれだけだった。`catalog/types.ts` の `Density` と `search/types.ts` の `Snippet` が
「1 ファイルからしか import されていない = 共有しているという嘘」と指摘された。実際その通りで、
両方とも唯一の消費者である `core.ts` に移した。

「型が幹に居座っているが実は誰も共有していない」を検出する仕組みを、私は他で見たことがない。
共有を**方向**ではなく**実際の消費者数**で測っているのが良い。地味だが、これは他所に持ち出す価値のある発想だと思う。

### 2.5 依存ゼロ・1 秒 — 「常時走らせられる」ことの効き目

`verify` は TypeScript をパーサとして使うだけで、React も Next も要らない。約 1 秒で終わる。
CI 専用の重いゲートではなく、書きながら何度でも叩ける。
掟が「守られているか不安な規約」ではなく「いつでも 1 秒で確認できる事実」になるかどうかは、この速度差で決まる。

## 3. 並列エージェント運用での所見 (ここが本題)

### 3.1 L1 が委譲の契約そのものになった

私は 4 体のサブエージェントに、それぞれディレクトリを 1 つずつ渡した。

```
agent A → src/shared/ui/*                          (15 ファイル)
agent B → src/features/pageview/components/*        (9 ファイル)
agent C → src/features/{catalog,search,profile}/components/*  (9 ファイル)
agent D → src/features/{moderation,materialrequest}/components/*  (6 ファイル)
```

L1 (feature 間の内部 import 禁止) と L7 (shared → features 逆依存禁止) があるおかげで、
**この 4 体が互いの成果物を壊す経路が物理的に存在しない**。
共有点は「私が先に確定させた `types.ts` と `core.ts` の関数シグネチャ」だけで、
そこは私が握っている。エージェントは自分の箱の中しか触れない。

これは通常の Next.js プロジェクトでは成立しない。
普通なら agent C が「TraceCard が pageview にあるじゃないか」と import して、
2 つの feature が癒着し、後で片方を直すと両方壊れる。L1 はそれを**規約ではなく失敗として**止める。

### 3.2 受け入れ検査が機械化されたので、私は成果物を読まずに済んだ

並列委譲の本当のコストは「4 人分の成果物を 1 人でレビューする」ことである。
Spacta はここを `verify` + `tsc` に肩代わりさせた。私が実際にやったのは:

1. `bun run verify` → 緑 (L6 の自己テスト付きなので信用できる)
2. `bunx tsc --noEmit` → 0 エラー (プロップの型が shell の呼び出しと合っているか = 契約違反がないか)
3. dev サーバを立てて 1 画面だけ目視 + curl で E2E

これで 22 ファイルを受け入れた。**精読はしていない。**
「機械が保証する範囲」と「人間 (私) が見る範囲」の切り分けが、掟の定義によってあらかじめ決まっているのが効いた。

これは SPACTA.md が想定している「1 体の AI の文脈節約」とは別の効用である。
文脈が節約されたのは主にサブエージェント側で、私 (指揮側) の文脈はむしろ**前倒しで重くなった**。
プロンプトが生成されたファイルより長いことすらあった。
つまり Spacta は指揮者のコストを減らさない。減らすのは**検収のコスト**である。ここは正確に区別されるべきだと思う。

### 3.3 掟より厳しいルールをエージェントに課す必要があった

これは後述の L8 の問題 (§4.4) と直結するが、実務上の教訓として先に書く。
私がエージェントに与えたのは、L8 が実際に検査するルールではなく、**それより厳しい自作ルール**だった:

> 「Tailwind 既定パレットの色名は一切使うな。`tailwind.config.ts` のセマンティックトークンだけ使え」

L8 が実際に弾くのは無彩色 (slate/gray/zinc…) と「ブランド色＋透過度」だけで、
ステータス色 (red/green/blue/sky…) は無条件に許容される。
この条件をエージェントに正確に説明するのは難しく、しかも説明すると必ず抜け道として使われる。
だから「全部禁止」にした。結果として L8 違反は 0 件だが、**それは掟が機能したからではなく、
私が掟を信用せず上書きしたから**である。掟がそのまま委譲プロンプトに書き写せなかったのは、設計上の弱点だと思う。

### 3.4 「重複してよい」は本当に安く済んだ (実測)

L1 に従い、似た見た目のカードを feature ごとに複製した。実測値:

| ファイル | 行数 |
|---|---|
| `pageview/components/TraceCard.tsx` | 71 |
| `profile/components/ProfileTraceCard.tsx` | 37 |
| `search/components/SearchGroup.tsx` | 56 |

書き出す前は「3 つも同じものを書くのか」と思ったが、実際に出来上がったものを見ると
**3 つは同じものではなかった**。TraceCard は投票・返信・通報を持ち `<header>` を持つ。
ProfileTraceCard は場所 (どの教材のどのページか) を主役にして操作を一切持たない。
タグ構成も className もほとんど共有していない (clone 検知が 0 件だったのは閾値が緩いからではなく、
実際に別物だからである — 私は両ファイルのタグとクラスを目視で突き合わせて確認した)。

つまり「重複」に見えていたのは**私の予断**で、文脈が違えば UI は自然に分岐する。
共通化していたら `showActions` `showLocation` `variant` のようなフラグが 3 つ生えていたはずで、
そちらの方が確実に高くついた。§2.5 の「重複は許容され、結合より好ましい」は正しい。

## 4. 悪かった点・不足していると感じた点

ここからは批判である。使えたからこそ、穴も見えた。

### 4.1 【最大の不満】書き経路の戻り値について、掟が何も言っていない

Spacta の一文は「膜を越えるのはデータだけ」で、読み経路には `InitData` という明示された通路がある。
ところが**書き経路の戻り**には通路が定義されていない。`runEffect(effect): Promise<void>` は片道である。

現実の UI は IO の結果を必要とする。サーバが採番した ID、バリデーションエラー、429、権限エラー。
これらをどう膜の内側に戻すのか、SPACTA.md にも starter にも記述がない。

私はこう解決した:

```
Core が楽観的に状態を更新し、Effect を宣言
  → shell が runEffect を await
    → 失敗時は throw されるので shell が catch
      → { type: "FAILED", message } という Action として Core に戻す
```

結果としては良い設計になったと思う (エラー状態が純粋層に入るので、エラー時の表示も再現可能になる)。
だが**これはアプリ全体で最も重要なパターン判断であり、それを私が即興で決めた**。
別のエージェントが同じ Spacta を渡されたら、まず間違いなく違う解き方をする。
`effect` にコールバックを埋める者、`runEffect` の戻り値型を変える者、shell に業務判断を書いてしまう者。
どれも `verify` は緑になる。

**掟が効果の出口を規定しておきながら、戻り口を規定していないのは非対称である。**
v1.0 に向けて最優先で埋めるべき穴はここだと思う。

### 4.2 「shell を薄く保つ」は掟ではないので、実際には強制されていない

§2.5 と §4.1 は「純粋な判断はすべて `core.ts` へ移せ」「まず logic は core.ts に書け」と繰り返す。
これは Spacta の思想の中核だと読める。ところがこれを検査する掟が**存在しない**。

`verify` が shell について見るのは L4 (effect.type の switch に網羅性終端があるか) だけである。
したがって:

- shell に 300 行のバリデーションを書いても緑
- shell に `if` を 40 個並べて状態遷移を書いても緑
- core.ts を空にして全部 shell に書いても緑 (IO さえ無ければ)

私の shell が薄い (`pageview/shell.tsx` は state 配線と Action 変換だけ) のは、私がそう決めたからだ。
締切に追われたエージェントは、`core.ts` に純関数を足すより shell に直接書く方が速いと判断するだろうし、
その判断は `verify` に一切咎められない。

**掟が強制しているのは「IO がどこに居てよいか」であって、「思考がどこに居るべきか」ではない。**
この 2 つは別物で、Spacta が本当に守りたいのは後者に見える。ここが最大の「言っていることと証明していることのギャップ」である。

改善案としては、法にするのが難しければ advisory (info) でよいので、
shell の非 JSX 文の数や分岐数を数えて閾値超過を報告する、程度でも効くはずだ。
`types.ts` の行数予算をすでに数えているのだから、同じ発想で測れる。

### 4.3 `shared/` の予算が「方向」でしか守られていない

L7 は shared → features の逆依存を禁じる。方向の保護としては正しい。
だが**量**については、`types.ts` 250 行という info があるだけである。

本件で私は、ドメインの読みモデル (`TraceRecord`, `CommentRecord`, `AdminReport`, `AdminRequest`, `AdminUser`, `TraceWithPage` …) を
`shared/types.ts` に置かざるを得なかった。理由は明快で、
**`shared/source/queries.ts` (IO 縁) と features の両方がこれらを必要とし、
L7 により source は features から型を借りられない**からである。

結果として `shared/types.ts` は画面が増えるたびに単調増加する。
そして**全 feature が依存する唯一のファイル**になる。
Spacta が防ごうとしている結合が、消えたのではなく shared に移動しただけ、とも読める。

現状 175 行なので info には触れていないが、これは Spacta の構造が招いた必然であって、
私の設計の緩さではないと思っている。`types.ts` を「膜語彙 (Action/Effect/State/InitData)」と
「ドメイン読みモデル」に分けるか、読みモデルは feature 側に置いて source が構造的部分型で返す、
といった指針が §2 にあってほしかった。

### 4.4 L8 のエスケープハッチが広すぎる

`verify.mjs` の分類はこうなっている:

- 無彩色 (slate/gray/zinc/neutral/stone/white/black) → info を出す
- **ステータス色 (red/orange/amber/yellow/green/emerald/blue/sky) → 無条件に許容**
- その他のパレット色 → 透過度が付いているときだけ info

つまり `text-slate-500` は叩かれるが `text-red-500` は素通りする。
「ステータス色は意味を持つから」という理屈は分かるが、実務上は
**パレットの半分が常時開放されている**のと同じで、ここから提示語彙は容易に崩れる。

私は §3.3 の通り、エージェントには「パレット色は一切禁止」という掟より厳しいルールを与え、
痕跡タイプの 4 色 (stuck/insight/resource/footprint) すら `tailwind.config.ts` の
セマンティックトークンとして定義した。L8 に従っていれば `text-amber-600` で済ませられたが、
それをやると「なぜこの色なのか」が UI に散らばって復元不能になる。

**掟に従うより厳しくした方が良い結果になる掟は、掟として弱い。**

### 4.5 L1 の「重複せよ」と clone 検知が、指示として衝突している

§2.5 は「重複を恐れず feature 内に閉じよ」と言う。同時に clone 検知は
「UI が重複しているぞ」と info を出す。SPACTA.md はこれを「庭師 (人間/AI) が判断する」と整理しているが、
**同じツールの出す 8 つの信号のうち 2 つが設計上矛盾している**という事実は変わらない。

本件では clone 0 件だったので実害は出なかった。だが、経験の浅いエージェントが
clone info を「直すべき赤」と誤読した場合、最も自然な「修正」は
共通コンポーネントを片方の feature に作って他方から import することであり、
それは即座に L1 違反になる。**info を解消しようとすると法を破る**という罠が構造的に存在する。

§2.5 に一文 —— 「clone info は決して feature 間 import を追加する理由にはならない」—— が明記されていれば防げる。

### 4.6 starter の日本語コメントと英語ドキュメントの混在

これは些細だが実務では効いた。`SPACTA.md` は英語、`starter/src/**` のコメントは日本語である。
私は starter を参照実装として読んだが、生成するアプリの UI と規約は英語で統一する必要があった (要件定義の指定)。
starter をそのまま真似ると言語が混ざる。私は全コメントを英語で書き直したが、
「参照実装をコピーして始めよ」と言うなら、参照実装の言語は出力の言語に対して中立であってほしい。

## 5. Spacta は何に向いているか (私の結論)

### 向いている

- **複数の AI エージェントに並列でコードを書かせ、成果物を精読せずに受け入れたい場合。** これが本命だと思う。
  L1/L7 が衝突を物理的に防ぎ、L6 付きの `verify` が受け入れテストになる。
  今回、22 ファイル・4 体分の成果物を私は読んでいない。これは Spacta なしには取れないリスクだった。
- **同じ計算をサーバとクライアントの両方で走らせるアプリ。** 純度が同一性を保証するので、
  楽観的 UI と SSR の乖離という定番のバグクラスが構造的に消える。
- **監査可能性が要るアプリ。** 非決定性と IO の在り処が、規約ではなく事実として 1 箇所に畳まれる。

### 向いていない・効果が薄い

- **1 人 (1 体) で小さいものを書くだけの場合。** 掟が要求する配置は、注意深い実装者なら
  どのみちそう書く。得られるのは「証明」であって「指導」ではないので、証明が要らない規模では純粋なオーバーヘッドになる。
- **設計をアーキテクチャに考えてほしい場合。** Spacta は思考の置き場所を教えてくれない (§4.2)。
  膜の語彙 (`InitData`/`State`/`Action`/`Effect`) を自分で設計できる人が使う道具であって、
  設計を代行する道具ではない。

## 7. 総評

私は掟に一度も止められなかった。それは掟が緩いからではなく、
**掟が要求する配置が、注意深く設計した場合の配置と一致していたから**である。
これは Spacta にとって良い性質だと思う。正しくやろうとしている実装者に対して、コストがほぼゼロだった。

その上で、Spacta が本当に価値を出したのは私の実装作業そのものではなく、
**私が他者 (サブエージェント) の成果物を信用するかどうかの判断**だった。
L6 付きの緑を見て 22 ファイルを読まずに受け入れられたこと。これが本件で Spacta が生んだ唯一の、
しかし決定的な価値である。

だから私の結論はこうなる。
**Spacta は「AI が全体を把握せずに実装するためのアーキテクチャ」ではなく、
「人間が AI の成果物を精読せずに受け入れるためのアーキテクチャ」である。**
v0.9 のドキュメントは前者を売りにしているが、実装して分かった強みは後者にある。
そして後者として売るなら、§4.1 (書き経路の戻り) と §4.2 (shell の厚み) の穴は、
「読まずに受け入れる」の信頼範囲に直接穴を開けているので、埋める価値が高い。

最後に、一実装者として最も敬意を持ったのは L6 である。
自分が赤を出せることを毎回証明してから緑を名乗るという態度は、
検証ツールの誠実さの基準を一段上げていると思う。他の掟が明日すべて変わっても、L6 の発想は残る価値がある。
