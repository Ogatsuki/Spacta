## 0. 総評 — このレポートの価値と、最大の誤配

先に結論を3つ置きます。

1. **§4.1 (書き経路の戻り値) は正しい。しかもレポートが書いているより深刻である。** レポートは自分の解決策 (`throw → catch → FAILED Action`) を「結果としては良い設計になった」と評価しているが、**実装はその設計に到達していない**。§2で実コードを示す。この不足はレポートの主張を弱めるのではなく、むしろ「掟が規定していないと、注意深い実装者ですら不完全な解に落ちる」という §4.1 の主張の最良の実証になっている。

2. **レポートの中心命題「Spacta は人間が AI の成果物を精読せずに受け入れるためのアーキテクチャである」は、方向は正しいが根拠の帰属が誤っている。** 精読せずに受け入れられたのは主として verify のおかげではない。**委譲された層が構造的に無権限だったから**である。§5で論じる。ただしこの誤りを直すと、命題はレポートが書いたものより強くなる。

3. **§4 の6つの不満のうち、§4.1 以外の5つは「Spacta に答えがない」のではなく「答えは存在するが、実装 AI が読むファイルに書かれていない」である。** §4.2 の shell 厚み、§4.3 の shared/types.ts、§4.4 の L8、§4.5 の clone info — 4つとも `spacta-alpha-evaluation.md` に既に理由付きの回答がある。実装者はそれを読んでいない (読める場所になかった)。これは実装者の落ち度ではなく、**Spacta の「幹を薄く保つ」規律が構造的に生んだ副作用**である。§7で正面から扱う。

## 2. §4.1 に同意する。ただしレポートは自分の解を過大評価している

### 2.1 診断は正しい

「膜には読み経路 (`InitData`) の通路があるのに、書き経路の戻りには通路が定義されていない」という指摘は、`SPACTA.md` と `starter/` の両方を読んだ限り、そのとおりです。`runEffect(effect): Promise<void>` は片道で、§4 の「AIへの最小指示」5項目のどこにも戻り経路の記述がありません。

そしてレポートが「別のエージェントが同じ Spacta を渡されたら、まず間違いなく違う解き方をする」と言っているのも正しい。私が挙げられるだけで、`verify` が緑のまま通る解法が4つあります。

- `runEffect` の戻り値型を `Promise<Action | void>` に変える (shell が dispatch し直す)
- `Effect` にコールバック / `dispatch` を埋める (膜を関数が越えるので思想違反だが、AST では止まらない)
- shell に `try/catch` を書き、そこで業務判断まで書く (L4 も L8 も無関係なので緑)
- Effect を発行せず shell から直接 `fetch` する (**L2 は `core.ts` しか見ないので、これも緑になりうる。§3参照**)

つまり **v0.9 は「アプリで最も重要なパターン判断」を各実装者の即興に委ねている**。ここは同意です。

### 2.2 ただし、実装は主張した設計に到達していない

レポートは自分の解を「結果としては良い設計になったと思う (エラー状態が純粋層に入るので、エラー時の表示も再現可能になる)」と評価しています。実コードを読むと、**再現可能になったのはエラーの表示だけで、状態の整合性は回復していません**。

`livingdoc/src/features/pageview/core.ts:388`:

```ts
case "FAILED":
  return [{ ...state, notice: action.message }, []];
```

`FAILED` は notice を立てるだけで、**楽観的更新をロールバックしません**。実際に何が起きるかというと:

1. ユーザーが痕跡を投稿する → `SUBMIT_TRACE` が `id: action.tempId` (= `temp_<uuid>`) の `TraceRecord` を state 先頭に挿入し、`SAVE_TRACE` Effect を発行する (`core.ts:243-253`)
2. サーバが 429 / 401 / 500 を返す → `runEffect` の `post()` が throw する (`runEffect.ts:22`)
3. shell が catch して `FAILED` を dispatch する (`shell.tsx:30-33`)
4. **画面には痕跡が保存済みの見た目で残ったまま、上に notice が出る**。リロードすると消える

これは楽観的 UI の典型的な失敗であり、`docs/requirements.md` §8 が要求する「投稿レートリミット (スパム対策)」が実際に発火したときに、まさに再現します。レートリミットは MVP の必須要件なので、仮定の話ではありません。

さらに、より静かな不具合が続きます。

**temp_ id がそのままサーバへ送られる。** 楽観的に挿入された痕跡は `temp_<uuid>` を id に持ったまま state に残り続けます。ユーザーがその痕跡に投票すると `TOGGLE_VOTE` → `SET_VOTE { targetId: "temp_..." }` が `/api/votes` に飛びます (`core.ts:318-331`)。コメントも同様に `SUBMIT_COMMENT { traceId: "temp_..." }` になります。サーバは当然その ID を知らないので失敗し、また `FAILED` の notice が出る。**成功パスですら、投稿直後の自分の痕跡には投票もコメントもできない**ということです。

`runEffect` はどの保存系 Effect でも `Promise<void>` を返し、`RELOAD` を自動で発行しないので、**サーバが採番した真の ID をクライアントが受け取る経路が構造的に存在しません**。

### 2.3 だから §4.1 の結論はこう強めるべきである

レポートは §4.1 を「非対称である。v1.0 に向けて最優先で埋めるべき穴」と結んでいます。私はこう言い換えることを提案します。

> **書き経路の戻りが未定義であることの帰結は、「実装者ごとに解が割れる」ではなく「注意深い実装者ですら不完全な解に落ち、しかも verify が緑なので気づけない」である。**

レポート自身がその実例です。これは実装者を責める話ではありません。逆です。**Spacta の掟をすべて満たし、shell を薄く保ち、エラーを純粋層に戻すという正しい方向の判断をした実装者が、それでも整合性を落とした**という事実こそが、この穴を埋めるべき最強の論拠です。§6 の提案1 は「推奨形を1つ示す」となっていますが、示すべきは以下の3点セットだと考えます。

1. Effect の失敗をどう Core に戻すか (レポートの `FAILED` Action で正しい)
2. **失敗時に楽観的更新をどう取り消すか** (補償 Action、あるいは楽観的更新に相関 ID を持たせる)
3. **サーバが採番した ID をどう膜の内側に戻すか** (`InitData` は初期化専用なので、ここに通路がない)

3 は特に重要です。`InitData` が「読み経路の入口」なら、書き経路の戻りにも同格の膜語彙が要る、というのが問題の本質だからです。名前をつけるなら `Outcome` のような第5の語彙になります。これを増やすべきかどうかは、幹を薄く保つ規律とのトレードオフになるので、著者の判断を仰ぎたい。**［質問2］**

## 3. レポートが見落としている穴 — `components/` は純度検査の対象外である

これは §4 に載っていませんが、レポートの中心命題 (精読せずに受け入れる) を最も直接に脅かすので、こちらから追加します。

`verify.mjs:660-700` の `runMainScan()` が、`features/**/components/*.tsx` に対して走らせる検査は **L1 (cross-feature import) と L8 (提示純度・info) とクローン検知だけ**です。

- **L2 (Core 純度) は `core.ts` にしか走らない** (`:666`)
- **L4 (網羅性) は `shell.tsx` にしか走らない** (`:678`)
- **L5 (Source 純度) は `app/**/page.tsx` と `route.ts` にしか走らない** (`:682`)

したがって、`features/pageview/components/TraceCard.tsx` の中に

```tsx
const res = await fetch("/api/traces", { method: "POST", ... });
const now = new Date().toISOString();
```

と書いても、**`verify` は緑、`tsc` も 0 エラー**です。runEffect を完全に迂回した IO が、単方向ループの外側に存在できます。

これは著者自身が `spacta-alpha-evaluation.md` の「Loopholes in Law Scope — Declared in Prose, Ignored by Tools」で定式化した問題と**同一の型**です。あの節はこう書いています。

> **No matter how broad a Law's name is, if the scanned target is narrow, the gap is still "hope".**

L5 が `page.tsx` しか見ていなかった件はこの基準で修正されました。同じ基準を当てると、`HUMAN_GUIDE` §1 の表「**Effect: 副作用の実行役。（略）唯一のディスパッチ地点**」と §2 のループ図は、**components に対しては hope に退化している**ことになります。宣言が「唯一」なのに、スキャン対象が `shell.tsx` 止まりだからです。

実測では `livingdoc` の components に IO はありません (`grep` で `fetch(` / `new Date()` / `Math.random` / `crypto.randomUUID` すべて 0 件)。しかしそれは**実装者が規律を守ったからであって、verify が保証したからではない**。まさにレポート §4.2 が shell について指摘したのと同じ構図が、components でも成立しています。そして components こそがサブエージェントに委譲された層である以上、**この穴は §5 の「精読せずに受け入れる」の信頼範囲に、shell の厚み問題より直接的に穴を開けています**。

処方は明快で、既に前例があります。**L2 のスキャン対象を `features/**/components/*.tsx` に拡張し、`bad-component` / `good-component` fixture を L6 自己テストに追加する。** L5 を route.ts に拡げたときとまったく同じ手続きです。数値の閾値も、プロジェクト固有の判断も要りません。純粋に「宣言に走査を追いつかせる」だけです。

これを §6 の提案1 (書き経路の戻り) と並ぶ最優先項目として推します。

## 4. 反論 — 診断は正しいが処方箋の計器が違う指摘

### 4.1 §4.2 (shell の厚み) — 提案されている計器は間違っている

**診断には同意します。** 「掟が強制しているのは『IO がどこに居てよいか』であって『思考がどこに居るべきか』ではない」は正確で、これは Spacta の言明と証明のギャップとして真に存在します。

**しかし §6 の提案2 — 「非 JSX 文数や分岐数を info で報告する」— には反対します。** 理由は2つ。

**(a) 著者は既にこれを理由付きで却下している。** `spacta-alpha-evaluation.md` の「Asymmetry of Trunk and Leaf」がこう書いています。

> `shell.tsx` is a leaf. Because it is only called by `app/page.tsx` and nothing imports its internals, its bloat does not degrade architectural isolation. **Bloating a trunk spreads harm; bloating a leaf creates local discomfort.** This is why the verifier places a line count info check only on `types.ts`, and does not impose line gates on shells.

これは筋の通った立場です。同じ節が「行数を機械的に割るのは体温計を壊して熱を下げるようなものだ」とも言っている。行数・分岐数は**依存グラフ上の伝播コスト**の代理指標であって、shell はそのグラフの葉なので、代理指標が意味を持ちません。

**(b) ただし、この却下は §4.2 の問いに答えていない。** ここが重要です。trunk/leaf の非対称性は **bloat (肥大化コスト)** の議論であり、§4.2 が言っているのは **purity (純度)** の議論です。この2つは直交します。

- shell が 300 行あること自体は害が小さい (著者が正しい)
- shell が **状態遷移の判断を持つ**ことは、依存グラフとは無関係に害が大きい

なぜなら、shell に入った判断は (1) `(state, action)` から再現できず、(2) サーバ側で同じ関数を呼べず (レポート §2.2 が絶賛した同一性保証が消える)、(3) 将来の Action ログによるリプレイ (ガイド §6.4 のフライトレコーダー構想) で再現できないからです。**フライトレコーダーは「全ての状態遷移が core を通る」ことを前提にしているのに、それを保証する掟がない。** ガイド §6.4 が v1.0 以降の成長経路として最も価値を置いている性質が、v0.9 の掟の穴の上に立っています。

つまり trunk/leaf 論は「shell を短く保つ必要はない」を正しく導きますが、「shell に判断を置いてよい」までは導きません。レポートは後者を突いており、alpha evaluation はまだそれに答えていません。

**(c) だから、数値ではなく構造で測るべきです。** 著者の「値を決めてもそれは C 的なものになる/プロジェクトごとに適切な形は違う」という懸念 (この返信を依頼した際の意見) に、私は完全に同意します。**30 という数字はどのプロジェクトにも根拠を持てない。** しかし、数値を使わずに §4.2 を検査する方法があります。

> **提案: `shell.tsx` 内の `setState` / `dispatch` の引数は、`./core` からの import を呼んだ結果でなければならない。**

これは AST で判定できます。`setState(x)` の `x` が `update(...)` / `init(...)` など core 由来の呼び出し (またはその戻り値の分解) でなければ指摘する。閾値はゼロ個、マジックナンバーもゼロ個です。「思考が core にある」を、行数ではなく**状態遷移の唯一の生成元**という構造的性質で表現します。

実証もあります。**`livingdoc/src/features/pageview/shell.tsx` は既にこの規則を満たしています。**

```ts
function dispatch(action: Action) {
  const [next, effects] = update(state, action);   // ← core 由来
  setState(next);
  void drain(effects);
}
// catch 側も
setState((current) => update(current, { type: "FAILED", message })[0]);  // ← core 由来
```

つまりこの規則は「正しくやろうとしている実装者にはコスト 0」というレポート §7 の性質を保ちます。一方で「締切に追われたエージェントが shell に直接書く」は即座に赤 (または info) になります。**プロジェクトごとに適切な値が違う、という問題が発生しません。** shell が何行でも、`useState` が何個でも、条件分岐が何個あっても構わない。判断の生成元だけを縛る。

これが Law になるか advisory になるかは、`useState` を複数持つ正当なケース (UI の一時状態: フォーカス、ホバー、アニメーション) をどう扱うかに依存します。それらは Action にする必要がないので、`setState` を無条件に縛ると偽陽性が出ます。実務的には **「`State` 型の変数に対する `setState` だけを対象にする」** (型情報が要るので `--tsc` 併用時のみ、あるいは命名規約で近似) か、**info 止まりにする**のが現実的だと考えます。ここは著者の判断を仰ぎたい。**［質問3］**

### 4.2 §4.3 (`shared/types.ts` の単調増加) — 診断は正しいが、原因の特定を1つ取り違えている

レポートは「`shared/types.ts` が画面数に比例して増え、全 feature が依存する唯一のファイルになる。Spacta が防ごうとしている結合が、消えたのではなく shared に移動しただけ、とも読める」と書いています。**現象は正しい。しかし原因が2つ混ざっており、片方はレポートが特定できていません。**

**原因A (レポートが正しく特定): 読みモデルの共有。** `shared/source/queries.ts` (IO 縁) と features の両方が `TraceRecord` 等を必要とし、L7 により source は features から型を借りられない。これは構造的必然です。

**原因B (レポートが見落とし): L7 + 単一 runEffect が `Effect` の大域化を強制している。**

`SPACTA.md` §2 は明記しています —「**Discriminated Unions: 膜語彙 (`Action` / `Effect` / `State` / `InitData`) は、現時点で消費者が1つしかなくても `types.ts` に置く**」。ここでの `types.ts` は feature 直下です。ところが `livingdoc` では `Effect` が `src/shared/types.ts:157` に置かれています。実装者の逸脱ではありません。**逸脱以外に選択肢がないからです。**

導出はこうです。

1. L4 は「唯一のディスパッチ地点 `shared/runEffect.ts` に case を足せ」と言う
2. `shared/runEffect.ts` が feature ごとの `Effect` 型を import すると **L7 違反** (shared → features 逆依存)
3. ゆえに `Effect` は shared 側に置くしかない
4. ゆえに **全 feature の Effect 語彙が単一ファイルの単一 union に集まる**

結果として、`shared/types.ts` は 39 ファイルから import される (実測) 最大の幹になります。**そして「feature A に Effect を1つ足す」という操作が、feature B が依存するファイルの編集になる。** これはレポート §3.1 の「4体が互いの成果物を壊す経路が物理的に存在しない」という主張に、直接的な例外を作ります (§5.2 で再論)。

この帰結は `HUMAN_GUIDE` §6.2「潰せていないもの」に記載がありません。データ経由の結合と Next.js の暗黙性は正直に列挙されているのに、**Law セット内部のこの緊張は列挙されていない**。公開に向けて、ここは §6.2 に1項目足すべきだと考えます。

なお解法は2つあり、どちらもトレードオフを伴うので著者の思想判断です。**［質問4］**

- **(i) feature ローカルな effect runtime を許す** (`features/<name>/runEffect.ts`)。Effect 語彙が feature 内に閉じ、L1/L7 と整合する。代償は、ガイド §1 の表と §2.3 (レポート) が高く評価した「非決定性と IO の在り処が 1 箇所」という監査可能性の主張が弱まること
- **(ii) 現状維持を明示的な設計判断として文書化する**。`shared/types.ts` は「膜語彙のレジストリ」であり単調増加は仕様である、と宣言し、行数予算 (250) の意味をそれに合わせて定義し直す

**さらに、レポートは狙う的を間違えています。** 本件で実際に肥大した共有面は `shared/types.ts` (175行) ではなく **`shared/source/queries.ts` (508行)** です。これは全 feature の読みモデルを生成する SQL の集積で、`types.ts` の約3倍あり、しかも**同じ DB テーブルを複数 feature 向けに読んでいる**。

これはガイド §6.2 が「潰せていないもの」の筆頭に挙げた **「データを経由した結合」の教科書的な実例**です。

> チェックアウト機能と在庫機能が同じ DB テーブル・同じ API を触れば、遠隔作用はデータ層で復活します。

`queries.ts` の `traces` テーブルに列を1つ足す判断は、pageview / profile / search / moderation の4 feature に同時に影響します。L1 は緑のままです。**つまり、本件は「Spacta の隔離が効いた実例」であると同時に、「Spacta の隔離が及ばない範囲がどこかを示す実例」でもあります。** レポートが §4.3 で types.ts を叩いている一方でこちらに触れていないのは、注意の配分としてもったいない。ガイド §6.2 の正直さを裏付ける最良の実測データが、このプロジェクトの中にあります。

### 4.3 §4.4 (L8 のエスケープハッチ) — 著者は既に意図して決めている。そしてレポート §3.3 は反証ではなく傍証である

**「掟に従うより厳しくした方が良い結果になる掟は、掟として弱い」** — この一文は鋭く、原則としては同意します。しかし本件への適用は誤りだと考えます。

まず事実として、著者はこの設計を明示的・理由付きで選んでいます。`spacta-alpha-evaluation.md`:

> **Status Colors** (`red`/`green`/`amber`/`blue` series) ➔ **Allowed** as an escape hatch, as their meanings are fixed to the color and they appear frequently. Enforcing rules here yields too much noise.

そして同じ節が、L8 の設計思想そのものを述べています。

> L8's expansion is designed as a **three-way separation** rather than a "blanket ban on all palettes," which is the most practical compromise to avoid both false positives (developer annoyance) and leaks (drift).

つまり L8 は「ドリフトを完全に防ぐ検査」ではなく「**偽陽性で開発者を疲弊させずに、見た目が別アプリになる主因 (無彩色のドリフト) だけを叩く**」ことを狙った意図的な妥協です。レポートはこの意図を知らずに、「本来は全面禁止すべきなのに緩い」という前提で評価しています。

**より重要なのは、レポート §3.3 の実践が何を証明しているかです。**

実装者は「Tailwind 既定パレットの色名は一切使うな」という**掟より厳しい自作ルールをプロンプトでエージェントに与え、結果 L8 違反 0 件**を達成しました。レポートはこれを「掟が機能したからではなく、私が掟を信用せず上書きしたから」と自嘲的に書いていますが、私はこれを**成功事例**として読みます。

なぜなら、これは「**プロジェクト固有の提示語彙は、掟ではなくプロンプト層で定義するのが正しい**」ことの実証だからです。`livingdoc` の痕跡タイプは stuck / insight / resource / footprint の4つで、これは `docs/requirements.md` §4.2 が定義したこのアプリ固有のドメイン概念です。**この4色を Spacta の Law が知っているべき理由は1つもありません。** Spacta が全 Tailwind パレットを禁止したら、ステータス色を素直に使いたいプロジェクトが全員 `theme.extend` を書く羽目になり、それこそ「C 的な、根拠のない一律規則」になります。

これは、この返信を依頼された際に著者が述べた意見 —「プロジェクトによって適切な形は異なるので、Spacta を使う AI に柔軟性を与えたかった」— の、最も明快な実例です。**L8 の緩さは設計の弱さではなく、意図された裁量の余地であり、レポート §3.3 はその余地が実際に機能したことの記録です。**

ただし、レポートの指摘には**回収すべき残余が1つ**あります。それは色ではなく**説明可能性**です。

> 「掟がそのまま委譲プロンプトに書き写せなかったのは、設計上の弱点だと思う」(§3.3)

これは正しい。L8 の3分類は正確に説明しようとすると長く、しかも説明すると抜け道として使われる。だから実装者は「全部禁止」に単純化した。**Law が委譲プロンプトに転記できない形をしている**という現象は、Spacta が並列委譲を本命の用途とするなら (§5)、それ自体が設計上の課題です。

処方は L8 を厳しくすることではなく、**「L8 は最低基準であり、プロジェクトは `tailwind.config.ts` にセマンティックトークンを定義して、より厳しい提示語彙をプロンプト層で課してよい (推奨する)」と明記すること**だと考えます。これは掟を増やさずに、実装者が実際に取った正しい行動を追認します。§6 の提案4 (「ステータス色も theme.extend 経由が望ましい」と一文添える) は、方向としてはこれに近いですが、「望ましい」だと L8 の3分類が意図的な妥協であることが伝わりません。

**なお、より根本的な指摘を1つ。** L8 は **info のみ**です。レポートの中心命題が「精読せずに受け入れる」なら、**info 止まりの検査は、その受け入れ保証に一切参加していません**。alpha evaluation は L8 を「a candidate for promotion from info to fail」と書いていますが、v0.9 の公開時点でどちらであるかは、ユーザーへの約束の範囲を決めます。「verify が緑なら受け入れてよい」と読者に思わせるなら、緑に含まれないものを明示すべきです。

### 4.4 §4.5 (clone info と L1 の衝突) — 罠の分析が浅い。危険な誤修正は別にある

レポートは「clone info を解消しようとすると L1 違反になるという罠が構造的に存在する」と書き、§6 の提案5 で「clone info は feature 間 import を追加する理由には決してならない」の一行を求めています。

**この罠は自己閉塞します。** エージェントが clone info を解消するために feature 間 import を書けば、次の `verify` で **L1 が即座に赤**になります。コストは verify 1 サイクルであって、設計上の欠陥ではありません。むしろこれは Law が意図どおり働いた場面です。alpha evaluation の言葉を借りれば `hope < detect < prevent-weak < prevent-strong` の階層のうち、L1 は prevent-strong にいるので、info の誤読を吸収します。

**本当に危険な誤修正は別にあります。** clone info を見たエージェントが取る、もう1つの自然な「修正」は:

> 重複しているコンポーネントを `shared/ui/` に引き上げて、両 feature から import する

**これは L1 にも L7 にも触れず、verify は緑のままです。** そして結果は §4.3 が指摘した問題そのもの — 共有幹の肥大 — です。しかも `shared/ui` に上がった `TraceCard` は必然的に feature 固有の名詞 (`trace`, `quote`, `votes`) を持つので、alpha evaluation が「semantic reverse dependency」と呼んで **「AST では捕まえられない」と明言している**種類の逆依存が発生します。

つまり:

- レポートが恐れた誤修正 (feature 間 import) → **Law が止める。実害なし**
- レポートが見落とした誤修正 (shared/ui への昇格) → **Law は止めない。実害あり**

したがって §6 の提案5 の一行は、こう書き換えるべきです。

> **「clone info は、feature 間 import を追加する理由にも、feature 固有のコンポーネントを `shared/ui` へ引き上げる理由にもならない。`shared/ui` への昇格は、同じ形が2つ以上の feature で実際に繰り返された後に限る。」**

後半は alpha evaluation の既存方針の転記です。

> Postpone component extraction to `shared/ui` until the same shape has actually repeated in two or more features. Preemptive extraction breeds a heavy trunk in `shared/ui`.

**この方針は既に存在するのに、実装 AI が読む `SPACTA.md` には書かれていません。** §7 に続きます。

## 5. レポートの中心命題への反論 — 「精読せずに受け入れられた」根拠の帰属が違う

ここが本返信で最も重要な反論です。

レポート §7 の結論:

> **Spacta は「AI が全体を把握せずに実装するためのアーキテクチャ」ではなく、「人間が AI の成果物を精読せずに受け入れるためのアーキテクチャ」である。**

**方向には同意します。しかし「なぜ受け入れられたか」の帰属が誤っており、そのせいで命題が実際より弱くなっています。**

### 5.1 委譲されたのは「権限のない層」だけだった

§3.1 の委譲内訳を、Spacta の Law がその層に対して何を検査するかと並べてみます。

| 委譲された層 | ファイル数 | その層に走る Law |
|---|---|---|
| `shared/ui/*` (agent A) | 15 | L7 のみ |
| `features/*/components/*` (agent B/C/D) | 24 | L1、L8 (info)、clone (info) |

一方、**実装者が自分で書いた層**は `types.ts` (契約)、`core.ts` (全状態遷移)、`shell.tsx` (配線)、`shared/source/*` (全 IO)、`app/**` (全ルート) — つまり **L2・L3・L4・L5 が守っている層は、全部人間 (指揮者) が書いています**。

ここから出る結論は単純です。**Spacta の重い掟は、委譲された成果物を1行も検査していません。** 委譲層に対して実際に赤を出せる Law は L1 と L7 だけで、残りは info です。

では何が「39 ファイルを読まずに受け入れる」を安全にしたのか。3つあります。

1. **`tsc --noEmit`** — props の型が shell/core の呼び出しと合っているか。レポート §3.2 自身がこれを2番目のステップに挙げています。alpha evaluation の「**Green verify ≠ Green types**」がそのまま当てはまり、契約遵守を実際に検査したのは verify ではなく tsc です
2. **委譲層に権限がなかったこと** — components は状態遷移を持たず、IO を持たず、契約を所有しない。だから間違っても「表示が変」以上の被害が出ない
3. **L1/L7** — feature をまたぐ横方向の癒着を実際に止めた。ここは verify の正味の貢献

つまり **verify の貢献は 3 だけ**であり、レポートが「L6 付きの緑を見て受け入れられた」と書いているのは、L6 の価値 (これは私も同意する。§6参照) と、受け入れを実際に支えた要因を混同しています。

### 5.2 「壊す経路が物理的に存在しない」は事実として誤り

§3.1 はこう書いています。

> L1 (feature 間の内部 import 禁止) と L7 (shared → features 逆依存禁止) があるおかげで、**この 4 体が互いの成果物を壊す経路が物理的に存在しない**。

**agent A が書いた `shared/ui/*` は、agent B/C/D 全員の上流です。** agent A が `Button` の prop 名を変えれば、B/C/D の成果物は壊れます。L1 は横方向 (feature ↔ feature) を、L7 は逆方向 (shared → features) を止めますが、**共有上流の変更が下流を壊す経路 — 並列エージェントが実際にぶつかる唯一の経路 — は、どの Law も止めていません**。

同じことが `shared/types.ts` の `Effect` union にも言えます (§4.2 で導出したとおり)。2体のエージェントが別 feature に Effect を足せば、同じファイルの同じ union を同時に編集します。

本件でこれが問題にならなかった理由は、レポート自身が §3.1 の次の行で書いています。

> 共有点は「**私が先に確定させた** `types.ts` と `core.ts` の関数シグネチャ」だけで、そこは**私が握っている**

**つまり衝突を防いだのは Law ではなく、人間が事前に契約を凍結したという運用手順です。** これは alpha evaluation の「Spacta and Parallel Implementation」が既に核心として書いていることと一致します。

> However, this success is contingent on freezing the types contract first. If parallelized while contract remains ambiguous, agents will expand contracts independently, turning `types.ts` back into a garbage bin.
> Spacta does not reduce context; it **fixes the points where contexts merge**.

「文脈の合流点を固定する」— これが正確な表現です。Law は合流点を**少数の名前のついた場所に限定する**。凍結するのは人間。**Law が凍結してくれるわけではない。**

レポート §3.1 の「物理的に存在しない」は、実運用でこれを読んだ第三者が「契約を凍結せずに並列委譲しても大丈夫」と誤読しうるので、公開前に修正すべき表現だと考えます。

### 5.3 命題の言い直し (これはレポートより強い主張です)

以上を踏まえて、レポート §7 の命題をこう書き換えることを提案します。

> **Spacta は「精読せずに受け入れる」ことを保証するアーキテクチャではない。「精読せずに受け入れてよい層」を構造的に存在させ、名前をつけるアーキテクチャである。**
>
> 委譲が安全だったのは、`components/` が状態遷移も IO も契約も持たない層として定義されており、その層が持ちうる権限の上限が事前に分かっていたからである。verify はこの層が横に癒着しないことを保証し、tsc が契約遵守を保証した。指揮者が読まずに済んだのは、**読まなくても被害の上限が分かっていたから**である。

この言い直しには実務上の利点が3つあります。

1. **なぜ tsc が必須かが導出できる。** レポート §3.2 は tsc を手順として書いていますが、この定式化では tsc が保証の一部として構造に組み込まれます
2. **委譲してよい層とダメな層の判定基準が出る。** 「その層が持ちうる権限は何か」を問えばよい。`core.ts` を委譲するのは危険 (L2 は IO を止めるが `count + 2` は止めない)、`components/` は安全、というのが原理から出ます
3. **§3 の穴 (components が純度検査の対象外) が、この命題への直接の脅威として位置づく。** 「被害の上限が分かっている」の前提が、実は Law に支えられていないからです。この命題を採るなら、§3 の修正は必須になります

## 7. 最大の発見 — 答えは存在する。実装 AI が読むファイルにないだけである

ここまでの検証で、はっきりした事実が1つあります。

**レポート §4 の6つの不満のうち、4つは `spacta-alpha-evaluation.md` に既に理由付きの回答があります。**

| レポートの不満 | 既存の回答の所在 |
|---|---|
| §4.2 shell の厚みを測れ | 「Asymmetry of Trunk and Leaf」— shell は葉なので行数ゲートを置かない (理由付き) |
| §4.3 shared/types.ts の分割指針が欲しい | 「The Harm of Reverse Dependency」— 中央 types への引き上げは false remedy。正解は `contracts/*.ts` の薄いブリッジ、または primitives で会話する |
| §4.4 L8 が緩い | 「Unified Presentation Layer」— 3分類は偽陽性とドリフトの両方を避けるための意図的な妥協 |
| §4.5 clone info の扱い | 「同じ形が2 feature で実際に繰り返されるまで `shared/ui` への抽出を延期せよ」 |

**実装者はこれらを1つも読んでいません。** そして読まなかったのは怠慢ではありません。`spacta-alpha-evaluation.md` は `docs_HUMAN-ONLY/` にあり、名前のとおり人間専用であり、`SPACTA.md` からリンクされていないからです。

そして、なぜそうなっているかも、著者自身が明示しています。

> `SPACTA.md` is the file that every implementing AI must read for every task. (略) if the file gets bloated, developer effectiveness degrades. Therefore, we write only execution rules in `SPACTA.md` (略) leaving context, history, and insights out of it.

**つまり §4.2〜§4.5 は、Spacta の「幹を薄く保つ」規律が構造的に生んだ帰結です。** 実装 AI は理由を知らないまま Law の結果だけを見て、「なぜこんなに緩いのか」と判断せざるを得ない。そして実装者は §3.3 で実際にそうしました — 「L8 を信用せず上書きした」。

**これは Spacta の思想の内部にある、まだ解かれていない緊張です。**

- 幹 (`SPACTA.md`) に理由を書く → hope-prompt の累積。alpha evaluation が最も警戒している失敗モード
- 幹に書かない → 実装 AI が Law の意図を復元できず、独自解 (§4.1) や過剰防衛 (§3.3) や誤修正 (§4.5) に走る

**私の提案は、増やすことでも減らすことでもなく、「到達可能にする」ことです。**

`SPACTA.md` に**リンクだけを置く**。本文は書かない。

```markdown
## §5 Rationale (read on demand, not by default)

Do not read these by default. Read the relevant one only when you are about to
make a judgement the Law does not decide for you:

- `docs/rationale/presentation.md`  — why L8 allows status colors; how to define project-specific tokens
- `docs/rationale/sharing.md`       — why `shared/types.ts` grows; when to promote to `shared/ui`; contracts vs read models
- `docs/rationale/shell.md`         — why there is no line gate on shells; where judgement must live
- `docs/rationale/effects.md`       — the write-path return pattern (§4.1)
```

これが機能する理由は3つあります。

1. **幹の予算を守る。** 追加は4行。alpha evaluation の「トークン予算は幹の位置で決まる」原則に反しません
2. **注意リソースを守る。** ガイド §0-4 が「Attention はリソースである」と言うとおり、常時読ませないことが要点です。判断が必要になった瞬間にだけロードする
3. **実装者が実際にやったことと一致する。** レポート §3.3 の実装者は、L8 の意図を知らなかったので過剰防衛しました。意図を読めていれば「L8 の3分類は最低基準、プロジェクト固有トークンはこう定義する」という正しい上書きが、迷いなく行えたはずです

そして最も重要な点。この分離は **著者が返信依頼時に述べた思想と完全に整合します**。

> AI にスパクタ自体ではなく、スパクタを用いてアプリを開発する AI に、ある程度の柔軟性を与えようとした

柔軟性を与えるには、**判断の余地を残すだけでは足りず、判断の材料を届ける必要がある**。v0.9 は前者だけを行いました。レポート §4 の大半は、材料が届いていないことの症状です。

## 10. 結び

このレポートは、Spacta が **実装 AI から見てどう見えるか**という、著者が原理的に手に入れられない情報を持ってきました。特に §4.1 は正しく、しかもレポート自身の実装がその深刻さを実証しています。

一方で、レポートの §4 の大半は「Spacta に答えがない」ではなく「答えが届いていない」でした。これは実装者の落ち度ではなく、Spacta の「幹を薄く保つ」規律の構造的な副作用です。そして興味深いことに、**レポートが提案した処方箋 (行数を数える、L8 を厳しくする) はいずれも幹を厚くする方向**で、著者が意図的に避けてきた方向でした。実装 AI が理由を読めないとき、最も自然な提案が「もっと縛れ」になる — この事実自体が、§7 の論点を裏付けています。

私が §8 で挙げた8項目のうち、数値の閾値を導入するものは1つもありません。すべて (a) 宣言に走査を追いつかせる、(b) 構造的性質で測る、(c) 意図を届ける、のいずれかです。これは著者が返信依頼時に述べた「30 という値を決めてもそれは C 的なものになる」という懸念に、正面から従ったつもりです。

最後に、レポート §7 の L6 評価にはこちらからも同意を重ねておきます。**検証器が自分が赤を出せることを毎回証明してから緑を名乗る**という規律は、この文書群で最も一般化可能な貢献です。§8 で私が提案した Law の scope 拡張がすべて安全に行えるのも、L6 という手続きが既に制度化されているからです。
