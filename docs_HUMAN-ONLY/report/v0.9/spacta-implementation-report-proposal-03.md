## 0. 総評 — 主張は1つだけ

reply-02 §2.2 で実装者が認めたとおり、agent A (`shared/ui`) と agent B/C/D (各 feature の `components/`) は**同時に**走り、B/C/D は agent A の実コードを見ないまま、プロンプトに書かれた散文の props 仕様だけを頼りに `shared/ui` を import していた。

この事実に対する処方として、著者は2案を検討している。(1) UI 層は全て1体の AI が書く、(2) layout/page/shell/components を1ファイルに戻し、重複を clone 検知器で担保する。

**私の提案はどちらでもない。** 実コードを測ると、危険な依存の辺は**1本しかない**。したがって直すべきは並列そのものではなく、**並列の順序**である。

先に結論を3点置く。

1. **`import` は下向きの一方通行であり、危険な辺は `shared/ui ← components/shell` の1本だけである。** feature 同士 (兄弟) は L1 が prevent-strong で守っているので、いくら並列に走らせても衝突経路がない。今回無傷だったのは偶然ではない (§2)
2. **「UI は1体の AI で実装せよ」という規約は存在しない。** 著者の記憶にあるものより、実際の記述は弱い。しかもそれは実装 AI が読まないファイルにある。これは reply-02 §1.4 の発見の2例目である (§1)
3. **層ごとの規模を実測すると、分割の判断を「負荷」で決めるべき根拠がない。** shell は3本・合計252行しかない (§3)

## 1. 事実確認 — 規約は破られていない。存在していない

著者は「UI に関しては統一性が取れないから、各 feature を1つの AI で実装するように、と人間用ファイルに書いたはずだ。今回その規約が守られなかったのではないか」と述べている。

**該当する記述は1箇所だけ存在し、そして内容が異なる。** `HUMAN_GUIDE_tactical_20260725-modify.md:67`:

> *なお、UIの見た目の統一だけは、1つの機能に閉じては保ちきれません。ページ間でデザインを揃えたいときは、複数機能のUIを横断して**見ながら**整えることを**推奨します**（他機能を import するわけではないので、隔離のルールには触れません）。*

これは **「デザイン調整時に横断して見よ」という推奨**であって、**「1体の AI が実装せよ」という作業分割の規約ではない**。「整える」対象は既に書かれた UI であり、実装フェーズの話をしていない。

さらに決定的な点がある。**この一文は `docs_HUMAN-ONLY/` にある。** reply-02 §1.4 が確立したとおり、実装 AI が読むのは `SPACTA.md` と `starter/` だけである。仮にここに「1体で実装せよ」と書かれていたとしても、**実装 AI には構造的に届かない**。

したがって今回起きたことは「規約違反」ではなく「**規約の不在**」である。そして、これは reply-02 §1.4 が発見した現象の2例目にあたる。

> 実装者は「逸脱してよい」と2回書かれているのを読んだ上で、逸脱を一度も検討しなかった (reply-02 §4.1)

1例目は「書いてあるのに従われなかった」、2例目は「書いたつもりが届く場所になかった」である。**症状は違うが原因は同じで、規範力が `SPACTA.md` と `starter/` に集中している一方、著者の意図が `HUMAN_GUIDE` に置かれている**という配置のズレである。

この観点は、reply-02 の編集計画 C2 (rationale の切り出しを「空白を埋めるもの」と「意図を説明するもの」に分ける) に、**第3の分類**を足すことを示唆する。すなわち「**運用手順**」である。並列委譲の順序は rationale でも Law でもなく手順であり、現状どの文書もそれを担当していない。

## 2. 診断の精緻化 — 危険な辺は1本しかない

### 2.1 `import` は下向きの一方通行である

実測 (`livingdoc/src/features/pageview/shell.tsx`):

```ts
import { useState } from "react";
import { runEffect } from "@/shared/runEffect";
import type { Effect } from "@/shared/types";
import { EmptyState } from "@/shared/ui/EmptyState";     // ← 下向き
import { NoticeBar } from "./components/NoticeBar";      // ← 下向き
import { PageMasthead } from "./components/PageMasthead";
import { ReportDialog } from "./components/ReportDialog";
import { SpotCard } from "./components/SpotCard";
import { TraceComposer } from "./components/TraceComposer";
import { buildSpots, init, pageStats, update } from "./core";
import type { Action, InitData, State } from "./types";
```

そして逆方向の実測:

```sh
$ grep -rn "shell" src/features/*/components/*.tsx
# 0 件
```

**`components/` は `shell.tsx` を一度も import していない。** これは pageview に限らず全 feature で 0 件である。

この非対称性は重要である。**「まだ存在しないファイルを import する」のは、常に上の層である。** `components/` の作者が必要としているのは「どんな props が渡ってくるか」という型契約だけで、それは `types.ts` と `tsc` が押さえている。上の層のファイルが存在しなくても、下の層は書ける。

したがって、**直列化すべき順序は一意に決まる。下から上である。**

```
shared/ui を確定 → components → shell → app/(page, layout)
（import される側が、常に先に存在している状態を保つ）
```

### 2.2 危険な辺と安全な辺の区別

| 辺 | 方向 | 守っている Law | 並列の安全性 |
|---|---|---|---|
| feature A ↔ feature B | 横 | **L1 (prevent-strong)** | **安全**。import 経路が物理的に存在しない |
| shared → features | 逆 | **L7 (prevent-strong)** | **安全**。同上 |
| `shared/ui` ← `components` / `shell` | 縦 (下向き) | **なし** | **危険**。tsc のみが事後に検出 |
| `components` ← `shell` | 縦 (下向き) | なし | 危険だが、同一 feature 内なので同一 AI が担当すれば消える |

**Law が守っているのは横方向と逆方向だけで、縦方向 (正しい向きの依存) は誰も守っていない。** これは L1/L7 の欠陥ではない。縦方向は**禁止すべき依存ではなく、正当な依存**だからである。Law に守らせる対象ではなく、**手順で守る対象**である。

実測すると、この危険な縦の辺を渡っている import は **30 ファイル** (`grep -rl "@/shared/ui" src app`) にのぼる。`shared/ui` は 15 ファイル・373 行しかないが、**アプリの過半のファイルの上流**である。

reply-02 §2.2 が告白した「もし agent A が `tone` を `variant` に改名していたら、B/C/D の 24 ファイルが同時に壊れていた」は、この 30 本の辺の話である。

### 2.3 したがって処方は「並列をやめる」ではない

review-01 §5.2 と reply-02 §2.2 は、揃って「衝突を防いだのは Law ではなく、人間が事前に契約を凍結したという運用手順である」と結論した。**これは正しいが、まだ一段抽象度が高い。**

実コードから言えるのは、より具体的な形である。

> **凍結すべきなのは「契約」一般ではなく、「縦の辺の下側」である。そして下側を実ファイルとして確定させてから上側を書けば、凍結という作業自体が不要になる。**

散文で props 仕様を凍結する (reply-02 §2.2 で実際に行われた方法) 必要があったのは、**下側がまだ存在しなかったから**である。存在していれば、契約は散文ではなくコードとして参照でき、`tsc` は事後検出ではなく**執筆中の即時検出**になる。

## 3. 実測 — 層ごとの規模

著者は「複数ページの shell を全て1体の AI で編集するのは負荷が高いのではないか」と懸念している。実測値を置く。

| 層 | ファイル数 | 行数 |
|---|---|---|
| `app/*` (layout + page) | 8 | **300** (うち `layout.tsx` は 26) |
| `features/*/shell.tsx` | **3** | **252** (48 / 86 / 118) |
| `features/*/components/*` | 24 | 1,188 |
| `shared/ui/*` | 15 | 373 |
| (参考) `shared/source/*` | 7 | 1,037 |

**懸念は実測では成立しない。** shell と app を合わせて 552 行であり、1体の AI が1セッションで扱う量として重くない。

### 3.1 副次的な発見 — 層は一律ではない

より重要な事実がある。**6つの feature のうち3つ (`catalog` / `search` / `profile`) には `shell.tsx` が存在しない。**

```
catalog/         components/  core.ts  types.ts          ← shell なし
materialrequest/ components/  core.ts  shell.tsx  types.ts
moderation/      components/  core.ts  shell.tsx  types.ts
pageview/        components/  core.ts  shell.tsx  types.ts
profile/         components/  core.ts  types.ts          ← shell なし
search/          components/  core.ts  types.ts          ← shell なし
```

静的表示だけの feature は `page.tsx → components/` の**2層**で完結しており、`shell.tsx` は**対話 (state と Effect) が必要な箇所にだけ生えている**。

これは「4階層が一律に存在する」という理解を修正する。層の深さは feature ごとに 2 か 3 であり、必要に応じて生えている。したがって「階層が深いこと自体が複雑性である」という懸念は、実測では過大評価になる。

## 4. 提案 — フェーズゲート

以上から、私の提案は次の形になる。**並列を減らすのではなく、並列の断面を依存の辺に合わせる。**

```
Phase 1 ─ 直列・1体 ─────────────────────────────
  shared/ui/* を書き切る（15ファイル・373行規模）
  ゲート: tsc が通り、実ファイルとして確定していること
  ↓
Phase 2 ─ 並列・N体 ─────────────────────────────
  各 feature の components/ を並列で書く
  各エージェントは Phase 1 の実コードを参照できる（散文の契約が不要になる）
  安全性の根拠: 兄弟間は L1 が prevent-strong で守る
  ↓
Phase 3 ─ 直列・1体 ─────────────────────────────
  各 shell.tsx + app/(page, layout) を書く（3+8ファイル・552行規模）
```

### 4.1 なぜこれが効くか

1. **危険な辺 (縦) を渡る並列が消える。** Phase 2 の各エージェントが import する `shared/ui` は、既に実ファイルとして存在する。散文で props を凍結する作業自体が要らなくなり、reply-02 §2.2 の失敗モードが構造的に消える
2. **安全な辺 (横) の並列は残る。** 今回実際に無傷だった 24 ファイルの並列執筆は、そのまま維持される。Spacta の L1 が実際に価値を出している唯一の場所を捨てない
3. **著者が最も気にしている UI の統一性が、Phase 3 で自然に担保される。** shell と layout を1体が最後にまとめて書くため、`HUMAN_GUIDE:67` が推奨する「複数機能の UI を横断して見ながら整える」が、追加の指示なしに手順として発生する

### 4.2 これは Law ではなく手順である

明示しておくが、**この提案は掟を1つも増やさない。** `verify.mjs` に検査を足す必要もない。フェーズ違反を機械的に検出する方法は (少なくとも安価には) 存在しないと考える。

したがってこれは reply-02 の編集計画で言えば **群 A でも B でも C でもない、第4の群「運用手順」**に属する。そして §1 で述べたとおり、現状どの文書もこれを担当していない。

### 4.3 置き場所についての意見

reply-02 §4.1 の発見 —— **「採用させたいパターンは、散文ではなく `starter/` に置くべきである」** —— をこの提案にも適用すべきだと考える。

フェーズゲートを散文で `HUMAN_GUIDE` に書けば、§1 で述べた「届かない場所に書く」を3度繰り返すことになる。手順を構造として表現する方法を、著者と前2者に問いたい (§6 ［質問1］)。

## 5. 著者の2案の評価

### 5.1 案1 (UI 層は全て1体の AI で書く) — 方向は正しいが、払いすぎ

**この案は確実に問題を消す。** 縦の辺を渡る並列が存在しなくなるからである。

だが、**安全だった横の並列 (24 ファイル) まで同時に捨てる**。Spacta の Law が実際に価値を出していた唯一の場所を、Law とは無関係な理由で使わなくなる。

§4 のフェーズゲートは、この案から「Phase 2 の並列」だけを救い出したものである。実質的には**案1の修正版**と言ってよい。

ただし公平のために書くと、§3 の実測 (UI 層合計 2,113 行) を見る限り、**この規模なら案1をそのまま採っても実務上のコストは小さい**。並列を捨てて失うのは実行時間であって、正しさではない。規模が数倍になるまでは、案1で運用して問題は起きないと思われる。

### 5.2 案2 (1ファイルに戻し、重複を clone 検知器で担保する) — 反対する

著者の案は「layout / page / shell / components を1ファイルに統合し、ページ間の重複を許した上で、`verify` の clone 検知器を応用して『重複したものが同じであること』を保証する」というものである。

**3つの理由で反対する。**

#### (a) clone 検知器は、期待されている仕事ができない

clone 検知は「**似ているものを見つける**」道具 (similarity detection) である。案2 が必要としているのは「**同じであるべきものが、まだ同じか**」という検査 (conformance verification) であり、これは別種の道具である。

そして実測が既に答えを出している。report-00 §3.4 の記録:

> clone 検知は 0 件。3つは同じものではなかった。TraceCard は投票・返信・通報を持ち `<header>` を持つ。ProfileTraceCard は場所を主役にして操作を一切持たない。タグ構成も className もほとんど共有していない

**重複させたものは、文脈が違えば自然に分岐する。そして clone 検知器は、分岐したものを「別物だ」と判定して黙る。** report-00 §3.4 はこれを Spacta の美点として記録したが、案2 の文脈では**同じ性質が担保の失敗を意味する**。8つのページに複製された layout は、放置すれば分岐し、分岐した時点で検知器は反応しなくなる。

#### (b) 現行の Gardener 仕様と正面から矛盾する

`garden/GARDENER.md` の `dedupe-clone` の定義:

> **Deduplicate only when there is a 100% exact match within the same feature** (Jaccard high similarity partial matches or cross-feature duplications are out of scope). ... **Cross-feature duplication and raising components to `shared/ui` is outside the Gardener's domain**

現行設計は、clone info の扱いを (i) 同一 feature 内、(ii) 100% 完全一致、の2条件に絞っている。**ページをまたぐ重複は、明示的に管轄外である。** 案2 が担保させようとしているのは、まさにこの管轄外の領域である。

これは実装の都合ではなく設計判断だと読める。review-01 §4.4 と reply-02 §2.3 が合意した「`shared/ui` への昇格こそが危険な誤修正であり、どの掟も止めない」という結論と、この管轄制限は整合している。

#### (c) Spacta 自身の評価基準で、2段の格下げになる

`spacta-alpha-evaluation.md` が定義し、review-01 §4.4 が引用した階層:

```
hope < detect < prevent-weak < prevent-strong
```

- layout を1箇所に抽出する = **prevent-strong** (食い違いようがない。`app/layout.tsx` は 26 行で、`shared/ui/AppShell` を1回呼ぶだけである)
- 8ページに複製して検知器で見張る = **detect** (食い違ってから気づく)

**案2 は、Spacta が自分を評価するために使っている物差しで、2段下がる。**

そしてもう一点。著者が layout を括り出した動機は、著者自身の説明によれば「複数ページに拡張したとき、ホームページとお問い合わせページで全く違う感覚で書かれてしまう」問題だった。案2 は**その病気を意図的に呼び戻し、検知器で治療しようとする**構図になる。現在 `app/layout.tsx` が 26 行に収まっていることは、抽出が成功している証拠だと考える。

#### (d) ただし、案2 には正しい洞察が1つ含まれている

著者はこう述べている。

> 1つのファイルだったら並列も何もないから、構造上「1つのファイルですよ」と AI に示した方が、並列でやるかどうかで迷わなくていい

**これは正しく、しかも reply-02 §4.1 の中心的発見と同じ系譜である。**

> 具体的なコードは、それを否定する散文より常に強い (reply-02 §4.1)

**指示は散文より構造で伝える方が強い。** この洞察は採用すべきである。ただし採用の仕方は「1ファイルに戻す」ではなく、**フェーズという時間的な区切りを、構造として表現する**方向だと考える。具体案は持っていない (§6 ［質問1］)。

## 6. 前2者および著者への質問

- **［質問4］(著者に)** §5.2 で案2 に反対したが、案2 の動機である「AI に並列可否を構造で伝えたい」は正当だと考える。**フェーズゲートを採ったとして、Phase 2 の各エージェントに「あなたは Phase 2 である」をどう伝えるか**。プロンプトに書けば §1 と同じ「消える影の掟」(reply-02 §3.2) になる。ここが未解決である。

## 7. 結び

この文書の正味の貢献は、実測に基づく1点に絞られる。**`import` が下向きの一方通行であるため、並列委譲において危険な依存の辺は1本しかない。** feature 同士は L1 が既に守っており、今回の失敗は「並列にしたこと」ではなく「**縦の辺をまたいで並列にしたこと**」に由来する。

したがって処方は、並列の放棄でも1ファイルへの回帰でもなく、**並列の断面を依存の辺に合わせること**である。これは掟を増やさず、`verify.mjs` を変更せず、今回実際に価値を出した横方向の並列を維持する。

前2文書が到達した「凍結するのは人間である」という結論に、私はこう付け加える。

> **凍結が必要になるのは、下流を先に書いたからである。上流から順に実ファイルとして確定させれば、凍結という作業自体が消える。散文の契約を tsc に検算させるのではなく、コードそのものを契約にできる。**

なお、L6 の評価については前2文書の一致に私も同意する。ここは動かない。
