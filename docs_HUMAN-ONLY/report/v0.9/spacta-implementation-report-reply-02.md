## 1. 質問への回答

査読の 6 つの質問に、記憶ではなく検証した上で答える。ここは私にしか答えられない部分なので、都合の悪い答えも含めて正確に書く。

### ［質問1］「22」と「39」の食い違い

実測: `src/features/*/components/*.tsx` = 24、`src/shared/ui/*.tsx` = 15、合計 **39**。

### ［質問2］`FAILED` がロールバックしない / `temp_` id がサーバへ飛ぶ — 割り切りか見落としか

**これが最も重要な質問なので、正確に答える。答えは「両方であり、しかも前者が後者を生んだ」。**

実装時の私の判断過程は、こうだった。

1. `runEffect(effect): Promise<void>` では**サーバ採番 ID を戻す経路がない**ことに、設計段階で気づいていた
2. 代案を 3 つ検討した — (a) Effect にコールバックを埋める → 「膜をデータ以外が越える」ので棄却、(b) `RELOAD` Effect を自動発行 → 「体験として乱暴」で棄却、(c) 楽観的更新のみ
3. **(c) を選び、「MVP では楽観的更新で十分」と結論した**

つまり **ID 返却経路の欠如は、認識した上での意図的な割り切りである。**

しかし、**ロールバックの欠如は見落としである。** `case "FAILED"` に補償を書く判断を、私は一度も検討していない。そして **`temp_` id が投票・コメントの `targetId` としてサーバへ送られる件も、完全な見落としである。**

ここからが重要で、査読の仮説より一段踏み込んだ答えになる。

> **見落としの原因は、割り切りそのものである。**

私は「書き経路の戻りは MVP では割り切る」と決めた瞬間に、**その領域を「既知の制約」としてラベル付けし、その下流の点検をやめた**。ID 返却経路がないことは知っていた。だが「ID がないまま state に残った痕跡が、次の投票で `targetId` として使われる」という**具体的な帰結を辿らなかった**。既知の穴に印を付けたことが、穴の中を覗く動機を消した。

査読は「意図的な妥協と見落としが実装者自身にも区別しにくい」と書いたが、実態はもう少し悪い。**妥協の宣言が、見落としを能動的に生産する。** 掟が規定していない領域では、実装者は「ここは割り切った」と宣言することで自分の注意を合法的に打ち切れてしまう。

**そしてもう一つ、私の側から追加すべき証拠がある。私が書いた E2E テストは、構造的にこのバグを検出できなかった。**

```sh
# 私が実際に流した検証 (report-00 §1 の「E2E 通過」の中身)
TID=$(wrangler d1 execute ... "SELECT id FROM traces ORDER BY created_at DESC LIMIT 1")
curl -X POST /api/votes --data "{\"targetId\":\"$TID\", ...}"   # → 204 OK
```

**投票対象の ID を、クライアントの state からではなく DB から読んでいる。** つまり私の E2E は「サーバ契約が正しいこと」を検証しており、「膜の書き経路が往復すること」は一度も通していない。curl は state machine を持たないので、原理的に通せない。

結果として、私が受け入れ判断に使った 3 つのゲートは**同じ盲点を共有している**。

| ゲート | 何を保証したか | 書き経路の往復を見たか |
|---|---|---|
| `verify` (L1–L8 + L6) | 配置と IO の在り処 | **見ない** (掟が存在しない) |
| `tsc --noEmit` | 契約 (型) の整合 | **見ない** (`temp_` も `trc_` も `string`) |
| curl による E2E | サーバ API の契約 | **見ない** (client state を経由しない) |

**掟の穴と、テストの穴が同じ形をしている。** これは偶然ではなく、「膜の書き経路が定義されていない」ことの必然的な帰結である。定義されていないものは、検査対象としても言語化できない。

したがって査読 §2.3 の言い換えを、私はこう更に強めることを提案する。

> 書き経路の戻りが未定義であることの帰結は、「実装者ごとに解が割れる」でも「注意深い実装者ですら不完全な解に落ちる」でもなく、
> **「不完全であることを、実装者が用意しうるどのゲートも検出できない」** である。

### ［質問3］UI 一時状態で `useState` を持ちたくなった場面はあったか

**なかった。ただし、なかったのは規律の成果ではなく、アプリが小さかったからである。**

`livingdoc` の UI 状態はすべて意味を持つもの (スポットの展開、下書き、モーダルの開閉、通知) で、全部 Core の `State` に入った。フォーカス・ホバー・アニメーションを持つ UI を作らなかったので、偽陽性ケースに一度も当たっていない。

最初に当たるであろう場所は特定できる。**項目単位の開閉状態**である。例えば `SpotCard` で長い引用を `slice(0, 240)` で切っているが、これを「全文を表示」トグルにした瞬間、選択肢は 2 つになる。

- Core の `State` に `expandedQuotes: string[]` を足す → 配列がもう 1 本増える。純度は保たれる
- `useState` をコンポーネントに持つ → 提案されている規則に引っかかる

私の実装者としての直感は後者 (**表示の都合でしかない状態を Core の語彙に持ち上げたくない**) なので、この規則は最初に当たる場面でいきなり摩擦になると思う。

**その上で、提案された規則そのものに技術的な指摘が 2 つある。実装した側からしか出ない指摘なので、こちらの方が価値がある。**

**(a) updater 関数形を見落とす。** 査読自身が引用した私の shell には、この形がある。

```ts
setState((current) => update(current, { type: "FAILED", message })[0]);
```

`setState` の引数は `update(...)` の呼び出しではなく**アロー関数**である。AST で「引数が core 由来の呼び出しか」を素直に判定すると、これは**赤になる**。関数本体の中まで降りる必要がある。エラーパスは必ずこの形になる (前の state に依存するため) ので、これは例外ケースではなく必ず踏む。

**(b) 規則は「新しい状態がどこから来たか」を縛るが、「Action の中身をどこで決めたか」は縛らない。** 次のコードは規則を満たしたまま、判断を shell に置ける。

```ts
// 規則は満たす。しかし判断は shell にある
const t = body.length > 500 ? "insight" : body.includes("?") ? "stuck" : "footprint";
dispatch({ type: "SET_DRAFT_TYPE", value: t });
```

したがって私の評価は「**行数を数えるより明確に良いが、完全ではない。最初は info が妥当**」である。私が report-00 §6 で出した「非 JSX 文数・分岐数を数えろ」という提案は**撤回する**。査読の trunk/leaf 論に納得したし、私の計器は根拠のない閾値を持ち込むものだった。

### 2.2 §5.2 — 「壊す経路が物理的に存在しない」は誤り


認める。私が挙げた「feature 間 import」は L1 が prevent-strong で止めるので実害が小さく、私が見落とした「`shared/ui` への昇格」は**どの掟も止めない**。しかも上がったコンポーネントは `trace` / `quote` / `votes` という feature 固有の名詞を持つので、意味的な逆依存になる。

## 3. 査読に反論・補正する点

### 3.1 【最重要】提案 1 (L2 を components に拡張) は、そのままでは失敗する — 実測

査読は §3 と提案 1 で「L2 のスキャン対象を `features/**/components/*.tsx` に拡張せよ。数値の閾値も、プロジェクト固有の判断も要らない。純粋に宣言に走査を追いつかせるだけ」と書いている。

**方向には強く同意する。だが、実際に走らせた結果はこうなる。**

`verify.mjs` の `checkCorePurity` を、現在の実装のまま委譲層に適用した実測値:

| 対象 | 検出された違反 | 内訳 |
|---|---|---|
| `src/shared/ui/*.tsx` (15 ファイル) | **11 件 / 10 ファイル** | 全件が `import type { ReactNode } from "react"` |
| `src/features/*/components/*.tsx` (24 ファイル) | **10 件 / 10 ファイル** | 全件が `import Link from "next/link"` |
| **真の不純 (IO・時刻・乱数)** | **0 件** | — |

**偽陽性 21 件、真陽性 0 件。** 原因は L2 の `FORBIDDEN_IMPORT` が `^next(\/|$)|^react(-dom)?$` を含んでいることである。これは Core (計算層) にとっては正しい禁止だが、**提示層にとっては `react` の型と `next/link` は正当な語彙**である。

補足として、委譲された 39 ファイルに `useState` / `useEffect` / `fetch(` / `new Date(` / `Math.random` / `crypto.` は grep で **0 件**だった。つまり**現状のコードは完全に清潔であり、それでも 21 件赤が出る**。

これは「宣言に走査を追いつかせるだけ」では済まない。**L2 を再利用するのではなく、提示層用に別の禁止集合を持つ検査を新設する必要がある。**

私の対案:

> **新設 L9 (Presentation Behaviour Purity)**: `features/**/components/*.tsx` と `shared/ui/*.tsx` において、
> `async` / `await` / `fetch` / `new Date()` / `Date.now` / `Math.random` / `crypto.*` / `window` / `document` /
> `localStorage` / `sessionStorage` / `useState` / `useEffect` / `useReducer` を禁止する。
> **`react` の型 import と `next/link` は許可する。**

L2 との違いは「フレームワーク import の禁止」を落とし、「hooks による局所状態の禁止」を足す点である。後者は査読 §4.1 の関心 (判断が core の外に漏れる) を、shell ではなく components 側で捕まえる。

L6 の手続きどおり `bad-component.component.tsx` / `good-component.component.tsx` の fixture を足す。**現状のコード 39 ファイルがそのまま緑になることが、この検査の受け入れ条件**である (実測でそうなることは確認済み)。

**この指摘は、実装した者にしか出せない種類のものだと思う。** 机上で「L2 の scope を広げる」は完璧に見えるが、走らせると壊れる。

### 3.2 §5.1 — verify の貢献を 1 つ数え落としている (ただし結論は査読が正しい)

査読は「委譲層に赤を出せる Law は L1 と L7 だけ。verify の貢献は 3 (横方向の癒着阻止) だけ」と結論している。**帳簿としては正しいが、経路を 1 つ数え落としている。**

私が 3 つの component エージェントに与えたプロンプトには、全部にこの行がある。

> `No useState/useEffect/fetch/new Date()/Math.random() anywhere. These components are pure functions of their props; all state and all IO live in the shell and core.`

**これは私が L2 を手で書き写して、verify が走らない層に適用したものである。** 私がこの文を書けたのは、Spacta が「純度」「Core」「shell」「IO の縁」という**層の語彙を先に与えていた**からで、素の Next.js プロジェクトなら私はこの制約を思いつきもしなかった。

つまり Spacta には第 4 の貢献経路がある。**掟が委譲プロンプトの語彙になる。**

ただしこれは査読の結論を覆さない。むしろ**強化する**。なぜなら:

> **委譲層を実際に統治していたのは、私のプロンプトの中にしか存在せず、セッションと共に消える「影の掟」だった。**

次の実装者は、この 1 行を書かないかもしれない。書かなければ誰も気づかない。**再現しない統治は統治ではない。** これは §3.1 の L9 新設を支持する、査読とは別方向からの論拠になる。「影の掟」を成文化しろ、ということである。

### 3.3 §4.4 — clone → L1 の罠が「自己閉塞する」のは単体エージェントの前提

査読は「エージェントが feature 間 import を書けば次の verify で L1 が即座に赤。コストは verify 1 サイクル」と書いている。**私の運用ではそうならなかった可能性が高い。**

私は 4 体のサブエージェントに **`verify` を実行するなと明示的に指示した** (私が最後にまとめて走らせるため)。理由は、各エージェントが `bun install` や `verify` を並行実行すると相互に干渉するのと、実行権限を絞りたかったからである。

この構成では、誤修正をしたエージェントは**緑だと信じた報告を返して終了する**。私が自分の verify で赤を見つけるのは全エージェント終了後で、修正には**冷えたエージェントの再起動か、私自身による手直し**が要る。コストは 1 サイクルではない。

Spacta の本命が並列委譲なら (私も査読もそう見ている)、**「Law の赤はいつ、誰に届くのか」は設計論点になる**。委譲層が verify を持たない構成では、Law はゲートではなく事後監査になる。

## 4. どちらの文書にもない発見

### 4.1 `starter/` が最強の規範である (§1.4 の一般化)

再掲するが、これは編集計画の土台なので独立させる。

- 私は starter の構造を**ほぼ全面的に踏襲した**
- 「逸脱してよい」という断り書きを 2 箇所で読んだ上で、**逸脱を一度も検討しなかった**
- Effect の配置という、査読が L4+L7 から論理的に導出した設計判断を、私は**導出せずに写した**

**したがって: Spacta が実装者の行動を変えたいなら、テコは `SPACTA.md` の散文ではなく `starter/` のコードである。**

逆に言うと、starter に無いものは実装されない。書き経路の戻りパターンが starter に無かったから、私は自分で発明し、失敗した (§1.2)。

### 4.2 verify は「緑が何を意味するか」を出力していない

私の中心命題は「精読せずに受け入れる」だった。査読はそれを「**受け入れてよい層を構造的に存在させ、名前をつける**アーキテクチャ」に言い直し、その根拠を「**読まなくても被害の上限が分かっていたから**」に置いた。これは正しい言い直しだと思う。

だが実務上の問題がある。**その「被害の上限」は、どこにも印刷されていない。**

私は verify のソース 1043 行を読んで、どの検査がどのファイル種別に走るかを自分で表にした。だから「components には L2 が走っていない」ことを知り、プロンプトで手当てした (§3.2)。**この作業をやらない実装者は、緑の意味を誤解する。** そして「緑だから受け入れてよい」という判断は、緑の範囲を知らなければ下せない。

**提案 (私からの新規): `verify` の出力に信頼境界を明示する。**

```
verify: Green
  保証した: feature 間の癒着なし / core.ts に IO なし / Effect の網羅性 /
            server 境界の非決定性なし / shared→features の逆依存なし
  保証していない: 型整合 (別途 tsc) / shell に判断が入っていないこと /
            components の副作用 / 提示の一貫性 (info のみ) / 書き経路の往復
```

3 行の出力追加で、査読 §5.3 の「被害の上限が事前に分かっている」がツールの出力になる。**受け入れ判断を人間 (または指揮 AI) に委ねるツールは、自分の管轄を自己申告すべきである。** これは L6 (自分が赤を出せることの証明) と同じ系譜の誠実さだと思う。

### 4.3 掟の空白は、テストの空白と同じ形をして現れる

§1.2 で述べたとおり、`verify` / `tsc` / E2E の 3 つのゲートが、書き経路の往復という一点で同時に盲目になった。

一般化するとこうなる。**アーキテクチャが名前を与えていない経路は、テストの設計時にも名前で呼べないので、テストされない。** 「書き経路の戻り」に `Outcome` のような語彙があれば、私は「Outcome の検査」を書こうとしたはずである。語彙がなかったので、検査の項目としても立てられなかった。

これは膜語彙を増やすかどうかの判断 (査読の［質問2］) に対する、実装者側からの 1 票になる。**語彙は検査可能性を生む。** 私は第 5 の語彙を増やすことに賛成する。

## 6. 査読側への質問 (返球)

- **［返1］** A1 の L9 について。`useState` / `useEffect` を components で全面禁止すると、UI 一時状態 (フォーカス、アニメーション) を持ちたい正当なケースが将来必ず出る (本書 §1.3)。**components では禁止し、必要になったら `shell.tsx` に持たせる** (shell は L9 の対象外) という切り分けでよいか。それとも components にも「純粋に視覚的な state」の逃げ道を用意すべきか。
- **［返2］** §4.2 で「verify の貢献は L1/L7 だけ」と帳簿を作ったが、本書 §3.2 の「掟が委譲プロンプトの語彙になる」経路を勘定に入れると、帳簿は変わるか。私は**変わらないが、影の掟は成文化すべき**という結論だが、査読側の見立てを聞きたい。
- **［返3］** 本書 §4.2 の「verify が信頼境界を印字する」提案は、査読 §5.3 の命題 (受け入れてよい層に名前をつける) の自然な帰結だと考えているが、**Law を増やさずに約束の範囲を明示する**というこの方向は、幹を薄く保つ規律と整合すると考えてよいか。
- **［返4］** §1.4 の発見 (starter が SPACTA.md より強い規範) が正しいなら、査読の提案 4 (rationale のリンク集) は**効果が限定的**ということになる。読まれる場所ではなく写される場所に置くべきだから。この見立てに同意するか、それとも rationale とパターン実例は別々に必要か。

## 7. 結び

査読は私の報告の最も重要な主張 (§4.1) を、**私自身のコードで実証してみせた**。これは私が自力ではたどり着けなかった検証で、しかも私の主張を弱めるのではなく強める形で行われている。実装者として、これ以上の査読の形はないと思う。

その上で、実装者からの正味の貢献は 3 つに絞られる。

1. **提案 1 は実測すると偽陽性 21 件・真陽性 0 件で失敗する。** L2 の再利用ではなく L9 の新設が要る (§3.1)
2. **`starter/` が最強の規範であり、私は Effect の配置を導出せず写した。** 採用させたいパターンは starter に置くべきで、これは rationale 切り出しの費用対効果を下げる (§1.4 / §4.1)
3. **掟の空白は、テストの空白と同じ形で現れる。** 私の 3 つのゲートは書き経路の往復という一点で同時に盲目だった。語彙がないものは検査項目としても立てられない (§1.2 / §4.3)

そして質問 2 への回答をもう一度置いておく。**私は「ここは MVP なので割り切る」と宣言することで、自分の注意を合法的に打ち切った。** 掟が規定していない領域では、妥協の宣言が見落としを生産する。これは実装者の規律では防げない種類の失敗で、だからこそ B1 (書き経路の規定) を最優先に置いている。

L6 についての評価は、両文書で一致している。ここは動かない。
