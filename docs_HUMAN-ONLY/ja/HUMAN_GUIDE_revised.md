# Spacta — AI-First Vibe Coding ガイド & アーキテクチャ

Spactaへようこそ。
このガイドは、Spactaがアプリの各機能をそれぞれ独立した境界（bounded context）の中に閉じ込め — あなたもAIもアプリ全体を頭に入れておく必要がなくなる — その境界が保たれていることを機械的に証明する仕組みを説明します。
UI、状態管理、API呼び出しなどを一つのファイルに書く密結合なNext.jsは、構造的にvarify検証が困難です。一方、型契約でそれらを疎結合に成立させれば、スクリプト介入の余地が産まれます。
Spactaは、その性質を利用し、Next.jsのアプリ全体にスクリプトによる検証可能性を導入します。これはVibe Codingと非常に相性が良い {ここにEmiだっけ？それの設計思想を使ったことを示唆する？}

## 0. Spactaとは何か

ここで言う「機能（feature）」とは、1つの自己完結したアプリの振る舞いの単位を指します — 例えばチェックアウト{そんな機能あるの？後者２つに比べてイメージができない。削除候補}、ユーザープロフィール、コメントスレッドなど。それぞれが `features/<name>/` という専用のディレクトリの中に完全に収まっています。

diff- Spactaはいくつかの中核的な考え方の上に成り立っています。重要度順に並べると:
diff+ Spactaは一つのツールの名称ではなく、複数の考え方の上に成り立つ設計思想です。
{削除：優先度順に並べると 理由：以下の位項目の優先度はそこまで重要じゃない。}

1. **コンテキスト隔離（Context Isolation）**:
Amazon規模のNext.jsアプリを作ろうとすると、2つの問題にぶつかります。{別にAmazonという名前を出必要はないかも。また、このコンテキスト隔離のところが長く、以下２項目もあって、この項目がタイトル(コンテキスト)}
- 1. Next.jsはUIと状態管理を密結合させる構造なので、1つの機能変更が他の広範囲かつ絡み合ったロジックに影響を及ぼしかねません。そして、Next.jsでは現状状態管理ロジックを検証する手段が存在せず、TypeScriptの静的型チェックで確認するしか術がありません。これは暗黙的なエラー内包と、スパゲッティコードの温床になっています。
- 2. たとえAIがその絡み合いを解きほぐせたとしても、あらゆるタスクのたびにアプリ全体の状態とロジックをコンテキストとして保持する必要があり、これは単に実行コストが上がるというだけでなく、そのタスク自体を正しく推論することを難しくします。5年後、モデルがコードベース全体をコンテキストに収められるようになったとしても、それだけではどちらの問題も解決しません。すべてを読めることと、チェックアウトへの変更が在庫管理をひそかに壊していないと保証できることは別問題だからです。
Spactaの答えは物理的な隔離です — すべての機能は専用のディレクトリ（`core.ts` / `shell.tsx` / エッジファイル群）に閉じ込められ、他の機能の内部を import することはできません。あなた（あるいはAI）が1つの機能に触れるとき、必要なのはその機能自身のファイルだけであり、`app/` ツリー全体でも、その裏に隠れた因果の絡み合いでもありません。初期評価では、複数の独立したAIエージェントが凍結された契約に対して別々の機能を並行実装し、衝突ゼロで統合できました。これは、Spactaがタスクを「AIが確実に扱える大きさ」に切り詰める2つの手段のうちの1つです。もう1つは次の項目で説明します。
2. **明示的構造による複雑性の低減**: 人間が手で書けば疲弊してしまうような冗長さ — 網羅的なswitch文、あらゆる分岐に対する明示的な `Action`/`Effect` 型 — は、AIの精度を損なわないというだけでなく、タスクそのものの複雑性を積極的に下げます。網羅的で明示的な状態機械は、「隠れた相互作用をたどって何が起こるべきかを推論する」という作業を、「欠けている1つのケースを埋める」という機械的でパターンマッチ可能な作業に変えます。これは判断を要する仕事ではありません。注意すべき失敗モードは、圧縮された暗黙のロジックであって、冗長で明示的なロジックではありません。*（これは項目1の隔離によるコスト削減の話とは逆方向に働く点に注意してください: 隔離はAIが読むべき入力コンテキストを縮小しますが、明示的な状態機械の構造はAIが書くべき出力を増やします。これが総体として安くつくのか高くつくのかは計測されていません — ここでは決着した主張としてではなく、未解決の問いとして書き留めています。）*
3. **契約駆動開発（Contract-driven development）**: 各機能は凍結された `types.ts`（その `State` / `Action` / `Effect` の形状）を公開します。契約が事前に固定されているため、機能はあなた、AI、あるいは複数のAIエージェントが別々の機能を担当する形で、互いに内部の調整をすることなく独立して実装できます。
4. **機械的検証（hope-promptの排除）**: 「このファイルにfetchを書かないで」とAIにプロンプトで伝えることは *hope-prompt*（祈るように頼むだけの指示）です — AIが覚えていることを願うだけで、確認する手段がありません。Spactaは、上記の隔離の主張をスクリプト（`npm run verify`）で裏付けます。このスクリプトは実際のコードを読み取り、境界が破られていればビルドを失敗させます。隔離が保たれていることを信じる必要はなく、確認できます。
5. **The Gardener（庭師）**: 速く動くと、UIコードには場当たり的なTailwindの値や重複したマークアップが蓄積していきます。`npm run garden` はAIによるパスを実行し、この乱れを共有のセマンティックなUIプリミティブへと集約します。今日のスピードが、後々の散らかりに変わらないようにするためです。

*ここまで読んで「Redux/Elmのパターンと同じでは？」と思ったなら、その直感は正しいです。目新しいのはパターン自体ではなく、この境界が単なる規約ではなく物理的に強制され、機械的に検証される点です（項目4）。*

## 1. SpactaとNext.jsの橋渡し

これまでにNext.jsアプリを作ったことがあるなら、Spactaはコードを再編成することで、AIが機能同士を絡み合わせてしまうのを防ぎます。実際のディレクトリ構成はこのようになります:
{日本語が不自然}

```txt
src/
  features/
    checkout/
      core.ts       # 純粋ロジック（State/Action/Effectの計算のみ）
      shell.tsx     # UIの配線（状態とレイアウトを結びつける）
      types.ts      # State / Action / Effect の契約
  shared/
    source.ts       # 非決定的な値を読み取るエッジ（時刻・UUID・fetch）
    runEffect.ts    # 副作用を実行する唯一のディスパッチ地点
```

Spactaの境界の概念が、標準的なNext.jsの構成要素にどう対応するかを示します:

| Spactaのコンポーネント | Next.jsでの対応・役割 | ディレクトリ |
| :--- | :--- | :--- |
| **Core** | **純粋ロジック層**。reducerのような関数（`init`, `update`）。非同期処理、fetch、日時の動的生成は一切含まない。どこで実行しても安全。 | `features/*/core.ts` |
| **Shell** | **クライアントコンポーネントの状態配線**。状態をUIレイアウトに結びつける。ユーザー操作を `Action` に変換する。 | `features/*/shell.tsx` |
| **Source**（エッジ） | **非決定的な処理の入口**。現在時刻の取得、UUIDの生成、DB/APIのフェッチ（RSCエッジ）を行う。 | `shared/source.ts` |
| **Effect** | **副作用の実行役**。ルーター遷移、トースト通知、クライアント側fetchを一手に引き受ける唯一のディスパッチ地点。 | `shared/runEffect.ts` |

### パラダイム比較: 標準的なNext.js vs. Spacta

なぜSpactaがこれほど厳格な境界を課すのかを理解するために、標準的なNext.js開発パラダイムとの対比を示します。Spactaは2つの異なる軸で隔離を行っている点に注意してください — 以下の表の最初の2行は*機能内部の純粋性*（Core vs. 副作用）についてで、残りは*機能間・ワークフロー間の境界*についてです:

| 観点 | 標準的なNext.js | Spactaアーキテクチャ |
| :--- | :--- | :--- |
| **関心の結合** | 状態、非同期フェッチ（IO）、日時ロジック、UIレンダリングがReactコンポーネント内で絡み合いがち。 | **完全な物理的分離**。純粋関数ロジック（`core.ts`）は副作用（`shell.tsx`, `runEffect.ts`）から厳格に隔離されている。 |
| **AIとの協働** | AIは結合したコードベースを理解する必要があり、際限のないコンテキスト肥大化と高いマッピングコストにつながる。 | **コンテキストの封じ込め**。AIはアプリ全体ではなく、隔離された機能コンテキストの中だけで作業でき、注意のコンテキストスイッチングによる精度低下を防ぐ。 |
| **ルールの強制** | ガイドラインはドキュメントやチームの慣習（**「hope-prompt」**）として存在するのみで、AIモデルは容易に無視・忘却する。 | **機械的検証**。上記の隔離の主張を裏付けるもの: 厳格な境界（機能の隔離、Coreの純粋性）はASTパースによって監査・強制される（`npm run verify`）。 |
| **データフロー** | 状態変化、APIフェッチ、副作用が様々なフックに散らばり、複雑で予測しづらいイベントを引き起こす。 | **単一方向のループ**。データは厳密に1つの閉じたループを流れる: `UI ➔ Action ➔ Pure Core ➔ New State & Effect ➔ runEffect ➔ UI`。 |
| **見た目の保守** | 人間/AI開発者が、インラインのTailwind値や色名、レイアウトの重複を手動でリファクタリングする労力を費やす。 | **自動化された庭仕事（Gardening）**。AI gardener（`npm run garden`）が生の見た目コードをセマンティックトークンと共有UIプリミティブへ集約する。 |

## 2. データフローのループ

非同期の状態をあちこちに散らばらせる代わりに、データは単一の予測可能なループを流れます:

```txt
[UI (Shell / Component)] ➔ Action ➔ [Core (core.ts / Pure)] ➔ New State & Effect
           ▲                                                      │         │
           │───────────── Rerenders UI with New State ────────────┘         ▼
           └────────────── Returns result as a new Action ─────────── [runEffect.ts]
```

### Before / After コード比較

#### Before（結合されたNext.jsコンポーネント）
UI、非決定的な値（`new Date()`）、副作用（`fetch`）が絡み合った典型的なReactコンポーネント。AIによる回帰（リグレッション）が非常に起きやすい。

```typescript
// src/components/Counter.tsx (Client Component)
'use client';
import { useState, useEffect } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);
  const [lastUpdated, setLastUpdated] = useState('');

  useEffect(() => {
    // ❌ UI内部に副作用がある（追跡不可能）
    fetch(`/api/log?count=${count}`);
  }, [count]);

  const handleIncrement = () => {
    setCount(count + 1);
    // ❌ UI内部に非決定的な値がある（テスト不可能）
    setLastUpdated(new Date().toISOString());
  };

  return (
    <div>
      <p>Count: {count} (Updated: {lastUpdated})</p>
      <button onClick={handleIncrement}>Increment</button>
    </div>
  );
}
```

#### After（Spactaによる分離）
UIはシンプルなままで、計算処理と副作用は分離されている。AIはCSSに触れることなく、`core.ts` 内の計算ロジックだけを安全に再生成できる。

```typescript
// 1. src/features/counter/core.ts (純粋な計算処理)
export function update(state: State, action: Action): { nextState: State; effect?: Effect } {
  switch (action.type) {
    case 'INCREMENT':
      return {
        nextState: {
          ...state,
          count: state.count + 1,
          lastUpdated: action.now, // ✅ 非決定的な時刻はエッジからActionを通じて注入される
        },
        effect: { type: 'LOG_COUNT', count: state.count + 1 } // ✅ 実行ではなく宣言のみ
      };
  }
}

// 2. src/features/counter/shell.tsx (薄いUIシェル / 状態フック)
'use client';
import { useReducer } from 'react';
import { update } from './core';

export function CounterShell({ initialNow }: { initialNow: string }) {
  const [state, dispatch] = useReducer(update, { count: 0, lastUpdated: initialNow });

  return (
    <div>
      <p>Count: {state.count} (Updated: {state.lastUpdated})</p>
      <button onClick={() => dispatch({ type: 'INCREMENT', now: new Date().toISOString() })}>
        Increment
      </button>
    </div>
  );
}
```

## 3. 中核となるビジョン: AIが書き、人間が仕上げる

標準的な開発では、状態機械、バリデーションルール、統合のためのボイラープレートを書くのは骨の折れる作業です。Spactaモデルでは:

* **AI-First開発**: **AIが初期コードベースの100%を書きます** — `core.ts` の純粋なビジネスロジックも、`shell.tsx` や `components/` のUI構造も両方です。
* **任意の人間介入 — なぜ（Why）**: これはAIが論理面で「賢く」、人間がデザイン面で「賢い」という話ではなく、相対的な向き不向きの話です。AIの強みは、これまで何度も見てきたような密で機械的、反復的な構造（reducer、バリデーションルール、状態遷移）で発揮されます。一方でAIが本質的にアクセスできないのは、あなたの暗黙知です — 何が正しく見え、正しく機能するかという蓄積された感覚や、全体を俯瞰しながら書く能力です。これはまさにピクセルパーフェクトなUI作業が要求する類の判断です。
* **任意の人間介入 — どのように（How）**: あなたは必須のボトルネックではありません。`shell.tsx` は `core.ts` のロジックに一切触れないため、UIを調整することは慣習によってではなく、構造的に安全です。AIの生成結果がうまく動くならそのまま出荷できます。しかし、UIをピクセルパーフェクトにしたい場合や、デザインが主観的な調整を要求する場合は、**いつでもレイアウト・スタイル・CSSを手直しするために介入できます**。
* **恣意的な割合はゼロ**: 「AI 90% / 人間 10%」のような硬直した割り当てはありません。どこで、いつ自分がコードを書くかはあなたが選びます。

## 4. なぜASTベースの検証なのか（`npm run verify`）

隔離は、それを信頼できる手段があって初めて意味を持ちます。AIモデルは指示を幻視したり忘れたりする傾向があるため（例: *「core内には new Date() を書かないで」*）、Spactaは境界が保たれたとあなたに信じさせるのではなく、「hope-prompt」をTypeScriptのASTパーサー（`verify.mjs`）による**機械的検証**に置き換えます。

* **L1 Isolation（隔離）**: 機能間のimportを禁止することで、AIがFeature Aを読み込んだり壊したりすることなくFeature Bに取り組めるようにする。
* **L2 Purity（純粋性）**: Coreファイルは物理的に監査され、IO・フェッチ・時刻生成が紛れ込んでいないことを確認する。
* **L4 Exhaustiveness（網羅性）**: `effect.type` を分岐するswitch文は、必ず網羅性チェック（`assertNever` / `: never`）で終端しなければならない。これは、セクション0の項目2で述べた「AIの複雑性を下げる明示的な状態機械」という主張を、実際に強制している部分です — どの分岐も暗黙のまま取りこぼされていないことを検証器が確認します。
* **審判の仕事**: 検証器はあなたの審判です。vibe coderであるあなたは、AIのアーキテクチャ的な規律を二重チェックする必要はありません。`npm run verify` がグリーンになれば、境界は保たれています。

## 5. Gardenerのワークフローとマインドセット（`npm run garden`）

* **速く書き、後でリファクタリング**: あなたやAIがUIを書いている間は、場当たり的なTailwindの値（`bg-[#ff0000]` など）を使ったり、レイアウトのマークアップを重複させたりして、遠慮なく速く進めて構いません。
* **Gardenerによるリファクタリング**: `npm run garden` を実行すると、AI gardenerに対して、生の色・間隔をリファクタリングし、レイアウトの重複を統合し、それらを共有UIプリミティブ（`src/shared/ui`）に集約するよう指示します。
* **Vibe Coderのマインドセット**: AI gardenerのリファクタリングはヒューリスティックであり、時には小さな見た目の調整が必要になることがあります。高速なプロトタイピングと引き換えに、出力が完璧ではないかもしれないことを受け入れてください。
* **検証による裏付けは引き続き有効**: Gardeningは上記の境界を回避するための抜け道では決してありません — すべてのgardeningタスクは `npm run verify` をグリーンに保つ必要があり、変更が隔離や純粋性を壊す場合は、そのまま採用されるのではなく元に戻されます。
