## 0. Spactaとは

Spactaとは、Vibe Coding用のNext.js開発フレームワークです。人間が介入することはUI部分以外想定されていません。
これは、「アプリの各機能をそれぞれ独立した境界（bounded context）の中に閉じ込め、その境界が保たれていることを機械的に検証する」仕組みです。
機械的に検証すれば、今まで暗黙的で複雑なNext.jsの状態管理やAPIロジックなどを、AIが自明の下管理することができます。

そういった暗黙的な複雑性は、Next.jsの特性上検証することができません（ビルドでエラーにならない）。
「AIが正しく書いてくれている」と信じるしかなく、スパゲッティコードの原因にもなりうるこれは、特に状態管理やロジックが複雑化する大規模アプリでは致命的な弱点になると考えます。（AIの推論能力に頼るしかなかった。機械的な検証可能性がないから合っている確証が得られない。不健全な状態管理ロジックが、ビルドを素通りしてしまう。）
Spactaはその複雑性自身を検査し、AIの開発体験やアプリの保守性を向上させます。


*現在β版であり、改善が不可欠です。フィードバックを歓迎します。*
*土台に FCIS（Functional Core, Imperative Shell）の考え方を採用しました。*
*Installationは[docs_HUMAN-ONLY/setup.md](../setup.md) を参照してください。*

## 1. 概念紹介

Spactaは1つのツールの名称ではなく、複数の考え方の上に成り立つ設計思想と、スクリプト群の総称です。
- コンテキスト隔離
- ステートマシンによる複雑性の低減
- 契約駆動開発
- 機械的検証

### 1-1. コンテキスト隔離（Context Isolation）

AIの回答品質は、コンテキストの質によって変わります。
*Attention散逸*(α評価）の観点からも、コンテキストは短く、そしてシンプルであることが望ましい。

しかし、以下の観点から、それを普通のNext.jsで実現することが難しくなっています。

- **関連コンポーネントのロード** : UIとロジックが密結合しているNext.jsは、一つのタスク解決に関連コンポーネントのロードを要求します。AIは小さなタスクでも多くのコンテキストを読み込み、暗黙的なつながりの理解・解決に多くの推論コストを投下します。（これは*外因性認知負荷*（α評価）です。） また特に大規模なアプリでは、コンテキストの読込みだけでウィンドウの多くを消費してしまいます。これはAPIコストの増加と、AIの出力精度の低下に繋がります。
- **複雑な状態管理** : Next.jsはUIと状態管理を密結合させるため、1つの機能変更が離れた場所の広範なロジックへ波及しかねません。しかも、その波及が起きていないことを機械的に確かめる手段が存在せず、ビルドを素通りしてしまいます。これが、暗黙のエラーとスパゲッティコードの温床になります。スパゲッティコードは文法的にNext.jsに許容され、コンテキストの複雑化と、非自明なせいでAIの推論コストを上昇させます。（この暗黙の整合性維持が、私たちがOpus級の高性能モデルを使う理由の1つになっています。）

**Spactaの答えは物理的な隔離です。**
- "dashboard", "home"といった機能は、関連コードと共に専用ディレクトリに隔離され、"dashborad"が"home"を参照することは検証器(npm run verify)で禁止されます。
- ファイル間の横断的な閲覧はプロンプトで制限しています。入力と出力のデータ型を、TypeScriptの**型契約**（後述）で宣言・束縛し、AIがその要求を満たすように実装すれば自動的に関数の健全性が担保されます。「Input、Outputを合わせればいい」このタスクの束縛は、他のファイルを見なくてもそのファイルのみで実装を実現できること、つまりコンテキスト隔離を可能にします。

あなた（あるいはAI）が1つの機能に触れるとき、必要なのはその機能自身のファイルだけであり、`app/` ツリー全体でも、その裏に隠れた複雑な因果関係でもありません。型契約に従えば、アプリ全体の仕様を知らなくても、独立して境界を破らない実装ができます。初期評価では、複数の独立したAIエージェントが凍結された契約に対して別々の機能を並行実装し、衝突ゼロで統合できました。これはSpactaがタスクを「AIが確実に扱える大きさ」に切り詰める2つの手段のうちの1つで、もう1つが次の項目です。

### 1-2. ステートマシンによる複雑性の低減

Spactaはステートマシンを採用しています。網羅的なswitch文、あらゆる分岐に対する明示的な `Action` / `Effect` 型は、人間が手で書けば疲弊していまうような冗長なものですが、これはAIの出力精度を損なわないAIフレンドリーな設計の一つです。 - これはα評価の内因性認知負荷（タスク自体の複雑性）に該当します。 - 網羅的で明示的なステートマシンは、「隠れた相互作用をたどって何が起こるべきかを推論する」作業を、「欠けている1つのケースを埋める」という機械的でパターンマッチ可能な作業へ変えます。これは判断を要する仕事ではありません。LLMはただ、学習データに則って適切な語句を埋めていけば良く、TypeScriptの静的型チェックも最後の砦として機能します。

*（１点コストについて述べておきます。ステートマシンの冗長な記述は、outputトークンを増加させAPIコスト増に貢献します。しかし、Inputトークンと推論コストは上記コンテキスト隔離によって削減されています。総体として安くつくのか高くつくのかはまだ計測されていません。）*

### 1-3. 契約駆動開発（Contract-driven development

"dashbord"や"home"といった各機能は、凍結された `types.ts`（その `State` / `Action` / `Effect` の形状）を公開します。契約が事前に固定されているため、各機能は、あなた・AI・あるいは別々の機能を担当する複数のAIエージェントによって、互いに内部を調整することなく独立して実装できます。

### 1-4. 検証器駆動開発とhope-promptの排除

「このファイルに fetch を書かないで」とプロンプトでAIに伝えるのは、*hope-prompt*（祈るように頼むだけの指示）です。AIが履行してくれることを願うもので、守られる保証がありません。むしろこうした禁止事項の列挙は、LLMの注意機構を分散させ、AIの回答精度を低下させることに繋がります。注意が薄く広がれば、重みの計算の際に "hope" を取りこぼしてしまう可能性が高まります — **Attention はリソースです**。
Spactaは指示を*rule-prompt*で伝え、*検証器*(`npm run verify`)にhope-promptが担う役割を代替させます。「fetchが必要なときはcoreにActionを投げる」といった*rule*は書きますが、「fetchを書くな」とは書かないといった具合です。hope-promptの列挙はAIに「プロンプトの遵守」という新たな責務を与え、不要な認知負荷の上昇をもたらします。 -AIはプロンプトを守るため、実装と指示を突き合わせ、指示通りであると確証を得るためにリソースを投下します。-
Spactaが規律の違反に寛容になることで、AIを「プロンプトの遵守」という責務から解放します。検証器が規約遵守を代わりに保証します。

AIの規律違反は検証器で検出します。もしruleに違反があれば、検証器がエラーを返し、グリーンになるまで自分で直すだけです。境界が守られていることは、記憶や祈りではなくスクリプトが実際のコードを読んで保証します。だからAIは、自身のAttentionリソースを目の前のタスクだけに集中させることができます。

ただし、verifyが保証するのは**境界のルールが遵守されている**ことであって、**バグがないこと**ではありません。`count + 1` と書くところを `count + 2` と書き間違えたコードはグリーンのまま通ります。

**verifyがグリーンのとき言えるのは「バグがない」ではありません。**
- バグがあっても、それは1つの機能のcoreの中に閉じ、`(state, action)` だけから再現できる
- 隠れた入力がない
- 他機能への波及を削減する。*現状、コードレベルでこれは真です。ただ、同じテーブル・同じAPIを読むことによる間接的な結合はのこっています。しかもこの結合は**プロセス内のActionログには現れない**ので、リプレイ照合でも検出できません。*
Spactaは暗黙の接続を*証明する*のではなく、要らない接続を消し、残った接続を全部*明示のドア（型契約）*に通します。だから正しさは、アプリ全体を見渡す問いではなく、1つの純粋関数を読めば答えられる**ローカルな問い**になります。(α評価：「複雑性の凝縮」参照)

**なぜこれがそんなに効くのか。** 密結合なNext.jsでは「これは正しいか？」がアプリ全体を見ないと答えられない問いになります。状態がどこで書き換わるか、effectがどこで発火するか、追跡不能だからです。Spactaはこれを**「1つの純粋関数を読めば答えられる問い」**に縮めます。正しさを保証するのではなく、正しさを人間やAIやテストが*実際に確かめられる形*に落とす。ここがAIと相性がいい本当の理由です — 推論の対象が1ファイルに畳まれます。

### 1-5. The Gardener（庭師）

   速く進めるほど、UIコードには場当たり的なTailwindの値や重複したマークアップが溜まっていきます。`npm run garden` を実行すると、AIがコードベースを一巡し、この乱れを共有のセマンティックなUIプリミティブへ集約します。今日のスピードが、後々の散らかりに変わらないようにするためです。

*ここまで読んで「Redux / Elm のパターンと同じでは？」と思ったなら、その直感は正しいです。目新しいのはパターン自体ではなく、この境界が単なる規約ではなく物理的に強制され、機械的に検証される点です（前述の機械的検証）。パターンの系譜と、その中でSpactaがどこに立つのかは §6 で詳述します。*

*なお、UIの見た目の統一だけは、1つの機能に閉じては保ちきれません。ページ間でデザインを揃えたいときは、複数機能のUIを横断して見ながら整えることを推奨します（他機能を import するわけではないので、隔離のルールには触れません）。共有トークンと `shared/ui` は部品単位の一貫性は保証しますが、ページ全体の調和までは自動化しきれないためです。*

*これは**調整フェーズの推奨**であって、実装の作業分割の規約ではありません。実装フェーズで並列委譲するときの順序は `SPACTA.md` §4-6 に置いてあります（実装AIが読むのは `SPACTA.md` であり、この人間向けガイドではないため、**手順は向こうに書く**必要があります）。実務上は、shell と `app/` を最後に1体がまとめて書く形にすると、この「横断して見ながら整える」が手順として自然に発生します。*
