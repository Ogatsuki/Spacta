## α1. [SPACTA.md](SPACTA.md) というファイルについて

- [SPACTA.md](SPACTA.md) は、軽量でなければなりません。実装を担当するすべてのAIがタスクのたびに読まなければならないファイルです。ここが10行伸びると、全てのAIにそれだけの読解・追従コストを与えることになります。読まれる頻度と範囲という点で、プロジェクトの中核的な「幹」にあたり、これの肥大化は、全ての開発者(AI)の実効性低下に繋がります。よって、このファイルの整備優先度は高く捉えるべきです。`[確定]`
  - Opus, Sonnetで、10行程度の増加は問題ないかもしれませんが、 `SPACTA.md` は他のドキュメントより情報密度が高く、後述のAttention散逸の影響をより大きく受ける可能性があります。増える行数よりも、いかにAttentionが散逸するか、認識・遵守コストの高低について留意しておく必要があります。`[認識]`
- したがって、`SPACTA.md` とその周辺スクリプト（verify など）には実行ルールのみを書き、文脈・経緯・洞察はそこから追い出すことになりました。AIの文脈保全としては、α評価も与えるのが妥当でしたが、α0によりα評価は外部ファイルに押し出されています。`[含意]`

## α2. Hope Prompt

- 「これをやってください」「あれに気をつけてください」といった、ツールによって強制されない散文的な指示には、従われる保証がありません。私たちはこれを "hope prompt"（祈るように頼むだけの指示）と呼び、Spactaの信頼性階層（hope < detect < prevent-weak < prevent-strong）のうち最下層（`hope`）に位置づけています。`[中核仮説]`
- こうした指示は、単発で導入する分には大きな性能劣化を引き起こしません。現代のモデルは少量の散文指示に対して頑健です。`[観察]`
  - しかし本当の危険は、1回の追加そのものではなく、累積的な肥大化にあります。「害のなさそうな一行」を繰り返し追加していくことで、すべてのAIが毎回読まなければならない幹が膨張していきます。
  - 旧 `CLAUDE.md`（v3）の歴史的な肥大化は、この積み重ねの典型例でした（`docs_HUMAN-ONLY/spacta-alpha-evaluation-archive.md` を参照）。
- 対処法は「`SPACTA.md` というファイルについて」と同じです。散文的な指示に予算を課すこと。`[含意]`
  - 「書きすぎないよう気をつけよう」といった精神論に頼るのではなく、経緯や文脈を置くための場所をこの外部ドキュメントとして切り出すことで、構造的に予算超過を防ぎます。
  - 核心となる言い回し: 危険なのは hope prompt が1行あることではなく、それが本来あるべきでない場所に居着き、積み重なっていくことです。

## α3. 幹と葉の非対称性（肥大化のコストは依存グラフ上の位置で決まる）

- 同じ「1000行のファイル」であっても、それが幹（多くの場所からimportされる）なのか葉（どこからもimportされない）なのかによって、被害の深刻さは指数的に異なります。`[中核仮説]`
  - `types.ts` は幹です。すべてのレイヤーがそれをimportするため、無駄な一行がN箇所に税を課すことになります。だからこそハードな予算（行数の info チェック）が正当化されます。
  - `shell.tsx` は葉です。`app/page.tsx` からしか呼ばれず、その内部を誰もimportしないため、肥大化してもアーキテクチャ上の隔離度を損ないません。**幹の肥大化は害を広く撒き散らし、葉の肥大化はその場限りの不快感で済みます。**
  - これが、verifierが行数の info チェックを `types.ts` にのみ課し、shellには行数ゲートを設けない理由です。`[含意]`
- 行数の info チェックは「型が多すぎる」ことを叱るものではありません。むしろ、「膜（membrane）を越えない型が契約ファイルに置き去りにされている」といったアーキテクチャの歪みを検出するための代理指標として行数を使っています。`[観察]`
  - したがって、数値を合わせるためだけに機械的にファイルを分割してはいけません（それは温度を下げるために温度計を壊すようなものです）。正しい治療法は、実際に共有されている量そのものを減らすこと——単一所有の型をコロケーションし、死んだ契約を削除することです。`[含意]`
  - `SPACTA.md` もまた、あらゆるAIがすべてのタスクで読む極端な幹であり、同じ予算規律の対象です（「`SPACTA.md` というファイルについて」を参照）。

## α4. Attention散逸と、切り替えコスト

- コンテキスト的には極めて小さい、軽量なはずのタスクを複数与えたところ、精度低下・回答不全が確認されました。`[観測]`
  - 実例: 個々の設問が極めてシンプルな200問のサーベイにおいて、Sonnetで70問に達する前に精度が急落しました。（例：残りの全てが同じ回答になる・そもそも回答されない） 性能の低いモデルでも、20問ずつのバッチで回答させると精度は安定しました。`[観測]`
  - 教訓: モデルの絶対的な能力限界とは無関係に、「Attention切り替えコスト」が精度を劣化させます。逆に言えば、コンテキストウィンドウが一杯でなくても、やろうと思えば簡単に精度を低下させることができる、またそういったタスクを作れるということ。AIにタスクを与える際には、これに注意しなければなりません。`[確定]`
- 私の簡単な観測では、GPT系系がAttention散逸に最も強く、ついでGemini、最後にClaudeとなりました。ただ、これは2026年1月頃の古い観測、かつ廉価モデルのみでの測定であり、知見に影響するほどの検証土台が整っていないことに注意が必要です。`[要検証]`
- AIの進化により、このAttention切り替えコストへの耐性は強くなっています。今後も耐性が高くなると予想しています。 `[認識]`

## α5. Attentionはリソース

- 注意すべき事項がコンテキストにおいて多岐に渡って広がっている場合、LLMはそれら全てを把握しながら推論することが難しくなります。`[確定]`
  - 重みの計算の際に取りこぼしてしまい、「AIが忘れる」とよく言われる現象が起こります。「AIが前提を忘れる」とは、有限なコンテキストウィンドウの中で、必要コンテキストが外に押し出されてしまう以外に、Attention散逸により推論時に取りこぼすことも含まれてると考えられます。`[確定]`

## α6. 思考の寡占状態
- LLMは「Read」「Think」「Write」という3つの思考状態で動作します。タスク全体を通じて1つの状態が負荷を支配しているのが理想的です（分散した4:4:1ではなく、集中した2:7:1のような比率）。`[認識]`

## α7. AIの認知負荷
- AIには、人間と同様な認知負荷の機構が存在すると認識しています。`[認識]`
  - **外因性認知負荷** : タスク以外の推論コスト。削減可能。
    - 例：コードベースの読解、Next.jsの暗黙的で複雑な状態管理のマッピング
    - AI開発においては、計算リソースが限られています。いくらコードベースを読解しても、複雑な状態管理を把握しても、タスクは少しも実装されません。限られた計算リソースを、削減可能な認知負荷に浪費することは非効率です。100あるリソースは、全て内因性認知負荷の解決に注ぐことが理想と考えます。`[確定]`
  - **内因性認知負荷** : タスク自身の推論コスト。基本的に削減不可能。
    - 例：複雑なロジックの実装
    - Spactaでは、ステートマシンの採用により、タスクそのものの複雑性を低下させることに成功しています。
  - **学習性認知負荷** : 学習し、習得しなければならないタスクの負荷。
    - 例：「AIに学習に利用されたことのない全く文法を使わせる」

## α8. 統括AIの認知負荷爆発
- アプリケーション全体の文脈を把握する「統括AI」は、アプリケーションの肥大と共に認知負荷が爆発的に増大します。`[確定]`
- 実装が進むにつれ、実装と仕様の突き合わせがこの負荷にさらに加わり、単一状態の支配は容易に崩れます。`[観察]`
  - 例：Opus - 文章読込み(Read) → 実装を考える(Think) → 実装(Write) → 仕様書とあっているか確認(Read)
- 解決策: 意思決定権限を下位レイヤー（feature/Core/Shell）に委譲し、最上位レイヤーの負荷を構造的に軽減する。これはSpactaの「機能の隔離/水平方向の隔離」がすでに果たしている役割と完全に一致します。`[含意]`
