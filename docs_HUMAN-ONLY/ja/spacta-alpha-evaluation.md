## α1. [SPACTA.md](SPACTA.md) というファイルについて

- [SPACTA.md](SPACTA.md) は、軽量でなければなりません。実装を担当するすべてのAIがタスクのたびに読まなければならないファイルです。ここが10行伸びると、全てのAIにそれだけの読解・追従コストを与えることになります。読まれる頻度と範囲という点で、プロジェクトの中核的な「幹」にあたり、これの肥大化は、全ての開発者(AI)の実効性低下に繋がります。よって、このファイルの整備優先度は高く捉えるべきです。`[確定]`
  - Opus, Sonnetで、10行程度の増加は問題ないかもしれませんが、 `SPACTA.md` は他のドキュメントより情報密度が高く、後述のAttention散逸の影響をより大きく受ける可能性があります。増える行数よりも、いかにAttentionが散逸するか、認識・遵守コストの高低について留意しておく必要があります。`[認識]`
- したがって、`SPACTA.md` とその周辺スクリプト（verify など）には実行ルールのみを書き、文脈・経緯・洞察はそこから追い出すことになりました。AIの文脈保全としては、α評価も与えるのが妥当でしたが、α0によりα評価は外部ファイルに押し出されています。`[含意]`

## Hope Prompt

- 「これをやってください」「あれに気をつけてください」といった、ツールによって強制されない散文的な指示には、従われる保証がありません。私たちはこれを "hope prompt"（祈るように頼むだけの指示）と呼び、Spactaの信頼性階層（hope < detect < prevent-weak < prevent-strong）のうち最下層（`hope`）に位置づけています。`[中核仮説]`
- こうした指示は、単発で導入する分には大きな性能劣化を引き起こしません。現代のモデルは少量の散文指示に対して頑健です。`[観察]`
  - しかし本当の危険は、1回の追加そのものではなく、累積的な肥大化にあります。「害のなさそうな一行」を繰り返し追加していくことで、すべてのAIが毎回読まなければならない幹が膨張していきます。
  - 旧 `CLAUDE.md`（v3）の歴史的な肥大化は、この積み重ねの典型例でした（`docs_HUMAN-ONLY/spacta-alpha-evaluation-archive.md` を参照）。
- 対処法は「`SPACTA.md` というファイルについて」と同じです。散文的な指示に予算を課すこと。`[含意]`
  - 「書きすぎないよう気をつけよう」といった精神論に頼るのではなく、経緯や文脈を置くための場所をこの外部ドキュメントとして切り出すことで、構造的に予算超過を防ぎます。
  - 核心となる言い回し: 危険なのは hope prompt が1行あることではなく、それが本来あるべきでない場所に居着き、積み重なっていくことです。

## 幹と葉の非対称性（肥大化のコストは依存グラフ上の位置で決まる）

- 同じ「1000行のファイル」であっても、それが幹（多くの場所からimportされる）なのか葉（どこからもimportされない）なのかによって、被害の深刻さは指数的に異なります。`[中核仮説]`
  - `types.ts` は幹です。すべてのレイヤーがそれをimportするため、無駄な一行がN箇所に税を課すことになります。だからこそハードな予算（行数の info チェック）が正当化されます。
  - `shell.tsx` は葉です。`app/page.tsx` からしか呼ばれず、その内部を誰もimportしないため、肥大化してもアーキテクチャ上の隔離度を損ないません。**幹の肥大化は害を広く撒き散らし、葉の肥大化はその場限りの不快感で済みます。**
  - これが、verifierが行数の info チェックを `types.ts` にのみ課し、shellには行数ゲートを設けない理由です。`[含意]`
- 行数の info チェックは「型が多すぎる」ことを叱るものではありません。むしろ、「膜（membrane）を越えない型が契約ファイルに置き去りにされている」といったアーキテクチャの歪みを検出するための代理指標として行数を使っています。`[観察]`
  - したがって、数値を合わせるためだけに機械的にファイルを分割してはいけません（それは温度を下げるために温度計を壊すようなものです）。正しい治療法は、実際に共有されている量そのものを減らすこと——単一所有の型をコロケーションし、死んだ契約を削除することです。`[含意]`
  - `SPACTA.md` もまた、あらゆるAIがすべてのタスクで読む極端な幹であり、同じ予算規律の対象です（「`SPACTA.md` というファイルについて」を参照）。

## 逆方向依存（shared → features）の害と、それが遅れて顕在化すること

- 共有レイヤー（`shared/runEffect` や `shared/ui`）が特定の機能（feature）から型・Gateway・hookをimportすると、依存の矢印が逆転します。機能が1つ増えるたびに、共有の幹が膨張していきます。`[観察]`
  - この違反は機能が1つしかないうちは害を示さず、2つ目の機能が追加された瞬間にだけ顕在化します。したがって「動いているから大丈夫」は信用できず、L7としての機械的な強制が必要になります。`[含意]`
  - 回帰を防ぐため、逆依存のテストフィクスチャを `verify/fixtures/` に配置し、L6セルフテストで継続的に監視しています。
- 明示的なimportを伴わない意味的な逆依存も存在します。たとえば、共通コンポーネントのpropsや語彙が機能固有の名詞（`hintData` のような）を学習してしまう場合です。これはASTでは検出しづらく、設計レビューでカバーします:「`shared/ui` が機能固有の名詞を学習したら、機能側に戻す」。`[含意]`
- 複数機能から必要とされる型を中央の `types` ファイルに引き上げることは、偽りの解決策です。依存を消しているのではなく、共有のゴミ箱に押し込んで隠しているだけです。正しい解決策は、(a) 永続化/API契約の薄い橋渡しには `contracts/*.ts` を使うか、(b) UI上の関心事についてはコンポーネントをプリミティブでやり取りさせることです。`[含意]`

## 統一されたプレゼンテーション層 — Frame・Vocabulary・Componentsの3層

- 構造的な検証（L1〜L7）がグリーンであっても、ユーザー体験の一貫性は保証されません。実際に、`idea-vectorizer`（明るいUI）と `dashboard`（暗いUI）は、verify・tsc・buildすべてでグリーンでありながら、まったく別のアプリケーションのように見えました。根本原因は共有デザイントークンの欠如でした。`[観察]`
  - 核心となる言い回し: **構造はグリーンでも、体験は未達成。**
- UIの統一性と機能の独立性の両立は、責務を次の3層に分割することで実現します。`[中核仮説]`
  1. **Frame**: ヘッダーや外殻は `app/layout.tsx` と `shared/ui` に引き上げられ、全機能で共有されます。Shellはメインコンテンツ領域の専門化に徹します。
  2. **Vocabulary**: 色・余白・角丸はtokens/themeに置かれます。データに `types.ts` があるように、プレゼンテーションにはtokensがあります。どちらも肥大化を嫌う薄い幹です。
  3. **Components**: 機能固有のUIコンポーネントは、その機能の `components/` 内に閉じ込められ、重複が許容されます。**共有されるのは完成したUIではなく、語彙（vocabulary）です。** 重複したコンポーネントが同じtokensを参照している限り、見た目の一貫性は崩れません。重複のコストは、肥大化した幹のコストより安いのです。
  - コンポーネントを `shared/ui` に抽出するのは、同じ形が実際に2機能以上で繰り返された後まで先送りにします。先回りした抽出は、`shared/ui` に重い幹を生みます。`[含意]`
- 生の色やアービトラリな値を検出すること（L8 Presentation Purity）は、L2 Core Purityのプレゼンテーション版であり、infoからfailへ昇格させる候補です。ただし、UIには例外が多いため、まずはburn-in用のinfoチェックとして導入しています。L8が強制できるのは語彙の一貫性だけであり、情報設計・密度・コピーの質は `frontend-design` スキルや人間のレビュー（外部の脳）の領分として残ります。`[含意]`
- Shellを物理的に分割すること（container + components）は、UIの統一性そのものの解決策ではなく、tokens/shared-uiを適用するための読み書き単位を作る足がかりです。分割の副作用として、不安定なReact hookの依存配列（`/api/hints` の無限ループ事案のような）がJSXのノイズに埋もれなくなり、レビュー対象の面積が最小化されます。`[観察]`
- L8の初期版（`#hex` と アービトラリな `bg-[...]` のみをチェック）には抜け穴がありました。実際、「色の統一」を完了しverifyを通した後も、`bg-fuchsia-400/10`、`border-fuchsia-300/20`、`bg-white/[0.06]`、`bg-gray-50`、`bg-slate-950` が残り、見た目が乖離していきました。**ソースに生のhexがなくても、「名前付きパレット」や「色名 + 不透明度」は特定の色をハードコードしていることに変わりなく、自動的なライト/ダーク対応を妨げます。**`[観察]`
  - 核心となる言い回し: **プレゼンテーション純度のグリーンは、その検出語彙が正直である限りにおいてしか正直ではない。** 検出範囲が狭ければ、グリーンという状態そのものが嘘になります。L2（Core Purity）がgrepからASTへ拡張されて初めて正直になったのと同じ問題が、プレゼンテーション側でも起きました。
- L8の拡張は「あらゆるパレットの一律禁止」ではなく、**3方向の切り分け**として設計されています。これは、誤検知（開発者の苛立ち）と漏れ（乖離）の両方を避けるための、最も実践的な妥協点です。`[含意]`
  1. **グレースケールパレット**（`gray`/`slate`/`zinc`/`neutral`/`stone`/`white`/`black`） ➔ `background`/`foreground`/`card`/`border` への置き換えを促すためinfoフラグを立てる。ここでの乖離が「別アプリに見える」ことの主因です。
  2. **色 + 不透明度**（`fuchsia-400/10` など） ➔ 隠れたハードコードとしてinfoフラグを立て、セマンティックトークン + 不透明度（例: `bg-primary/10`）へ誘導する。これはCSS変数がHSL/RGB値として定義されていることを前提としています（不透明度修飾子はhex変数には効かない、という技術的な教訓です）。
  3. **ステータスカラー**（`red`/`green`/`amber`/`blue` 系） ➔ その色に意味が固定されており頻出するため、**許容**します。ここにルールを課すとノイズが過大になります。
  - L8が守るのは**語彙の一貫性**だけです。タイポグラフィ・余白・マージン・グラフィック、そしてトーン&マナー全体は、カラートークンの外側にあり、マルチモーダル能力を使ったAIレビュー・`frontend-design` スキル・人間（3層の外側にある「統一性の第4軸」）の領分です。
- クローン検出（B3）は、`.map()` コールバックが返すJSX要素を「独立したルート要素」として親要素と比較したため、親の `<ul>` と子の `<li>` を0.9以上のJaccard類似度で重複と誤検出していました。コールバック内で返されるルートJSXは、意味的には親の子孫であるため、親との比較から除外する必要があります。**この種のverifierヒューリスティックの誤検知は、フィクスチャ（`clone-map-callback`）を用いたL6セルフテストで固定し、回帰を防止します。**`[観察]`

## Spactaと並列実装

- Spactaは「良い設計を思い出させるための規約」ではなく、「並列実装者が衝突しないようにする地形」です。`[中核仮説]`
  - `dashboard` 機能を追加する際、まず `types.ts` を凍結し、その後core/source/shellを複数のエージェントに並列で分配しました。これがSpactaの価値をはっきりと示しました。
  - `types.ts` は「あらゆる型のゴミ捨て場」としてではなく、並列実装者が足並みを揃えるための膜の契約として機能します。`[観察]`
    - 型契約が事前に凍結されていれば、Core開発者は純粋な集約処理だけを、Source開発者はIOだけを、Shell開発者は描画だけを書けばよく、互いの実装を知らなくても最後には統合できます。
  - Spactaはコンテキストを削減しているのではなく、**コンテキストが合流する地点を固定している**のです。その結果、複数のエージェントが同時に書いても、衝突したり責務が曖昧になったりすることはほとんどありません。
- ただしこの成功は、型契約を最初に凍結することを前提としています。`[含意]`
  - 契約があいまいなまま並列化すると、各エージェントが勝手に契約を拡張し、`types.ts` は再びゴミ捨て場に戻ってしまいます。
  - `types.ts` は実装の副産物ではなく、並列化に**先立って**凍結される小さな設計成果物として扱わなければなりません。
- 機能間の連携も、この地形の一部として機能します。`[含意]`
  - 機能間の連携は直接のimportではなく、外部の境界（API / DB / URL / shared）を経由します。`features/<name>/types.ts` は機能同士をつなぐ中央の橋ではなく、1つの機能内でCore/Source/Shell/Pageをつなぐ膜の契約です。

## なぜL6（verifierの自己検証）が背骨なのか

- 「ツールで強制する」と言うだけでは、その強制が実効的であることは保証されません。実例（L4コメント事案）: 検証用の正規表現がコメント文字列に騙され、網羅性の終端が欠けたコードブロックを未検出のまま通過させてしまいました。`[観察]`
- したがってL6はこのフレームワークの背骨です。意図的に壊したフィクスチャに対してverifierをテストすることで、verifierが機能していることを毎回証明します。Formが柔軟であっても、この証明だけは固定されたままです。L6がなければ、L1〜L5/L7はメタレベルで再びhopeに逆戻りします。`[中核仮説]`

## types.ts共有バジェットとverifyの限界

- `npm run verify` がグリーンであることは非常に有効ですが、成功の唯一の指標ではありません。`[観察]`
- Spactaの成果を評価するには、少なくとも4つのレイヤーが必要です。`[中核仮説]`
  1. **構造の測定**: L1〜L6はグリーンか？ CoreにIOが混入していないか？ 機能の隔離は保たれているか？
  2. **型/契約の測定**: dead-exportはないか？ `types.ts` に単一所有のexportが残っていないか？ DB/APIの契約の出どころは明確か？
  3. **体験の測定**: 同じアプリに見えるか？ 色・密度・コピー・ナビゲーションは揃っているか？
  4. **運用の測定**: 並列実装はやりやすかったか？ エラーの原因は局所化されていたか？ 典型的な編集で触るファイル数は減ったか？
  - Verifyは1を直接検査し、2の一部と3の語彙的側面まで拡張できます。3の体験の質と4の開発者体験を統合するには、人間または高度なモデルによる評価が必要です。
  - 核心となる言い回し: **Verifyは合格条件であって、成功条件ではない。**
- この理解はSpactaを弱めるのではなく、強めます。verifyが何を検査しているのかを明確にすることで、残りの判断をプロセスに組み込めるようになります。`[含意]`
- dead-exportとsingle-owner-exportは、置き場所を誤った契約を機械的に検出します。しかし、ローカルでしか使われていない型を所有者ファイルへ移すべきかどうかの判断は自動化されていません。`[含意]`
  - single-owner-exportには誤検知や、設計段階での共有候補が含まれうるため、failではなく永続的にinfoのまま残します。「今日のところは1箇所だけ」という判断は人間/AIに委ねられます。
- 構造測定（レイヤー1）でさえ、`verify`（`--tsc` なし）単体では不完全です。実際に、型を `types.ts` から所有者へ移した後、**古い未使用のimport文が残っているのにverifyはグリーンのまま**で、`tsc --noEmit` だけがそれを赤として検出しました。Verifyが検査するのは法（構造的な境界）であり、型解決ではありません。`[観察]`
  - 核心となる言い回し: **グリーンなverify ≠ グリーンな型。** この2つは別の軸です。グリーンなverifyを型安全性と混同すると、リファクタリング中に壊れた参照を見逃すことにつながりかねません。verifyと並行して `--tsc` / `tsc --noEmit` を実行し、これを `SPACTA.md` §3 と `verify/README` に手順として明記しています（「気をつけて」と開発者に伝えるのではなく、手順として固定する）。`[含意]`

## 法の範囲の抜け穴 — 散文では宣言されているのに、ツールでは無視される

- 「hope prompt」は「§1の外側の散文」でだけ起きるわけではありません。**§1のLawの実際のスキャン範囲が、その宣言よりも狭い**場合にも発生します。実測例: マイグレーション作業の指示には「非決定的な値や集約の漏れがないか、APIルートも確認すること」と書かれていました。しかし当時のL5（source-purity）チェックは `app/**/page.tsx` しかスキャンしておらず、`route.ts` は無視されていました。開発担当のAIは「気をつけて手動で確認する」しかなく、「prevent-strong」を名乗っていたLawが、ルートに関しては事実上「hope」に退化していました。`[観察]`
  - 核心となる言い回し: **Lawの名前がどれだけ広くても、スキャン対象が狭ければ、その隙間は依然として「hope」である。** L5は「サーバー境界における純粋性」を謳っていましたが、実装はページしか見ていませんでした。この宣言とスキャン対象のギャップは、L4コメント事案やL2がgrepで `new Date()` を取りこぼした事案とまったく同じ穴です。
  - 修正はL2/L4のときと同じです: **スキャン対象を宣言に追いつかせ、フィクスチャで固定する。** L5を `page.tsx` と `route.ts` の両方をカバーするよう拡張します。非決定的な生成（`new Date`/`Date.now`/`Math.random`/`crypto.randomUUID`）は `err`、直接的な業務集約は `warn` として扱い、`bad-route` と `good-route` をL6セルフテストに追加します。`[含意]`
  - ルートはIO（`await` によるfetch/DB）を正当に行う境界であるため、IOそのものはL5の対象ではありません。禁止されるのは「非決定的な生成」と「直接的な業務集約」だけで、ページに適用しているのと同じ基準・同じASTによる検査を、ルートにも適用します。境界がページかルートかによって純粋性の基準を変える理由はありません。`[含意]`
  - 一般化: 新しいLawを追加するとき、あるいは既存のLawの文言を広げるときは、**スキャン対象のglobとテストフィクスチャを同時に広げなければなりません。** 文言だけを広げると、即座に「hope」へ退化します。「このLawが実際にどのファイル群を検査するのか」をREADMEのチェック表に明示することが、この抜け穴に対する恒久的な予防策になります。`[含意]`

## Attention散逸と、切り替えコスト

- コンテキスト的には極めて小さい、軽量なはずのタスクを複数与えたところ、精度低下・回答不全が確認されました。`[観測]`
  - 実例: 個々の設問が極めてシンプルな200問のサーベイにおいて、Sonnetで70問に達する前に精度が急落しました。（例：残りの全てが同じ回答になる・そもそも回答されない） 性能の低いモデルでも、20問ずつのバッチで回答させると精度は安定しました。`[観測]`
  - 教訓: モデルの絶対的な能力限界とは無関係に、「Attention切り替えコスト」が精度を劣化させます。逆に言えば、コンテキストウィンドウが一杯でなくても、やろうと思えば簡単に精度を低下させることができる、またそういったタスクを作れるということ。AIにタスクを与える際には、これに注意しなければなりません。`[確定]`
- 私の簡単な観測では、GPT系系がAttention散逸に最も強く、ついでGemini、最後にClaudeとなりました。ただ、これは2026年1月頃の古い観測、かつ廉価モデルのみでの測定であり、知見に影響するほどの検証土台が整っていないことに注意が必要です。`[要検証]`
- AIの進化により、このAttention切り替えコストへの耐性は強くなっています。今後も耐性が高くなると予想しています。 `[認識]`

## Attentionはリソース

- 注意すべき事項がコンテキストにおいて多岐に渡って広がっている場合、LLMはそれら全てを把握しながら推論することが難しくなります。`[確定]`
  - 重みの計算の際に取りこぼしてしまい、「AIが忘れる」とよく言われる現象が起こります。「AIが前提を忘れる」とは、有限なコンテキストウィンドウの中で、必要コンテキストが外に押し出されてしまう以外に、Attention散逸により推論時に取りこぼすことも含まれてると考えられます。`[確定]`

## 思考の寡占状態
- LLMは「Read」「Think」「Write」という3つの思考状態で動作します。タスク全体を通じて1つの状態が負荷を支配しているのが理想的です（分散した4:4:1ではなく、集中した2:7:1のような比率）。`[認識]`

## AIの認知負荷
- AIには、人間と同様な認知負荷の機構が存在すると認識しています。`[認識]`
  - **外因性認知負荷** : タスク以外の推論コスト。削減可能。
    - 例：コードベースの読解、Next.jsの暗黙的で複雑な状態管理のマッピング
    - AI開発においては、計算リソースが限られています。いくらコードベースを読解しても、複雑な状態管理を把握しても、タスクは少しも実装されません。限られた計算リソースを、削減可能な認知負荷に浪費することは非効率です。100あるリソースは、全て内因性認知負荷の解決に注ぐことが理想と考えます。`[確定]`
  - **内因性認知負荷** : タスク自身の推論コスト。基本的に削減不可能。
    - 例：複雑なロジックの実装
    - Spactaでは、ステートマシンの採用により、タスクそのものの複雑性を低下させることに成功しています。
  - **学習性認知負荷** : 学習し、習得しなければならないタスクの負荷。
    - 例：「AIに学習に利用されたことのない全く文法を使わせる」

## 統括AIの認知負荷爆発
- アプリケーション全体の文脈を把握する「統括AI」は、アプリケーションの肥大と共に認知負荷が爆発的に増大します。`[確定]`
- 実装が進むにつれ、実装と仕様の突き合わせがこの負荷にさらに加わり、単一状態の支配は容易に崩れます。`[観察]`
  - 例：Opus - 文章読込み(Read) → 実装を考える(Think) → 実装(Write) → 仕様書とあっているか確認(Read)
- 解決策: 意思決定権限を下位レイヤー（feature/Core/Shell）に委譲し、最上位レイヤーの負荷を構造的に軽減する。これはSpactaの「機能の隔離/水平方向の隔離」がすでに果たしている役割と完全に一致します。`[含意]`
